## Independent take — written before opening design, tasks, or delta

1. Pin unchanged v1 Challenge fields and exact challenge bytes; refuse session keys, grants, or new algorithms in the identity proof.
2. Pin the expected audience to an independently trusted stable edge XID; a caller-supplied audience cannot establish edge trust.
3. Preserve algorithm-committing holder fingerprints from protocol section 5; refuse raw-key fingerprints and OIDC subject substitutions.
4. Require the second authorization signature to prove continuity with the verified holder, including its applicable classical/PQ policy.
5. Pin deterministic, domain-separated signed bytes for the exact session key, requested authority, challenge linkage, and channel context.
6. Require channel provenance from the actual authenticated transport, with fail-closed handling when an adapter cannot supply it.
7. Reject an intercepted exchange on another live connection even before its original nonce is consumed; a transport label alone is insufficient.
8. Couple one-use challenge consumption to authorization issuance with a defined race winner and durable crash/retry outcome.
9. Treat managed and self-custody claimants identically at the edge; keep consent enforcement at the claimant and privilege decisions outside possession verification.
10. Tradeoff: strict channel binding and one-use issuance may require reconnecting clients to restart authentication; prefer that explicit cost over replay ambiguity.

## R4 remains open — authenticate the shared connection value

Evidence: `design.md:55–68,85–92`; `specs/edge-auth/spec.md:75–93`; `native/mjolnir_gateway/src/main.rs:1050–1071`.

“TLS server identity as the client verified it” plus a connection id the client did not choose still leaves the producer, authenticated delivery, and verifier comparison of that id unspecified. Server identity is shared across connections. At gateway termination the client and API see different connections; naming the pinned API origin does not transport the client's authenticated session context across that boundary. The cited gateway opens a backend connection and forwards a scheme header, which supplies no such binding by itself. Similarly, an Iroh peer id needs a stated connection-scoped value and a binding to the pinned edge authority.

Finish the existing R4 contract with one mapping per supported adapter: who derives the value, how the client authenticates it before signing, where the verifier obtains its trusted comparison value, and how the pinned edge authority is tied to that session. For HTTPS, locate verification at termination or define the trusted handoff to the API. Explicitly defer plain HTTP or any adapter that cannot meet this contract. No specific TLS API or implementation is required.

Carry Decision 7's vector into the delta. Its current scenario still begins with a **completed** exchange on N1 (`spec.md:84`), so nonce replay rejection alone can pass it. Require a valid, unexpired, **unconsumed** exchange first submitted on N2 to fail specifically on channel mismatch, plus a separate N1 success control. A further submit after the N1 commit is replay, not a second success.

## R5 remains open — reconcile the normative state transitions

Evidence: `design.md:70–81,94–98`; `specs/edge-auth/spec.md:95–116`.

Decision 7 selects a workable rule: invalid bind or pre-commit failure leaves the nonce unconsumed; post-commit response loss requires a fresh challenge; restart restores committed state. But Decision 6 still permits “consumed-without-issue,” and the delta's invalid-bind scenario still assumes a failed bind consumed the nonce (`spec.md:115–116`). The requirement still ambiguously forbids a usable capability after issuance failure without distinguishing failure before commit from loss after successful commit.

Reconcile Decision 6 and the delta with Decision 7. State that no usable credential escapes before commit; successful commit durably records issuance and consumption; delivery loss does not undo that issuance or mint a replacement from the old proof. Add independent scenarios for combined success, invalid bind/policy denial and retry, pre-commit failure, concurrent submissions with one winner, and post-commit response loss/crash/restart. The current success scenario asserts identity acceptance only. The upstream verifier's early `consume` call (`identikey-auth/src/verify.rs:76–83`) makes the proposed transaction-scoped store an appropriate seam, but the seam does not resolve contradictory observable outcomes by itself.

## Steelman against the independent take

This node should remain a small consumer of v1. Adapter code, storage selection, capability minting, exact encoding, and managed signer implementation belong downstream. Decision 7 can reasonably be read as superseding Decision 6, and its replay wording shows the author understood the prior request. I accept that interpretation of the author's intent and do not request a different design or expanded cryptography.

However, independently implemented clients and endpoints still need to agree on the authenticated value across the gateway, and a normative scenario must actually exercise its claimed rejection. An implementer following the unchanged delta can still consume an invalid bind or pass the transport test using nonce rejection alone. These are the same bounded R4/R5 amendments, not new acceptance criteria.
