## Independent blind take

Written before opening design.md, tasks.md, or the proposed edge-auth delta; based on the proposal, reachable upstream v1 protocol, cited code, and LEARNINGS. No living edge-auth spec exists.

1. Pin the exact v1 Challenge and Response bytes and verification policy; refuse session fields or a new identity protocol.
2. Pin Challenge.aud to the independently trusted stable edge XID, with authenticated transport terminating at that edge.
3. Keep identity proof distinct from permission to issue a session or execute an operation; a valid signature alone grants neither.
4. Require the authenticated identity key to authorize the session public key and complete requested operation in a domain-separated signature.
5. Bind that authorization to this exact challenge exchange so proofs from separate logins cannot be spliced together.
6. Require channel context that the verifier derives and checks against the live connection; a claimant-supplied transport label is insufficient.
7. Specify replay ownership, expiry, concurrency, and the failure boundary between proof verification and issuing a usable credential.
8. Derive holder fingerprints with v1 section 5, preserving the algorithm tag; refuse raw-key fingerprint substitution and inferred custody rungs.
9. Require negative vectors for wrong edge/audience, altered operation, substituted holder key, expired proof, duplicate redemption, and transport replay.
10. Tradeoff: a separate authorization signature preserves shared identity interoperability but adds signer integration and state that must have explicit contracts.

## Required amendments

### R4 — Finish the channel provenance contract and isolate its vector

Evidence: `design.md:57–68`; `specs/edge-auth/spec.md:75–93`; `native/mjolnir_gateway/src/main.rs:1050–1071`.

“Edge proof ... plus connection id” does not yet identify who creates that id, how the client obtains and authenticates it, or which connection the verifier compares. This matters for the explicitly supported existing HTTPS API: the gateway terminates TLS and opens a separate backend TCP connection. Its shown handoff adds `X-Forwarded-Proto`; that is not proof of the client's TLS session. Likewise, the edge-key dependency authorizes an operational key but does not define how an edge-proof signature binds that key to this transport session. A relayed authentic challenge or delegation alone does not establish that the current peer is the pinned edge.

For each supported adapter, name the source and scope of the shared connection value, how the client authenticates it before signing, and how the edge obtains the independently trusted comparison value. For the gateway path, locate that check or specify the trusted handoff across termination. For Iroh, distinguish the transport peer/session from the stable edge pin and explain their binding. Explicitly defer any adapter lacking those inputs; plain HTTP must not acquire authenticated-peer status merely by being listed as HTTP(S). Implementation and exact encoding can remain downstream.

Also change the same-transport vector (`spec.md:82–87`) to use a **valid but unconsumed** proof/bind from N1, first submitted on N2 while unexpired. The current GIVEN says the exchange already completed, so an implementation with no channel check passes simply by rejecting the used nonce. Require a channel-specific rejection and a positive same-connection control. This is the same isolation principle already applied correctly to the new unused-proof expiry scenario.

### R5 — Make commit, crash, and retry outcomes consistent

Evidence: `design.md:72–81`; `specs/edge-auth/spec.md:95–116`.

Decision 6 says one commit consumes the nonce and records issuance, and invalid binds leave it unconsumed. It then allows a crash to leave the nonce “consumed-without-issue.” The normative requirement forbids consumption before successful issuance commit, while its invalid-bind scenario assumes a failed bind consumed the nonce. These cannot all describe the same transaction contract. The intended at-most-one-grant property is clear; the observable recovery behavior is not.

State outcomes on both sides of the commit boundary: invalid bind/policy denial, failure before commit, successful commit followed by response loss or process crash, and concurrent duplicate submissions. Distinguish a committed issuance record from delivery of its credential. A crash after a successful commit is not automatically an issuance failure; a credential already released cannot be presumed unusable merely because the process restarted. Select the retry rule for that case—reject and require a fresh challenge is sufficient—and guarantee that the old proof never mints a second grant. If durable consumed-without-issue tombstones are intended, define that abort state and reconcile it explicitly with the atomic requirement; otherwise remove that alternative.

Carry those outcomes into independent scenarios, including a successful combined authorization/issuance precondition. The current success scenario only asserts identity acceptance, and the invalid-bind scenario should assert the selected retry behavior instead of relying on a nonce-consumption path the design forbids. No database choice or endpoint implementation is requested.

## Steelman against the blind take

The strongest defense is that this node is intentionally a protocol consumer. It should establish security invariants while transport adapters, durable storage, managed signing, and capability enforcement live in their named downstream nodes. The revision substantially does that: same-holder signing, consent coverage, local policy, a transaction seam, missing-input rejection, and exact-challenge association are real answers. Requiring finalized CBOR fixtures, a specific TLS API, a storage engine, or an implemented managed signer would exceed this review and the steer.

I accept that defense for implementation detail and for R1. It does not resolve which authenticated session the two sides are signing/comparing across an existing proxy, or which state survives the stated commit. Those are interface semantics downstream implementations must agree on. R4 and R5 request small, testable contract amendments rather than a competing design.
