## Independent take (written before opening design, tasks, or delta)

1. Pin the edge's stable XID as the expected audience before accepting its challenge.
2. Preserve v1 Challenge fields, exact signed bytes, algorithms, and fingerprint derivation.
3. Bind authorization to the identity actually verified from the Response.
4. Require the holder to sign the session key, operation, and channel context together.
5. Refuse substituted keys, altered operations, and cross-protocol signature reuse.
6. Compare channel claims against independently trusted transport observations.
7. Make challenge freshness and single-use enforcement atomic under concurrency.
8. Define whether denial, issuance failure, and lost delivery consume the challenge.
9. Treat managed and self-custody Responses identically, without inferring custody or authority.
10. Accept extra signing and connection-management costs to preserve v1 interoperability.

## Comparison and resolved findings

**Identity and authorization separation (take 1–5, 9).** Decisions 1–4 preserve upstream v1, pin `aud` to the stable edge XID, require the same classical holder for Response and bind, and domain-separate the bind over exact challenge bytes plus session key, operation/resource, and channel. Local policy remains necessary. Managed consent covers both proofs; no custody rung or permission is inferred from the Response. Holder fingerprints remain upstream section 5, distinct from raw-key Sites fingerprints and OIDC subjects. Exact bind encoding is explicitly deferred by steer; this review does not override that decision.

**R4 closed (take 6).** `design.md:84–110` now makes the gateway the HTTPS channel authority: it allocates the external connection id, returns it beside the Challenge, strips caller copies, and supplies conn_id plus served-origin SPKI over a trusted backend. The verifier computes its expected channel independently of the bind. The normative channel requirement at `specs/edge-auth/spec.md:77` carries that boundary and rejects missing/untrusted inputs. Iroh has an edge-assigned connection id and a node identity tied to the pin's edge proof; plain HTTP is explicitly deferred. The replay scenario now performs the decisive sequence: unconsumed N1 proof rejected on N2 without consumption, accepted on N1 with one issuance, then rejected on N1 as replay. This rules out both accepting copied context and rejecting all binds.

**R5 closed (take 7–8).** Decisions 6 and 7 now agree with the normative commit requirement: consumption and issuance commit together, no usable credential escapes before commit, and no durable consumed-without-issue state exists. Invalid bind, denied policy, and pre-commit failure preserve the nonce. Concurrent attempts have one winner. Post-commit delivery loss preserves issuance and requires a fresh challenge; restart restores the commit and a closed connection requires a new exchange. Separate scenarios cover combined success, unused expiry, invalid bind, policy denial, pre-commit failure, concurrency, and post-commit loss. Same-connection retry after a verifier crash is conditional on that connection surviving; the gateway/verifier split makes this possible, while Decision 7 covers connection loss.

Upstream `verify_response` calls `NonceStore::consume` before returning (`verify.rs:76–83`). The specified transaction-scoped store is a credible seam: that mutation can remain provisional until bind/policy/issuance commit. The upstream in-memory store alone would not meet this contract. Storage and endpoint implementation remain downstream work.

## Steelman against the take

The take could be overread as requiring a TLS exporter, another signed identity envelope, or a new transactional verifier API. None is necessary here. An id delivered over the authenticated origin connection, then independently associated with each backend request by a trusted gateway, supplies the required connection distinction. A transaction-scoped NonceStore preserves the v1 verifier API. Requiring a fresh challenge after committed delivery loss sacrifices transparent retry but gives a coherent single-issuance rule. Those are justified choices within this small consumer contract.

Implementation must preserve the stated trusted-peer boundary. Current `native/mjolnir_gateway/src/main.rs:1050–1071` forwards the connection without this new handoff, and `lib/mjolnir/api/auth.ex:139–144` grants broad scope to configured loopback callers. Merely changing the existing API backend to loopback would therefore be unsafe. The endpoint/adapter work must enforce the specified gateway provenance and direct-auth checks without inheriting that bypass; current proxy code is not evidence that the new contract is already implemented. This is a concrete downstream integration constraint, not an additional protocol gate.
