## Independent take, written before reading the proposed contract

1. Pin the profile boundary: define login authorization and request policy over the shared Biscuit runtime; do not create a second mint/verifier.
2. Pin holder-bound issuance as the default, with the authenticated IdentiKey exchange authorizing the exact ephemeral session key and intended edge.
3. Pin holder fingerprints to auth-challenge v1 section 5, never the raw-key IdentiKey fingerprint even though both now use Blake3.
4. Require possession on every protected request and bind that proof to the exact token, intended verifier, and operation including security-relevant request bytes.
5. Require freshness and atomic single-use proof handling, including concurrent requests, process restart, and loss of replay state.
6. Refuse implicit bearer downgrade: mode must be issuer-authenticated, unambiguous, and unaffected by attenuation or missing proof.
7. Require bearer issuance to be explicit and measurably shorter-lived and narrower in authority than the default profile.
8. Refuse caller-supplied authorization facts or reusable verification output that could authorize a different request or widen the granted scope.
9. Refuse fallback from a failed Biscuit to the existing full-scope JWT or localhost paths; keep other capability domains and VM-spawn RBAC distinct.
10. Accept the availability and client-complexity cost of request possession proofs if the contract makes nonce ownership, failure behavior, and cross-language signing bytes testable.

## Assessment against the blind take

**Request proof and replay are now a bounded contract.** Decision 7 (`design.md:74`) supplies canonical dCBOR, a distinct signing context/purpose, complete presented-token and body Blake3 preimages, raw query binding, local edge identity, and an edge-issued nonce. Proof expiry is bounded by both capability and nonce expiry. Only outstanding nonces qualify; concurrent reuse, eviction, expiry, and loss of state reject. The delta (`specs/edge-auth/spec.md:46`) carries these rules and query-substitution/state-loss scenarios. This resolves the previous proof-contract blocker. `add-direct-auth-endpoints` owns nonce storage and proof transport; neither requires a second capability runtime.

**The authorization boundary now preserves attenuation.** Decision 8 (`design.md:103`) names trusted operational roots/delegations, expected edge, time, holder evidence, requested operation, and resource-bearing request facts. It runs all checks and expiry and returns allow/deny for this request. The delta (`specs/edge-auth/spec.md:102`) expressly rejects reusable ambient scope output and adds the `vm=A` versus `vm=B` case. Denial cannot populate claims or fall through to JWT/localhost. This resolves the previous adapter-boundary blocker; successful verification cannot become the current Auth plug's `@all_scopes` assignment.

**The earlier mode and integration repairs hold.** Decisions 2, 5, and 6 preserve issuer-authenticated mode, immutable holder checks, rejection of token-supplied holder facts, explicit bearer issuance, and precedence before localhost bypass. Strictly shorter lifetime and narrower authority are enforceable mint constraints even with numeric ceilings deferred. Holder fingerprints remain auth-challenge §5. The sibling capability standard §3.3 supplies chain verification and all-check evaluation; its redemption-specific §7 is not silently substituted for the login proof. The related direct-challenge delta binds the session key to the authenticated exchange, and the edge-key delta supplies delegated-root purpose and validity checks.

## Steelman and tradeoffs

My blind take could have demanded a complete endpoint protocol, storage transaction mechanism, or new capability engine here. That would exceed this node's profile-and-vectors scope. The strongest case against further design requirements is that the revised contract now fixes what a proof authorizes, while the named endpoint and shared-runtime work own how it is transported and executed. I agree. Unknown-on-state-loss is a valid fail-closed replay strategy; it does not require durable consumed-nonce tombstones. Its availability cost is another challenge after restart. Consumption must still prevent two protected effects, including when the backend effect itself cannot share a database transaction with the nonce store.

The one-shot result is also a sound alternative to exporting structured effective rights. Audit metadata, including subject XID, must not later become a second authorization path. The current Decision 8 treats those fields as audit metadata, so it does not leave an ambient grant to reconstruct downstream.

## Implementation and editorial notes

These notes belong to the existing unchecked profile/vector work, not a new architecture gate:

- Use Decisions 7–8 and the revised delta as the governing contract. Decision 4 still abbreviates the target as `path`; Decision 6 still describes effective-rights output. Consolidate those older summaries when maintaining the document so implementers do not revive the superseded behavior.
- Cross-language vectors should show literal inner and outer signing bytes, CBOR types for hashes/nonce/time, and the exact token bytes hashed. The existing sibling `identikey_auth::signing_payload` helper hardcodes `identikey-auth/v1` + `challenge`; it is not the new `identikey-mjolnir/v1` + `login-proof` payload. Preserve that domain distinction without modifying auth-challenge v1.
- Exercise unused-but-expired proofs, nonce validity boundaries, concurrent consumption and crash paths, different attenuation bytes, resource substitution, foreign/expired delegations, and failure from loopback. Header versus body transport can remain an endpoint choice, provided the actual request bytes and facts used for the effect are the ones verified.
