# Focused C2 lifecycle assessment

Reviewed product `64582cac1d4c53cd837a57092c80c1cef50de634`, accepted `add-webrtc-edge` D3/D8 and advise-4, cb1481c code review, ownership-fix evidence, real edge/runner code, vendored moq response/session driver, and locally cached Hyper **1.12.0** source. This is an independent design recommendation, **not code acceptance, release acceptance, or a normative contract edit**. No production files, deployments, agents, credentials, or real RTC services were used.

## Recommendation: owned HTTP/1 response ticket plus underlying flush

C2 is valid. Its claimed impossibility is limited to the Body-only boundary. Keep Hyper; replace `axum::serve` with a small owned **HTTP/1** connection adapter that supplies a per-connection delivery context to the router and wraps the actual IO. An accept-loop replacement without these two linked objects does nothing.

A candidate has an opaque ticket `(session id, generation)` and one terminal transition. Body completion marks that ticket **serialized**, not delivered. The IO adapter commits serialized tickets only after its underlying `poll_flush` returns `Ready(Ok(()))`. Dropping the connection future cancels its still-pending tickets. A committed ticket is removed from connection ownership, so neither a later failure nor normal HTTP closure cancels its RTC session. Do not associate by bearer, latest session, Location parsing, or a global connection-failed flag.

Use this exact restricted boundary:

- `hyper::server::conn::http1::Builder`, explicitly `pipeline_flush(false)`, with `TokioIo<DeliveryIo<IO>>` and `service_fn` calling the router via `oneshot`. The listener currently serves plain HTTP; the effective Axum features from `cargo tree --offline -e features -i axum` include http1 and **not http2**. Do not switch to the auto HTTP/2 builder.
- Service inserts a cloneable `DeliveryContext` request extension **before** calling the router. Each candidate enrolls before its response can escape. Require this context for media success; no silent Body-EOF fallback. Admission/error/DELETE responses enroll no candidate. An enrollment guard covers a middleware/body replacement or an unconsumed response.
- The special SDP Body keeps `is_end_stream` false and unknown size hint, yields data, then marks its own ticket serialized when returning `None`. Preserve chunked HTTP/1 framing: do not add Content-Length or another optimization that lets Hyper finish without polling `None`. Body drop before EOF cancels; body drop after EOF transfers responsibility to the connection pending set and does **not** disarm the ticket.
- `DeliveryIo::poll_write`/`poll_write_vectored` forward exactly the returned byte counts, including partial writes and Pending. No successful write is a commit. `poll_flush` first delegates to the underlying IO, commits only on successful completion, never on Pending/error. Preserve vectored semantics or explicitly advertise no vectored support. The probe uses the latter.
- The connection owner and error exits cancel pending candidates on every terminal result, including `Ok`, read failure/EOF, write/flush failure, cancellation and task panic/drop. Ensure an error is terminal before any later flush could commit. Do not rely only on inspecting `serve_connection`'s returned error. RAII covers an aborted connection future. Never cancel committed ids. An IO flush with no serialized ticket, including an interim 100 response or an early streaming flush, does nothing.

This supports persistent HTTP/1 and pipelined requests. With pipeline flushing disabled, Hyper flushes response A before advancing the server connection to write response B. A's ticket has already left the pending set when B fails. The body, service and IO share the same connection-local ticket state; no byte-count guessing or on-wire HTTP parser is required. Keep that constraint pinned and tested when upgrading Hyper or adding response-transforming middleware.

### Why the acknowledgement is real at this boundary

Cached `hyper-1.12.0/src/proto/h1/dispatch.rs:165-185` calls `poll_write` then `poll_flush`. Its `poll_write:350-435` polls Body EOF and invokes `conn.end_body()` before the next underlying flush. `proto/h1/io.rs:278-334` drains **all Hyper write buffers**, respecting partial writes/WriteZero, before calling the underlying IO's `poll_flush`. `proto/h1/conn.rs:855-859` calls `try_keep_alive` only after this flush succeeds. Thus the final chunk terminator as well as SDP and headers are covered. Body consumption alone covers none of that.

An underlying successful flush establishes **local transport acceptance of the complete serialized response**. It does not establish TCP peer receipt, proxy forwarding, browser parsing, or SDP application. A TCP flush can succeed just before a disconnect becomes visible. The current contract's write-failure cleanup can be implemented at this boundary; literal remote delivery cannot be promised without a peer-level acknowledgement. The existing 503/403 precedence remains applicable while an HTTP error can still be sent; after partial output a replacement error status is impossible, so terminate HTTP and record the classified failure while cleaning resources. This is an unavoidable transport limitation, not a reason to send a second status line.

## Minimal product changes and ownership API

Preferred ownership: retain the **unrun** moq Response in the session registry until this flush acknowledgement; it avoids starting then aborting a runner on failed output and meets “run only after 201 queued.” Do not wait for ICE before starting it.

1. Add a small `edge_http` module exposing `serve_connection(io, router)` (and the listener wrapper used by the binary), `DeliveryContext`, the marking body and IO wrapper. Promote the already locked Hyper/hyper-util and required Tower features to direct dependencies. Switch `src/bin/mjolnir-edge.rs:77` to that adapter. Tests must use this same function.
2. Replace `queue_http`'s immediate spawn/EOF-disarm with enrollment of the negotiated `(id,generation)` plus its unrun Response. Carry the original setup deadline into `Negotiated`. Keep pending Response ownership reachable by `finish_id`/token teardown, so drain, DELETE, expiry and relay death immediately drop the mux registration even if the HTTP connection is stalled. A mutex-protected Pending/Running state inside the existing session record is enough; do not add a second independent pool.
3. Provide `ack_delivery(id,generation)` and `cancel_delivery(id,generation)` operations. Under the pool lock, ack verifies the matching session/generation, non-draining state, token expiry, original deadline and live relay, then takes the unrun Response and installs the runner's cancellation handle atomically. Start the runner behind a start gate if necessary so it cannot finish before its handle is registered. Perform drops/abort work outside locks. A stale ack after DELETE/drain is a no-op, never resurrection. Preserve existing `finish_id(id,generation,...)` exactly-once cleanup and same-token/other-token isolation.
4. Bound pending output by the original `min(exp, setup_start+5s)` deadline (not a fresh five seconds). A pending deadline/relay death/drain wakes the connection driver, cancels the ticket and terminates an incomplete HTTP response. Already acknowledged RTC sessions on that HTTP connection survive candidate-local cancellation. Expiry/drain retain their existing broader scopes. Do not leave unrun Responses trapped in an idle connection context after registry teardown.
5. `router.oneshot(...).body.collect()` is no longer a successful *delivery* test. Use the owned connection adapter and successful transport for runner-positive tests; keep a separate test proving bare body collection cannot activate a candidate. A raw Hyper wrapper without the delivery context should fail closed for media success. Adapt the old FailedWire test to exercise the production adapter, retaining the same failing IO and incumbent assertions. This changes the test's ownership boundary, not its acceptance criterion.

Do not hold a context mutex while invoking Edge cleanup and then acquire those locks in reverse on drain. Extract terminal actions under the context lock, release it, then call Edge. Ensure the IO wrapper is placed above the complete buffered transport (e.g. wrapping a TLS stream if TLS is added), not beneath a TLS buffer whose flush has not completed.

## Empirical evidence

`http-delivery-probe/` is a standalone crate using exact Hyper 1.12.0, Axum router `oneshot`, synthetic `AsyncRead/AsyncWrite`, dummy candidate ids/counters, and no sockets or RTC credentials. It proves the transport mechanism, **not the full proposed pool integration**. `result.txt` records the command output; Cargo.lock fixes the tested dependency resolution. Built offline with one job and debug=0 on local rustc 1.96.0: **12 passed, 0 failed**, 0.41 s test runtime.

Cases cover successful close with 17-byte partial writes; successful keepalive followed by connection cancellation; BrokenPipe after EOF; failure after 17 bytes; underlying flush failure; cancellation after EOF while flush is Pending; two pipelined responses with second failing; three successful pipelined responses; large multi-frame response failure; successful large response with early flush before EOF; unconsumed body drop; WriteZero. Existing id 99 is never connection-owned. In the two-response failure case the result is committed `[99,1]`, cancelled `[2]`. No connection-end heuristic is used to decide success.

An exploratory large-body assertion initially assumed a single 400 KB data frame necessarily forces a flush before EOF. Hyper buffered it and that assertion failed. The final test uses 4 KB frames with explicit Pending between frames and explicitly proves an early successful flush occurs before EOF, without committing until the final flush. This reinforces why chunk size/backpressure guesses are not a delivery API.

## Alternatives assessed

**Body-only controlled streaming/framing:** rejected. Returning Pending after a chunk may cause a flush but gives the body no reliable acknowledgement that it happened. A final frame, EOF, trailers, exact Content-Length or `is_end_stream` is still consumed before output. Waiting for IO acknowledgement before producing the final terminator creates a second unacknowledged tail unless the IO boundary also owns final completion. `Connection: close` plus successful whole-connection completion could simplify one-shot HTTP but discards keepalive and still needs candidate ownership and honest local-write semantics; unnecessary here.

**Server-level hooks:** a public per-response serializer completion callback would work if provided, but Hyper Body/service callbacks are not that callback. The owned service+IO adapter above supplies the missing boundary without a Hyper fork. H2 cannot use the same EOF-to-next-flush rule: flow control may retain a stream's DATA while another stream/control frame flushes. Future H2 support needs stream-specific output completion (and reset handling), or a separately accepted RTC admission design. Keep H1 explicit now; an outer proxy speaking H2 to browsers does not turn this backend connection into H2, nor make backend flush prove browser receipt.

**Bounded pending RTC admission:** technically possible but changes the contract. Start Response::run provisionally, await a vendor-exposed authenticated transport-ready event, promote that exact id/generation, and expire unsuccessful attempts on an explicit short handshake deadline bounded by token exp. Enforce global and per-token pending quotas, release quotas on every terminal path, and never close another established id on failed HTTP/handshake. Plain STUN receipt or ICE reachability alone is not SDP-consumption/authenticated-session proof; use DTLS/RTC connected state with a documented meaning. `server::Response` currently exposes only `run(self)`; `session::Session::run_loop` drives `agent.next()` and `handle_event` only logs ICE changes. A ready receiver/callback must be plumbed through the vendor, and the runner **must run before** the event can occur. “Wait for ICE then run” deadlocks. WHIP also announces its route during `accept`, before run, so pending attempts are not cost-free; consider that in admission limits. A bounded orphan until timeout is weaker than immediate write-failure cleanup, and success could race failed HTTP. Choose this only if changing the accepted ownership semantics is desired, not as a necessary C2 repair.

Least-cost choice is the HTTP/1 adapter, with the existing contract interpreted as observed local write success/failure. A strict end-client-receipt guarantee or H2 support is a real scope choice and requires explicit contract work. Neither is needed to fix the demonstrated C2.

## Cheap cross-check of the other five fixes

C3 now drains flights and rejects stale/drained publication; C4 generation validation/detachment and session insertion are under the pool lock; C5 clones the moved URL; C6 makes nonempty origin lists authoritative and limits the empty-list fallback to the plain HTTP listener. C1 now calls `Shared::close`/connection abort instead of relying on Arc disappearance. These match the reported targeted improvements; this assessment did not rerun the real relay/TLS suite or accept all five wholesale.

Two source-level cautions for the implementer, not newly reproduced failures: final release removes the link under lock and calls `close` after unlocking, leaving a narrow concurrent redial-before-close window if the requirement is literally zero live overlap; the detached expiry task still retains Edge/token until exp. Also current `queue_http` spawns and inserts its runner outside the atomic session admission, allowing drain/completion to race registration. The recommended Pending-to-Running transaction must eliminate that latter gap rather than move it into the flush callback. Preserve the already fixed generation checks.

Next action belongs to the parent/builder: implement the adapter and ownership transaction, add actual Edge regression coverage for drain/expiry/DELETE/relay-close versus ack and for successful natural runner completion, rerun the existing real C2 and ownership probes, then request fresh code review. This note neither closes `.13` nor changes an acceptance verdict.
