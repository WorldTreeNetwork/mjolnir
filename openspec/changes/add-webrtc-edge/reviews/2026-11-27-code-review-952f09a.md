## Required repairs, prioritized

### N1 — P1: pre-expiry setup deadline becomes whole-token expiry

`native/mjolnir_relay/src/edge.rs:686–687`, called at `435–441` (also the test-dial path).

`insert_pending` returns `BadToken` for **either** actual token expiry **or** the setup deadline. `open_session` interprets that result as expiry, disarms the candidate reservation, and calls `drop_token`, removing incumbent sessions too. A thread can pass `finish_gate`, be descheduled or wait for the pool mutex, and reach this final insertion after the five-second budget but before token expiry. This is the final atomic gate that must preserve the distinction.

The controlled exact-code probe passes a past pending deadline with a valid unexpired `Checked`, a live reservation and an incumbent: result is `BadToken`. This directly reproduces the misclassification; it does not claim to have forced the full production scheduler interleaving. The caller's whole-token cleanup is source-proven. The ordinary real catalog-timeout test still correctly preserves incumbents, so that passing test does not cover this window.

**Smallest fix:** separate expiry from setup timeout in the locked insertion gate; carry phase/classification with the original deadline, return the D8 pre-expiry error, and release only the candidate. Carry the same original monotonic deadline through insertion/ack instead of reconstructing a wall-clock budget. Test expiry versus pre-expiry deadline at final registration with an incumbent and another token.

### N2 — P1: pending teardown never wakes or terminates stalled HTTP output

`edge.rs:714–721,788–798`; `edge_http.rs:98–120,265–273,298–329`.

The registry owns and drops the real unrun Response, but it has no cancellation notification back to the HTTP driver. `serve_connection` only awaits Hyper. `commit_serialized` ignores a rejected ack apart from another cleanup call and still returns a successful flush. Thus deadline, DELETE, drain or relay death can invalidate a candidate while its output is stalled, leaving the socket task waiting indefinitely. If output resumes, Hyper can finish the stale 201 and keep the connection alive despite no RTC session. D8's bounded pending output and the accepted mechanism's wake/terminate requirement are not implemented.

**Reproduced on actual TLS relay + real WHIP Response + production `serve_connection`:** hold the underlying final flush Pending, assert a real `Some(Response)` is parked and no runner exists, then (separately) let the original five-second deadline elapse, DELETE the candidate, or close the relay connection. In each case the gateway id and vendor session registration disappear, but the HTTP task remains pending. Releasing/waking the flush still does not terminate it. External task abortion is required. These are controlled IO tests, not TCP-reset or browser-delivery claims.

**Smallest fix:** give each pending ticket a terminal notification observed by the connection driver. Candidate invalidation must wake and terminate incomplete output, including after EOF; a failed ack must terminate rather than silently authorize continued HTTP output. Retain the per-ticket distinction so previously acknowledged RTC sessions survive that HTTP close. Add held-write and held-flush tests for deadline, DELETE, drain and relay death; assert driver completion without the test aborting it.

### N3 — P2: ack observes expiry but only removes one candidate

`edge.rs:746–764`.

Expiry, deadline, drain and relay death are collapsed into `stale`, followed by `finish_id`. When acknowledgement itself first observes expiry, same-token incumbents remain running until the independently scheduled expiry task or sweep executes. Unlike the other setup expiry exits, this path does not perform whole-token teardown. Relay-death acknowledgement similarly relies on the separate watcher. The check/start transaction does prevent an expired candidate from starting; the missing part is the required broader cleanup when that check fails.

A controlled real-Response probe injects an expired `session.exp_unix` into the parked candidate to isolate this branch ahead of the independent timer. Ack returns false, but the same-token incumbent and distinct-token control both remain (`refs=1/1`, two runners). This is branch/order evidence, **not** a genuine short Mint-issued token or proof of permanent expiry bypass. The separate normal whole-token expiry regression passes.

**Smallest fix:** classify failure under the pool lock. Expiry/known dead relay detach the matching token generation and its sessions atomically; a pre-expiry candidate deadline detaches just that candidate. Close/abort detached resources appropriately. Test the ack-first ordering with consistent controlled token expiry and real parked responses, ensuring the other token survives.

### N4 — P2: final release still exposes an empty slot before closing the old connection

`edge.rs:1045–1052,1068–1075,1120–1145,1204–1224`.

The original indefinitely retained connection is fixed by explicit `Shared::close`. However, final release removes the hold/link under lock and invokes close after unlocking. Source-proven schedule: release removes generation G and pauses; another acquire observes no hold/flight and establishes G+1; release resumes and closes G. The at-most-one-live-connection requirement is not protected across this interval. The checked-in real-close test waits for close before redial, so it cannot falsify this schedule. No new empirical overlap claim is made here.

**Smallest fix:** keep a closing-generation barrier until synchronous abort has been issued, or issue the bounded synchronous abort before making that token slot reusable. No awaiting under the mutex. Add a controlled release/redial interleaving that observes actual connection liveness, not only map count.

### N5 — P2: settled delivery tickets accumulate for the lifetime of keepalive

`edge_http.rs:98–114,123–139`.

Both commit and cancellation mark tickets settled but retain their original entries. Every new media response adds an id and `Arc<Edge>` to this connection-local vector, and each subsequent flush scans its entire history. DELETE, runner completion and token expiry cannot remove those entries. Long-lived proxy keepalive therefore has unbounded ticket retention and increasing per-flush work. This is direct source evidence, not a load benchmark.

**Smallest fix:** extract/remove terminal tickets while holding the context mutex; invoke Edge actions after releasing it. Only unsettled tickets belong in this context. Test many successful POST/DELETE cycles on one connection and assert the pending set returns to zero.
