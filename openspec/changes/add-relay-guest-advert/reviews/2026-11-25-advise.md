## Independent take (written before opening design.md / tasks.md)

From the goal, the living specs and the code:

- **Endpoint id source.** The controller does not know the relay's Iroh id. The relay derives it from `/var/lib/mjolnir-relay-state/iroh-secret` and only prints it (`native/mjolnir_relay/src/main.rs:247`). The clean channel is a file the relay writes in its own `RuntimeDirectory=mjolnir-relay` (`systemd/mjolnir-relay.service:22`). The relay already writes `keys.active` there (`main.rs:48,66-71`), so the sandbox (`ProtectSystem=strict`) allows the write. root reads it. The file needs atomic rename, a write before `READY=1`, removal at drain, and systemd's default non-preserved runtime dir handles cleanup on stop, failure and `Restart=`. I would refuse having Elixir read `iroh-secret` to derive the public key: that hands private key material to the controller.
- **Absent when disabled.** The guest agent rebuilds `/etc/mjolnir/vm.json` from scratch and overwrites it (`native/mjolnir_guest_agent/src/protocol.rs:426-458`, `vsock.rs:924-928`). `maybe_configure_identity` always re-sends on resume (`lib/mjolnir/vm.ex:3480-3483`). So "absent" holds at each setup and needs no guest-agent change. Only the allowlist in `lib/mjolnir/vsock/protocol.ex:189-205` stands in the way. Anything stronger, such as withdrawing from a running guest, would be a promise the system cannot keep.
- **Pairing.** The relay.env hostname and the running process's id can disagree after an edit without a restart. The pair should be published only when they match.
- **mj.** A JWT session confers `@all_scopes`, which includes `relay:join` (`lib/mjolnir/api/auth.ex:51,250`), so `mj login` (`scope=openid`, `native/mjolnir_api/src/auth.rs:22`) does not block the mint. Send `{}` so `rurh.11`'s `kind` defaults to protected. The shared error path leaks bodies and must be avoided.
- **Tradeoff.** Snapshot-at-setup versus live refresh. Snapshot is right for a small node.

## Comparison with the contract

The contract matches the take on every point and is more careful than the take in three places:

- It requires the runtime document's hostname to match relay.env.
- It discards any prior file at startup, so a fixture can test a failed start without systemd.
- It routes the mj response handling around `send_text`'s body-bearing errors.

The answers to the five questions:

1. **Stale locator.** Honestly scoped. The SHALL says "absent *after identity setup*" and states outright that a continuously running guest keeps the values from its last setup (`specs/edge-relay/spec.md:5`). Proposal "Out of scope: Live refresh" agrees. The harm is mostly fail-closed: a disabled relay or a renamed host gives a dead dial, and TLS hostname checks fail for WebTransport. One case is not fail-closed. After a key reset caused by compromise, a running guest dials the old endpoint id. Whoever holds the old secret then receives a bearer room token, valid for at most the ceiling (default 3600 s). That is narrow, but it belongs in the operator guidance (condition 2).
2. **`locator.json`.** Written by the relay user in its runtime dir. Read by root. Atomic rename. Published before `READY=1` and withdrawn at drain. Systemd cleanup covers stop, failure and restart. When the relay is down or running an older binary there is no file, so both fields are absent. Stale files are handled by the startup discard and runtime-dir removal. The sandbox permits the write, with `keys.active` as precedent. **This does change the relay binary**, so production needs a relay redeploy, which restarts the relay and drains live sessions. The contract puts "Relay deployment" out of scope and says an older binary supplies no locator (`design.md:7`). It never says that the guest fields stay absent in production until an owner-gated `deploy.sh --relay`. Condition 1.
3. **No secrets.** Confirmed by design and SHALL. Only `host` and `endpoint_id` go in the runtime file. Only `relay_url` and `relay_iroh_endpoint_id` go to the guest. The resolver touches no private key, TLS key or signing key (`design.md:9`). The guest agent's info log (`vsock.rs:912-915`) prints only blob/AIE, and both new values are public anyway. No owner id is involved.
4. **`mj relay token`.** Uses the saved or refreshed session. Prints the token only to stdout. No logging or persistence. Bodies stay out of diagnostics. Supports `--json` with raw passthrough, including extra fields. That passthrough already covers the `kind` field `rurh.11` adds to the response. The `{}` body means `kind` is omitted and defaults to protected under `add-open-room-kind`. The contract does not touch `lib/mjolnir/relay/mint.ex` (`proposal.md:32`). Both changes edit the `relay-room-auth` spec, but this one only ADDs a separate requirement, so the folds do not collide. It has no `--ttl` and no distinct exit codes per status (the spec says "nonzero" and the status goes to stderr). Both are acceptable at this size. See nits and the owner decision.
5. **SHALLs and tasks.** Every SHALL is built and testable. "No document after the unit has cleaned up" depends on systemd's default `RuntimeDirectoryPreserve=no`. It is testable through the unit file plus the startup-discard fixture. Every task names a baseline observation (O1–O4) and a failing test or a captured excerpt. Task 2 says Linux for guest-agent build and test. The Framework laptop (`dorje@…`, see `CLAUDE.md`) is the named Linux host for that. The relay crate tests also need Linux, because of the `sd_notify` and UDP 443 fixture, and only task 1 implies that.

## Conditions (write into the contract before code)

1. **State the activation gate.** In `proposal.md` (Out of scope or Impact) or as a final unchecked task, record:
   - landing this changes the `mjolnir-relay` binary;
   - production guests see no relay fields until the owner runs `deploy.sh --relay`, which restarts the relay and drains live sessions, plus a normal app deploy;
   - the guest agent is unchanged, so no `--agent` rebuild is needed.

   The redeploy is a human gate and the implementer must not run it.
2. **Name the stale-locator rule in the operator guidance task 3 already edits.** The catalog and the runbook must state that the locators are a snapshot taken at boot or resume. After the relay is disabled, renamed, or has its Iroh identity reset, running guests keep the old values until they resume or reboot. After a reset caused by compromise, the operator restarts affected guests. Guest apps should prefer the mint response's `relay_host` for WebTransport when it disagrees with `vm.json`.

## Nits (no gate)

- Make the locator and relay.env paths configurable (application env or opts, as `Mint` does with `opts`) so the resolver tests use temporary files rather than `/run`.
- The `mj` stderr hint should depend on the status: 401 → `mj login`, 403 → missing `relay:join` or not a user, 503 → relay not configured on this host. A distinct exit code per class would also be nice, but the spec does not need it.
- Task 1: say explicitly that the relay lifecycle fixture runs on Linux.

## Owner decisions

- Whether `mj relay token` should take `--ttl` now. The server accepts an integer `ttl` up to the ceiling. Alternatively it could come later with a `--kind open` flag after `rurh.11` lands. Leaving both out keeps this node clear of `rurh.11`. The reader recommends deferring both to one follow-up.
- Scheduling the production `deploy.sh --relay`, since it drains live relay sessions.
