Checked against the image, none of these disagree with it:

- The three words are the only ones the parser needs, and any other word fails the parse (`net.zig:110`–`136`). `reflect.wire_port` omitted leaves the guest in the plain QUIC loop (`net.zig:81`).
- 512 MiB is not only the homoiconic contract. The guest refuses a device address below 512 MiB (`net.zig:43`), so fixing the size is right.
- The readiness literal is `reflect: quic <port>` (`net.zig:56`).
- The header layout, the 1176 limit, the budget range, status 2 and status 3 with empty payloads, and status 0 for budget exhaustion all match `answerBytes` (`net.zig:643`–`664`) and the frame `quic-client.zig` builds.
- `reply_b64` as "payload only" is the same cut `check-quic.sh` makes before it compares (`body()` skips 24 bytes).
- A later factorial after a budget reply works for a client with new connection ids: the guest opens a fresh connection on the next long-header packet once it has answered (`net.zig:512`), and a fresh connection keys itself from whatever destination id arrives (`quic.zig:180`).

Checked against Mjolnir:

- `:never` is an existing policy and Reconcile finalizes such a record before it tests for a rootfs (`reconcile.ex` `build_plan`), so the data-loss line is already avoided on that branch.
- `:never` alone does not stop an owner's revive, which authorizes one resume (`vm.ex:735`). The delta's `unikernel_restart_refused` is therefore needed, and it is there.
- `default_memory_mb` is 512, so an omitted `--memory` is consistent with the rule. `default_vcpus` is 2, so the explicit 1 is needed, and it is there.
- `guest_agent_ping` is the real name of the health check the delta exempts.

## Independent take (written before opening the amended design)

1. The host BEAM is the client. What is left is which stack it uses and whether that stack can meet the listener's fixed handshake (8-byte connection ids, X25519, hello of at most 1024 bytes, AES-128-GCM, no ALPN).
2. Pin the connection lifetime: one connection per message, new connection ids each time, and what the host does after a handshake it refuses or abandons. The guest resets its one connection only after it has answered.
3. Compare the pin after the server flight and before any stream data. Check the certificate signature and Finished as well as the hash.
4. Give the correlation id a type at the API. Check the echoed id, kind 1, magic and reserved bytes in the reply before trusting the status byte.
5. Give each named error an HTTP status and a body shape.
6. Export the `reply run` outputs at `793b583` and store them with provenance, since Mjolnir has no Lean.
7. Write `:stopped` / `guest_exit` when the hypervisor exits, and branch Reconcile on kind before the rootfs test.
8. Branch `do_boot` on kind at the top. Poll the serial file for the readiness line under a deadline, because a guest that rejects its command line prints a different line and powers off.
9. Refuse TCP, `wire_port`, programs on `reflect.port`, retry, resume, and the agent verbs.
10. Tradeoff unchanged: one verb with two contracts. The CLI needs a rule for which form it is sending.

## Notes that do not block

**A. An abandoned handshake stops the guest from accepting another connection.** The guest replaces its one connection only when it has answered and a long-header packet arrives (`net.zig:512`). It sets "answered" only after the client's stream ends (`net.zig:632`). A connection installs its initial keys once, from the first destination id it sees (`quic.zig:180`), and frame handling has no case for a close (`quic.zig:302`–`349`). So if the host stops after the server flight, a later connection with a new destination id cannot be decrypted and is dropped, for the rest of that boot.

`check-quic.sh` does not show this. It runs `wrong` and then `loss` and the second succeeds, but `quic-client` seeds its generator with a constant (`quic-client.zig:18`), draws both connection ids and the key share from it (`quic.zig:69`–`76`), and uses a fixed hello random (`quic.zig:822`). Every run sends the same first packet, so the guest sees a retransmission of the handshake it already has. A client with fresh ids does not get that.

What follows for this contract:

- Wrong peer key: the first message returns `peer_key_refused`, as the scenario says. A second message to the same guest will most likely return `unikernel_timeout` after 60 seconds. The pin is fixed at spawn, so that guest was never going to answer, but the caller sees two different errors for one cause.
- Any handshake cut short before the stream ends (a BEAM crash, a lost packet run) leaves a healthy guest that times out every message until it is killed.

Two ways out that stay inside the contract. The host can remember the refusal for that guest and answer `peer_key_refused` without connecting again. Or the host can finish the handshake and end the stream with no bytes: `answerBytes` returns nothing for fewer than 24 bytes (`net.zig:644`) and the guest then marks itself answered, so the next connection is accepted. "SHALL send no RFL1 payload" allows the second. I read this from the source and did not run it.

Add two cases to the H1 spike, both with fresh connection ids: refuse, then connect again; abandon mid-handshake, then connect again.

**B. One clause of the wrong-key scenario cannot fail.** "The guest serial log shows no program evaluation for that request." The image writes its ready lines and its halt reasons to serial and nothing per request (`net.zig:47`, `:56`, `:1001`). The log would look the same if the program had run. The response `peer_key_refused` is the observable half. For "SHALL send no RFL1 payload", observe it on the host: the client never writes to the stream.

**C. `id` has no type.** Today `id` is a string checked by `Mailbox.valid_id?` and the CLI takes `--id turn-1`. The correlation id is 8 bytes. The delta does not say how one becomes the other, what is sent when `id` is omitted, or what a non-numeric id gets. Suggested: an unsigned 64-bit integer, `invalid_message_id` otherwise, host-chosen when omitted. The id never appears in the response, so the only test is on the frame bytes. The host should also check that the reply echoes the id it sent.

**D. Four results have a sentence and no scenario of their own.** Status 2, status 3, the default budget when `budget` is omitted, and `invalid_budget` from the host's range check. Each names an observable result, so each can be tested. Status 3 cannot be reached through the API because the host rejects the budget first; it needs a stub peer or a test of the reply-to-response mapping. Status 2 against the real image needs a program whose reply exceeds 1176 bytes, and no fixture is named for it.

**E. Error bodies.** The response is specified as `{"ok": true, "transport_status": <0|2|3>, ...}` and status 2 and 3 are also named errors. As written an error carries `ok: true`. The other named errors have no HTTP status. The route's existing convention is `{"error": "<name>"}` with a 4xx or 5xx.

**F. H1 should name the language.** "The host stack named below" resolves to "a client written to those constraints". The requirement has the BEAM open the socket, which reads as Elixir on `:gen_udp` and `:crypto`. If so, that client is about the size of `quic.zig` and is the riskiest code in the change, and the spike's client is its first draft. A spike done with a different tool would leave H1 open for what ships.

**G. Smaller.**

- The CLI line shows `--budget`, and `budget` is optional on HTTP. Say whether `--budget` is what selects the program-file form, or whether `mj` looks up the kind.
- Skipping the vsock wait also skips its deadline. A guest that rejects its command line prints `reflect: the network address is not valid` and powers off, and never prints the readiness line. The serial poll needs its own deadline and a named boot failure.
- A hand-run `systemctl restart mjolnir` kills every guest. Linux guests come back. Under this contract every unikernel guest ends as `:stopped` / `guest_exit` and stays down. That follows from `:never` and no replay, and is worth one line in the operator docs.
- `peer_key_refused` covers a certificate hash that differs. A bad signature or Finished is a different failure and has no name yet.
