## Findings and required edits

1. **High — keep the signed payload’s semantics intact.** Design:17–26; spike rust/src/claim.rs:49,92–103. The header selects a local key. jsonwebtoken 11.1.0 decoding.rs:270–290 verifies the compact signing input and deserializes the verified payload. The spike takes only the returned claims, removes kind and calls from_value. It neither re-signs a reconstructed JWT nor splices in bytes from another request. The defect is semantic: Members rejects duplicate top-level names, but each value has already been deserialized into serde_json::Value. Within a publish/subscribe access object this erases repeated members before moq-auth can see them. The upstream typed decoder visits object members directly (moq-auth/src/access.rs:64–85). Thus signed input the upstream decoder rejects can acquire a grant interpretation. No signature forgery or ability for a room-token holder to edit their token is implied. Narrow spike C5’s claim to the cases actually observed.

   **Prefer route (c).** Extend moq-auth’s typed wire claims by one exact field, distinguish absence from explicit null, preserve duplicate-field rejection, and retain its signature, key-operations, key-scope and time verification. Keep claim-free serialization for protected mints. Preserve the authenticated kind through the return value; ensure all deployed consumers that use the extended decoder interpret the extension consistently. Check the vendor diff, licence and resolved package IDs for both consumers at the pin. This is a smaller change to trusted verification logic and lets future upstream verification fixes flow through the normal rebase. It costs a maintained patch, a lockfile change and graph checks at each pin move. Route (b) avoids that packaging and uses established cryptography, but independently owns key selection, conversion, validation and projection for every room token, including existing ones. If (b) wins, preserve raw member values into the strict typed decoder or reject duplicates recursively before any lossy conversion. Specify compatibility for ignored fields. Reject malformed/non-object input, unknown claims, duplicate or escaped-equivalent names, nested duplicate grant members and conflicting legacy/current grants in defensive regression cases.

2. **High — make the parity gate compare the deployed trust boundary.** Tasks:22–32; spec:80. The relay loader already rejects private material, missing/duplicate kids, and algorithms outside EdDSA/ES256 (native/mjolnir_relay/src/lib.rs:61–97). The spike uses exact local kid lookup, verify permission, key algorithm and asymmetric material. Keep this invariant in the gateway’s public entry point too: bind the allowed algorithm to the *configured* key and its validated curve/material; reject none, symmetric algorithms including HMAC using public-key bytes, mismatched alg/kid, unknown/missing kid, and ambiguous key sets without fallback. Use the same atomically loaded trust snapshot for lookup and verification. No verification key or URL may come from jku, jwk, x5u or a certificate chain in the header. Specify whether such headers are ignored or rejected; refuse unsupported critical semantics and ambiguous header fields, and exercise these policies. The pinned jsonwebtoken Header models crit and key-location fields; decoding a Header is not enforcing their semantics. Keep any deliberate stricter header refusal explicit for legacy compatibility.

   The corpus includes positive HMAC, scoped-key and generated-payload cases (moq-auth/tests/corpus.json:47,65,112). Rejecting all scoped keys in (b) is a behavior change even for valid in-scope EdDSA grants; the current loader does not ban scopes. “Kid-less only” at design:26 is incorrect. Preserve existing scoped grants or obtain explicit compatibility disposition with evidence before deployment. Run the upstream corpus under its own rules and compare the selected verifier against the old *relay profile* on equivalent inputs/allowed keys, with positive EdDSA and ES256, verify-only and scoped keys. Check resulting root, access including caps, times and kind as well as acceptance. Re-sign equivalent ordinary positive/negative cases with a relay-eligible fixture key when an HMAC refusal would mask decoder behavior. Add raw signed JSON/header cases which cannot be represented faithfully as a parsed JSON fixture, with/without kind. Require zero unexplained differences; list each intended difference in advance. The new claim is the only intended widening. Claims at exp == now fail, nbf > now fails, iat is required and limited to now + 5 s, exp/iat lifetime is bounded, and path/grant checks still run. Exercise both algorithms, all boundaries and one controlled kio wall clock through verification and admission.

   **First executable task:** run this differential gate in the existing scratch harness against the chosen candidate decoder (for c, the minimal scratch wire change). Then run it against the final public admission entry point as the first product build gate. H-parity currently requires an as-yet-unbuilt product module to pass “before act.” The Iroh and Chromium boxes do name real transfer and refusal controls; rerun them with the selected route before deployment. The recorded positive transport evidence is native WebTransport with b, not either of those runs or evidence for c.

3. **High — drain unrecorded legacy tokens before the first open mint, including on roll-forward.** Design:42,61–69; tasks:48,55–57. An old issuer may have minted protected R seconds before cutover. The new issuer sees no record for R and signs open R; both valid tokens now authorize the same namespace. The same hole reappears after an old-controller rollback, when its protected renewals extend no record. Require a protected-only recording interval after the **last untracked issuer and in-flight mint** stop, long enough for all unrecorded tokens and sessions to expire, or a demonstrably complete equivalent migration. Repeat after each legacy interval. Test both transitions with a still-live legacy token. Use the greatest actual outstanding expiry, or the conservative maximum lifetime in force when those tokens were issued plus clock allowance; today’s ceiling can have been lowered. Ensure gateway legs end with their token grants.

   Only the mint reads the root-owned switch on each request; neither relay version checks it. This is an operator-controlled issuance fence, not automatic reader discovery. Confirm **every** serving verifier reachable by the issuer's tokens, by deployed artifact/version and local compatibility proof. Normally no open issuance under an old reader once this is enforced; premature enable or a reader rollback can put open tokens in front of one. Old readers refuse them. Resolve the circular prerequisite: tasks:48 and design:64 require live open-token admission before enabling, while tasks:55–57 forbid the first live open test until afterward. After recorded readiness and the legacy drain, enable and canary with a real mint, then close issuance on failure. On rollback turn off issuance, fence/finish requests that read the old switch, and drain from the last possible issuance. Cover automated rollback as well as the operator path. Decouple .11 completion from .13’s future release: every gateway actually serving must have the reader, and .13 must have it from day one.

4. **High — make store loss, stale restore and time discontinuities fail closed.** Design:46–50,90; ADR 0019:33. Missing is both the ordinary first-mint case and the result of lost state. An old backup can also contain a valid record with a too-small last_exp. A one-time loss with all issuers fenced, bounded clocks and no further loss limits overlap of the *old tokens* to their remaining issued lifetime. It does not limit the consequences of plaintext exposure, ensure continuous integrity or cover repeated loss, another writer, clock rollback or reuse while an old session is still alive. A backup is not evidence of the latest mint. Specify detection/health of the store, distinguish initial provisioning from unexpected absence, and **fence both kinds** on known/suspected loss or stale restore until records are reconciled or all potentially untracked grants/sessions have drained. Turning off open alone still permits a protected mint into a formerly open room. State the trusted-storage assumption for undetectable individual deletion; if surviving that failure is required, provide an independently durable journal/watermark. Test missing store, stale restoration, forward/backward clock changes and the recovery gate. Reuse only after the latest grant and its admitted sessions have expired across all readers, with defined clock skew/clock-step handling. Where that cannot be established, retain the kind. Stale roster/cache/media references also need retirement before representing the name as a new call.

5. **Medium — specify one durable writer and bounded record growth.** Design:39–49; tasks:42. One GenServer serializes simultaneous mints in one BEAM. Atomic rename alone cannot coordinate two writers’ read/decide/replace cycles. The actual app-only deployment quiesces, switches the release symlink, and **restarts the systemd unit**, with an automatic previous-release restart on failure (scripts/deploy.sh:95; scripts/release_control.py:210,251–265; systemd/mjolnir.service:56). The ordinary restart stops the old service before the new start; this is not hot-loaded code in one BEAM. Specify and test the enforced single-writer assumption across cutover and crash. A host-wide process lock acquired before serving mints is one option if overlapping processes are possible. A second host sharing a relay trust domain needs a common transactional authority with fencing; separate local stores do not suffice. Test overlapping starts or stopped-writer handoff, crash recovery, and concurrent same-kind renewals retaining the maximum exp.

   Write-before-sign safely over-reserves on signing failure. Check the directory fsync after rename and persist newly created owner-directory entries in their parent before returning success: StateStore.write_atomic at lib/mjolnir/state_store.ex:337–352 stops at rename. Validate record version, owner/room against path, kind and time fields; errors including read-only/ENOSPC/fsync failures return 503 without signing. Test I/O failure by injection or a read-only mount since a mode bit alone need not stop root. The canonical owner and bounded hex(room) prevent traversal; protect all ancestors, temp and final files, reject symlinks/nonregular records, and keep owner namespaces distinct on supported filesystems (base58 owners remain case-sensitive). Add a cleanup task naming the supervised sweeper, retention, restart, batched work and serialization/recheck against renewal before unlinking. A day’s retention alone leaves authorized users able to exhaust inodes or disk with fresh names. Provide a bounded creation budget per tenant plus a host limit/reserve with explicit failure, or isolate capacity and record the remaining availability risk. Never evict live records to recover space. Test both boundaries and cleanup versus renewal.

6. **Medium — give .13 full admission, and scope handoffs by room lifetime.** Design:23–25,55,81–83,95–100; tasks:28,32. The spike's verify_room ends after optional exp/nbf checks (claim.rs:104–112); assess_room applies required fields, TTL, root, path and grant validation afterward (claim.rs:125–131). Both are called “the verifier” in this contract. Give .13 the shared *full* admission operation returning authenticated kind, canonical original room identity and validated grant. Refuse non-room/wide roots, non-open kind, URL mismatch and insufficient operation grants before relay connection or SDP. Differentiate invalid credentials from a valid protected-room denial. Preserve existing Grant-returning entry points where callers depend on them. The relay can enforce the signed constraints and its existing media grants; it cannot compare against the current controller record or distinguish a WebRTC bridge that presents a protected bearer. No relay-level content or origin guarantee. Authenticating readers reject plaintext, but the host/plain subscribers can receive it. Access through a broader token still depends on its grant patterns.

   The protected-credential and renewal handoff is appropriate: check expected owner, room and kind against the authenticated admission identity, bind the response to the token being used, and stop before media/credential use on mismatch. Reusing a name later does not create cryptographic separation for a reused secret and label. Keep fresh credentials per call and versioned KDF/invite binding before enabling encrypted open calls. Roster must discard prior membership; tag metering with kind/lifetime for historical attribution. TURN allocation/usage may outlive username expiry. Carry issuance lifetime in attribution or explicitly aggregate; TURN itself grants no MoQ admission. Keep product gateway/client tests with those nodes. The delta mostly does so; distinguish operational readiness from enforceable mint behavior at spec:147–156, and replace the unresolved reuse placeholder at spec:114 after the decision.

## Disposition of the first review

The claim decision resolves the silent same-name split, and the marker parser, transport-tilde test and sibling-root accounting collision are obsolete. The body-only authority, validated enum log, missing-kind protected default and claim-free protected mints are retained. An explicit signed protected value is valid for new readers but only open mints add a field. Gateway-only enforcement and the buggy-gateway residual are stated accurately; full admission needs the API correction above. The earlier E2EE issue shifts from simultaneous sibling rooms to credential misuse across lifetimes. The old-controller client signal and controlled-clock requirement survived; the migration/drain and differential gates remain incomplete. Native WebTransport spike results are evidence only for the implementation tested. No production access, test execution or empirical transport validation in this review.

## Remaining owner decisions, in the recorded answer order

1. **ASK 2 — recommend 409 on a live conflicting mint**, no mutation or signature, and permit changing kind only after verified expiry/drain of the last grant/session. This costs a durable assignment, safe clock/recovery policy and delayed reuse. Never-reuse simplifies kind changes but permanently reserves names and requires lasting state.
2. **ASK 4 — retain relay:join** for the verified owner. It preserves existing provisioning; delegated holders of that authority can choose open for a new room. Separate authority would cost scope/client rollout.
3. **ASK 5 — protected credentials only on protected joins and renewals**, with a visible refusal before publishing. This costs consistent checks in every supported client and precludes protected credentials on the open playback path.
4. **ASK 6 — accept gateway enforcement with the documented residual.** This keeps the relay source-agnostic; an independent refusal would cost authenticated bridge identity and relay policy/rollout.
5. **ASK 7 — relay/readers first, record-aware controller protected-only, legacy drain, switch last.** Keep protected service during that migration; open availability is delayed and relay deploy/drain remains an owner gate. State-loss recovery can require pausing both kinds.
6. **ASK 8 — prefer the narrow carried moq-auth change (c)** for the smaller security-sensitive code path. Pay the explicit patch/rebase and consumer graph cost. Choosing (b) saves that packaging but requires Mjolnir to own long-term verifier compatibility and fix the demonstrated parser differential before use.

ASK 1 is settled; ASK 3 is moot. The six remaining decisions are genuinely open. ADR 0019 should distinguish recommendations and residual risks awaiting acceptance from costs already accepted.
