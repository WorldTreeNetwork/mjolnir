## Comparison and steelman

The chosen direction answers blind concerns 1, 4, 5, 7, and 8 at the architectural level: the consumer VM remains the holder, the human key stays outside the guest, authorization is rechecked after try-lock, failures refuse admission, and personal offers bypass guild infrastructure. The online availability tradeoff in concern 10 is appropriate. D5 need not be reopened: this is an additional AIE application admission condition, not a generic holder-class requirement on all v1 tokens.

The strongest reading of the short design is that it deliberately inherits the parent's accepted admission machinery and leaves mechanical codec/client work to implementation. I agree that this node need not redesign occupancy, offer incarnation, or request proofs. However, the signed delegation's meaning, the source of membership authority, and the interface that combines those decisions are the security boundary this node explicitly owns. No referenced concrete contract supplies them. Different implementations could obey every current sentence while granting materially different rights. The three blockers below therefore precede implementation, rather than asking for implementation in the review.

## R1 — Define what the member signs and how delegation stays current

**Blocking.** `design.md:14–19`, `tasks.md`'s delegation encoding task, and `specs/aie-compute/spec.md:5–10` say only that the signed leaf names the consumer VM. They do not specify signed bytes, signature algorithm/key representation, domain/version, guild binding, allowed purpose/scope, validity, or how the verifier obtains the current leaf. The member's signature must be checked against the same member key for which the lookup establishes membership; the delegated holder must equal the verified request holder using the protocol fingerprint namespace.

For example, if M belongs to G1 and G2, a leaf saying only “M delegates to H” plus a fresh G2 membership response can authorize H in G2 even if M intended G1 only. Likewise, fetching a fresh roster does not invalidate a replayed delegation that M withdrew while remaining a member. These are underspecified behaviors, not demonstrated implementation exploits.

**Owed:** specify the canonical signed envelope and exact identity/scope comparisons. Decide explicitly whether authority is guild-wide or limited by offer/resource/audience; offer-specific scope is not mandatory if guild-wide consent is intentional. Specify leaf discovery/publication authority, expiry and clock semantics, and withdrawal/replacement behavior including replay after restart. A bounded expiry-only model is an available choice if its revocation limit is explicit; a particular storage/tombstone design is not imposed. Add contract scenarios/vectors for valid delegation, bad signature, wrong member, wrong holder, cross-guild/wrong-purpose use, expiry, and the selected withdrawal/replay policy.

## R2 — Replace “trusted lookup” with a bounded, authenticated provider contract

**Blocking.** `design.md:21–27` and `specs/aie-compute/spec.md:11–17` mention a trusted lookup, provider `issued-at`, max-age, and a hard deadline, but identify neither the source of trust nor its request/response contract. A provider response for the wrong guild/member or an attacker-selected endpoint must not satisfy the gate merely by saying “member.” An old signed positive response cannot become current just because it was fetched again.

**Owed:** name the supported provider/adapter boundary, how trusted configuration binds a guild/keyspace to that authority, how responses are authenticated and bound to the queried member and guild, and how current delegation evidence is obtained. Pin timestamp units, permitted future skew, who controls max-age and its finite limit, and the finite deadline configuration shared with admission. Distinguish current non-member/missing evidence from transport failure; all refuse without falling back to an earlier positive. If a production provider contract is not yet available, identify that dependency explicitly rather than treating a stub as an operational trusted lookup.

Add scenarios for wrong-provider/wrong-subject evidence, forged or malformed response, stale/future-dated evidence, timeout/unavailability, and a fresh negative overriding an older still-within-TTL positive. The existing removal scenario is useful, but does not define how the client can know its response is authoritative and fresh.

## R3 — Pin the BEAM admission interface that enforces the conjunction

**Blocking.** `design.md:8–11` says `member` is injected while `mint`/`authorize` remain unchanged. The current `lib/mjolnir/biscuit.ex:195–209`, `native/mjolnir_biscuit/src/lib.rs:87–98`, and CLI `Authorize` request support holder injection only. `lib/mjolnir/secrets/redeem.ex:53–73` demonstrates the separation of external proof validation from Biscuit evaluation. There is no existing membership injection input in that path. The parent guild requirement expressly places membership outside `mint`/`authorize` Datalog.

The coherent interpretation is a BEAM application authorization gate whose trusted context includes membership, with Biscuit authorization remaining a separate necessary check. State that contract explicitly. Otherwise an implementer must either invent a new runtime fact API or treat an unused `member` value as enforcement.

**Owed:** define the callable interface/data contract consumed by `add-aie-host-sidecar`: verified current offer and policy, proven consumer holder, current admission attempt/deadline, and success/error output. Name where trusted membership/delegation evidence lives and where the conjunction is enforced: valid execute proof AND valid Biscuit/resource/incarnation AND current guild membership AND valid delegation for that holder. Personal policy bypasses only the guild portion. Tie success and late-result rejection to the current attempt; a result from a timed-out/released attempt must not authorize another. This specifies the shared boundary without implementing the sidecar or its lock.

Add scenarios proving that valid Biscuit authorization alone cannot admit a guild request, token-authored `member` facts cannot replace verifier evidence, member/delegation key mismatches refuse, and success from an abandoned attempt is unusable. Preserve the parent's fresh lookup on every successful try-lock and its no-lookup personal path. Generic “Guild member runs” must also include the consumer holder and delegation prerequisites, as the normative paragraph already requires.
