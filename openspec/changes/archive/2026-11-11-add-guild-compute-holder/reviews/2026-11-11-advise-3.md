## Comparison and steelman

The central architecture is sound: the consumer VM proves possession of its single holder key, and the BEAM separately checks membership and member consent. No human key enters the guest; no guild holder class or new membership Datalog enters the Biscuit runtime. The current offer and incarnation remain mandatory, and personal offers bypass only the guild portion. The lookup and leaf read belong after successful try-lock under the attempt deadline, with no reuse of enqueue evidence or abandoned-attempt success.

Guild-wide AIE consent answers my scope concern. Requiring each delegation to name one offer or host would narrow the author's explicit policy, so I do not require that. Deferring the production Recrypt roster behind an authenticated, subject-bound callback is also reasonable: unconfigured guilds must refuse, and an always-member stub cannot count as completed integration. The freshness and skew bounds are explicit.

R4 now supplies a member selector from the pending request, a deterministic leaf path, and the storage-fingerprint derivation. Treating that selector as untrusted while comparing it against both the signed leaf and roster response is appropriate. R5 now owns SecretStore codec integration and separates storage fingerprints from protocol holder fingerprints. I independently reconstructed the unsigned vector: it is exactly 160 bytes and matches the documented field grammar. The zero-key example is a byte-encoding fixture, not evidence of successful signature verification.

The strongest case for acceptance is that the new monotonic floor resolves R6 and the remaining work is implementation. It resolves replay after a *completed* withdrawal, but leaves two security-relevant state transitions unspecified. Neither finding below asks for product implementation during review or reopens the accepted parent architecture.

## R7 — Define a member-authenticated withdrawal operation

**Blocking.** `design.md:19–35,78–85,95–110` and `specs/aie-compute/spec.md:161–171` require a member-authorized tombstone but define signing bytes only for a live delegation. Those bytes contain purpose `aie-execute`, identities, validity, and sequence; they contain no grant-versus-withdraw action. There is no separate tombstone profile or authenticated mutation request defining what the member signs to withdraw. An unsigned JSON `type` or deletion flag would not resolve this, because envelope signing bytes are expressly the existing profile bytes.

This matters at the named integration seam: `SecretStore.put/3` and `delete/3` currently verify an envelope without authenticating a distinct caller or binding the signature to the mutation (`lib/mjolnir/secret_store.ex:254–284,660–670`). The proposal correctly excludes generic delete, but does not yet give its replacement an authenticated withdrawal message. For example, while floor N is current, someone holding a valid, not-yet-published grant envelope at N+1 must not be able to submit those same signed bytes as a withdrawal at N+1. A monotonic sequence alone does not distinguish the two intents. This is a missing contract, not a claim about an already deployed delegation endpoint.

**Owed:** pin the signed tombstone or signed mutation-request grammar, including operation/domain separation, target member/holder (and guild semantics for the chosen per-member/holder key), sequence, and validation rules. State that a live-grant signature cannot authorize withdrawal, that a withdrawal cannot be interpreted as a live grant, and that stale tombstones cannot withdraw a later regrant. Give a deterministic withdrawal signing vector and scenarios for authorized withdrawal, grant-to-tombstone substitution, tombstone-to-grant substitution, wrong-target withdrawal, and an old tombstone replayed after regrant. A separate authenticated request protocol is acceptable; no specific encoding redesign is mandated.

## R8 — Make the floor/current-leaf transition fail closed across interruption

**Blocking.** `design.md:99–107` chooses two files and says tombstone writes the floor then clears the leaf. The admission contract reads the current leaf, but specifies no comparison against that floor and no recovery of partial mutations. `specs/aie-compute/spec.md:186–190` tests restart only after a floor has already persisted, followed by a replayed *put*. It does not test admission from a stale file left by an interrupted withdrawal or replacement.

Concrete trace: leaf N is valid; withdrawal advances the floor to N+1; the process exits, the delete fails, or an admission read interleaves before the leaf is cleared. Leaf N is still present and signature-valid. Under the stated admission checks it can still authorize execution, even though the durable state records withdrawal at N+1. Replacement has the same partial-state question. Updating the leaf first instead would require its own replay/recovery argument. The existing store serializes mutations through a GenServer but `get/2` directly reads files (`lib/mjolnir/secret_store.ex:60–67`); its atomic writer covers one file at a time (`:563–580`). Serialization or per-file rename alone does not establish a coherent two-file authorization state.

**Owed:** pin the commit/recovery invariant for the floor and current leaf, the point at which admission observes a mutation, and fail-closed handling of mismatched, missing, malformed, or unreadable state. State how a legitimate live leaf at the current floor is distinguished from a withdrawal and how reads cannot combine incompatible versions. Reserve the floor against generic put/delete paths that would reset or bypass it. An authoritative single state record or an ordered, recoverable two-file protocol are both viable; choose and describe the contract rather than relying on "a SecretStore file" as the durability argument. Add interruption tests between persistence steps, concurrent admission versus withdrawal/replacement, failed leaf deletion, restart with partial state, and floor-reset attempts. No requirement is imposed to cancel a job that was validly admitted before withdrawal or already loaded under the parent policy.
