# Advise — add-mailbox-durable-accept (architecture)

> **ADVISE:** accept-with-nits

Reader: Claude Fable 5 (cross-family sole-accept per ADR-005; author Grok 4.6; Sol not subscribed).
Date: 2026-08-22. Rigor: architecture. Scope reviewed: `proposal.md`, `design.md`,
`tasks.md`, `specs/vm-mailbox/spec.md`, ADR 0006, `docs/philosophy/mailbox-as-spool.md`,
and every cited code path.

## Verdict

Accept, with nits the act must absorb. The architecture is coherent, correctly
scoped, and — unusually — every factual claim it makes about the existing code
is true. The two-ACK split, filename-as-identity, and "state gates *when*, never
*whether*" are the right primitives, and the deletable-code tell
(`retry_deliver_message`, the `:restoring` reject, the `finish_boot` drain all
become dead) is the strongest kind of evidence that the missing layer was found.

The one nit that touches the spec's central SHALL: the durability mechanism the
spec names does not, by itself, deliver the guarantee the spec states. Details
in Finding 1. It is a one-line fix in act, not a design flaw, which is why this
is accept-with-nits and not send-back.

## Claims verified against code

The design's "traps" table is accurate, line for line:

- Running delivery is a fire-and-forget cast: `lib/mjolnir/vm.ex:1130-1132`
  calls `Vsock.Connection.deliver_message`, which is `GenServer.cast`
  (`lib/mjolnir/vsock/connection.ex:97-98`). 200 means "enqueued a write."
- Booting queue is in-memory: `lib/mjolnir/vm.ex:1135-1136`; drained by casts
  and zeroed at `lib/mjolnir/vm.ex:2609-2618` (`finish_boot`).
- Dormant persistence is `File.write` + rename with **no `:file.sync`**, behind
  a 250 ms debounce: `lib/mjolnir/dormant_registry.ex:273-284` (schedule),
  `lib/mjolnir/dormant_registry.ex:326-341` (write). Instant mode
  (`flush_delay_ms: 0`) is still not fsync.
- Restore is take-then-send: `lib/mjolnir/vm.ex:3104-3111` clears
  `pending_messages` before any vsock attempt; a crash in that window is
  permanent loss.
- `:restoring` reject + 5×200 ms retry: `lib/mjolnir/dormant_registry.ex:188-191`
  and `lib/mjolnir/vm.ex:3028-3043`.
- Guest agent buffers in a RAM `VecDeque` and ACKs immediately:
  `native/mjolnir_guest_agent/src/vsock.rs:1091-1098`.
- Guest HTTP `GET /messages` destroys on read: `drain(..)` at
  `native/mjolnir_guest_agent/src/agent.rs:502-514`.
- Today's API returns bare `{ok: true}` with no message id:
  `lib/mjolnir/api/router.ex:1035-1037`.
- The fsync discipline to copy exists and works as described:
  `lib/mjolnir/forge/store.ex:179-183` (tmp + `:file.write` + `:file.sync` +
  close + rename).

## Steelman against (three, as chartered)

**1. Postgres sidecar as the ledger.** The strongest version: the fiddly parts
of a filesystem spool — atomic dedup on concurrent same-id POSTs, durable
rename, tombstone GC, ordering, a future claim protocol — are exactly what
`UNIQUE`, WAL, `SKIP LOCKED`, and `LISTEN/NOTIFY` already do correctly, and act
will re-implement a sliver of a database with subtle bugs (see Findings 1 and
3, which are precisely the bugs PG prevents for free). Why the design still
holds: `:pg_enabled` is off by default, so a PG accept point either forks two
accept implementations or silently degrades to today's lossy path on every
test host and Mac — that alone is decisive. The crash domain is identical
(same disk), the control-plane contract is already FS-first with PG derived
(`sites.head_index`), dual-write is a lie after a crash in one direction or
the other, and the spool must travel with the actor's subvolume, not sit in a
table decoupled from it. The design's own escape hatch is right: PG earns a
table when two workers claim from one pile, and a derived index of `@mail/`
for operator UI is allowed at any time.

**2. Front-proxy VM as the mailbox.** The strongest version: tenant-authored
wake policy in a sandbox is the product's own aesthetic (everything is a VM),
and a per-workspace proxy gives isolation the host facade can't. Why it
fails as the *accept point*: the proxy's inbox is RAM plus a rootfs this
system deletes on dormancy; for its ACK to be honest it must write host disk,
at which point the disk write is the mechanism and the VM is decoration —
plus someone must queue while the proxy itself boots (turtles), and N
always-on proxies fight the dormancy cost model. The design's disposition —
host accepts durably first, a policy VM may later *read* the spool
(`mjolnir-5le4.4`) — preserves the steelman's actual value (tenant policy)
without letting it corrupt the 200. Blob-door already litigated this shape.

**3. Split guest peek/ack out of this architecture write.** The strongest
version: host durable accept alone already fixes the laptop-close drop (the
headline symptom), the review surface halves, and the guest protocol rev could
ship as its own capability. Why bundling is right: without application ACK the
spool has no delete condition except TTL — every successfully processed
message would eventually *bounce*, which is nonsense; the "one queue" SHALL is
false while the guest's destructive `drain(..)` remains a second, losable
copy; and the two-ACK distinction is the semantic heart of the capability, not
an implementation detail. The design already permits the act-level split
(`mjolnir-5le4.1` / `.2` "may weave"), which captures everything the steelman
wanted.

## One real tradeoff

**Barrier-free `handle_done` buys race-freedom at the price of dormancy
churn.** Decision 4 is correct that a POST racing dormancy needs no barrier —
the file is the wake. But the same rule means a VM that signals done while
*any* mail is unacked (delivered, buffered, even mid-processing) is
snapshotted, registered dormant, and then immediately restored by the
delivery worker. Each cycle costs a BTRFS snapshot plus a multi-second boot.
A guest that processes but acks late — or a buggy app that never acks — turns
this into a wake loop bounded only by give-up (Decision 8). The design accepts
this: redelivery is cheap to reason about, the guest is idempotent forever,
and give-up caps the damage. That is the honest price of at-least-once with no
barrier, and it is worth paying — but act should consider letting
`signal_done_ack` carry an unacked-mail count so a well-behaved guest can
drain before sleeping instead of paying a snapshot/restore round trip.

## Findings

1. **Directory-entry durability gap (the spec nit that matters).** The spec's
   central requirement — "A host crash after 200 SHALL leave that file" — names
   the mechanism "tmp file, `:file.sync`, rename" and cites the `Forge.Store`
   path. That path (`lib/mjolnir/forge/store.ex:179-183`) fsyncs the *file* but
   never the *parent directory*, so on a crash after rename the new directory
   entry may not have reached disk: the 200 was returned and the file is gone.
   For Forge state (rebuildable) that's tolerable; for a spool whose entire
   point is that 200 survives a crash, it isn't. The philosophy file cites the
   qmail lineage — qmail's spool discipline is exactly fsync file, rename,
   **fsync directory**. Act must add the directory fsync (open the dir,
   `:file.sync`, close) and the folded spec text should say "fsync of the file
   and its directory entry" rather than inheriting the Forge wording verbatim.
   Copying `Forge.Store` unchanged would technically pass today's spec text
   while violating its scenario.

2. **Tombstone retention is undefined against a duplicate SHALL.** The spec
   requires duplicate detection "whether the first copy is still unacked or
   already tombstoned" (`specs/vm-mailbox/spec.md`, Producer id requirement),
   but the design says tombstones are "retained briefly" (Decision 3). A
   tombstone GC'd before the producer's last possible retry silently reopens
   the duplicate window — the exact failure the capability exists to close.
   The philosophy already notices tombstones are nearly free ("until ACK, or
   for days"). Act must pick a retention floor that dominates the documented
   producer retry horizon, and document both numbers together.

3. **Concurrent same-id accept is a TOCTOU unless create is exclusive.** Two
   simultaneous POSTs of the same `id` (Tatastu retry racing its own timeout)
   through a stat-then-write path can both 200 with `status: queued`, or worse,
   interleave tmp/rename. Filename-as-identity solves this only if the final
   materialization is atomic-exclusive (rename-noreplace / `O_EXCL` link
   semantics, or all accepts serialized through one writer process). Implementer
   gap; one sentence in act's design settles it.

4. **Delivery-worker ownership is unnamed.** "Host delivery worker" appears
   throughout, but nothing says whether it is the VM GenServer, a per-mailbox
   process, or a singleton scanning `@mail/`. The Rejected list asserts "one
   consumer per mailbox" — that invariant needs an owner, because the startup
   sweep, the POST-triggered delivery attempt, and the restore path can all
   race on the same files (who moves a file to `acked/`? who counts delivery
   attempts?). Acceptable to leave open at architecture rigor, but it is the
   first decision act must make, before any code.

5. **Ordering is unspecified.** A directory of producer-named files has no
   arrival order, and producer-supplied ids cannot encode one. For Tatastu
   (queue depth ≈ 1) this is moot, but the spec makes the files "the only
   delivery queue" without saying delivery order is undefined/best-effort.
   Either state that, or have the host stamp an arrival sequence in the file
   body (not the filename — the filename is identity). One sentence at fold.

6. **Orphan mailboxes.** Give-up (Decision 8) covers a wedged *guest*; nothing
   covers a *deleted* VM. `mj kill` (or `kill --all`) on a VM with unacked
   mail leaves `@mail/<vm_id>/` owned by nobody — not running, not dormant,
   no wake possible. `Mjolnir.Cleanup`'s startup sweep needs a rule: mail for a
   VM that exists in neither VMRegistry, DormantRegistry, nor `@snapshots/`
   goes to the bounce area. Otherwise the disk-fill guarantee has a hole.

7. **The migration claim outruns the layout.** Decision 7 asserts "the spool
   migrates with the actor (`btrfs send`)," but `@mail/<vm_id>/` as a plain
   directory under a shared `@mail` tree does not ride a send of the VM's
   subvolume — it needs either a per-VM subvolume or an explicit copy step in
   future migration tooling. Not built in this change, so this is only an
   ADR-precision nit — but the ADR is the document people will quote later.
   Relatedly (ops, not spec): `@mail/` joins `@snapshots/`/`@base/`/`@vms/` in
   having no off-box copy today; whatever lands for `mjolnir-qwp` should name
   `@mail/` explicitly.

8. **Vsock frame `id` semantics change is real guest-protocol work.** Today
   the `DeliverMessage` `id` is a host correlation UUID and the guest echoes it
   in `DeliverMessageAck` (`native/mjolnir_guest_agent/src/vsock.rs:1085-1098`).
   Decision 2 has the frame carry the producer `message_id` — that either
   overloads request/response correlation or needs a distinct field. Fine
   either way, but it means the "host store" act and the guest rev are coupled
   at the wire format even if peek/ack code lands separately; `mjolnir-5le4.2`
   should own the field decision.

9. **Don't-thaw mail ages into the bounce path.** Decision 5's "valid message,
   don't thaw → file waits" interacts with Decision 8's TTL: mail refused thaw
   by policy for longer than the give-up horizon gets bounced even though
   nothing is wedged. Possibly desired (policy-parked mail shouldn't wait
   forever either), but the give-up documentation should say whether the TTL
   clock runs while Admit refuses thaw, because the operator reading the
   bounce area will otherwise misdiagnose it as a delivery failure.

## What is solid

- **The problem statement is earned, not asserted.** Every trap is real and
  cited accurately; I could not find a single overstated claim about the
  existing code. That is rare and it makes the "spool deletes three mechanisms"
  argument load-bearing rather than rhetorical.
- **The two-ACK table** (Decision 3) is the sharpest piece of the design — it
  names the exact confusion (`deliver_message_ack` as a RAM hint that must
  never delete) that makes today's system look more reliable than it is.
- **Honest omitted-id semantics** ("retry safety is then off... Document it;
  do not pretend") — the easy lie was to hash the body SQS-style and pretend.
- **The SQS FIFO analysis is correct** as history and as a design lesson:
  ingress identity + a store that doesn't invent duplicates, no leases, no
  second product named exactly-once.
- **Admit's two no's** (never-message → no file; don't-thaw → file waits) put
  policy outside the 200's meaning, which keeps the producer contract stable
  as policy evolves.
- **Scope discipline**: proxy VM, PG queue, EventBus persistence, maildir
  mount, freeze/thaw, PUSH/PULL are all explicitly parked with revisit
  conditions, not silently dropped.

## Implementer gaps (act checklist, no owed boxes — this is accept)

- Add parent-directory fsync to the spool write path; fold-time spec wording
  to match (Finding 1).
- Exclusive-create semantics or single-writer accept serialization (Finding 3).
- Name the delivery worker and the single-consumer-per-mailbox owner before
  writing code; define who moves files to `acked/` and where attempt counts
  live — not only in the VM struct, since `build_running_record/1` rebuilds
  `runtime` from scratch on boot/resume (`lib/mjolnir/vm.ex:2948-2949`)
  (Finding 4).
- Tombstone retention ≥ documented producer retry horizon (Finding 2).
- Ordering statement, arrival stamp in file body if needed (Finding 5).
- Cleanup rule for mailboxes of deleted VMs (Finding 6).
- Decide the vsock frame field for producer `message_id` vs correlation id
  (Finding 8).
- Document whether the give-up TTL runs during Admit don't-thaw (Finding 9).
- Consider `signal_done_ack` carrying unacked-mail count to avoid the
  dormancy-churn round trip (Tradeoff section).
