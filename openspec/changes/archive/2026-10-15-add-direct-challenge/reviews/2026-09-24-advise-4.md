## Independent take (written before opening design, tasks, or delta)

1. Pin the unchanged v1 Challenge fields and exact signed challenge bytes; refuse an edge-specific identity-protocol revision.
2. Pin audience to an independently trusted edge identity; a claimant must not learn whom it trusts solely from an unauthenticated challenge.
3. Bind identity to the v1 algorithm-committing holder fingerprint; refuse implicit equivalence with raw-key Sites fingerprints or pairwise OIDC subjects.
4. Require a separately domain-separated authorization signature covering the authenticated holder, session key, precise requested operation, and channel context.
5. Refuse holder-key substitution or an authorization signature that is merely valid under an unrelated key; verification must join the two proofs explicitly.
6. Pin channel context to authenticated transport observations and the particular connection, with a specified trusted boundary wherever TLS terminates.
7. Pin nonce issuance, expiry, concurrent single-use acceptance, and failure/retry behavior so malformed authorization cannot grant access or silently burn a valid proof.
8. Require independent failure vectors with success controls for altered requests, wrong audience/edge, substitution, expiry, and replay across and within transport kinds.
9. Preserve identical verification for managed and self-custody claimants; identikey-core may sign, but cannot become the edge verifier or evidence of a custody rung.
10. Accept the tradeoff of a second signature and connection-bound retry complexity for explicit authorization, while keeping existing OIDC entry points and endpoint implementation outside this contract review.

## R4 — Finish the termination boundary and positive control

Evidence: `design.md:85–97`; `specs/edge-auth/spec.md:75–95`; `native/mjolnir_gateway/src/main.rs:1050–1071`.

The HTTPS formula is a usable proposed comparison value, but the contract still does not locate its authoritative connection state. The client observes the origin TLS connection; Bandit observes a backend socket. The current gateway terminates TLS, sets `X-Forwarded-Proto`, and opens that backend connection. Saying the proxy is not a second peer does not specify how the verifier obtains a trusted association between that backend request, the actual external TLS connection, its served certificate, and the edge-generated id. Returning an id beside a Challenge fixes delivery to the client, not this verifier-side association. Looking up the id only by Challenge or accepting the copied id as the comparison value would allow an unconsumed N1 proof on N2.

Close R4 by naming where this check occurs: at termination, or through an explicitly trusted gateway-to-verifier handoff. State that the id is scoped to the external connection, how the verifier gets that connection's expected value independently of the submitted proof, and how untrusted callers cannot supply that context. A documented one-to-one gateway/backend mapping is also a possible contract if its required properties are stated. For Iroh, identify the shared connection-id delivery/comparison and how the authenticated edge node is tied to the stable pin. Plain HTTP must be deferred unless an authenticated adapter is specified. This asks for interface semantics, not adapter implementation or a replacement hash.

The delta's N1 control is still absent. Lines 88–89 assert only that a submit **after** a first commit is replay; no preceding step commits on N1. Require a valid, unexpired proof first rejected on N2 for channel mismatch without consumption, then accepted on N1 with exactly one issuance, then rejected on N1 as replay. Decision 7's “second submit ... success control” can describe that sequence, but the normative scenario must spell it out. An implementation that rejects every bind otherwise satisfies these negative assertions.

## R5 — Complete the selected commit/recovery contract

Evidence: `design.md:72–80,99–103`; `specs/edge-auth/spec.md:12–19,97–118`; upstream `identikey-auth/src/verify.rs:76–83`.

The selected rule in Decision 7 is sound: pre-commit failure leaves the nonce unconsumed; committed issuance followed by delivery loss requires a new challenge; restart restores committed state. Invalid-bind handling now agrees with it. However, Decision 6 still permits “consumed-without-issue,” and the delta still says restart after issuance failure leaves no usable capability without distinguishing an aborted transaction from a committed issuance whose delivery failed. The normative success scenario still asserts only identity acceptance. Concurrency, pre-commit failure, and post-commit loss/restart have no independent scenarios.

Remove the durable consumed-without-issue alternative, or explicitly reconcile it with the claimed atomic state model. Distinguish **issued** from **delivered**: no usable credential escapes before commit; commit durably records consumption and issuance together; response loss does not undo that record or permit another issuance from the old proof. Carry these outcomes into the delta, including combined success, denied bind/policy with no consumption, pre-commit failure/retry, concurrent submissions with exactly one winner, and post-commit loss/restart rejecting the old proof and requiring a fresh challenge. If restart closes the original connection, retry must also satisfy the channel rule.

The transaction-scoped NonceStore is a credible seam for upstream `verify_response`, which calls `consume` before returning. A storage engine or endpoint implementation is not required for this review; consistent observable states are.

## Steelman against the take

This is intentionally a small protocol-consumer node. Its author has already chosen the important security boundaries, and Decision 7 could reasonably be read as superseding older prose. A trusted gateway mapping could make the channel construction work without a TLS exporter, and an edge-generated id delivered over authenticated TLS need not itself be a new signed v1 field. I accept those choices and do not require a different construction, new algorithms, exact CBOR fixtures, or product code.

The remaining gaps cannot be resolved solely by that charitable reading: the verifier's trusted external-connection association is still unnamed, and the delta retains contradictory/underspecified failure outcomes and omits the promised positive control. Small contract amendments can close both existing findings.
