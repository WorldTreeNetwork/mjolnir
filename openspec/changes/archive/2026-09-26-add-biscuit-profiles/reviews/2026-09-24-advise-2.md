## Independent blind take

Written before opening design.md, tasks.md, or the proposed delta; inputs are the packet rationale, living secret-tokenator spec, cited Auth code, and fingerprint learning.

1. Pin this node to login profiles over the shared mint/verify primitive; the living spec does not establish a working Biscuit runtime.
2. Pin the authenticated IdentiKey principal's authorization of the exact ephemeral session key, audience, and requested authority at exchange.
3. Pin holder fingerprints to auth-challenge v1 §5 canonical algorithm/key encoding and real Blake3, never the existing identity helper.
4. Require possession on every protected request, binding proof to the token, target edge, operation, and freshness context.
5. Refuse replayable proofs or caller-supplied holder facts; specify nonce consumption and the verifier's trusted evidence boundary.
6. Refuse ambiguous, missing, conflicting, or attenuated mode facts that could turn holder-bound credentials into bearer credentials.
7. Require explicit bearer issuance with concrete lifetime and authority limits that both issuance and verification enforce.
8. Keep Biscuit authorization narrow through dispatch and claims assignment; existing full-scope JWT and localhost paths must not upgrade it.
9. Pin the shared runtime input/output contract and adversarial profile tests without implementing a second mint or verifier here.
10. Accept the tradeoff of extra proof work and session-key custody for theft resistance, while retaining deliberately constrained bearer automation.

## Findings

### 1. High — Finish the signed request and replay contract

`design.md:44–50` and `specs/edge-auth/spec.md:48–53` now name the tuple, token binding, replay owner, and failure behavior. They still do not define its encoded bytes, the digest algorithms/preimages, whether `biscuit_hash` includes the complete presented attenuation chain, or what `path` means. A version label alone does not make two implementations sign the same bytes.

The missing query rule is security-relevant in this repository: `lib/mjolnir/api/router.ex:615` uses `?session=` to select a shared terminal, and line 488 uses query selectors to filter the VM list. If `path` means the path component alone, changing those parameters leaves the signed tuple unchanged. A captured proof could be substituted onto that altered request before its first use; single-use nonces prevent a second acceptance, not substitution of the first request. This is a gap in the proposed contract, not a claim of an existing Biscuit exploit.

Naming an edge nonce store and concurrent-reuse rejection is progress, but issuance, expiry, and retention remain open: who chooses/registers the nonce, what makes it outstanding, how proof `exp` relates to nonce validity, and when the consumed record may safely be discarded. Otherwise a proof with a later expiry could become usable again after eviction or restart. The contract can use either verifier-issued challenges or another explicitly bounded scheme; no particular storage implementation is required.

**Owed:** define the versioned encoding and field representations; hash the intended token bytes and body bytes under specified rules; bind the actual request target including query semantics and any other authorization-relevant inputs, with explicit normalization/rejection rules. Specify nonce origin, scope, validity, atomic consumption before the protected effect, and fail-closed behavior after expiry, eviction, or state loss. Numeric windows may remain configuration choices. Alternatively name a concrete prerequisite that must deliver this contract before profile vectors and endpoint integration can land; a general runtime citation is insufficient. Add vector obligations for query/method/path substitution, different attenuated token bytes, stale/unknown nonce, concurrent reuse, and post-retention/state-loss replay.

The sibling `../identikey-protocol/docs/standards/identikey-capability-v1.md` §7.1 expressly leaves tuple encoding and token identity unresolved and limits that profile to redemption. Auth-challenge §5 defines the holder fingerprint only; it does not fill these login-proof gaps.

### 2. Medium — Define what the authorization result is valid for

`design.md:63–72` and `specs/edge-auth/spec.md:84–90` specify success as subject, edge, mode, attenuated rights, and expiry, but do not specify the trusted inputs or request context needed to produce that success. The shared primitive bead demonstrates a supplied root, injected holder fact, and Datalog policy; it does not define the login adapter boundary.

The remaining distinction matters for attenuation by resource or other request facts: a result containing an operation such as `vms:read` must not be treated as reusable authority for every VM merely because it was derived from a token with a narrower resource check. The protocol requires evaluation against request facts, but this profile does not say whether the adapter returns a decision for this request, retains structured resource constraints, or evaluates the token again at the route. All are possible approaches; a flat scope name alone is not the contract.

**Owed:** name the adapter's trusted inputs (authorized operational root/delegation from the named edge-key dependency, expected local edge/audience, current time, verified holder evidence, requested operation/resource and relevant request facts). State where all applicable checks and expiry are evaluated and how the output preserves their restrictions through Auth and route authorization. Name issuer-authenticated subject provenance and a rejection result that cannot populate claims or trigger credential fallback. Add vector obligations for foreign root, expired capability/delegation, and resource-restricted attenuation exercised against a different resource. This can be a short semantic contract; an Elixir/NIF signature is not required.

## Comparison and steelman

The strongest case for accepting is that the design now expresses the intended security properties, while byte serialization and endpoint plumbing naturally belong to later implementation. That is persuasive for storage choice, concrete TTLs, NIF details, proof transport, and client key custody. I do not require those choices here. I also accept inheritance of chain/check verification from the shared protocol and pin/delegation policy from the named edge-key change instead of duplicating them.

It does not resolve the two findings. Signing a query-bearing request and defining the scope of an authorization result determine what is authorized, rather than merely how code is organized. The proposal calls this node the contract and vectors; the current tasks mark the earlier proof and integration obligations complete despite these remaining decisions. A named gated prerequisite is enough for byte-level details, but an implicit handoff is not. Holder-bound default and explicit constrained bearer remain the right tradeoff; no competing architecture is proposed.
