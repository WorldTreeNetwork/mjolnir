## Independent blind take

Written before opening design.md, tasks.md, or the delta, using the proposal's Why/What, cited Auth code, secret-tokenator living spec, and fingerprint learning.

1. Pin this node to login-profile contracts and vectors over the shared mint/verify primitive; refuse a second runtime or claims that unbuilt Biscuit paths already exist.
2. Pin the default to an ephemeral session key authorized by the IdentiKey exchange, with issuer identity and session holder identity kept distinct.
3. Require proof by that session key on every protected request; possession of the token alone must never suffice for the default profile.
4. Pin holder fingerprints to auth-challenge v1 section 5, including canonical key encoding; refuse reuse of the raw-key IdentiKey fingerprint helper.
5. Require the proof to bind the token and intended request and to have a fail-closed freshness/replay rule, rather than treating a signature alone as possession for all requests.
6. Require an authenticated, unambiguous profile discriminator; missing, unknown, conflicting, or attacker-appended mode facts must not downgrade a holder token to bearer.
7. Pin issuer, edge audience, expiry, and granted authority checks independently of the holder proof; refuse to inherit the JWT branch's unconditional full scope set.
8. Keep bearer issuance an explicit decision with enforceably shorter lifetime and narrower authority; refusal of holder proof must never trigger bearer fallback.
9. Require integration contracts and negative vectors for the existing Auth precedence, including malformed credentials and loopback, without implementing the runtime or HTTP endpoints here.
10. Tradeoff: per-request possession adds client state and replay handling; accept that cost for theft resistance while keeping bearer compatibility deliberate and separately constrained.

## Assessment

The architecture chooses the right boundary: login profiles over `mjolnir-axsb.1.3`, with holder-bound default and an explicit bearer exception. Send-back is for missing security contracts at that boundary, not for missing implementation. The proposal remains PENDING; this review neither activates it nor authorizes product work.

Reviewed the current proposal, design, tasks, delta, steer, beads `mjolnir-22ff.5` and `mjolnir-axsb.1.3`, and the local sibling protocol after writing the blind take. No plan file was opened. The protocol references below are to `../identikey-protocol/docs/standards/` in this checkout.

## Findings and owed changes

### 1. High — Define what possession proves on each request

`design.md:26-29` and `specs/edge-auth/spec.md:5-11` require a request signature but do not define its signed input, token identity, freshness, or replay behavior. A valid signature over a constant or an earlier request would satisfy the stated signature requirement without establishing possession for the current operation. The stolen-token scenario only exercises absence of a signature.

The upstream `identikey-capability-v1.md:206-229` specifies token identity, verifier nonce, and audience for **secret redemption**, and explicitly says other agency profiles must opt into those rules (`224-226`). It also leaves tuple encoding and token identity unresolved (`220-222`). Merely citing this protocol or the primitive's bead does not supply a login-request proof contract. The primitive bead currently describes verification with an injected holder fact, not validation of an HTTP possession proof.

**Owed:** define or explicitly reference a versioned login proof contract binding the presented capability, intended operation/request (including relevant body and target), edge/audience, and freshness. Name the replay owner and acceptance rule, including concurrent reuse and invalid-proof handling. Specify the boundary at which the authenticated session key becomes the verifier-only holder fact. Add positive and negative vector cases for wrong key, wrong token, altered request/body, wrong audience, stale proof, and replay. Encoding work may be assigned to a named prerequisite, but it must be an explicit gate rather than an implicit inheritance from redeem. HTTP handling and runtime implementation remain outside this node.

### 2. High — Make mode and holder checks issuer-authenticated and immutable under attenuation

`design.md:31-36` and `specs/edge-auth/spec.md:19-31` state the desired outcome, but never identify the mode's representation, trusted source, or malformed-mode behavior. A mode read from presentation metadata or an appended block is not the issuer's decision. A holder token must also retain its original holder check when attenuated; selecting a bearer policy must not bypass that check. The design correctly prohibits token-supplied holder facts, but the delta does not explicitly require rejection when such a fact is present in any block.

**Owed:** pin a versioned profile discriminator and its authority/trust rules, reject absent/unknown/conflicting modes, and make the original holder restriction non-removable. State that every accepting verifier verifies the authority chain and evaluates every applicable check, including a verifier supporting only bearer. Require rejection of token-supplied holder facts in authority or attenuation blocks. Add downgrade vectors covering a forged/overridden mode, appended holder fact, unsupported holder profile, and attenuation that attempts to widen rights or remove holder requirements. This is the profile contract consumed by the shared verifier, not a new verifier.

### 3. High — Specify the verified output and Auth integration boundary

The edge/audience scenario at `specs/edge-auth/spec.md:40-44` is useful, but the contract does not name the trusted issuer/root selection, subject XID, audience source, effective granted authority, or verification result passed to Auth. It provides no credential precedence or failure behavior. This matters in the actual caller: `lib/mjolnir/api/auth.ex:49-62` reaches localhost bypass before generic token verification, and `146-155` replaces a valid JWT's scope with `@all_scopes`. Routing a new narrow credential through either behavior would erase its restriction. That is an integration hazard, not a claim that the current code already accepts Biscuits.

**Owed:** define the shared primitive/profile adapter inputs and success/error outputs, authenticated subject and edge binding, effective authority after attenuation, and which layer checks expiry. State how an explicitly presented Biscuit is recognized and rejected before any bypass/fallback that could grant more authority; include coexistence with sites tokens and JWTs and a fail-closed ambiguity rule. Carry only verified capability authority into authorization. Keep numeric lifetimes deferred as steered, but define an enforceable comparison/ceiling for bearer versus the corresponding holder policy, and reject requests that cannot satisfy it. Add vectors for foreign root/edge/audience, expired tokens, overbroad bearer issuance, attenuated authority, and rejected credentials on loopback. Record audit-event expectations from bead `mjolnir-22ff.5` without logging credentials or private keys. The endpoint node can implement this boundary later.

## Comparison and steelman

The author answered blind concerns 1-4 well: one shared primitive, a session key authorized by login, a verifier-injected holder fact, and the algorithm-committing fingerprint namespace. The bearer exception and separation from VM-spawn RBAC also follow the steer. No second mint runtime is proposed, and there is no claim that the living tokenator spec means Biscuit HTTP verification is already built.

The strongest case for acceptance is that this is deliberately a small, PENDING contract-and-vectors node: its tasks will produce details, while the runtime and endpoints own implementation. I agree that requiring a NIF, deployed endpoint, client key store, or numeric TTL here would exceed the brief. I also withdraw any implication in blind line 5 that the redeem nonce mechanism itself must be copied; a different explicitly specified request-bound replay defense could meet the requirement.

That steelman does not resolve the findings. The profile is the agreement those later nodes consume, and neither its design nor its tasks explicitly assigns the missing proof, trust, or Auth-boundary decisions. The sibling protocol expressly does not apply redeem's holder rules to all profiles. A declaration that downgrade must fail is not yet enough for independent issuer and verifier implementations to agree on what to accept. These owed changes strengthen this profile without expanding its implementation scope.

The shorter/narrower bearer policy is a reasonable compatibility tradeoff. Deferring concrete lifetimes is not a blocker; leaving its policy comparison unenforceable is. For a holder session, authority attenuation also does not by itself transfer possession to a new key: vectors should keep the original holder restriction unless a separately specified reissuance/delegation flow applies.
