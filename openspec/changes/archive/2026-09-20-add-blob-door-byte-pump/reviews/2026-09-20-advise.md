## Independent blind take

These ten lines were persisted in `2026-09-20-blind-take.md` before opening
`design.md`, `tasks.md`, or the delta. Inputs were the packet's Why, the
living blob-store spec, cited implementation, and ADR 0003.

1. Pin acceptance to canonical B2 HEAD/GET after validated PUT; local completion or multipart completion alone cannot count.
2. Pin incremental Blake3 and the existing blob/b3/base58 layout, with outboard semantics kept distinct.
3. Pin bounded transfer memory on PUT and GET, including multipart buffers at the 1 TiB rail.
4. Refuse cache placement inside the snapshot tree; configured paths and actual resolved locations must agree.
5. Refuse unchecked request identifiers becoming filesystem paths; cache hits must stay within the object directory.
6. Require concurrent promotion and eviction to preserve the cache budget and availability of canonical objects.
7. Require interrupted PUT/GET and multipart failures to clean temporary state without ever implying acceptance.
8. Require failed or partial GET fills to remain invisible as complete cached objects.
9. Preserve repeat-PUT no-op behavior when B2 already holds the key, including uncertainty from failed HEAD requests.
10. Accept disk staging latency and finite free-space limits as the tradeoff for bounded RAM, provided cache failure does not redefine durability.

## Comparison and steelman

Design pins 1–5 answer the central concerns: incremental hashing precedes
upload, `put_file` confirms B2 before promotion/2xx, GET streams, oversize
objects need not remain cached, and the default cache is outside the
snapshot tree. `put.rs:43–60` uses the canonical store directly; HTTP HEAD
cache hits do not substitute for that confirmation. Removing the canonical
GET on repeat PUT is reasonable under the existing content-addressed-store
contract. Multipart buffering is per part (about 105 MiB at the default
1 TiB rail), rather than per object. Full-file staging and disk exhaustion
are explicit tradeoffs, not grounds to demand a different architecture.

The strongest case against my concerns is that the cache is disposable:
failed promotion after confirmed PUT may safely leave only B2, and a GET
may continue from B2 when its cache write fails. I agree. That argument
does not permit reading arbitrary host files, publishing a failed fill,
or treating racing accounting as a cache bound. The default location and
serial happy-path tests do not establish those properties.

## Required repairs

**R1 — P1: Validate GET/HEAD identifiers before filesystem access.**
`http.rs:55–64` dispatches decoded path strings; only PUT validates them
(`http.rs:81`). GET/HEAD reach `cache.rs:80–96`, where an absolute path
replaces the objects root and `../` escapes it. An in-process router probe
returned **200 and the marker bytes** for an encoded absolute path outside
the cache, **200** for HEAD of that path, and **200 with unaccepted bytes**
for `..%2Fincoming%2F<pid>-<seq>`. The production service runs as root;
read-only systemd mounts do not prevent reading root-readable files such
as the door's credentials. This also directly violates the delta's
“GET SHALL NOT serve an incoming” invariant. Validate the base58 32-byte
hash after optional `.obao` splitting for every object read before any
cache/store access. Add GET/HEAD traversal, absolute-path, invalid-hash,
and outboard-path regression cases using harmless marker files.

**R2 — P1: Make cache admission/accounting coherent under concurrency.**
`cache.rs:123–137`, `149–161`, and `164–189` perform separate existence
checks, eviction, rename, and atomic-counter updates. Two distinct
80-byte promotions into an empty 100-byte cache can both pass admission:
the probe retained 160 bytes in **5/100 trials**. Same-key promotions can
also double-count, and eviction stores can overwrite concurrent accounting
updates. This defeats the stated working-set budget on the host OS disk.
Coordinate admission/publication/eviction and test concurrent PUT/GET-fill
promotions and actual disk usage, not only the counter. Also close the
read/eviction race: `http.rs:144–145,192–199` returns 404 if a cache path
disappears before open, despite B2 still holding the object. Obtain a usable
file handle or fall back to B2 when the cache entry disappears; test that
interleaving.

**R3 — P1: Do not publish GET fills after failed local completion.**
`http.rs:261–269` ignores both `flush()` and `sync_all()` errors, then
promotes the file based on bytes received from upstream. Tokio file writes
can report a pending write failure on flush; `written == len` therefore
does not prove that the cached file contains those bytes. A final local
write failure can publish a truncated object, and later cache hits return
it with its truncated filesystem length. Continue serving origin bytes if
possible, but discard the fill on any local completion error. Add a
late-write/flush failure test proving that no object is published and a
subsequent GET uses B2. This finding is source-derived, not fault-injected
in this review.

**R4 — P2: Enforce the resolved cache-placement boundary.**
`install-blob-door.sh:53–60` checks a textual prefix only and does not
revalidate its fallback. An alias/symlink or a path containing `..` can
resolve under `btrfs_root` while passing the check; a configured root of
`/var/lib/mjolnir` even contains the fallback. Direct process startup
(`main.rs:38–48`) also accepts any configured location. Establish and test
the production enforcement point using resolved locations, rejecting an
unsafe fallback. Keep custom accepted paths consistent with the unit's
fixed `ReadWritePaths` (`systemd/mjolnir-blob-door.service:20`). Reconcile
the checked task that still says the installer creates `@blobs` with the
design's migration/removal behavior. The delta explicitly rejects placement
under the snapshot tree; choosing a safe default alone does not enforce it.

## Evidence and limits

- Existing compiled test binaries: **18 door tests and 5 cache tests
  passed**. They were executed directly, not freshly rebuilt. The invalid
  hash test covers PUT; the budget tests are serial.
- Temporary Rust harness linked the existing crate/dependency artifacts
  and exercised the router with `oneshot`, plus concurrent cache promotions.
  It used only temporary marker files, no credentials, and no product edits.
  Source inspection corroborates both reproduced defects. A preceding
  loopback probe was blocked by the sandbox; the in-process probe succeeded.
- No live B2, Linux installer/systemd, disk-full fault injection, fresh
  build, lint, or typecheck was run. The packet's historical live-B2 evidence
  is not claimed as a new verification result.
- Follow-up notes: multipart abort runs only on `upload_part` errors
  (`s3.rs:92–164`), not local I/O, missing ETag, completion failure, or
  cancellation. Define cleanup/reaping for unfinished uploads. Failed HEAD
  and concurrent repeat-PUT version races remain in `put.rs:43–49`; the
  failed-HEAD pattern predates this node and is not a new blocker here.

Required repairs are recorded as owed boxes in `tasks.md`. No implementation,
fold, deployment, or disposition-banner change was made.
