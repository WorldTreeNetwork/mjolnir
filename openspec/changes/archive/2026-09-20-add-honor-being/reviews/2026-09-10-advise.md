## Blind take (written before design.md / tasks.md)

1. PIN: "device" must name a `credentials.kind`. The CHECK admits only
   `passkey | oidc_apple | oidc_google | identikey_auth`
   (`identikey-core/crates/identikey-keys/migrations/0001_initial.sql:87-89`).
   An SSH git pubkey is none of those; `identikey_auth` is "a device key
   that can authenticate *to us*" (`:83-85`), which a Forgejo signing
   key never does. New kind + migration, or say the overload out loud.
2. PIN: "Elect-gated" is the wrong gate for a device row. `authorize_elect`
   gates *document* updates (managed-custody spec). Device rows are
   credentials, inserted under an authenticated session. At C2 the A3
   assertion *is* the consent artifact (custody-ladder §Access). A
   passkey-only friend holds no Elect private key in a browser; requiring
   an Elect signature makes the device row unprovisionable for exactly
   the user this is for. Gate = fresh A3 assertion + consent-log row.
3. PIN: the passkey login yields a Mjolnir JWT that "confers the full
   scope set; scopes are ours, not the token's"
   (`lib/mjolnir/api/auth.ex:13-14`, `@all_scopes` `:42`). Today
   `/term/:id` is same-origin and rides `mj_term` (`router.ex:175-184`).
   The ADR must bind XID → vm_id and scope the friend to `pty:connect`
   on that one VM, or the passkey gates nothing.
4. PIN: the host is custodian of the git key. `_opaque/vms/<id>/` is
   root-readable 0600 on the host (`secret_store.ex:149-169`) and
   re-injected every boot (`vm.ex:2767-2772`). Mjolnir can sign as the
   friend without the friend. Name that honestly (it is C1 for the git
   device, same as the Buzz nsec) and name the three-place revoke:
   opaque delete + `revoke_device` + Forgejo key removal.
5. PIN: `_opaque` is keyed by `vm_id`, and the ticket is the Iroh node
   id, fresh per spawn (`deploy/runtime.ex:33`). Kill + respawn yields
   a new vm_id, a new URL, and no key. The durable handle is the
   friend's XID, not the vm_id. Say where the
   `xid → {vm_id, device credential id, forgejo key id}` binding lives.
6. REFUSE: prod Medusa CORS for `https://<ticket>.vm.worldtree.network`.
   Either the entry is per-ticket (stale on every respawn, see 5) or a
   `*.vm.worldtree.network` wildcard, which lets every VM on mimir make
   credentialed calls into prod. Pick per-ticket now and record that a
   named subdomain (v2) is what makes CORS stable.
7. REFUSE: "or grok.com session" as an inference credential. A grok.com
   session is a personal account credential with a lifecycle nobody
   here owns; whose account is it, Duke's or the friend's? v1 is
   `XAI_API_KEY` only, in tmpfs like `buzz.env`, never on the rootfs
   the snapshot captures.
8. PIN: the Vite preview on the ticket host is unauthenticated (gateway
   routes `(apex, subdomain) → guest_ip:port`, `gateway/routes.ex`), so
   "passkey gates the being" covers `/term` only. Say so.
9. Blast radius: `git push main` = prod cutover with no gate between a
   grok commit and `hypersigil.world`. That is the ask; record it as a
   known risk in the ADR, not silently.
10. Tradeoff I accept: no `@base/honor`, snapshot of a bootstrap, clone
    in the guest, reuse `/term` + tmux `main`. Consistent with ADR 0009
    and base-images "Snapshot is not a catalog entry".

is a `credentials` row and explicitly reject `add_key` Sign (take 1
half-answered, kind still unnamed). Decision 2 rejects Grok OIDC
against identikey and Keycloak growth (agrees). Decision 5 chooses a
per-ticket CORS entry (take 6, the right pick; coupling to take 5 not
noticed). Decision 6 matches take 10. Take 4 is half-answered:
"attribution and revocation" is why a bare deploy key was rejected,
but the three-place revoke is not written down.

Steelman on take 3: owner scoping already exists. `owner_id` is
stamped from the authenticated `user_id` at spawn
(`lib/mjolnir/api/router.ex:418-419`), `user_id` is the JWT `sub`
(`lib/mjolnir/api/auth.ex:155`), and `GET /api/vms/:id/pty` goes
through `authorize_vm(conn, id, :pty, …)`
(`router.ex:589`, `lib/mjolnir/api/authz.ex:37-48`). So the
full-scope JWT is bounded by ownership and the friend cannot reach
other VMs. That softens take 3 from "gates nothing" to "the ADR
never says what `owner_id` is". It still has to say it (S3 below).

Steelman on take 5: `preserve_iroh_key: true` keeps
`/etc/mjolnir/iroh.key` across a spawn-from-snapshot
(`lib/mjolnir/vm.ex:2362-2367`, `lib/mjolnir/btrfs.ex:434-442`), so
the ticket URL can survive a respawn. It only survives from a
per-Honor snapshot; preserving from the shared `honor-hypersigil`
bootstrap would give two VMs one Iroh identity. `vm_id` is still
fresh per spawn (`vm.ex:220`), so `_opaque/vms/<id>/` does not
follow. Narrowed, not closed (S4).

## Send-back items (ADR 0011 + delta edits)

S1. **Replace "Elect-gated" with the C2 consent gate.** At signup the
user's Elect key is generated and dropped; only `ours` is persisted
as the managed blob
(`identikey-core/crates/identikey-server/src/main.rs:406-418`). No
passkey-signup C2 identity can produce an Elect signature today.
`authorize_elect` gates document writes only
(`identikey-keys/src/store.rs:254-256`), and migrate_c2_to_c3 already
models the C2 consent artifact as an A3/A4 proof + consent-log row
(`store.rs:283-291`). Delta requirement 1 ("SHALL require an
Elect-gated instruction") and ADR item 1/3 should read: creating the
device SHALL require a fresh A3 assertion for that XID and SHALL
append a consent-log entry (`action = add_device` or similar). This
is the same fix in three places: delta, ADR one-screen, design.md
Decision 3.

S2. **Name the credential kind.** `credentials_kind_known` and
`credentials_kind_shape` reject an SSH key today
(`0001_initial.sql:87-113`). Pick one and say it in the ADR: a new
`kind = 'ssh_git'` with `device_public_key` populated (migration in
identikey-core, owned by `add-vm-git-subkey`), or overload
`identikey_auth` and accept that its column comment ("for
authenticating TO this server") becomes false. I recommend the new
kind. Delta requirement 3 then says which row the "device credential"
is.

S3. **State the Mjolnir-side identity binding.** "Whose identikey the
machine is" has one concrete answer in this repo: `owner_id`. The ADR
should say: Honor's `owner_id` SHALL equal the friend's XID as the
`auth.identikey.me` OP issues it in `sub`; `/term` and the PTY attach
are authorized by `authorize_vm` on that equality; a VM Duke spawns
under his own `sub` is not a Honor being until `owner_id` is the
friend's XID. This also pins the `add-identikey-being-client` contract
(`sub == XID`, `MJOLNIR_AUTH_ISSUER` moves to `auth.identikey.me`)
without designing it.

S4. **Say what survives a respawn.** `spawn/1` mints a fresh `vm_id`
(`vm.ex:220`); `_opaque/vms/<id>/` and the device pubkey are bound to
it; the ticket survives only with `preserve_iroh_key: true` from a
per-Honor snapshot. Pick the v1 rule and write it: either (a) a new
VM is a new device: new key, new credentials row, new Forgejo key,
old ones revoked (simple, honest, matches "device" semantics), or (b)
an operator copies `_opaque/vms/<old>/` to `<new>` and re-registers
nothing. I recommend (a) for v1 and a `honor-<xid>` per-friend
snapshot with `preserve_iroh_key` so the URL and the CORS entry hold.
Note in the ADR that (a) makes take 6's per-ticket CORS entry stale on
every respawn until the named subdomain lands.
