## Blind take (written before design.md / tasks.md / first review)

1. PIN, holds: device = `credentials` row, never a Sign key on the
   document. Hosted signup generates the user's Elect key and drops
   it (`identikey-server/src/main.rs:406-407`, only `ours` becomes
   the managed blob at `:418`), so no passkey-only C2 friend can
   Elect. The delta's "SHALL NOT require an Elect signature" is the
   only provisionable gate. Correct.
2. PIN, holds: `ssh_git` must be a new kind. `credentials_kind_known`
   and `credentials_kind_shape` (`0001_initial.sql:87-113`) admit
   four kinds; `identikey_auth`'s comment says "authenticating TO
   this server" (`:125-126`). Delta names the kind and the owing
   node. Correct.
3. PIN, holds: consent-log shape fits without schema change.
   `access_level 'a3'`, `proof_kind 'webauthn_assertion'` are in the
   CHECKs (`0001_initial.sql:229-243`); `action` is free text
   (`consent.rs:75`), so `add_device` needs no migration.
4. PIN, holds: `owner_id == sub == XID` is already the whole authz
   story. `owner_id` is stamped from `conn.assigns[:user_id]` at
   spawn (`router.ex:419`); every resource action is `uid == oid`
   (`policy/vm.ex:36-39`). The OIDC living spec makes `public`
   `sub` the 64-hex XID. Design.md pins `subject_type=public` for
   the Mjolnir client; the delta and ADR say "public OIDC sub". A
   pairwise client would silently break the equality. Pinned.
5. CONCERN, non-blocking: the ADR says the key rides "the same
   vsock path as `buzz.env`". That path is Buzz-shaped, not
   generic: `Identity.env_entries/1` hard-codes `BUZZ_PRIVATE_KEY`
   and `BUZZ_RELAY_URL` (`identity.ex:97-99`) and
   `inject_identity_request/2` wraps exactly that map
   (`protocol.ex:263-269`). The host re-sends it per boot
   (`vm.ex:2770-2772`). `add-vm-git-subkey` will need a second
   opaque key under `_opaque/vms/<id>/` and a generalized or new
   inject message on both sides of vsock. The pattern is built; the
   message is not. Say "pattern", not "path".
6. CONCERN, non-blocking: three-place revoke is cross-system and
   non-atomic. Order matters: Forgejo key first (that is the push
   authority), then `revoke_device`, then opaque delete. A crash
   between steps must leave a stale Forgejo key as the thing a
   reconcile pass finds, not a live key with no identikey row.
7. CONCERN, non-blocking: respawn = new key, but the per-friend
   snapshot `honor-<xid>` carries the rootfs `git config
   user.signingkey`. The guest path of the injected key must be
   stable across devices (one fixed tmpfs path), or every respawn
   rewrites git config.
8. CONCERN, non-blocking: the proposal journey says "Friend (or
   Duke acting as the friend)". A3 means the friend's passkey. Duke
   can only act as the friend if Duke holds a passkey registered on
   the friend's XID, which is a second-person credential on a
   C2 identity. Either the friend performs the A3, or Duke's passkey
   on that XID is an explicit, consent-logged, revocable row named
   in the ADR. Not a blocker for the architecture; a blocker for
   provisioning day.
9. Tradeoff accepted: per-ticket CORS on prod Medusa is stale on
   respawn from a shared bootstrap. The delta's `preserve_iroh_key`
   split (per-friend yes, shared no) is the right cut and the
   snapshot name fits the validator (`btrfs.ex:18-22`, 128-byte cap,
   70 bytes used).
10. Tradeoff accepted: `XAI_API_KEY` only, tmpfs, Duke's xAI
    account. The snapshot is a BTRFS subvolume; `/run/mjolnir/` is
    tmpfs, so the delta's "bootstrap snapshot does not contain the
    key" is true by construction.
