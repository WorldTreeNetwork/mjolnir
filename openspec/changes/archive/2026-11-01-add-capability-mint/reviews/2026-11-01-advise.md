## Comparison and steelman

The author answers the cryptographic concerns: 32 CSPRNG salt bytes, the existing domain-separated commitment helper, protocol fingerprint derived from a 32-byte public key, durable production mint, and an appended holder check without an authority holder fact. Deriving the fingerprint internally is stronger than accepting a caller-supplied fingerprint string. A separate opaque `owner` object answers my metadata concern; adding it to JSON is unnecessary and the bead explicitly calls for another opaque key. Keeping the salt off the token is compatible with the living spec's permission to include it. No new HTTP surface or hop machinery is needed.

The strongest case for this small design is that trusted host callers can supply fresh IDs and the existing opaque store already provides individual atomic writes. That avoids a database or a new reader format. However, freshness and exclusive ownership are not in the contract, and individual file replacement does not make the three-object deposit atomic. Those gaps affect the named holder and the promised failure behavior, rather than merely implementation preference.

## Owed before acceptance

### R1 — Existing IDs and concurrent writers need an ownership contract (high)

`design.md:11` accepts a caller-supplied ID without requiring it to be unused. `SecretStore.put_opaque/4` (`lib/mjolnir/secret_store.ex:173`) overwrites each destination by rename and shares a fixed `.tmp` path between writers. A second deposit for the same ID can replace the value and commitment while changing `owner`. A previously issued holder-checked token still grants `redeem` on that ID: the existing reader checks the stored value against stored metadata, not against the token's original owner or commitment. Thus reusing the ID can expose the replacement secret to the previous token holder. This is a deposit-contract issue; no redeem redesign is requested.

Specify create-only reservation of an unused ID, including partial existing records and concurrent attempts, or an equally explicit policy that prevents old capabilities reaching a different secret. A separate existence check followed by writes is insufficient. Rejection must preserve existing records. Reconcile the delta's unconditional “a refused or failed deposit SHALL leave no ... object for that id” (`specs/secret-tokenator/spec.md:11`) with that preservation rule. Include duplicate-ID and competing-writer scenarios; a losing attempt must neither overwrite nor clean up the winner's files.

### R2 — Define the failure boundary and verify partial-write failures (medium)

`design.md:23` promises deletion of keys already written, but the tasks exercise only invalid inputs. The cited helpers can raise during commitment, mint, or holder append; opaque writes and deletes can return errors. `put_opaque/4` can also leave a secret-bearing `value.tmp` after a failed rename, which deleting only `value`, `meta`, and `owner` does not address. The contract does not say when success is returned or how cleanup failure and process interruption differ from a clean refusal.

Specify that success returns only the final holder-checked token after all three objects are published, and that rollback affects only this attempt's reserved record, including its temporary artifacts. State the supported failure boundary and what happens when cleanup itself fails or the process dies; narrow an impossible unconditional cleanup promise explicitly if necessary. This does not require a new database or a general SecretStore rewrite. Add fault-injection acceptance coverage for a later object write failure, mint/append failure, and cleanup failure, checking residual files and ensuring no token or secret-bearing diagnostic escapes.
