The frame direction is sound, but the request-to-bytes contract needs completion before implementation. This review covers preparation and the proposed contract, not a product-code implementation. Fresh advise remains unchecked.

## Blind pass

The following ten lines were persisted in [2026-11-04-independent-take.md](2026-11-04-independent-take.md) before opening `design.md` or `tasks.md`, using only the proposal, living requirement, and cited Redeem/Nonces code:

1. Pin one unambiguous, domain-separated byte frame with explicit field order, byte lengths, encoding, and version behavior.
2. Bind the exact nonce, capability bytes or explicitly chosen textual representation, secret id, method, and resource used by the operation.
3. Refuse an egress path that verifies one tuple and subsequently reads unsigned request fields or silently substitutes defaults.
4. Specify normalization once; verification and upstream dispatch must agree on the signed method and resource.
5. Preserve consume-before-proof, burning failed attempts, 60-second in-memory expiry, restart invalidation, and atomic single use.
6. Reject malformed field types and encodings without exceptions, secret reads, upstream calls, or acceptance of the old four-line signature.
7. Retain Biscuit-named holder verification and authorization of redeem for the same secret id, including rejection of holderless tokens.
8. Clarify what the request commitment covers, how copy-out and egress interpret it, and which proof checks remain outside this handler.
9. Require independently specified golden bytes, per-field tampering tests, nonce failure/replay tests, and evidence that egress uses the verified request.
10. Tradeoff: a strict replacement simplifies fail-closed semantics but breaks existing signers; record the api-proxy coordination boundary without adding fallback acceptance.

## Comparison and steelman

The author's uint32 big-endian lengths, fixed eight-field order, and NUL-terminated domain answer the framing concern. Keeping the `v1` spelling is defensible here: the NUL domain and length prefixes differ from the old newline encoding, and the contract explicitly rejects old signatures. No second version mechanism is needed for this node.

The copy-out restriction to `REDEEM`, resource equal to secret id, and empty-body Blake3 distinguishes copy-out from HTTP egress without adding another field. The delta preserves holder-required Biscuit authorization for `(secret_id, redeem)`, consume-before-proof, failure burning, and memory-only nonce lifetime. Dispatching the signed resource and method directly fixes the cited unsigned egress path. These satisfy the core of my independent take.

The strongest case for accepting this short design is that it intentionally freezes only this runtime's frame; api-proxy changes and its second proof remain outside the node. I agree with that boundary and do not request dCBOR, another signature check, guest networking, or a general idempotency service. However, a later independent signer still needs an exact mapping from the existing JSON API to these bytes. Deferring that mapping would defer part of the stated byte-string contract itself.

## Owed before acceptance

1. **P1 — Specify the JSON request and body-byte mapping.** `design.md:13–29` and the delta at `specs/secret-tokenator/spec.md:6–8` specify raw digest bytes but no request field names/encoding for the body or digest. The handlers pass `conn.body_params` directly (`lib/mjolnir/api/router.ex:1298–1312`), and the router uses JSON parsing (`:2042`); arbitrary 32-byte digests and binary upstream bodies therefore need an explicit transport representation or an explicit rule that the digest is computed from a defined body field. Pin required/optional fields, missing versus empty behavior, malformed-type rejection, and whether a supplied digest is decoded and compared or computed internally. State that the digest covers decoded upstream body bytes, not the outer proof JSON or a reserialized object, and that those same bytes are forwarded. Pin method casing and exact textual-field treatment so clients do not normalize differently. A compact request example and one exact expected frame are sufficient; no new encoding framework is requested.

2. **P2 — Finish the semantics of signed ancillary fields and legacy aliases.** `design.md:29` only says an empty idempotency key does not add a header; both ignoring a nonempty key and forwarding it satisfy that wording. Choose and record the nonempty behavior (including exact header/value handling if forwarded), without implying deduplication that this node does not implement. Audience is currently only required to be nonempty UTF-8 (`design.md:19`, delta `:6`): explicitly state whether it is an opaque signed label or checked against a verifier identity, and the expected value/source if checked. I do not infer a cross-service replay exploit from this alone: the local single-use nonce remains a separate defense. Also reconcile the task's instruction to reject unsigned method/URL (`tasks.md:5`) with the scenario that an unsigned conflicting field does not change the call (delta `:43–48`): rejection or ignoring can be safe, but select one observable result and one authoritative field location.

3. **P2 — Make verification cover the new security boundary.** `tasks.md:6` names only a fresh proof, an old-frame rejection, and nonce reuse. Existing tests sign via the production `signing_message/3` helper and test a bodyless egress GET (`test/mjolnir/secrets/redeem_test.exs`); that pattern can let signer and verifier share the same framing mistake. Add an independently specified golden byte vector, tampering of each newly bound field and the actual body, malformed JSON field/encoding cases, copy-out/HTTP operation separation, and upstream observation of the signed method, URL, body, and chosen idempotency behavior. Failed attempts with a fresh valid nonce must leave it burned; rejected egress proofs must make no upstream request. Retain existing holder, commitment, expiry, and concurrency coverage. These are implementation acceptance checks, not a demand to implement tests during preparation.
