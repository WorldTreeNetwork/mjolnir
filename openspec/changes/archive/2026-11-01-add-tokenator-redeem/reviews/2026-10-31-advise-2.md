1. Pin the already-mounted API and existing Redeem handler; refuse a second redeem route or vault.
2. Pin POST-only ceremony admission, empty ceremony scopes, and no VM JWT requirement or skip-auth entry.

## Comparison with the prior findings

1. **Salt provenance and failure behavior — resolved.** [Design](../design.md) and the [copy-out delta](../specs/secret-tokenator/spec.md) now pin opaque `value` plus UTF-8 JSON `meta` under the same secret id. They require a decoded 32-byte salt, a 64-character lowercase hex commitment, and a matching `Mjolnir.Biscuit.secret_commit(salt, value)`. That helper returns digest bytes (`lib/mjolnir/biscuit.ex:31-40`), so comparison is against the decoded commitment. Missing, malformed, mismatched, and legacy value-only material fail without returning or logging value or salt. Provisioning is a precondition; only test fixtures write the pair here. Shared egress keeps its response shape and stops before calling upstream on material-validation failure. This answers finding 1 of [the first review](2026-10-31-advise.md), including the compatibility decision for legacy records.

2. **Discriminating holder-proof verification — resolved.** The amended tasks and delta cover a real successful holder proof without JWT or operator shortcuts, wrong signer, holderless token, wrong resource/operation, signed-field tampering, replay, expiry, restart, concurrent consumption, and denial of unrelated authenticated routes. They explicitly burn the nonce on a failed proof, matching `redeem.ex:55` and the serial `Nonces` consume operation. Together with the retained exact newline tuple and current Auth precedence, these answer finding 2. These are acceptance obligations for act; today's three small redeem tests do not establish them.

## Steelman against the independent take

The strongest objection is that two opaque objects cannot guarantee an atomic provisioning update and rejecting legacy records also changes egress availability. The amended contract makes the useful bounded choice: recompute the commitment for the actual bytes read and fail closed on an inconsistent pair. It does not need a new storage transaction or deposit implementation to prevent release of a mismatched pair. Legacy rejection is explicit, rather than an accidental regression left to the implementer. The future writer still owns provisioning; this acceptance does not claim rotation atomicity.

Likewise, moving nonce consumption after verification might improve retries, but it would change the existing ceremony semantics. Explicit challenge burning plus focused concurrency and failed-proof tests answers the concern without redesign. The author has answered the take; a competing route, vault, signature format, or mint implementation is unnecessary.
