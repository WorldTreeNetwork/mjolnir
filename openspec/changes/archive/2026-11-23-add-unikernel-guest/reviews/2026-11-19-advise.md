# Advise: add-unikernel-guest

> **ADVISE:** send-back
> **READER:** fable-arch-review
> **SPAWN:** t3-delegate advise-add-unikernel-guest-fable

The direction is right and I would not change it: a guest kind, a boot path with no rootfs, QUIC on `reflect.quic_port`, one RFL1 stream, a P-256 pin, no TCP, no `wire_port`, homoiconic untouched, Linux spawn untouched. The send-back is about the half of the protocol that Mjolnir owns. The delta pins the guest side, which homoiconic already pinned, and leaves the Mjolnir side open: who opens the connection, how program and budget get in, how reply bytes get out, and what happens when the guest exits by itself. Five requirements cannot be tested as written and two can contradict the image.

The advise box in `tasks.md` stays unchecked. The PENDING banner is unchanged.

## Independent take (written before the design)

1. Pin the actor. `mj` is an HTTP client and cannot route to a guest TAP address. QUIC must terminate on the host behind `POST /api/vms/:id/messages`.
2. Pin the client stack and prove it against the 793b583 ELF before code. The only proven peer of the guest's own QUIC is homoiconic's `quic-client`, and its pin is compiled in, not configured.
3. Pin where the SHA-256 comes from (spawn field in `spawn_config`, hash of the certificate DER) and require proof of key possession. The certificate is compiled into the image, so the pin names an image, not a guest.
4. Pin the whole RFL1 header: reserved zero, 8-byte big-endian correlation id, budget 1..100000000, frame at most 1200 so program at most 1176. Map each reply class: kind 1 status 0 (budget exhaustion is a Lean payload here), status 2, status 3, timeout.
5. Pin the HTTP shape. `payload` is JSON today. Say how program bytes and budget go in, how reply bytes come out, what `id` means with no mailbox, the deadline, and what a second concurrent message gets from a sequential guest.
6. Pin the readiness literal `reflect: quic <port>`, a serial transport that cannot miss it, and the exact command line. The image refuses malformed or repeated configuration.
7. Pin VMM self-exit. The image powers off on a fatal request. Mjolnir must withdraw readiness and not restart; `normalize_restart_policy` fails open to `:always`. Reconcile, Cleanup and Health need a rule for a record with no rootfs.
8. Refuse TCP, the program on `reflect.port`, `wire_port`, snapshot/dormant/exec/connect for this kind (with a named refusal, not undefined behaviour), automatic retry, and a raw host kernel path from the public API with no allow-list.
9. Refuse "returns the Lean result" with no fixture. Acceptance needs reply bytes exported at 793b583 and a real KVM guest.
10. Tradeoff: one verb, two contracts. Reusing `mj message` keeps the surface small but makes it async at-least-once for Linux and sync at-most-once for unikernel, with a kind-dependent response.

## Where the design already answers the take

- Line 3 and line 6, partly. The design takes the pin as an explicit spawn field, stores it in `spawn_config`, and names the literal `reflect: quic <port>`. The delta's Requirement 1 does not list the pin, and its boot scenario says the serial line "names `reflect.quic_port`", which the line does not contain. Small wording fixes.
- Serial transport. My worry was unfounded. Mjolnir already runs serial in file mode (`lib/mjolnir/cloud_hypervisor/config.ex:67`), the same mode `check-quic.sh` uses, so nothing printed before a reader attaches is lost.
- TAP topology. `check-quic.sh` puts a /24 on the TAP; Mjolnir uses an unnumbered TAP, a /32 route and proxy ARP. I checked that this does not contradict the image: the guest answers ARP for its own address whatever the sender (`net.zig` `answerArp`) and replies to the source MAC of the datagram it received (`sendUdp` copies `req[6..12]`). It needs no gateway and no peer subnet.
- Line 2. H1 names the risk and says to stop and amend rather than add TCP. That is the right exit. See note A on why "medium" is generous and what the spike must hold fixed.
- Line 8, mostly. TCP, `wire_port`, building the ELF here, and editing homoiconic are all out of scope in so many words.

## Why it goes back

Each item says what the delta states, what the evidence shows, and what the author has to answer. None of these asks for a different design.

**1. The budget scenario has no budget.** Requirement 3 sends a budget and its third scenario turns on "the step budget". No surface carries one. `mj message` takes an id, a payload and `--id` (`native/mjolnir_client/src/main.rs:218`). The proposal's journey is `mj message <id> <program bytes>`. The guest accepts 1..100000000 and answers status 3 outside that (`net.zig:655`). Answer: where the budget comes from on CLI, HTTP and MCP, its default, and what the caller sees on status 3.

**2. Requirement 3 names an actor that cannot do it.** "`mj message` ... SHALL open one QUIC v1 connection to `reflect.quic_port`." `mj` talks HTTPS to the public API from anywhere. The guest address is a host-local /32. The design says only "`message` opens one QUIC v1 connection". Answer: which process on the host opens the connection and holds the pin, and restate the requirement with that subject. If the answer really is the `mj` binary, say how its datagrams reach the guest.

**3. The request and reply shapes are not stated, so "returns the Lean result" has nothing to compare against.** Today the route reads `payload` as JSON (`router.ex:1197`), the CLI documents it as JSON, and the response is `{ok, message_id, status}`. Program bytes are not a JSON object and the reply is Lean's binary reply form. Answer: the request encoding for program bytes, the response encoding for reply bytes, what `--id` means for this kind (there is no mailbox to dedupe against), and where the expected factorial and budget bytes come from. `check-quic.sh` compares against `out-net/reply run ...` built from the same commit; Mjolnir has no Lean, so it needs fixtures with stated provenance. Also say that Mjolnir returns the payload without reading it. A budget exhaustion is kind 1 status 0, the same as a result, so Mjolnir cannot tell "the budget outcome" apart from an answer and the requirement should not imply it can.

**4. A guest that exits by itself is not covered, and today's code would report it as data loss.** Homoiconic assigns this to Mjolnir: a fatal request powers the guest off, and "Mjolnir integration SHALL withdraw readiness on the VMM exit; a later explicit restart is a fresh boot with no replay" (`unikernel-net` spec, "A fatal request ends that guest boot observably"). The delta's Requirement 4 covers `mj kill` and an operator restart only. In the code, a hypervisor exit stops the VM process (`vm.ex:1898`), restart policy fails open to `:always` (`vm.ex:2314`), and Reconcile then finds a `:running` record with no rootfs and records "rootfs missing ... data lost — cannot resume" on every pass (`reconcile.ex:299`, `:428`). With the scope still active it takes the attach path, which rebuilds a vsock connection and looks for the rootfs (`reconcile.ex:359`, `vm.ex:3909`). Answer: a requirement and a scenario for VMM exit, the state the record ends in, and what Reconcile, Cleanup and Health.Monitor do with kind `unikernel`. The existing restart scenario also needs an observable result: which response the operator gets.

**5. The command line can contradict the image.** The guest's parser returns failure on any word it does not know (`net.zig:136`), and the image contract is one vCPU and 512 MiB. Requirement 2 says the three words go "on" the command line; it does not say they are the whole command line. Mjolnir's Linux `boot_args` carry `root=myfs rootfstype=virtiofs rw`, and `default_vcpus` is 2 (`config/config.exs:21`). Answer: state that the command line is exactly those three words, and state the vCPU and memory this kind boots with and what happens to `--memory`.

**6. Two messages at once are undefined, and the guest cannot serve them.** The guest holds one connection (`net.zig:31`). A second client's first packet during an exchange is fed to the live connection; after an answer, any long-header packet resets it (`net.zig:512`). Answer: one exchange at a time per guest, and what the second caller gets (wait or a named refusal).

**7. Silence is an outcome and has no name.** A frame over 1200 bytes, a bad header, or a non-run kind gets no reply and no FIN (`net.zig:634`, `:644`, `:654`); the homoiconic client just runs out its 60 s. The guest also does not service QUIC while Lean evaluates. Answer: the program size limit Mjolnir enforces before it connects (1176 bytes), the deadline, and the distinct results for timeout, status 2 and status 3.

## Notes that do not block

**A. H1 is narrower than "a QUIC v1 stack".** The cited evidence, homoiconic's `quic-client`, is the guest's own `quic.zig` on both ends. The design also says Mjolnir does not embed that source, so the evidence does not carry over to whatever Mjolnir ships. From `quic.zig` at 793b583 the listener needs: version 1 only; destination and source connection ids of exactly 8 bytes, or the packet is dropped (`:163`, `:166`); an X25519 key share, found by a byte scan for `00 1d 00 20` (`:746`); a ClientHello that fits 1024 bytes (`:51`); `TLS_AES_128_GCM_SHA256`; ECDSA P-256 SHA-256; no ALPN in the server's reply; packets up to 1400 bytes (`:209`). A stock client that picks longer connection ids, sends a larger hello, or insists on ALPN will fail the handshake for reasons unrelated to the contract. Name the stack, put this list in the design as what the spike holds fixed, and run the spike through a Mjolnir-style TAP (/32 route, proxy ARP) rather than the /24 in `check-quic.sh`. The spike writes no product code. I would let it run before the next advise so the reader is not asked to accept an unverified hypothesis; that is the author's and Duke's call.

**B. What the pin proves.** The private key is in the homoiconic tree beside the certificate (`quic.zig:14`), and every guest built from that commit shares it. The pin tells the host it reached an image built with that certificate. It does not identify one guest, and it is not a secret from anyone who has the repo. That is the image's choice and not this change's to fix. The delta should not describe it as more.

**C. `reflect.port` still runs programs with no pin.** The image requires the word, so the plain UDP service is live on every unikernel guest. The delta says Mjolnir does not send programs there. It should also say who else can reach it: confirm the guest-isolation rules cover this kind, or the pin on the QUIC port guards a door with an open one beside it.

**D. Kernel path from the public API.** Requirement 1 takes a host path from any caller with spawn rights. `extra_mounts` has `allowed_mount_prefixes` for the same reason. Either an allowed directory or a sentence saying why not.

**E. Other verbs.** `exec`, `connect`, `snapshot`, `done`/dormant, `doctor`, `ticket`, `url` all assume the agent. One sentence giving the refusal for this kind would keep them from failing in seven different ways. Likewise a persisted `spawn_config` with no kind should be stated to be `linux`, since that is what protects existing guests across Reconcile.

**F. Hosts.** The change says morphie only, not the Framework laptop. `CLAUDE.md` says Mjolnir compiles and tests on the Framework laptop. The QUIC spike belongs on morphie where the ELF and Cloud Hypervisor 54 are. The boot and kill scenarios need a host with a Mjolnir install, BTRFS and root. Say which host that is.

**G. The tradeoff in line 10 stands.** The design chose one verb. That is defensible. It is the reason items 1 and 3 matter: the second contract on `mj message` has to be written down somewhere.

## For the next advise

A revised delta that a reader can accept would have, for items 1 to 7, a sentence in a requirement and a scenario with an observable result. Items 1, 2 and 3 can share one requirement that states the host-side message contract. Item 4 is a new requirement. Items 5, 6 and 7 are a clause each. Nothing here needs TCP, a change to homoiconic, or a change to Linux spawn.
