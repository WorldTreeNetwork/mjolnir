## Blind take (from proposal Why + cited code, before design.md / tasks.md / spec / prior review)

1. **Pin:** the order is app custom domain, then live alias, then `404 name_not_found`. An app hit owns the host, including `404 app_not_found` for a non-owner, so the site path never runs for that name. Both lookups share the normalization in `app_for_domain/1` (`router.ex:2139-2146`), and the wildcard refusal stays first.
2. **Pin:** the site-only install is an explicit seam that skips `ensure_domain_block` (`gateway/certs.ex:417-422`). It is not an after-the-fact removal. `ops.ensure` is 3-arity today, so the seam has to reach the fakes too.
3. **Pin:** "would classify as Local/Iroh" must be the gateway's `classify` (`main.rs:781-816`), not an approximation. That includes the default Iroh fallthrough (`config.rs:401-404`), gateway `[[alias]]` vanity names that resolve to Iroh under any fallthrough, and the bare-apex `EmptySubdomain` case. The Elixir side and the Rust side will drift unless one is the oracle or they share test vectors.
4. **Pin:** `lookup_alias/1` (`secret_store.ex:118-140`) becomes tri-state: hit, miss (enoent or tombstone), or error. The gateway's Host-header path keeps its "anything bad is a miss" semantics. Only cert classification fails closed.
5. **Pin:** renewal (`api/certs.ex:86-101`, which calls `issue/2` directly) must never widen the apex list. A renewed PEM always differs, so `ensure_origin_ca` re-enters `ensure_domain_block` (`gateway/certs.ex:270-293`).
6. **Refuse:** any path where installing a cert for name A changes the classification of a sibling name B under the same `apex_of` (last two labels, `gateway/certs.ex:220-243`). That covers renewal, a stranger, and an app's first issue.
7. **Refuse:** `sites:publish` reaching issue (`authz.ex:15-28` already 403s, and `sites/token.ex` confers only `sites:publish`).
8. **Pin:** `GET /api/certs` (`router.ex:1998-2022`) widens to owned app hosts plus live alias hosts. An unreadable index must not 500 the whole list.
9. **Owed:** a test showing that a site-only `[[cert]]` config still classifies as `Reject(DomainMismatch)` before and after renewal.
10. **Tradeoff:** mirroring `classify` in Elixir (cheap, no new IPC, but it can drift) vs asking the gateway (one source of truth, but a new control surface between Elixir and the gateway). I'd take the mirror plus shared vectors.

## Prior send-back — answered?

**S1 — renewal must not add an apex, including over a sibling live alias; an unreadable index fails closed.** **Answered.**
- Spec Req 3: "SHALL NOT append a `[[domain]]` block that is not already present, on every branch". All three bullets say "Do not add an apex". That is stronger than the bounded form S1 asked for (only "covers a live alias"), and simpler.
- "Deleted alias does not capture a sibling" is exactly the `blog`/`docs` path from S1.
- "Unreadable index does not renew as a stranger" covers fail-closed. "A missing index file remains a miss" keeps enoent as a miss.
- The old hazardous text ("a missing apex for that name may be added") is gone.
- Design § Tradeoff on the bound states the cost: an app whose apex was later deleted does not get it back from the timer.

**S2 — a host already classified Local or Iroh is refused before HTTP-01.** **Answered.**
- Spec Req 1 paragraph 2 plus scenario "Host already routed elsewhere is refused": `409 host_routed_elsewhere`, Let's Encrypt not called, no `[[cert]]` installed.
- I checked against the code. `classify` emits only three `Reject` variants (`DomainMismatch`, `EmptySubdomain`, `NotFound`), and `main.rs:1235-1252` sends all three to the sites resolver. `Parked` consults the resolver first (`main.rs:1182`). So "Reject and Parked continue" is accurate, not an approximation.
- "Existing apex that still reaches sites is left alone" is narrowed to `none`/`parked` fallthrough with no route/alias. That is consistent with the 409.

## Steelman against my take

- **"The 409 is a point-in-time check, so the contract is still leaky."** True. An operator can later add a `[[route]]`, or flip the apex fallthrough, and move the host. But that is gateway routing policy, which the Refusals put out of scope, and the change does not claim durable routing. The 409 bounds what *this* surface spends and promises. Accept.
- **"With the renewal bound, renewal classification is decorative."** Mostly true, see N2. All three branches now do the same thing (reinstall, no apex). Classification at renewal reduces to "for a non-app host, fail closed on an unreadable index". That is still a real behaviour, and spec Req 3 pins it. Over-describing is not a contract defect. Accept.
- **"App first issue can still append `example.com` above a live `blog.example.com` site cert. That is S1 through a third door, so send it back."** I went looking for this, and it is mostly not reachable. `Mjolnir.API.Domains` refuses `set_domain` with `apex_not_registered` unless the fqdn's apex is already in `:gateway_apexes` (`lib/mjolnir/api/domains.ex:16-20, 72-93`). An app's custom domain therefore normally sits under an apex that is already declared, so `ensure_domain_block` is a no-op on app first issue, and the sibling site would already have met the 409 when it issued. What remains: `apex_of` (last two labels) disagreeing with a multi-label configured apex, or `MJOLNIR_GATEWAY_APEXES` drifting from gateway.toml. Both are pre-existing app-path behaviour that this change does not touch. That is a note (N5), not a send-back.
- **"The renewal bound contradicts the user steer ('neither keeps today's ensure')."** `steer.md` does say that. Design § Tradeoff on the bound names the departure explicitly: renewal is kept, only the append is dropped. The packet lists it as an amended rule already in Why. That makes it a provenance note (N4), not a defect.

## Notes (not verdict-bearing; for the ADR and `add-sites-alias-certs`)

- **N1 — classify fidelity.** The follow-on should either parse gateway.toml with the same defaults (fallthrough absent → Iroh; `[[alias]]` resolves under any fallthrough; bare apex without an empty-subdomain route → `EmptySubdomain`; longest-suffix `match_host`) and pin them with test vectors shared with `main.rs` `classify` tests, or ask the gateway. The ADR should name which one, so the two sides do not drift silently.
- **N2 — renewal reads simpler than it is written.** With the bound, the follow-on needs no three-way dispatch at renewal: "app host → reinstall; otherwise read the alias index → error ⇒ skip, else reinstall; never append". Renewal also does not re-apply the 409, so a site cert whose host later moved to Local/Iroh keeps renewing (quota for an unserved name). This is the same open question as prior N3. Follow-on.
- **N3 — corrupt vs unreadable.** `parse_alias_index` failure is currently `:not_found`. The spec's "cannot be read, and the failure is not a missing file" does not say whether a readable but unparseable file counts. On issue that gives `404 name_not_found` instead of `503`. On renewal it is harmless under the bound. Recommend the ADR say "parse failure ⇒ unreadable (fail closed)".
- **N4 — provenance.** The ADR should attribute "renewal never appends" to advise S1 as amended by the conductor, not to the 2026-10-15 user steer, whose text still says "keeps today's ensure".
- **N5 — app-path residual.** App first issue appends `apex_of(fqdn)`, the last two labels, even when the configured apex in `:gateway_apexes` is longer (e.g. `apps.example.com`), and `:gateway_apexes` can drift from gateway.toml `[[domain]]`. Either can still capture a sibling site alias. This is pre-existing and not widened by this change. Worth one ADR sentence and a bead.
- **N6 — list under an unreadable index.** Spec Req 4 does not say what `GET /api/certs` does when the alias index is unreadable. Recommend: omit the alias-only hosts for non-operators and still return 200 with owned app hosts. Do not 500 the whole list.
- **N7 — open issuance quota** is the explicit steer and is named in design § Tradeoff. Not relitigated.

## Verdict

Accept. S1 and S2 are answered in the spec with scenarios, in a form stricter than asked. The contract is internally consistent with the gateway as built (`classify` and the Reject/Parked → sites dispatch verified). Remaining items are follow-on mechanism and ADR wording, recorded above as notes.
