## Blind take (written from Why + cited code, before design.md / tasks.md / spec)

1. Pin: the site-only install path writes `[[cert]]` and never `[[domain]]`. Today `ops.ensure/3` takes no opts and `ensure_origin_ca` always calls `ensure_domain_block`, so this needs a new explicit seam (`domain: :skip`), not a default.
2. Pin: renewal must not add a `[[domain]]` that issuance did not. `ensure_origin_ca` short-circuits only on `:unchanged`. A renewed PEM differs, so it re-runs `ensure_domain_block`. Renewal must classify the host again, or (stronger) be cert-only.
3. Pin: a resolver **error** at renewal is not a **miss**. If "neither, so use today's ensure" also fires on a transient lookup failure or a just-deleted alias, it appends `[[domain]] <apex>`. That flips the whole apex to Iroh fallthrough and takes down every *other* live site alias under that apex. The blast radius is wider than one host.
4. Pin: issuance must refuse, or at least loudly flag, a site host already covered by a declared `[[domain]]` apex with `fallthrough = iroh` (for example, app `www.foo.com` already appended `foo.com`, and the site is `blog.foo.com`). Classify sends that host to Iroh before the sites resolver, so we would mint a cert for a host we cannot serve.
5. Pin: precedence is the app custom domain (exact host), then the live site alias, then 404. The same normalisation (trim, trailing dot, lowercase) applies on both lookups, and the wildcard refusal stays first.
6. Pin: a "live alias" check must be what the gateway resolver would hit, not merely a stored row. Otherwise issue succeeds and serving 302s to the berth.
7. Refuse: deriving `[[domain]]` from `apex_of` (last two labels) for any site path. It is wrong on `co.uk`, and sites never need it.
8. Refuse: letting `sites:publish` reach issue, and leaking site ownership through different 404 bodies across the app/site branches.
9. Tradeoff: re-classifying at renewal (steered) vs "renewal is cert-only; `[[domain]]` is only ever added by explicit issue". The second is simpler and cannot widen blast radius, but it diverges for legacy app certs whose `[[domain]]` was hand-removed.
10. Test owed: one end-to-end test where a gateway config with a site-only `[[cert]]` still classifies the host as `Reject(DomainMismatch)`, so it reaches the sites resolver, both before and after a renewal pass.

## Steelman against my take

- **Against S1:** the steer says "neither keeps today's ensure", and the spec scenario follows it to the letter. Its Why is `zine.identikey.io` still renewing. A deleted alias arguably *is* a stranger now, and sites-serve miss policy is out of scope.
  **Answer:** the steer protects *renewal continuing*. It does not protect *adding an apex at renewal*. Bounding the neither branch so it cannot add a `[[domain]]` that captures a live alias keeps `zine` renewing (`identikey.io` apex present ⇒ `ensure_domain_block` is a no-op). It changes nothing the steer decided. This is not relitigating. It closes the same hazard the change's Why names, reached by a second door.
- **Against S2:** a pre-existing Iroh apex over a site name is already broken today, without this change. Making routing correct is `sites-serve` / gateway work, not this change.
  **Answer:** agreed that fixing the routing is out of scope. But this change's Working journey promises `https://blog.example.com/` returns the snapshot, and the spec's own last scenario fences the case off with a GIVEN ("no `[[domain]]` apex causes … Iroh route"). The contract needs to say what `issue` *does* in the fenced-off case. Otherwise the follow-on will spend LE quota minting a cert for a host that then dials Iroh, and report 200. One sentence plus one scenario, in either direction, satisfies this.
- **Against send-back at all:** the change is ADR-only, so the follow-on could absorb both.
  **Answer:** the ADR is the contract the follow-on implements against, and spec requirement 3 currently *asserts* the hazardous behaviour ("a missing apex for that name may be added"). If it folds as written, the living spec mandates the bug.

## Send-back items

**S1 — renewal "neither" can add an apex that takes down live aliases.**
`Mjolnir.SecretStore.lookup_alias/1` (`lib/mjolnir/secret_store.ex:118-140`) collapses **every** read error (`EACCES`, `EIO`, …) and every parse failure into `:not_found`. Spec requirement 3 then routes "neither" to today's ensure. `ensure_origin_ca` (`lib/mjolnir/gateway/certs.ex:270-293`) re-runs `ensure_domain_block` whenever the PEM changes, which is every renewal. Two concrete paths:
- The owner deletes alias `blog.example.com`, and the cert stays in `[[cert]]`. On its renewal day: neither → `[[domain]] example.com` is appended with the default Iroh fallthrough (`config.rs:401-404`). `docs.example.com`, a different, still-live alias, now classifies `Disposition::Iroh` (`main.rs:808-812`) and stops serving.
- A transient read error on the alias index for a live alias has the same result, for the alias itself.

The contract must (a) bound the neither branch: renewal SHALL NOT add a `[[domain]]` whose suffix covers a live site alias (or, simpler, renewal never adds a `[[domain]]` that is not already present). It must also (b) make classification fail closed: an unreadable alias index is an error that skips or fails the pass, not a miss. The spec scenario "a missing apex for that name may be added" must be rewritten to the bounded form.

**S2 — issuing a site cert for a host an existing apex routes away.**
Spec requirement 2's scenario "Existing apex is left alone" installs `[[cert]]` for `blog.example.com` under an existing `[[domain]] example.com`. If that apex has `fallthrough = iroh` (the default, and exactly what app issuance for `www.example.com` writes today), or has a `[[route]]`/`[[alias]]` for `blog`, then `classify` never reaches the sites resolver (`main.rs:781-816`). The cert is minted and the site is not served. The spec must name the behaviour. My recommendation is to refuse before HTTP-01 with a named error (for example `409 host_routed_elsewhere`), so no LE quota is spent. Acceptable alternative: issue and return the routing disposition so `mj` can warn. Either one, with a scenario, and the ADR records it.

## Notes (not verdict-bearing)

- **N1:** `name_not_found` vs `app_not_found` now lets a non-owner learn that *some* app holds a custom domain. Today both cases return `app_not_found`. The steer names both codes, and custom domains are public via DNS CNAME, so this is accepted. The ADR should say it was a known cost.
- **N2:** `ops.ensure` in `Mjolnir.API.Certs` is 3-arity `(fqdn, cert, key)` with no opts. The "flag on `ensure/2`" also needs the ops seam widened, or the test fakes cannot observe the site-only path. This is follow-on detail, flagged so the ADR does not describe a seam that does not exist.
- **N3:** After S1, consider whether a cert for a tombstoned alias should keep renewing at all, since it spends quota for a name nobody serves. This is a follow-on question, not owed here.
