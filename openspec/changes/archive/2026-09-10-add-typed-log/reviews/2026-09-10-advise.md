# add-typed-log — architecture advise (Fable 5.1)

> **ADVISE:** accept
> **READER:** fable-5.1-arch-review
> **SPAWN:** .spawns/add-typed-log-1789006240-54363-534a80be

## Blind take (written before design.md / tasks.md)

1. **Pin: typed-record detection is by MSG shape, not ingress.** A pino line arriving on vsock ch2 from a guest myscape must route as `:app_log` too, or guest and host myscape are two dialects, which is the exact failure the Why names. The spec text ("Guest RFC 3164 text SHALL continue to publish as `:vm_syslog`") is consistent with this only if "text" means non-JSON MSG.
2. **Pin: the emitter cannot write a unix datagram.** Node `dgram` and bun have UDP only; `/dev/log` (guest agent binds SOCK_DGRAM, `syslog.rs:48`) and a host unix datagram both need a native addon from TypeScript. The spec's "(or localhost UDP)" hedge is the real answer and should be pinned: UDP to `127.0.0.1` on the host, `10.200.0.1` from guests (ADR 0005 item 5 convention).
3. **Pin: RFC 3164 on the wire, or extend the parser.** `Parser.parse_header/1` accepts only `Mmm dd hh:mm:ss host` (`parser.ex:~152`); an RFC 5424 line from pino-syslog lands as `{:error, :malformed}` with no tag or message. `Message` moduledoc claims 5424; it is not true.
4. **Pin: record size.** Guest recv buffer is 8192 (`syslog.rs:66`); `:gen_udp` default `recbuf` is 8192. A pino error with a stack exceeds that; a truncated JSON MSG is unparseable. Choose a max (64 KiB) and a truncation policy (route as malformed raw, never drop silently).
5. **Pin: app id is self-asserted.** Neither UDP nor unix datagram via `:gen_udp` gives peer credentials. `{:mjolnir_event, "myscape", :app_log, _}` is a claim, not an identity. Say so in the subscribe docs.
6. **Pin: id key space.** `EventBus.publish/3` keys `{:vm, id}` (`event_bus.ex:70,110`); app ids share that space with VM UUIDs and every `:all` subscriber (Listener `listener.ex:73`, Forge SSE `forge/api.ex:224`, RouteReconciler `route_reconciler.ex:71`) receives every app log line. They all ignore unknown events today, but a chatty debug logger becomes mailbox load on three unrelated processes. Either a separate `:pg` group name for app logs or a documented "app_log is not for `:all`" rule.
7. **Refuse: fold materializing `openspec/specs/typed-log/` from this change.** LEARNINGS 2026-08-16 (`docs/LEARNINGS.md:8`): an architecture change must not import unimplemented SHALLs. Every SHALL here is unimplemented. The proposal's "Empty ... Correct: fold creates it" contradicts that learning. The spec delta belongs to `add-log-emit` / `add-log-ingest`, with this change folding only the ADR.
8. **Correct the ADR's "Built" claim.** The guest half is built (`vsock.rs:547` spawns the forwarder). The host half is not wired: nothing calls `Listener.register_connection/3`, `:vm_spawned` falls into the catch-all at `listener.ex:136`, and with two VMs registered the Listener drops all data (`listener.ex:148-163`). "Built: guest syslog pipeline" overstates by one wiring step and one bug.
9. **Refuse: `:logger` sink for `:app_log` at default.** `Router.dispatch(:logger, ...)` (`router.ex:69-81`) writes every line to Elixir Logger; an app debug stream doubles into journald. `:app_log` default sinks should be `[:eventbus]`, with level mapped from pino `level`.
10. **Tradeoff: types-first + generate vs schema-first.** TS types with a codegen step (spec as written) gives the nicest authoring surface but two artifacts that can drift and a build step every app must run. Schema-first (TypeBox/zod, schema is the runtime value, types are `Static<>`) has no generate step and the LSP reads the same object. I would take schema-first; the author must show why the generate step is worth owning.

## Compare (after design.md, tasks.md, steer.md)

The five decisions stand. None of my concerns is a competing design;
each is a pin the author must write before `add-log-emit` or
`add-log-ingest` activates. Verdict is **accept** with the amendments
below recorded as unchecked tasks in `tasks.md`.

Steelman against my take, item by item:

- **(1) Discriminator.** Design D3 (`design.md:70-74`) lists "guests →
  `:vm_syslog`" and "typed app JSON MSG → `:app_log`" as parallel
  bullets and stamps `source: :guest | :host`. It never says which wins
  for a JSON MSG arriving from a guest. Steelman: myscape is a host
  process for v1, so the case does not arise. Answer: it arises the
  day myscape or any bun app runs in a VM, and the Why is explicitly
  "one record shape". **Pin required:** `:app_log` iff MSG parses as a
  JSON object carrying the `schema` field, regardless of source;
  `source` is a stamp, not the discriminator.
- **(2) Unix datagram from bun.** D3 keeps the hedge "unix datagram (or
  UDP localhost)"; steer says "host unix datagram". Steelman: the
  Elixir side is trivial either way (`:gen_udp` with `{:local, path}`).
  Answer: the constraint is the emitter. `node:dgram` and
  `Bun.udpSocket` are UDP only; AF_UNIX datagram needs the `unix-dgram`
  native addon, which is not "bun native runtime" (steer). On macOS
  there is no `/dev/log` at all. **Pin required:** the host ingest is
  UDP on a loopback port (and `10.200.0.1` for guests per ADR 0005
  item 5). Target is explicit config; unset means stdout only, no
  error. `bun:ffi` → libc `syslog(3)` is a valid guest-only route (it
  reaches `/dev/log` → agent) but on the server host it reaches
  journald, not Mjolnir, so it cannot be the host path.
- **(3) RFC 5424.** D2 says "RFC 5424 preferred; RFC 3164 still parsed
  for guests" and Built (`design.md:117`) honestly lists only the 3164
  parser. But the `add-log-ingest` handoff (`tasks.md:25`) says "JSON
  MSG parse", not "5424 header parse". A 5424 line today is
  `{:error, :malformed}` with tag and message nil
  (`parser.ex:99-101`). **Pin required:** either emit 3164 in v1 or
  add "RFC 5424 header parse" to the ingest handoff explicitly.
- **(4) Record size.** Not addressed. Guest recv is 8192
  (`syslog.rs:66`); `:gen_udp` `recbuf` default is 8192. A pino error
  with a stack overflows both. **Pin required:** max record (64 KiB
  suggested), oversize routed as malformed raw, never silently dropped.
- **(5) App id is a claim.** Not addressed. UDP and `:gen_udp` unix
  datagrams give no peer credentials. One sentence in the subscribe
  docs (`add-log-subscribe`).
- **(6) `:all` fan-out.** D3 acknowledges app ids share the
  `{:vm, id}` key space. It does not name the cost: every `:all`
  subscriber (`listener.ex:73`, `forge/api.ex:224`,
  `route_reconciler.ex:71`) receives every app log line. All three
  ignore unknown events, so nothing breaks; a debug-level app is
  mailbox load on three unrelated processes. Note for
  `add-log-subscribe`: either a distinct `:pg` group for `:app_log`, or
  document that `:all` includes app logs and subscribers should key by
  app id.
- **(7) Fold.** Answered: `design.md:121-123` and `tasks.md:16-20`
  refuse importing unimplemented SHALLs. But `proposal.md` still says
  "Empty — Correct: fold creates it" and "ADDED `typed-log`
  (materialized by fold)". The folder reads the proposal. **Fix:**
  align the proposal to tasks. Only two SHALLs are true today
  (vsock ch2 kept; no Phoenix.PubSub); the rest belong to the
  implementing deltas.
- **(8) "Built" is overstated.** Guest half is built: `vsock.rs:547`
  spawns the forwarder unconditionally under `feature = "full"`. Host
  half is not wired: nothing outside `lib/mjolnir/syslog/` calls
  `Listener.register_connection/3`; `:vm_spawned` falls into the
  catch-all at `listener.ex:136`; so every guest syslog frame hits
  "Data on unregistered channel 2" at `connection.ex:423-426` and is
  dropped. Even once registered, two VMs means all data dropped
  (`listener.ex:148-163`). **Fix:** ADR and design "Built" lines must
  say "guest forwarder built; host ch2 registration and multi-VM
  sender identification owed", and that work needs a home
  (`add-log-ingest` or its own bead).
- **(9) `:logger` sink.** Not addressed. `router.ex:69-81` mirrors
  every line into Elixir Logger. Pin for ingest: `:app_log` default
  sinks `[:eventbus]`, level from pino `level`.
- **(10) Types-first vs schema-first.** D4 rejects "hand-written JSON
  Schema as source (TS would drift)". That is a strawman: schema-first
  with derived types (TypeBox `Static<>`) has one artifact and nothing
  to drift, and the "generate step" is a serialise. Steer records the
  choice as decide-for-me, not a user pin, and the spec's wording
  ("provide TypeScript types" + "generate step SHALL emit JSON Schema")
  is satisfied by either. Not a send-back. Leave the door open in
  `add-myscape-log-types`.

One additional risk not in my take, for `add-log-emit`: pino
transports (pretty, syslog) run on worker threads via `thread-stream`.
Under bun that has been the flaky surface. Prefer in-process
`pino.multistream` with `pino-pretty` as a stream and a UDP writer, no
workers. Spike it first.

## Verdict

Accept. The architecture is right: syslog as wire, JSON as MSG, one
Router, `:pg` not PubSub, app-owned schema. What is missing is pins,
not decisions. Amendments (1), (2), (3), (7), (8) are required before
`add-log-emit` / `add-log-ingest` activate; (4), (5), (6), (9) are
ingest/subscribe scope lines; (10) is a note.
