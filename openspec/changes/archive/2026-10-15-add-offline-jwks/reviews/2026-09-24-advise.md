## Comparison and steelman

The author answers the core availability concern: load disk first, refresh in the background, start even without keys, and reject unknown kids. The fixed host directory and 0600 mode follow the steer. Keeping the existing token hook and authorization path is a reasonable narrow change; it does not need a second authentication protocol or a new UI.

The strongest case against my take is that v1 can retain every historically trusted public key and apply each presented token's normal expiry checks. That avoids inventing a TTL that would reject a legitimate token during a long outage. The steer explicitly skipped a numeric overlap window, so I withdraw an arbitrary numeric bound as a prerequisite. However, indefinite key trust must be stated as such, with its revocation consequence and an operator recovery rule. The current promise to remove a key when it is “no longer needed” is not computable from the described inputs. The findings below require explicit contracts, not my preferred cache implementation.

## Required amendments

### R1 — P1: Make retention and retirement executable

**Evidence:** `design.md:22-25`; `steer.md:10-13`; `specs/edge-auth/spec.md:28-32`.

The design retains A until no token needs it, but specifies neither issuer key-lifetime metadata nor a trusted maximum token lifetime. A verifier cannot enumerate tokens that have not yet been presented. JWT `exp` describes a token's acceptance deadline; the JWK format does not supply a general signing-key expiry rule. See [RFC 7519 §4.1.4](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4) and [RFC 7517 §4](https://www.rfc-editor.org/rfc/rfc7517.html#section-4).

Consequently, retaining A indefinitely also permits newly forged, future-expiring tokens after A's private key is compromised and the issuer removes A. Checking each token's expiry does not solve that. Conversely, retiring A when the last locally observed token expires can reject a still-valid token first presented later.

**Owed:** define what happens when `{A,B}` becomes `{B}`, including across restart. Identify the trusted inputs for any retirement decision, or explicitly choose indefinite v1 retention and describe how an operator withdraws trust, including memory and disk. Do not silently reinterpret the skipped numeric window as a chosen TTL. Add removal, post-restart overlap, and the chosen retirement/revocation scenarios. The current `{A}` → `{A,B}` test passes even with ordinary replacement and does not prove retention.

### R2 — P1: Bind the cache to its authority

**Evidence:** `design.md:16-18`; `specs/edge-auth/spec.md:5-10`; `lib/mjolnir/auth/keycloak_strategy.ex:25-33`; `lib/mjolnir/auth/token.ex:14-20`.

“For the configured hosted issuer” expresses intent but supplies no persisted binding or load-time mismatch behavior. With a shared cache path, switching issuer X to Y while Y is offline can leave X's keys trusted under Y's token-claim check. An X key holder can sign a token claiming `iss=Y`; comparing that claim to configuration does not establish the key's provenance.

**Owed:** specify issuer and effective JWKS-source identity in the cache contract (or equivalent namespace), check it before loading signers, and reject mismatches without preventing boot. Define the normalization used; retain the configured issuer's claim checks. Test an issuer switch with a colliding kid and a token signed by the old authority but claiming the new issuer. Include source changes if a JWKS URL override is supported.

### R3 — P1: Preserve last-known-good through refresh and disk failures

**Evidence:** `design.md:16-18`; `specs/edge-auth/spec.md:5-12`; `lib/mjolnir/secret_escrow.ex:28-30`.

Writing JSON after a “successful fetch” does not establish that the document contains usable verification keys, nor that an interrupted write preserves the previous cache. A crash during truncation could erase the only reboot verification path. File mode 0600 alone also does not protect against replacement through an untrusted writable parent directory.

**Owed:** define validation before publication, duplicate/conflicting kid handling, and behavior for malformed, empty, or unsupported-only responses. Preserve the prior usable set in memory and on disk on rejected refreshes. Specify atomic replacement, restrictive ownership/directory access, and how read, parse, chmod, write, and rename failures affect boot and verification. Distinguish an unusable cache from absence of an issuer: neither grants auth. State whether a valid new fetch can serve from memory after persistence fails, and how that degraded durability is reported. Add corruption, interrupted-write, failed-write, and invalid-refresh tests that inspect the next restart, not only the current process.

### R4 — P2: Identify the strategy seam and recovery behavior

**Evidence:** `lib/mjolnir/auth/keycloak_strategy.ex:23`; installed `deps/joken_jwks/lib/joken_jwks/default_strategy_template.ex:183-205,209-218,240-279` (locked version 1.7.0).

The existing template creates ETS during init, writes the entire newly parsed signer map on refresh, and accepts an empty map after logging a warning. Its parser is private, and its periodic check skips fetching when its refresh counter is clear. Dropping `first_fetch_sync` and saving a response does not establish the proposed additive, persistent behavior. Persisting only the latest response could also retain A in memory but lose it on reboot after a `{B}` refresh.

**Owed:** name the component that owns validated merging, disk loading, and signer lookup, and identify how it integrates with the Joken hook. Define what is persisted, retry triggers after an empty offline boot, and bounds on network attempts so refresh cannot block boot or known-key verification. Keep certificate verification from the Mint adapter. Add a deterministic empty-start → issuer-recovery test and a blocked-refresh test that verifies a known token concurrently. This needs a short data-flow contract, not implementation code in the design.

### R5 — P2: Carry bootstrap and negative verification into acceptance

**Evidence:** `proposal.md:24`; `tasks.md:3-8`; `specs/edge-auth/spec.md:14-32`.

Bootstrap provisioning appears in the proposal and bead, but has no task, entry point, or scenario. The delta also omits the proposal's empty-cache recovery and issuer-disabled behavior. “Unexpired token with a known kid” must not become sufficient evidence of authenticity.

**Owed:** identify the bootstrap entry point and require it to use the same source binding, validation, and safe persistence contract. Cover reachable seeding and unreachable best-effort bootstrap. Add explicit cache-path rejection for `btrfs_root`, configured-issuer/empty-cache recovery, issuer-disabled behavior, and known-kid tokens with a bad signature, wrong issuer, or expired claims. Qualify positive scenarios as otherwise-valid credentials; preserve existing authorization behavior.

## Accuracy and scope notes

The cited application code does synchronously fetch before completing strategy initialization. However, the installed template ignores a returned fetch error and can still return `{:ok, opts}`; some failures delay startup rather than invariably failing it. The HTTP fetcher also has incomplete error matching, so raised failures remain possible. The implementation tests should distinguish ordinary error returns, stalls, and exceptions. This nuance does not weaken the offline-cache requirement.

The token module explicitly skips audience validation despite its moduledoc and the bead's wording. `lib/mjolnir/api/auth.ex:146-160` does not add that check. This is an existing contract discrepancy, not evidence that the cache change introduces it; the conductor should reconcile or separately track it rather than report audience validation as already established by this review.
