## Blind take (Why + living spec + cited code only; written first)

1. **Pin: fail-close is real, and it is the recipe, not inject.**
   `scripts/build-rootfs-arch.sh:19` sources the helper, `:165` calls
   `install_guest_agent`, and `scripts/lib/guest-agent.sh:120` onward
   (`verify_guest_agent`) asserts binary + unit + `basic.target.wants`
   or exits non-zero. D3 matches code.
2. **Pin: D5's whole-cache delete is forced by code, not taste.**
   `lib/mjolnir/deploy/builder.ex:102` makes `base_layer_id` the alias
   string, `lib/mjolnir/deploy/cache_key.ex:74-75` hashes that string
   as the parent, the sidecar written at `lib/mjolnir/btrfs.ex:136-148`
   has no parent field, and `builder.ex:259` enumerates layers purely
   by the `deploy-` prefix. After an in-place alias rebuild a surviving
   layer is a **silent stale hit** on the old rootfs.
3. **Correct the spec's stated failure mode.** `{:snapshot_exists, _}`
   (`btrfs.ex:116`) fires only when the subvolume survives and the
   sidecar is gone. The two worse cases are: both survive → stale hit;
   sidecar survives, subvolume gone → planner resumes from a missing
   snapshot. "Via `mj snapshot rm`" is right; the sentence justifying it
   names the least dangerous of the three outcomes.
4. **Refuse-check: "every `deploy-*`" includes each app's release layer.**
   `Runtime.start` boots the service VM from it
   (`lib/mjolnir/deploy/runtime.ex:101`) and `Deploy.Registry` records
   `release_snapshot` per app (`lib/mjolnir/deploy/registry.ex:31`).
   Running service VMs survive (independent `@vms` subvolume; Reconcile
   resumes from the rootfs path, `lib/mjolnir/reconcile.ex:260`), but
   every Registry entry dangles until the next deploy and that deploy is
   a cold build. The spec must say this out loud.
5. **Pin: `deploy-node-bun` retirement.** `orchestrator.ex:50` stays until
   `remove-deploy-node-bun`. The "Deploy default" scenario is a later-act
   SHALL. Fold must not import it as built truth (LEARNINGS 2026-08-16,
   `docs/LEARNINGS.md:10`).
6. **Same for D6.** Five scenarios of unimplemented SHALL under "Pins are
   immutable". They go to PENDING `add-base-image-pins`, not
   `openspec/specs/`.
7. **Tradeoff accepted:** v0 in-place rebuild plus cache nuke costs one
   cold deploy per app and loses rollback to the previous release. It
   buys not writing a pin resolver before a second tenant. Correct order
   for one tenant.
8. **Concern: stale-agent fallback defeats "including a current guest
   agent".** `guest-agent.sh:43-44` falls back to the agent inside
   `@base/ubuntu-24.04` or `@base/ci-ubuntu-24.04` with only a warning.
   Rebuilding `ubuntu-24.04` on a host with no Rust tree copies an
   *old* agent into the *new* image and the build succeeds. D5's
   "current guest agent" is not fail-closed on that path.
9. **Minor: the pre-rebuild snapshot is invisible to the API.**
   `@snapshots/<name>-pre-rebuild-<date>` made with raw `btrfs subvolume
   snapshot` has no sidecar; `list_snapshots` (`btrfs.ex:314`) filters
   on `.json`, so `mj snapshot list` will not show it. `delete_snapshot`
   (`btrfs.ex:372`) still accepts a bare directory, so `mj snapshot rm`
   can remove it. Say which tool creates it.
10. **Tradeoff: closed catalog v1, ADR amendment per name, unmanaged never
    auto-deleted.** Right friction for a single host.

Steelmanning the author against the blind take:

- **Take 1, 2, 5, 6, 7, 10 — answered.** design.md D1–D6 and the
  fold table say the same things with the same cites. Rows for deploy
  default, Node-deploy-uses-mise, "Recipes SHALL NOT produce", and
  pins are PENDING with the waiting node named.
- **Take 3 (which failure the rationale names) — coherent on a second
  read, but under-explained.** In context the spec's "a surviving name
  fails the next re-snapshot" is the *partial-delete* case the prior
  re-advise traced (`plan.ex:95-98` then `btrfs.ex:116-117`), and it
  is there to justify "every", not "any". The reason for deleting
  *any* layer is the silent stale hit, which the spec leaves to D6's
  "cache poison" argument in design.md. Steelman accepted: the
  requirement is "Declared live images match current recipes", and a
  cached layer built on the old rootfs is by definition not that. A
  reader of the living spec alone will still ask why the step exists.
  One clause would close it; non-blocking.
- **Take 4 (release layers) — answered by consequence, not by name.**
  Traced every consumer of `Deploy.Registry`: `runtime.ex:255`
  (`previous_entry`) reads only `custom_domain`, `owner_id`, and the
  previous `service_vm_id` for cutover; `authz.ex:121,153` reads
  ownership; `tcp_liveness.ex:132` reads ports; `router.ex:1808` reads
  `custom_domain`. **Nothing re-clones from `release_snapshot`**, and
  there is no rollback route. So deleting every `deploy-*` layer,
  release layers included, breaks nothing running and nothing on the
  next deploy beyond a cold build. The spec's "Running `@vms/<uuid>`
  clones SHALL NOT be destroyed" plus design.md Risks ("existing
  `deploy-*` layers … miss. Accepted") price it. What the text does
  not say is that each Registry entry will name a deleted snapshot
  until the app is redeployed, and that `GET /api/deploy` will report
  it. Operator-facing sentence; non-blocking.
- **Take 8 (stale-agent fallback) — answered by operator step, not by
  code.** design.md D5 step 2 says "build or reuse a current
  `mjolnir-agent` at `AGENT_BIN`", and the landing record in tasks.md
  carries the agent md5. The ubuntu recipe deletes `@base/ubuntu-24.04`
  at `build-rootfs-ubuntu-24.04.sh:53` before `install_guest_agent` at
  `:102`, so the ubuntu-from-ubuntu fallback cannot fire, but the
  ci-ubuntu candidate (`guest-agent.sh:44`) can, with a warning. D5's
  "current" is operator discipline in v0. That is acceptable for a
  single host; `add-base-image-health` is where doctor should compare
  the baked agent against the built one. Handoff note; non-blocking.
- **Take 9 (pre-rebuild hatch) — answered better than I assumed.**
  `clone_from_snapshot` (`btrfs.ex:63-78`) checks only that the
  directory exists, so `mj spawn --snapshot ubuntu-24.04-pre-rebuild-…`
  works with no sidecar. Only listing and `GET /api/snapshots/:name`
  (`btrfs.ex:353`, reads the `.json`) miss it. design.md D6 calls the
  hatch "the wrong namespace" and is right. Non-blocking.

One thing I checked that neither prior review did: **the named delete
tool actually authorizes.** `Policy.Snapshot` denies `:delete` on
owner-less snapshots to token users (`lib/mjolnir/policy/snapshot.ex:32`)
and allows localhost everything (`:23`). Deploy layers are stamped
`opts[:owner_id] || state.owner_id` (`vm.ex:3145`), and the
orchestrator stamps the deployer on the build VM
(`orchestrator.ex:338,358`). So `mj snapshot rm` works for layers the
token's user deployed; layers from a localhost deploy (deployer nil)
need the localhost `DELETE`. The SHALL names both paths. Fine as
written; worth one line in the operator sequence.

## Findings (non-blocking; ride along with any later edit, or hand off)

- **D5 rationale names the partial-delete failure only.** Spec
  "Declared live images" paragraph, ADR line 5, design.md step 5. Add
  a clause of the form *a surviving layer is a cache hit on the old
  rootfs; a partially deleted chain fails with `{:snapshot_exists, _}`*
  so the living spec carries both reasons. Text only.
- **"Every `deploy-*`" includes release layers; say the consequence.**
  Running service VMs keep their `@vms` clones; `Deploy.Registry`

  `policy/snapshot.ex:32`. `mj snapshot rm` returns 404 for a layer
