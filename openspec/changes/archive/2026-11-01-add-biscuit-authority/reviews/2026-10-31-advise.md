The direction is sound, but the durable private key needs an explicit safe path through the existing runtime, and the acceptance evidence must exercise durability.

## Comparison and steelman

Design lines 7–13 and the delta's durable-root requirement answer blind concerns 1–4 and 8: one existing file, public key derived from it, configured-key mismatch rejected, no replacement on missing material, ephemeral tests separate, and the folded crypto path preserved. Placing the file outside guest storage and escrow is appropriate.

The strongest case for this design is its small provisioning boundary. It reads an existing root and refuses to create one during mint. That is enough to avoid requiring an automatic initialization service, locking protocol, or rotation system here. I withdraw blind concern 5 as a runtime requirement if operator provisioning is made explicit; safe publication then belongs to that setup procedure. A file is a reasonable tradeoff against a secret-management service for this host. None of the findings requires another mint implementation, changes to Blake3, or work on the other two changes.

## Changes owed before acceptance

1. **P1 — Keep the durable root out of process arguments and diagnostics.** `lib/mjolnir/biscuit.ex:50–57` puts `private_hex` in the mint request; lines 110–119 serialize it into `System.cmd(bin, [json], ...)` and include subprocess output in exceptions. Reusing that path promotes the existing argv exposure to exposure of the host's persistent signing authority. The design and delta prohibit environment storage but do not address this path. Pin a transport that keeps private bytes out of argv and redacts failure output, with a focused regression check. The CLI already accepts stdin (`native/mjolnir_biscuit/src/bin/mjolnir-biscuit.rs:82–89`), so preserving the JSON schema need not preserve argv transport. No subprocess-output leak was demonstrated; redaction is a required failure-path contract.

2. **P1 — Finish the provisioning and load contract.** Design line 13 says boot reads a `0600` file, but does not specify its encoding, who provisions it, or what happens when it exists but is malformed, unreadable, or has unsafe permissions. Nor does it identify the production authority entry point: today's `Biscuit.mint/3` accepts any caller-supplied private hex. Pin the file format and operator setup boundary, safe installation without overwriting an existing authority, validation of the required storage constraints, and an explicit error/no-regeneration policy for invalid material. Identify how production callers obtain the authority and when its public half becomes available to verifiers. A short contract is sufficient; no new UI or automatic root creation is requested.

3. **P2 — Prove restart continuity and the rejection cases.** `tasks.md:6` and delta lines 7–12 test only two mints. An ephemeral key cached for one process passes that test while violating the defining requirement. Add a fresh-process/reinitialization scenario that discards authority memory, reloads the same file, verifies a pre-restart token, and mints a new token under the same public key. Also require tests for configured-public mismatch, invalid-file cases from finding 2, missing-file non-creation, and an unset public override deriving the verifier. Keep the existing ephemeral round-trip coverage.

Owed boxes are appended to `tasks.md`; implementation boxes remain open. No product code, living spec, or disposition banner was changed.
