## Independent blind take

Written before opening the design, tasks, delta, or previous review; inputs were proposal Why, the living biscuit-runtime spec, and the two cited source files.

1. Pin one durable authority identity whose public key is derived from the persisted private key.
2. Pin restart behavior: an existing authority is loaded unchanged, and minting never silently generates a replacement.
3. Refuse ambiguity between explicit first initialization and missing, damaged, or unreadable production authority state.
4. Pin atomic publication and concurrent initialization so no caller can mint under a losing or incompletely persisted root.
5. Refuse private-key exposure through argv, environment, request logging, diagnostics, or permissive filesystem access.
6. Pin the BEAM-to-CLI transport to a private input channel; the existing stdin parser is a useful seam, not proof the caller uses it.
7. Pin verifier configuration semantics so an operator-supplied public key cannot silently disagree with the mint authority.
8. Preserve the existing Ed25519 Biscuit format, holder checks, and commitment primitives without inventing another mint implementation.
9. Demand observable failure contracts and tests for restart identity, malformed state, permission errors, races, and secret-bearing subprocess failures.
10. Tradeoff: a local durable key keeps this bounded, but accepts host custody and explicit recovery obligations rather than rotation or distributed key management.

## Comparison with findings 1, 2, and 3

1. **Finding 1 resolved — private transport and diagnostics.** [Design](../design.md) line 23 requires stdin and omits raw subprocess bodies from failures. The [delta](../specs/biscuit-runtime/spec.md) lines 5–7 prohibits private bytes in argv, environment, exceptions, and subprocess diagnostics; its final scenario and [task](../tasks.md) line 9 require a regression through a forced CLI failure. This directly addresses today's `System.cmd(bin, [json], stderr_to_stdout: true)` and output-bearing exception in `lib/mjolnir/biscuit.ex:114`. The Rust stdin parser already provides the receiving seam. The production caller still needs implementation; merely reusing the existing `rpc/1` unchanged would violate this accepted contract.

2. **Finding 2 resolved — provisioning, validation, and initialization.** Design lines 13–21 and delta lines 5–7 specify 64 lowercase hex characters with an optional newline, operator provisioning before boot, exact `0600` permissions, excluded storage locations, refusal of bad or unreadable files, and no creation, overwrite, mode repair, or replacement generation by the host. `authority/0` loads once per boot; `mint_production/2` uses its cache while `mint/3` remains explicit-key. Public-key publication precedes HTTP acceptance, an explicit mismatch fails boot, and an unset override derives the verifier. These are concrete obligations at the existing runtime-config/application-start boundary, not changes to the Biscuit wire format.

3. **Finding 3 resolved — continuity and rejection evidence.** Delta lines 16–47 and tasks lines 7–8 now require a fresh process to reload the file, verify a pre-restart token, and mint under the same public key. They also cover configured-public mismatch, malformed/unreadable/wrong-mode roots, missing-file non-creation, and an absent public override. The same-boot test remains useful alongside this restart test; a purely ephemeral cached key can no longer satisfy the acceptance criteria.

## Steelman against the blind take

The strongest argument for the amendment is the deliberately small provisioning boundary. My blind point 4 anticipated runtime creation and concurrent publication. The author instead requires an operator-provisioned file before boot and forbids runtime writes. I withdraw runtime initialization locking and atomic file publication as requirements for this node: safe installation is an operator precondition, and the host must validate what it receives without repairing or replacing it. A new provisioning service or rotation protocol would add scope without resolving an outstanding finding.

The derived verifier, startup ordering, immutable per-boot cache, and separate production entry answer blind points 1–3 and 7. Stdin and diagnostic restrictions answer points 5–6. Keeping the existing crypto face answers point 8, while the expanded acceptance evidence answers point 9 for the selected read-only provisioning design. Host custody and operator recovery remain the explicit tradeoff in point 10. No unresolved architecture blocker remains in this contract.
