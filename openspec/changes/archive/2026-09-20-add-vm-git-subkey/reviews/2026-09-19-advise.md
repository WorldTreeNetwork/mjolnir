## Blind take (written before design.md / tasks.md)

1. Pin the **fixed guest path** `/run/mjolnir/git_signing_key`, tmpfs,
   0600. The whole point is that key bytes rotate and
   `git config user.signingkey` does not.
2. Pin **a distinct opaque blob**, never `Identity.env_entries/1`.
   `BUZZ_PRIVATE_KEY` is a Buzz-shaped env map, not a generic inject.
3. Pin **no `_opaque` copy across `vm_id`s**. Respawn mints; any
   `copy_from` shape must be a hard error, not a convenience.
4. Pin the **revoke order** Forgejo → `revoke_device` → opaque delete,
   and the asymmetry: a failure must strand a *dead* remote key, never a
   live key with no identikey row.
5. Pin the guest **inject allowlist by name** — one accepted filename,
   no caller-supplied path.
6. Refuse a generic "write any file" vsock verb. Traversal / arbitrary
   overwrite for one key is a bad trade.
7. Refuse private material (or its path) on the VM struct, StateStore,
   or any `GET /api/vms/:id` view.
8. Refuse folding the Forgejo-registration SHALL. It has not landed;
   the living spec must not claim it.
9. Tradeoff: one fixed path means one signing key per VM, and a fresh
   device per respawn means old commits verify only against a revoked
   pubkey. Accepted because identity is per-device (ADR 0011 §7), but it
   is a real cost and should be named, not discovered.
10. Fold-specific: the living preamble must stop listing
    `add-vm-git-subkey` among the not-landed; and the stable-path
    scenario leans on `gpg.format ssh` set by a bootstrap *script*, not
    by any SHALL — say so or the scenario looks self-verifying.

## Compare

The author answered 1–5 and 7–8 directly. Decision 3 names the fixed
path and tmpfs; Decision 4 names the revoke order *and* the crash
asymmetry in the same words I reached for. Point 6 is answered better
than I framed it: `inject_file` takes a `name`, not a path, and
`vsock.rs:1303` hard-matches `git_signing_key` — the guest, not the
host, is the allowlist, which is the right side of the trust boundary.

Point 3 is stronger in code than in the delta: `store_git_signing/1`
turns both `%{copy_from: _}` and `%{from_vm_id: _}` into
`:cannot_copy_git_signing`, and `respawn(same, same)` is refused. That
is a real invariant, not a comment.

My point 9 was answered by something I had not seen: `git_signing_device`,
a **second** blob holding `xid` / `credential_id` / pubkey. Revoking the
old device needs to *name* it under the old `vm_id`, and without the
split you either copy private bytes or cannot revoke at all. `put_device/2`
refuses anything that smells private. That is the non-obvious call in the
change and it is recorded in LEARNINGS.

Point 10 is satisfied: the preamble now reads "Living truth here is the
dev-preview landing plus the `ssh_git` git-signing device", and it
correctly re-routes the passkey `/term` SHALLs to `web-pty-edge` rather
than claiming them here. `docs/architecture.md` §hosted being was
amended in the same commit and no longer lists `add-vm-git-subkey` as
pending.

## Notes the fold does not have to fix

- **`revoke/1` deletes the device blob it will need later.**
  `delete/1` removes `git_signing` *and* `git_signing_device`, so once
  `add-honor-git-remote` starts registering keys, a respawn under an
  unwired (`:not_wired` → `:ok`) Forgejo hook leaves a live remote key
  and destroys the only local record of its pubkey — the reconcile find
  has nothing to match on. Today nothing registers a Forgejo key, so the
  LEARNINGS line reads slightly ahead of reality; the hazard arms itself
  the moment `add-honor-git-remote` lands. Wiring the hook and keeping
  the device blob on Forgejo failure belongs to that change.
- **`gpg.format ssh` / `commit.gpgsign true` live in
  `scripts/hosted-being-bootstrap.sh:60-62`, not in a SHALL.** The
  "Stable path on new device" scenario asserts `user.signingkey` is
  unchanged, which is true only because that script wrote it. Correct to
  leave out of scope — but a future edit to that script can break a
  living scenario with no spec text pointing back at it.
- `identikey_revoke_device/1` treats a missing `xid`/`credential_id` as
  `:ok` ("never registered"). That is right for the mint-then-crash case
  and wrong for a corrupted device blob; the two are indistinguishable
  today. Small, and not a fold concern.
