## Blind take (written before opening design.md, tasks.md, the delta, steer, or prior reviews)

From Why, the living `blob-store` spec, and `sites_router.ex` / `store.ex` / `recrypt.ex` only:

1. Pin: the owner of a record is the authenticated JWT `sub`, never a body field. Chunk GET by hash is unscoped (`sites_router.ex:35-43`), so anyone can learn a hash. A first-writer-wins index keyed by hash can be squatted unless the writer is bound.
2. Pin: only that owner may add a friend wrap. Otherwise "a second, different wrap for the same friend is refused" lets a stranger fill a friend slot with junk first and lock the real share out.
3. Pin: the existence probe is a HEAD-class check. Under the Recrypt backend, `Store.has_chunk?/1` is `get_chunk/1` (`recrypt.ex:90-95`), which pulls the whole ciphertext and outboard into the BEAM. Sending a GiB recording through that path causes an outage.
4. Pin which store "already holds" the hash. The Local backend answers from `sites_root` and Recrypt answers from the door. The contract must name one.
5. Pin: wraps are opaque bytes with a size cap. Registering an identical wrap again is success. A different wrap for the same slot is a conflict. Nothing may parse the wrap in a way that needs a private key.
6. Refuse: any route or return value carrying a data key or a scalar, any IdentiKey call from this service, and any bytes of the recording in the index (living spec "Hosts store hashes, not bytes").
7. Pin who may read wraps. Friend XIDs form a social graph, so reads should go only to the owner or the named friend.
8. Say plainly that `owner_xid` and the wrap's recipient are claims. Mjolnir cannot check that a wrap opens under the owner's X25519 without the scalar.
9. Tradeoff: the ciphertext is confirmed on B2 before the ack. The owner wrap is the only way back to the data key, and it would sit on host disk until the backup runs. If the disk is lost before the backup, the recording cannot be read. Either the client keeps its own copy of the wrap or the record goes through the door to B2. The contract must pick one and say which.
10. Concurrency: two registers for one hash must be serialized through a single writer, using an atomic write+fsync+rename like `Store.write_atomic/2`.

## Steelman against my take

The take pushed for friends to read their own wrap from the index. The contract refuses that, and it is right to. A friend read keyed on `friend_xid` would need Mjolnir to authenticate an XID. It cannot do that today: a JWT `sub` is not an XID, and design §9 forbids treating a fingerprint or `user_id` as one. If the friend's wrap were readable through the index, that read path would go to whoever claims the friend XID. Having the owner hand off the wrap out of band leaves the index fully owner-scoped. The cost falls on product convenience, not on confidentiality or exit.

The take also floated sending the wrap through the door to B2 so it would be as durable as the ciphertext. The contract chooses "the client keeps it, and the row is backed up daily". That is the cheaper choice and is still safe under the exit test. The wrap is small, and it is encrypted to the owner's own X25519. The owner already holds it at the moment they register. A row lost from Mjolnir disk before the backup runs costs convenience, not data. Going through the door would only add a second mutable-pointer problem.

The remaining owner-slot squat is a real residual. It is narrow, though. An attacker needs a valid `:user` JWT and the hash during the gap between the PUT and the register, and the client only shares the hash with friends after registering. Recovery is a new ciphertext under a new hash. That is acceptable until XID proof exists.

## Exit test

The owner leaves with the ciphertext, which is fetchable by hash and confirmed on B2, and with the owner wrap. They hold the wrap themselves, and their own `sub` can read it. The private key never leaves their machine, and no step needs operator permission. **Passes.**

## Notes for the implementer (not blocking, not contract changes)

- **CBOR decode.** Mjolnir has no CBOR dependency today (`mix.exs`; `edge_keys.ex` matches fixed prefixes by hand). The shape check needs a small decoder or a new dep. It must reject trailing bytes and non-map tops, and it must not decode anything beyond the map's top-level keys.
- **Probe outside the GenServer call.** Run the HEAD before `GenServer.call`. Do not run it inside the call, or a slow door would block `put_manifest`/`put_ots` for up to the Req timeout. The existence check only has to happen-before the write, because blobs have no delete route.
- **Hash before path.** Validate `:hash` as base58 Blake3 before joining it onto `recordings/`. That follows the living requirement "Object identifiers are hashes before any filesystem access". `Store.validate_hash!/1` (alnum only) is enough to stop traversal but not to reject a wrong length.
- **Router body.** `/api/sites` skips body parsing (`router.ex:2013`), so the JSON routes must read and decode the body themselves. Cap it well below the 64 MiB chunk limit.
- **Status codes.** Refusing a non-registrant (as opposed to returning an empty list) reveals that a hash is registered. Since the blob itself is already probe-able by hash, that leak is negligible. Pick 403 vs 404 once and test it.
- **Friend fan-out.** Each friend add rewrites the whole JSON row, and the list has no bound. Only the owner can grow it, so this is self-inflicted. A soft cap is still cheap to add.
