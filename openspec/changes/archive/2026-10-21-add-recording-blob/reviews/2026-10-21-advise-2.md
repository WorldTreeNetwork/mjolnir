## Blind take (written before design.md / tasks.md were opened)

Sources: packet Why, `openspec/specs/blob-store/spec.md`, `proposal.md`,
`sites_router.ex`, `sites/store.ex`, `sites/storage/recrypt.ex`,
identikey-core `managed-custody` Friend rewrap.

1. Pin: owner XID comes from the authenticated principal (`:user` JWT sub), never the body. A Sites token or `:public` caller registers nothing. A new route with no `:fp` silently skips `enforce_token_binding` (sites_router.ex:92-96), so the route must check the principal itself.
2. Pin: the owner slot is keyed `(hash, owner_xid)`, not `hash`. A ciphertext hash is public (GET by hash is unscoped), so first-writer-wins on `hash` lets anyone squat a recording.
3. Pin: "the store holds the hash" is a HEAD (or local `File.regular?`), not `has_chunk?` — the Recrypt backend's `has_chunk?` is a full GET of ciphertext plus `.obao` (recrypt.ex:90-95).
4. Pin: the index is truth on the filesystem under the sites root with `write_atomic` (fsync + rename, store.ex:172-187). Postgres, if any, is a derived index, per the Sites contract.
5. Pin: friend wraps are added only by the authenticated owner, keyed by friend XID; the same bytes are a no-op, different bytes are refused. A wrap is opaque, size-bounded, and format-checked (`x25519-xchacha20poly1305` shape), never decrypted.
6. Pin: reads of wraps go only to the owner (all of them) or a named friend (their own). Wraps are not secret, but the share graph is metadata.
7. Refuse: any route that returns a data key or scalar, any call into IdentiKey, any client-supplied recipient public key, any second blob layout.
8. Refuse: wrap replacement in place. Rotation means new ciphertext and so a new hash; unshare is index-only and cannot recall a wrap the friend already fetched — say so.
9. Tradeoff: Mjolnir cannot verify that a friend wrap opens the same data key as the owner wrap, so a bad wrap is accepted. That is the price of never holding a key; the friend finds out on decrypt.
10. Exit test: ciphertext by hash plus a wrap to the user's own X25519 leaves with the user; the index must be exportable by the owner (a GET of their records is enough).

## Steelman

`conn.assigns.user_id` is the field the codebase uses for identity everywhere. For a verified JWT it is `sub`, and `reject_reserved_sub` (`auth.ex:262-269`) makes sure no JWT can claim `localhost`, `capability`, or `sites_token:*`. So names cannot collide across principal kinds. The honest recording client is a person on their own machine who ran `mj login`. That is a `:user` principal with a stable `sub`. Biscuits exist so a guest can run exec and similar operations. Nobody intends to record through a biscuit. Under that reading, B1 is closed for every caller that matters.

I agree about the honest client. The contract does not say that, though. The spec defines "principal" as `conn.assigns.user_id` and admits any non-empty value. An implementation that follows the spec will therefore inherit the values below.

## Finding that blocks

### C1. `user_id` is not a per-holder identity for three principal kinds that reach `/api/sites`

`/api/sites` is forwarded without `require_scope` (`router.ex:130`). `SitesRouter` checks only the Sites-token fingerprint binding, and only on routes with `:fp`. So every kind `Auth` assigns reaches the new routes, with these values (`auth.ex`):

| Kind | `user_id` | Problem |
|------|-----------|---------|
| `:capability` (biscuit) | `"capability"` (line 216) | **The same constant for every biscuit holder.** Biscuit A registers `{h}`. Biscuit B is then "the registering principal": it can read A's friend graph and squat A's friend slots with junk. That is the B1 friend squat and the N2 leak again. |
| `:operator` | `"localhost"` (line 73) | Shared by every operator call. Less important, because the operator is root and can read the file anyway. |
| `:sites` | `"sites_token:<id>"` (line 147) | Different for each token, not each owner. If the token is rotated or revoked, the owner can no longer read their own wrap or add a friend. A stranded owner wrap fails the exit test: getting their data back would need operator permission. |
| `:user` (JWT) | `sub` | Stable, unique, and reserved names are rejected. **This is the only kind the binding is real for.** |

The existing Sites routes get away with not checking principal kind because what they accept authenticates itself: a chunk by its Blake3, a manifest or HEAD by its signed envelope. The recording index is the first Sites route whose only authority is the caller's principal. It cannot borrow the reasoning the other routes use.

**Fix (one paragraph and one scenario):** register, friend add, and GET SHALL require `principal_kind == :user` and SHALL bind the row to the JWT `sub`. A `:capability`, `:operator`, `:sites`, `:ceremony`, or `:public` caller SHALL be refused before any probe or write. Add the scenario: a biscuit caller (and a Sites-token caller) is refused on register, friend add, and GET, and no row is written. If the author wants Sites tokens in v1, they must say whether the binding is the token id (stated rotation strands the row) or `token.identikey_fp` (stable, but then the spec must say it is a fingerprint and not an XID, per design §9). My recommendation is `:user` only.

## Owed but not blocking

- **N4. First-wrap-wins needs an exclusive compare-and-write.** `write_atomic` (`store.ex:172-187`) makes a replace atomic. It does not make an insert exclusive, and every writer uses the same `final <> ".tmp"` name. Two registers racing with different wraps can both read "no row" and both rename. Both get 2xx, and the second wrap silently replaces the first. That breaks the spec's "a different owner wrap SHALL be refused", and the race is exactly the owner-squat window. Pin that the read-check-write goes through one serializing process (the `Store` GenServer, as `put_manifest` already does) or uses an exclusive create, and add a test for concurrent different-wrap registers. Also name the path, for example `<sites_root>/recordings/<hash58>.json`, outside `blob/b3/`, so the index file can never be mistaken for a blob key.
- **N5. Shape floor on the wrap.** identikey-core `encode_wrap` (`identikey-keys/src/encapsulation.rs:754-768`) produces a CBOR map with `alg = "x25519-xchacha20poly1305"`, 32-byte `recipient`, 32-byte `ephemeral`, 24-byte `nonce`, 48-byte `ciphertext`, and `epoch`. Today a raw 32-byte data key fits inside 1..4096 bytes. A buggy client could register it, and the GET would then return a data key. Checking the CBOR structure, the `alg` tag, and the 48-byte ciphertext, without decrypting, makes "this service never returns a data key" true by construction instead of depending on the client.
- **N6. Durability is not symmetric.** The ciphertext is on B2 when it is acked. The row reaches B2 at the next daily `mjolnir-sites-backup` run. One sentence: until then, the client keeps its owner wrap.
- **N7. Two semantics to state.** (a) `owner_xid` is what the registrant claimed, not a proof. The self-friend check compares against that claim. (b) The same owner wrap from a *different* principal is refused, not treated as success. (c) This index does not deliver a wrap to the friend. A friend receives their wrap from the owner, because Mjolnir cannot authenticate an XID (design §9). Without that sentence, the next change will assume the index is the friend's delivery path.

## Outside this change (for the conductor to bead)

`SitesRouter` does not gate on principal kind. A biscuit or the operator can call every Sites route. The signed envelopes contain the damage on the existing routes, so this is not this change's problem to fix. It does deserve its own bead, together with the earlier side note that the Recrypt `has_chunk?` downloads every chunk it checks during snapshot publish.

## What would flip this to accept

C1 written into design §3 and the spec delta: principal kind `:user`, bound to `sub`, all other kinds refused, plus the two-biscuit scenario. N4 to N7 each need one sentence, and N4 also needs a task line. The owed boxes are on tasks.md.
