# Advise: add-recording-blob

> **ADVISE:** send-back
> **READER:** opus-arch-review
> **SPAWN:** .spawns/add-recording-blob-advise-1792620951-73974-5a0b1b65

## Blind take (written before design.md / tasks.md were opened)

Sources: proposal Why, `openspec/specs/blob-store/spec.md`, `sites_router.ex`, `sites/store.ex`, `sites/storage/recrypt.ex`, identikey-core `managed-custody` Friend rewrap.

1. **Pin writer authority.** Register is first-writer-wins and a second different wrap is refused. If any caller can register, anyone who learns a hash can squat the owner slot or a friend slot with junk. Owner wrap must be bound to an authenticated owner XID; friend wraps may be added only by that owner.
2. **Pin the existence probe.** `Store.has_chunk?` → `Recrypt.has_chunk?` → `get_chunk`, which GETs the whole ciphertext plus `.obao` into RAM (`recrypt.ex:89-95`). For a recording that is a full download per register. Need a HEAD probe.
3. **Pin the upload route.** Door binds only `10.200.0.1:7222`. An owner's machine reaches `PUT /api/sites/blob/:hash`, which buffers up to 64 MiB in RAM (`sites_router.ex:602-603`) and is framed. Say which route a recording uses and what size it supports.
4. **Pin the wrap shape.** Mjolnir cannot verify a wrap. Pin the algorithm tag (`x25519-xchacha20poly1305`, identikey-keyspace-v1), a byte ceiling, the recipient XID stored beside it, and that a byte-identical re-register is success.
5. **Pin wrap durability.** A lost owner wrap makes the recording unreadable to anyone. The wrap record must be fsync'd atomic on the filesystem (Postgres only as a derived index) and inside a backed-up root.
6. **Refuse** any route that returns a data key or scalar, any Mjolnir call to IdentiKey, any wrap Mjolnir creates.
7. **Refuse** a second hash or a parallel blob path; the key is base58 Blake3 of the ciphertext.
8. **Pin read authority.** The friend list is social-graph metadata. Owner reads all wraps; a friend reads their own.
9. **Pin revocation honesty.** Removing a friend wrap is not revocation; the friend may hold the data key and ciphertext is fetchable by hash.
10. **Tradeoff.** Wraps in a Mjolnir FS index (mutable, cheap, needs its own backup) vs. wraps as door blobs (B2-durable, but still need a mutable pointer). I would take the FS index under the sites root, which the B2 timer already copies, and say so.

## Steelman

The author's position is coherent. The trust model is that Mjolnir never holds anything that decrypts. Under that model, an unauthenticated wrap row cannot leak a recording. A forged wrap is useless without the data key. A forged friend wrap made from junk gives the friend nothing. Confidentiality survives every finding below, so in that sense the residual risk is the same as an unscoped chunk write. First-wrap-wins is the cheapest rule that makes the row immutable without needing XID proof, which Mjolnir cannot do today (§6 is correct that a Sites fingerprint is not an XID). Not calling IdentiKey and not checking the wrap decrypts are both right. They keep Mjolnir out of the custody path, as the packet requires.

I agree with all of that. The send-back is about integrity, availability and durability. It is not about confidentiality.

## Findings that block

### B1. First-wrap-wins without writer binding is a squat, not "the same residual risk"

The chunk write is safe unscoped because it is **deterministic**. Only one byte string can live at `{h}`, so the first writer and the honest writer write the same thing. The index is the opposite case. The first writer picks the wrap and the owner XID, and every later different value is refused **forever** (spec lines 7, 25-30). That makes the comparison in design §6 wrong.

Any principal that reaches `/api/sites` can do this: any Sites token for any fingerprint, any JWT, any biscuit, or operator loopback (`auth.ex:53-88`).

- **Owner squat.** The attacker learns `{h}` (the ciphertext GET by hash is unscoped, and hashes travel to friends) and registers before the owner. The owner's real wrap is then refused. The client has a window between its PUT and its register call.
- **Friend-slot squat (the cheap one).** After the owner registers, anyone holding `{h}` can POST `/recordings/{h}/friends` with friend XID `B` and junk. When the owner later stores the real rewrap for `B`, it is refused. `B` can never be given this recording unless the owner re-encrypts and re-uploads under a new hash.
- **Mislabelled ownership.** `GET` reports `owner_xid` as fact, but nothing proved it. Any consumer that trusts that field is trusting the first caller.

The fix is small and needs no XID proof. Store the authenticated principal (`conn.assigns.user_id`, e.g. `sites_token:<id>` or the JWT `sub`) on the owner row. Require the same principal for a friend add. This closes the friend squat completely. The owner squat stays as a stated residual until XID proof exists, and the spec should say so in one sentence rather than calling it equivalent to the chunk route.

### B2. "Already in the blob backend" must not mean `Store.has_chunk?`

In production the backend is Recrypt (`MJOLNIR_RECRYPT_STORAGE_URL`). There, `has_chunk?/1` calls `get_chunk/1`, which pulls the whole ciphertext **and** the `.obao` into BEAM memory through Req (`recrypt.ex:89-95`). Every register and every friend add would download the recording. Any authenticated caller who knows a hash could repeat that call to amplify door, B2 egress and BEAM memory.

The door already serves `HEAD /storage/blob/b3/{hash}` (living spec, "First face is HTTP"). Pin that the probe is a HEAD against the door, or `File.exists?` for Local, and never a GET.

Side note, not this change's to fix: `POST /:fp/:name/snapshot` already calls `has_chunk?` once per manifest entry (`sites_router.ex:127-130`), so a Recrypt-backed publish downloads every chunk it checks. That is worth its own bead.

### B3. The index has no substrate

Nothing says where a row is written. This matters more than for most indexes because the owner wrap is the **only** server-side way back to the data key. If the client did not keep it, a lost row means the recording is unreadable by anyone, while its ciphertext sits safely on B2. The project rule (CLAUDE.md "Postgres Sidecar") is that the filesystem is the source of truth and Postgres holds derived, rebuildable indexes. `:pg_enabled` is false in test.

Pin: atomic write plus fsync plus rename (the `write_atomic` already in `store.ex:172-187`) under the sites root, so `mjolnir-sites-backup.timer` copies it to B2. Postgres may only be a derived index. This also meets the exit test: the owner leaves with their wrap and their ciphertext, both of which are on disk and on B2.

## Owed but not blocking

- **N1. One recording = one blob, ≤ the 64 MiB body.** State it in the spec. A larger recording would be chunked, and then the index ought to key a manifest hash, not one chunk hash. Make that a non-goal now so nobody quietly keys a single chunk.
- **N2. Read authority.** Either limit `GET` to the registering principal, or state that the index is readable by any authenticated caller like the ciphertext is. Pick one. The friend XID list is new social-graph metadata, which the ciphertext route never exposed.
- **N3. Owner wrap-target rotation.** managed-custody says that changing `c2_wrap_recipient` nulls the seal. After that, the stored owner wrap points at a key the owner may no longer hold, and first-wrap-wins refuses a replacement. Saying "out of scope; re-encrypt to a new hash" in one line is enough. Once B1 exists, the same principal could be allowed to supersede, but that belongs to a later change.
- **N4. Optional.** Store SHA-256 of each wrap beside it. IdentiKey's rewrap begin binds that exact digest, and the consent log records it, so an operator can join the two logs without moving wrap bytes.

## What would flip this to accept

B1 to B3 written into design.md and the spec delta, each with a scenario:

- a different principal's friend add is refused;
- the register probe does not GET the ciphertext;
- a row survives a restart and sits under the sites root.

N1 to N3 each need one sentence. Owed boxes are on tasks.md.
