## Independent take — recorded before reading design, tasks, or delta

1. Pin the live-site boundary: a file miss stays on the original Host; only unbound names take the existing 307.
2. Pin existing-file precedence and preserve directory indexes, precompression, and the keep-alive Host check.
3. Pin an explicit miss decision table, including whether a snapshot 404 wins over `fallback = false` under the steered ordering.
4. Pin missing-target behavior: selecting `index.html` cannot turn a missing file into an empty successful response.
5. Refuse arbitrary fallback paths; validate the known key while continuing to ignore unrelated TOML keys.
6. Pin the complete policy path from operator TOML through publish to materialization; the deploy parser currently requires service fields.
7. Pin policy ownership and snapshot consistency across publish, rollback, restart, and rematerialization; derived disk state needs a recoverable source.
8. Refuse exposing policy through ServeDir or bypassing root containment when locating the park snapshot.
9. Pin fallback HTTP behavior for HEAD, methods, validators, compression, and cache headers; the current helper synthesizes a GET.
10. Accept local materialized park chrome as a latency/availability tradeoff if unavailable chrome yields an empty 404 without redirects or recursive fetching.

## Comparison and steelman

Reviewed the current `design.md`, `tasks.md`, `specs/sites-serve/spec.md`, and
`steer.md` after persisting the ten lines above. There is no living
`openspec/specs/sites-serve/spec.md`; this is an ADDED capability. This reader
did not author the Grok proposal.

The author answers the central concerns well: fallback runs only after a
snapshot miss, explicit SPA beats a local 404, explicit false suppresses it,
policy stays outside ServeDir, and park chrome is local data with no redirect.
The delta's “when policy is unset” resolves the terse steer's precedence
ambiguity coherently. These decisions should stand.

The strongest case against my lifecycle concern is that a sibling policy can
be deliberately site-wide and independent of snapshots. Likewise, caching
park's directory avoids adding backend availability to every file miss.
Neither choice needs a new framework or mandatory snapshot-schema change.
But the author must state those semantics and their recovery behavior: the
present text also permits a snapshot-scoped implementation, and “cache that
directory handle” leaves refresh and recovery undefined. The items below ask
for observable contracts, not a competing design.

## Owed before act

### R1 — High: Complete the policy's publish and recovery contract

`design.md:35` names a local sidecar and `design.md:42` names TOML parsing,
but neither connects the two. The actual `mj sites publish` path is Rust
(`native/mjolnir_client/src/sites.rs:628`): it publishes a directory using a
manifest/chunks/HEAD protocol. Both manifest implementations currently have
no fallback field (`native/mjolnir_client/src/sites.rs:84`,
`lib/mjolnir/sites/manifest.ex:67`). Server materialization receives only
identity, site, and snapshot hash (`lib/mjolnir/api/sites_router.ex:417`).
Changing `Deploy.Manifest` alone cannot carry this policy to that host.

Pin where TOML is discovered when publishing a build-output directory, how
site-only TOML avoids service-only required fields, the authenticated wire
and durable storage path, and defaults for older publishers. If signed
manifest bytes change, pin Rust/Elixir signing compatibility. Choose whether
policy belongs to a snapshot or the site; define removal/reset, failed or
concurrent publishes, rollback, and rebuild behavior. Materializer explicitly
treats its tree as disposable and flips `current` atomically
(`materializer.ex:23`, `materializer.ex:145`); a separate sidecar rename does
not by itself make policy and snapshot one consistent selection. The gateway
also holds a resolved snapshot for a connection (`sites_serve.rs:177`), which
must be accounted for if policy is read independently.

Add an end-to-end TOML-to-gateway scenario plus reset, failure, rollback, and
rematerialization cases matching the chosen ownership model.

### R2 — Medium: Give the park cache a refresh and failure contract

`design.md:50` resolves park once and caches its directory handle without a
lifetime or invalidation rule. Existing alias lookup is an HTTP call, not a
cache (`native/mjolnir_gateway/src/sites.rs:80`), and canonical snapshot
resolution pins a snapshot path (`sites_serve.rs:81`). A cached successful
resolution can serve old chrome after republish, then fail after pruning; a
cached miss can hide park forever if park is deployed later.

Pin cache scope, bounded refresh/retry or invalidation, alias rebind behavior,
and response during lookup failure. Reuse validated SiteRef components and
root containment; read park's file directly without invoking its fallback
chain. Cover absent-then-published park, republish/prune, lookup failure, and
an escaping `current` symlink. A bounded stale window is a reasonable choice
if explicitly stated; no new cache subsystem is required by this review.

### R3 — Medium: Close fallback target and HTTP response gaps

The SPA scenario requires `index.html` to exist, while the order also selects
explicit `404.html` unconditionally (`specs/sites-serve/spec.md:30`). Neither
defines what happens when the selected file is absent or unreadable. Pin
that outcome, and invalid known policy values, instead of leaving the
implementer to choose between park, empty 404, error, or accidental empty 200.

Carry the original method through fallback selection: the current helper
creates a fresh GET and forwards only Accept-Encoding
(`sites_serve.rs:282`). Specify bodyless HEAD, preservation of non-miss
responses such as 405/206, and a coherent conditional/range policy for SPA
versus forced-404 bodies. Preserve precompression and the design's HTML
revalidation rule even when a missing URL resembles an immutable asset.
Tests should cover missing explicit targets, HEAD, compression, conditional
requests, and a miss under `/_app/immutable/`; a full new HTTP subsystem is
unnecessary.
