5. PIN the ordering adopt → `domain set` → `certs issue`. `Certs.issue` is HTTP-01 through the gateway webroot and `POST /api/certs/issue` resolves `app_for_domain(fqdn)` first, so the cert cannot be issued before the registry row and custom_domain exist. `/etc/mjolnir/certs/` has no `buzz.identikey.me` today.
6. PIN what adopt writes. `Registry.Entry` enforces `app_name`, `release_snapshot`, `updated_at`; `Gateway.Routes` needs `custom_domain` + `port` + `service_vm_id`; `Policy.App` gates on `owner_id` (nil → localhost only). An adopted hive needs a real `release_snapshot` (take one at adopt time — it is also backup #1) and a new field the orchestrator checks before cutover ("refuse redeploy of adopted stateful app" is not expressible with today's struct).
7. CONCERN the author must answer: `secrets_mode: managed` and "`mj snapshot create` is the backup verb" do not compose today. The escrow passphrase is keyed by `vm_id` off the data volume; `VM.spawn/1` mints a fresh UUID for every spawn including `--snapshot` (`vm.ex:220`); a real kill deletes the escrow (`vm.ex:1822`); the guest refuses `init` when `secrets.luks` already exists (`secrets.rs:263`) and `open` with a fresh passphrase fails. So restoring the hive from its own backup ends in `secrets_unlock_failed` and a relay unit that never starts (it is wanted by `mjolnir-secrets.target`). `docs/secrets-architecture.md` line ~300 ("clone rootfs from snapshot → escrow HIT") is only true for same-id dormancy wake. Restore needs a named path: copy the escrow file to the new id before spawn, an `escrow_from` on spawn/adopt, or plain-rootfs env for B0.
8. SCOPE: `POST /api/vms/:id/secrets` is new guest-agent + Elixir work (`inject_secrets` delivers entries only on create; a post-spawn write needs a `push_env`-style op into the mounted volume). `POST /api/vms` already accepts `secrets` + `secrets_mode: "managed"` at spawn (`router.ex:372`). B0 spawns the hive once by hand; the new endpoint is rotation convenience, not a B0 dependency. Cut it or mark optional so the change does not carry a cross-compile.
9. TRADEOFF: LUKS-managed `.env` vs plain `EnvironmentFile=` on the rootfs, for a VM whose Postgres data directory and MinIO objects are plaintext on the same subvolume. Managed buys: a leaked or B2-synced snapshot lacks the DB password, MinIO creds and any relay signing key. Cost: item 7. I would keep managed only with the restore path written down; otherwise plain env at `0600` is the honest B0 and the LUKS story lands with B1's `btrfs send`.
10. Snapshot semantics are fine as amended: `do_snapshot` is guest `sync` → pause → btrfs snapshot → resume (`vm.ex:3120`), crash-consistent for PG/Redis AOF/MinIO. `freeze` additionally 409s `secrets_quiesce_required` on managed VMs (`memory_snapshot.ex:266`), so it is doubly not the backup verb. Host has 23 GB available for a 4 GB guest; 27 VMs running today.

## Steelman against the take

- **On R1 (`EnvironmentFile=`).** The author could say the deploy path already
  uses `/run/mjolnir/secrets.env` and works. It does — through
  `ExecStart=/bin/sh -lc` plus the agent-installed
  `/etc/profile.d/mjolnir-secrets.sh`, never through `EnvironmentFile=`.
  I ran a transient unit on the host (systemd 255): an `export FOO='bar'`
  line under `EnvironmentFile=` yields an empty `FOO`, a bare `PLAIN=1`
  line loads. The agent renders `export KEY='v'` (`secrets.rs:972`) at
  `0640 root:agent`, and the Block image runs as `buzz:buzz`. As written,
  `buzz-relay.service` starts with no `RELAY_URL`, or cannot read the file
  at all. Fix is wording, not design: copy the deploy unit's `sh -lc`
  pattern and run as root or put `buzz` in group `agent`.
- **On R2 (restore).** "Snapshot is the backup" is honest for the *data*;
  the design never claims secrets restore. But the delta makes
  `mj snapshot create` the backup verb, and `docs/secrets-architecture.md`
  draws "clone rootfs from snapshot → escrow HIT" as if it were generic.
  It is not: that arrow is same-id dormancy wake. A fresh `mj spawn
  --snapshot` mints a UUID, misses escrow, and the guest refuses `init`
  over an existing `secrets.luks`. One runbook paragraph closes it; a
  send-back would not change any decision.
- **On R4 (D3 text).** The task box is checked with the correct fact, so
  act is not misled. Only the design narrative is stale. Author-owned;
  I cannot write design.md from this packet.
- **On R5 (endpoint scope).** The author's reason for the endpoint is
  right: `mj secrets` is redeploy-only. But `POST /api/vms` already takes
  `secrets` + `secrets_mode: "managed"` at spawn (`router.ex:372`), which
  is the B0 path for a hand-spawned hive. The post-spawn endpoint needs
  a vsock `push_env` op (today `push_env_content` is reached only over
  Iroh, `iroh.rs:512`) plus a route: a guest-agent cross-compile that
  B0 does not need. Keep it as optional; do not block the hive on it.

## Findings (ranked)

**R1 — `EnvironmentFile=/run/mjolnir/secrets.env` loads nothing.**
The agent writes `export KEY='value'` lines; systemd 255 ignores the
`export` form under `EnvironmentFile=` (tested on the host). File mode
is `0640 root:agent`; the relay image runs as `buzz:buzz`. Units must
start via `/bin/sh -lc 'exec …'` (profile.d sources the file) and run
as root or as a user in group `agent`. Fixed in tasks.md; design.md D4
still says `EnvironmentFile=` and should be corrected by the author.

**R2 — restore from the backup verb loses the managed secrets.**
Escrow is keyed by `vm_id` (`SecretEscrow`), `VM.spawn/1` mints a new
UUID for `--snapshot` spawns (`vm.ex:220`), a real kill deletes the
escrow (`vm.ex:1822`), and the guest refuses `init` when `secrets.luks`
exists (`secrets.rs:263`). Relay unit is wanted by
`mjolnir-secrets.target`, so it never starts on a restored VM. Added a
restore-runbook task: before `mj spawn --snapshot <name>` root copies
`/var/lib/mjolnir/escrow/<old_id>` to `<new_id>` (or removes
`var/lib/mjolnir/secrets.luks` from the restored subvolume and
re-supplies `secrets` at spawn). Never `mj kill` the hive without a
fresh snapshot and an escrow copy. Not blocking; must be written before
the snapshot task is checked.

**R3 — extraction list is incomplete.** `skopeo inspect --config` of
`ghcr.io/block/buzz:main` (built 2026-09-10T22:49Z, rev `092c6a7`):
Entrypoint `/usr/local/bin/buzz-relay`, User `buzz:buzz`, WorkingDir
`/var/lib/buzz`, env `BUZZ_WEB_DIR=/srv/buzz/web`,
`BUZZ_ADMIN_WEB_DIR=/srv/buzz/admin-web`. Copy `/srv/buzz/*`, create
the `buzz` user and `/var/lib/buzz`, and confirm the binary is not
linked against a newer glibc than Ubuntu 24.04 ships. Fixed in tasks.md.

**R4 — design.md D3 still says Linode.** Authoritative Cloudflare
(`violet`/`osmar.ns.cloudflare.com`) answers `identikey.me A
45.76.77.97`; `buzz.identikey.me` CNAME apex resolves to the gateway
today. tasks.md has the right fact and a checked ASK. Design narrative
is author-owned. An explicit `buzz` record remains a good pin so the
hive does not follow the apex; left as a low-priority ASK.

**R5 — `POST /api/vms/:id/secrets` is not a B0 dependency.** See
steelman. Marked optional in tasks.md; the B0 path is spawn-time
`secrets` on `POST /api/vms`.

**R6 — MinIO binary provenance.** Community MinIO binaries have been
withdrawn from some channels this year. If the download is gone,
extract `minio/minio` from the compose file's pinned image with the
same `skopeo` path. Verify at act time; not blocking.
