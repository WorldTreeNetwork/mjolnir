## Blind take

I wrote this before I opened steer.md, tasks.md, or the earlier reviews. It is on disk in that order.

1. **Pin:** Reconcile from any caller, including the `Health.Monitor` tick at `monitor.ex:44`, attaches a record whose scope is active and does not resume it. `build_plan/1` still reads "not registered + rootfs exists" as `:resume`. The spec guards that only at startup and only for scopes the watcher saw die.
2. **Pin:** what `VM.terminate/2` does to the scope when the BEAM stays up and one VM GenServer crashes. The ADR only covers orchestrator shutdown (detach) and `VM.stop` (kill). If a crash detaches, the next Monitor tick resumes into a live unit name. That is a failure. Ten ticks retire a living guest to `:failed`, and the next restart stops it.
3. **Pin:** liveness means CH is in the scope, not only that the scope is active. A scope stays active while any member lives, so a lingering virtiofsd keeps a dead-CH scope "alive". The attach row would then register a GenServer with no VMM, and Reconcile would skip it for good.
4. **Pin:** `clean_stale_sockets/1` today removes every `.sock` and `_vsock` entry. An attached guest's CH API socket, vsock UDS, and virtiofsd sockets are what attach reconnects through. Ordering alone is not enough. Those paths have to be named as protected.
5. **Refuse:** "watcher record unreadable + unit gone → wait, and it does not count toward retirement". The spec's own liveness rule already makes "unit gone" a death. The record is never needed for that decision, so the wait buys no safety. It also contradicts "SHALL NOT stay unresolved forever".
6. **Refuse:** ADR line 9 putting the TAP in the scope. The spec says the TAP is a netdev keyed by the scope id and not a member. The two contract documents disagree.
7. **Tradeoff:** a named transient unit gives a structural mutex. systemd refuses a second `mjolnir-<id>.scope` while one is loaded, so a double VMM is impossible by construction. The cost is that every "start refused" has to be classified as a liveness signal (attach), not as a boot failure (retire).

## Steelman against my take

The direction is right and I'm not offering a competing design. The steer's central claim holds up: one restarter, a watcher that only witnesses, systemd as the authority for liveness, and the unit name as the single child id. Under that claim, take item 7 is the strength of the design, not a cost. Take items 3 and 4 fairly belong to `mjolnir-uepi.3` and `mjolnir-uepi.4`:

- **Item 3.** virtiofsd exits when its vhost-user frontend disconnects, and the uepi.1 probe saw both processes die together on SIGHUP. In practice a scope whose CH is dead goes inactive on its own. One sentence would make that a contract, but it isn't a missing row.
- **Item 4.** "SHALL do both before deleting sockets or TAPs" already implies the delete is selective. An implementer who unlinks an attached guest's API socket fails the first reattach test.

Items 1–2 and 5 survive the steelman. Both are the same class as advise-2 S3: the spec, read literally, ends with a living guest being stopped or never resumed by the change's own rules.

## B1. The BEAM-up path for a living scope with no GenServer (blocking)

The previous ADR body had two sentences the revision dropped: "'Not in the registry' is not 'dead' once the VMM can outlive the BEAM", and "Reconnect fails but the process is still alive: do not cold-boot … retry attach." Nothing in the spec replaces them. Every row in the restarter requirement is phrased "on startup", and the one guard against a second boot, "only after that scope is inactive", applies only to "a scope the watcher saw die".

Concrete path. While the BEAM is up, a VM GenServer exits for a reason other than `VM.stop` and other than application shutdown, for example a raise in a `handle_info`. Today `preserve_rootfs?/2` returns `true` for every non-`:normal` reason, and an implementer can reasonably read "preserve" as "detach". The scope keeps running. No watcher event fires, because the scope did not change state. Within 30 s `Health.Monitor` calls `Reconcile.run/0`. `build_plan/1` sees a `:running` record that isn't in `VMRegistry` and has its rootfs, and returns `{:resume, …}`. `VM.resume/1` asks systemd for `mjolnir-<id>.scope`, which already exists, and the start is refused. `record_failure/2` counts it. Ten ticks later, about 5 minutes with `reconcile_max_failures: 10`, the record is `:failed`. The next orchestrator restart applies "Failed guest stays down" and stops a guest that was healthy the whole time.

The unit-name mutex is what stops the double VMM, and that part of the design works. The spec still has to say what Reconcile does when the mutex trips.

**Owed:**

- A requirement. Reconcile, from any caller (startup or the `Health.Monitor` tick), SHALL attach, not resume, a `:running` record whose scope systemd reports active. A refused scope start because the unit is already active SHALL NOT count toward resume-failure retirement.
- One sentence on `terminate/2`. Name which exits detach (orchestrator shutdown) and which stop the scope (`VM.stop`, and also a crash of that VM's GenServer, if that is the choice). Either answer is acceptable, but it has to be pinned. The first bullet makes "crash detaches" safe.
- A scenario. Given the BEAM is up and a VM GenServer exits while its scope stays active, when Reconcile runs, the guest is attached, it is not booted, and `resume_failures` does not grow.

## B2. An unreadable record with the unit gone contradicts "not unresolved forever" (blocking, one line)

The fail-safe requirement says an unreadable watcher record "SHALL NOT count toward resume-failure retirement", and that "guests whose unit is gone wait for a readable record or a confirmed death". The restarter requirement says a guest that cannot be classified "SHALL back off using the existing resume-failure limit and SHALL NOT stay unresolved forever." With the record unreadable and the unit gone, neither "confirmed death" row applies. The Liveness rule needs "the record says active", and the no-entry scenario needs a readable record. That guest therefore waits and never counts, so it stays unresolved forever. That breaks the second SHALL. Concrete case: a host reboots with a corrupt watcher file, and every `:always` guest stays down until someone repairs the file. Nothing in the spec says who repairs it.

The wait buys no safety. With the unit gone there is no living VMM to collide with, and the unit-name mutex covers a race anyway. The record only supplies exit status, which the spec already allows to be "unknown".

**Owed** (pick one):

- (a), recommended: a `:running` record whose unit is gone or inactive is a death with unknown exit status, whether or not the watcher record is readable, and is handed to Reconcile's plan.
- (b): keep the wait, but count it toward retirement. Then make the "`:failed` with a living scope → stop" row unreachable from that path. It already is, because the unit is gone.

Add or adjust a scenario either way.

Otherwise a lingering `extra_mounts` virtiofsd keeps a dead guest "alive", it gets attached, and Reconcile skips it because it is registered.

## Not asked for

I'm not asking for a watcher record format, a D-Bus vs journal choice, a delivery channel, a record path, or a different convergence design. B1 is a requirement and a scenario, plus a sentence on `terminate/2`. B2 is one line.

## What accept would name

Once B1 and B2 land, the contract I would accept is `guest-lifetime` plus ADR 0014 as revised: a per-id scope under `mjolnir-vms.slice`, a watcher that only witnesses, systemd as the authority for liveness, the BEAM as the only restarter, attach for any active scope (whoever finds it), and cold resume through Reconcile's plan for any unit that is gone.
