## Blind take

Written before opening design.md, tasks.md, the delta, ADR 0011, or any prior review; inputs were the packet's Why, the living honor-being spec, and the three cited code files.

1. Pin the Forgejo write credential to the same public key and consented IdentiKey ssh_git device, preserving the friend's XID and VM ownership.
2. Refuse registration before nonempty xid and credential_id metadata exists; mint/1 currently persists only the public key before calling Forgejo.
3. Refuse treating the public git_signing boolean as consent to create a hosted write credential; ordinary signing and hosted registration need distinguishable prerequisites.
4. Pin repository scope and keep the Forgejo management token on the host; the guest should authenticate only with its injected tmpfs SSH key.
5. Pin registration failure recovery, including a remote key created before its returned ID is persisted; retain public-key lookup evidence until cleanup succeeds.
6. Refuse reporting revoke success when Forgejo access cannot be removed; a missing management token is not proof that no live key exists.
7. Pin revoke ordering as Forgejo delete, IdentiKey revoke, then opaque deletion, with retryable metadata retained on intermediate failure.
8. Pin respawn to a new device and key without copying private material, and require an explicit outcome for partial replacement failure.
9. Pin fresh-clone and push verification plus repeat bootstrap convergence; an existing checkout can otherwise retain the wrong origin despite URL rewriting.
10. Tradeoff: fail-closed registration and revocation can interrupt provisioning or respawn, but preserve accountable write access; signing-only development can remain available without remote authority.

## Comparison and steelman

The current [delta](../specs/honor-being/spec.md), [design](../design.md) Decision 5, and [tasks](../tasks.md) R1–R3 answer the blocking concerns. I did not open either prior review or adopt its verdict. The author family is Grok; this is the independent Codex/Astra reader named by the packet.

**Device binding and consent (take 1–3).** The delta's no-row scenarios and recovery requirement require IdentiKey metadata for the exact public key before Forgejo registration. Decision 5 and R1 bind that row to fresh A3 and the authenticated owner; the living spec already requires the friend's XID to equal VM ownership. Together these rule out merely checking that two arbitrary strings are present. Keeping ordinary `git_signing: true` signing-only until that binding exists is sufficient; a different public API is not intrinsically necessary. The implementation must enforce the trusted binding, including the mismatched-owner/key negatives already named in R1.

**Scope and custody (take 4).** A repository write deploy key is consistent with ADR 0011 when backed by the friend's consented device row. A separate Forgejo person would add identity machinery without strengthening that invariant. The delta pins the repository, injected private-key path, and absence of a guest Forgejo token. The same key can reasonably serve signing and SSH authentication; a Forgejo verified badge is outside the acceptance contract.

**Recovery and revocation (take 5–7).** The delta at lines 48–55 makes persistence precede registration, confines `:not_wired` to a grant that was never registered, and requires public-key recovery when the remote ID is lost. Decision 5 explicitly includes uncertain grants. Thus absence of an ID after timeout must not be interpreted as proof of no grant. R3 includes timeout, malformed success, and ID-persistence failure, with durable retry/cleanup and no forgotten grants. This is enough to direct an implementation without prescribing a distributed transaction. Decision 5 and the revised SHALLs supersede Decision 2's earlier broad missing-token language; they do not preserve a production bypass.

**Respawn and guest behavior (take 8–10).** The modified respawn requirement preserves new-device identity, per-friend ticket continuity, and Forgejo-first revocation. My concern about partial replacement does not require an atomic swap: a failed old-key delete may temporarily leave two accountable devices, provided failure is reported and recovery metadata survives. It must not erase the old row while its write grant survives. Bootstrap already selects the tmpfs key, pins host keys, and rewrites the advertised SSH user. It clones only when `.git` is absent, so live evidence should distinguish a fresh clone from a reused checkout and inspect the actual remote before pushing. General migration of arbitrary existing checkouts is not necessary to resolve these contract blockers.

## Evidence and implementation boundary

The inspected code still needs the work already recorded in R1–R3:

- `lib/mjolnir/git_signing.ex:76` registers during mint with public-key-only metadata; `:184` reads an optional XID and does not require the credential ID. `lib/mjolnir/api/router.ex:277` exposes signing as a boolean. R1 must separate that signing path from the consented write grant.
- `lib/mjolnir/git_signing.ex:204` maps `:not_wired` to success. `:213` skips IdentiKey revoke when metadata is incomplete. R2 must retain state on registered or uncertain grants when deletion cannot be confirmed.
- `lib/mjolnir/git_signing.ex:88` returns an ID-persistence error without compensation, while `:93` deletes local state on a registration error. `lib/mjolnir/forgejo/deploy_keys.ex:92` can return such an error after a malformed success or transport failure. R3 must preserve the durable public-key recovery handle or confirm remote cleanup before discarding it.

Existing tests illustrate why earlier green results cannot close the new obligations: `test/mjolnir/git_signing_test.exs:163` registers before adding XID/credential metadata, and `:231` expects local metadata deletion after a failed POST. Those expectations need to distinguish the revised signing-only path, definite no-create failures, and uncertain remote creation. I inspected these tests but did not run product tests or perform live clone/push/deploy operations in this contract review.
