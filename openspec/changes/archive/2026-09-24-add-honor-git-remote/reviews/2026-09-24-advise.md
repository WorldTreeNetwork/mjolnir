## Blind take

Written from the packet Why, living honor-being spec, and cited code before opening design.md, tasks.md, or the delta.

1. Pin repository write authority to the same consented `ssh_git` device that supplies the signing key.
2. Pin the device's XID to the authenticated VM owner and require the existing fresh-A3/add_device contract before granting write access.
3. Refuse registration from public-key-only metadata: a Forgejo key without a credential row has no reliable identity lifecycle.
4. Pin the Forgejo key identifier and repository association durably enough to delete the exact grant after restart or respawn.
5. Refuse success if Forgejo registration succeeds but metadata persistence fails without compensation or recoverable state.
6. Pin revoke ordering to Forgejo deletion, then identikey revocation, then local opaque deletion; failures must preserve retry information.
7. Refuse treating a missing host token as successful revocation when metadata identifies an existing live write key.
8. Pin respawn to a fresh device and complete retirement of the old grant, including cleanup or recovery when the second half fails.
9. Pin fresh clone and subsequent push to the injected key, correct SSH user, verified host key, and repository-scoped authority.
10. Tradeoff: reuse the signing key for SSH transport to simplify custody, accepting coupled rotation while keeping registration and revocation explicit and auditable.

## Comparison and steelman

The design answers the transport and custody concerns well: a repository write deploy key avoids a second person/account, the host retains the Forgejo token, the guest reuses the injected signing key, and a configured HTTP delete failure stops the revoke chain. The bootstrap supplies the key before clone, pins host keys, and rewrites the documented `forgejogit@` URL to the actual `git@` transport. The absence of a Forgejo verified badge is explicitly accepted and is not a blocker. Neither branch protection nor a new credential service is required by this review.

The strongest case against my blind concern about registration order is design Decision 1: “The pubkey is already an identikey `ssh_git` device.” If a trusted provisioner established that precondition, this adapter could remain small. But the reachable production caller is `VM.store_git_signing/1`, which invokes `mint/1` with only a VM ID. The code does not enforce that precondition, and tests add the XID/credential ID after the Forgejo POST. The proposal's empty state explicitly promises no A3/no row means no deploy key. This is an unmet existing contract, not a request for a competing design.

Similarly, an unconfigured development instance may legitimately have no Forgejo grant to delete. That does not justify treating token loss after successful production registration as proof that the remote grant is absent. A named key can aid manual recovery, but naming alone is not a durable, observable recovery workflow.

## Blocking findings

### R1 — P1: ordinary signing-key mint grants write authority without the consented identikey device

`lib/mjolnir/git_signing.ex:76–96` persists only `public_key` before calling Forgejo; `forgejo_register/2` at lines 184–198 permits a nil XID and does not pass a credential ID. `lib/mjolnir/forgejo/deploy_keys.ex:28–43` requires only public key and VM ID. `lib/mjolnir/api/router.ex:276–282` exposes this through a boolean, and `lib/mjolnir/vm.ex:1194–1213` calls mint without identity metadata. Stamping `owner_id` in the router does not bind the generated key to a consented credentials row.

With a host Forgejo token configured, an otherwise authorized ordinary VM spawn with `git_signing: true` therefore obtains a write key for the shared storefront repository without proving the friend's XID, fresh A3 consent, or `ssh_git` row. On a fresh VM, neither XID nor credential ID is written by this path; `identikey_revoke_device/1` at lines 213–220 subsequently skips revocation for missing metadata. The respawn helper likewise only mints a keypair, not a credentials row. This contradicts the living being-as-device requirement, design Decision 1, the proposal's empty state, and the modified respawn requirement.

Owed: make remote registration depend on the verified device binding for this exact public key and owner; preserve ordinary signing-only behavior without implicitly granting repository write authority. Exercise the real provisioning/respawn boundary: no A3, no credential row, or mismatched owner/key must cause no Forgejo POST; a valid device must have durable XID and credential ID before POST. Merely requiring caller-supplied nonempty strings is not sufficient proof.

### R2 — P1: losing the host token silently retires local/identikey state while leaving the write key live

`DeployKeys.credentials/0` at lines 62–66 returns `:not_wired` whenever the token is absent. `GitSigning.forgejo_revoke/1` at lines 204–209 converts that to `:ok` regardless of the saved `forgejo_key_id`; `finish_revoke/2` then revokes identikey and deletes opaque state.

Concrete sequence: register with a configured token, retain the issued key ID, remove or fail to load that token on restart, then revoke. No Forgejo DELETE occurs, yet local deletion can succeed (and identikey revocation can succeed when configured). The remote write credential survives with its recovery metadata removed. No environment or existing-grant check limits the exception to dev/test.

Owed: distinguish a device known never to have received remote authority from an existing or uncertain grant. Missing configuration for the latter must stop revocation and preserve retry metadata. Add a register-then-remove-token regression that verifies no identikey revoke or opaque deletion, followed by successful retry after restoring the token. Retain the no-grant development case.

### R3 — P1: ambiguous registration failure discards the only local record of a potentially live grant

`DeployKeys.create_or_find/3` at lines 92–104 forwards a transport error, and a successful HTTP response without a usable ID becomes `:missing_key_id`. In both cases, `GitSigning.mint/1` at lines 91–93 deletes private and device blobs without checking whether Forgejo created the key. A POST accepted remotely followed by a lost response can therefore leave a live grant with no local key/public-key metadata to reconcile. Separately, failure to persist the returned key ID at lines 85–88 returns an error without compensation or an explicit pending-registration recovery path; the earlier public-key blob helps but does not complete recovery.

Owed: define and implement recoverable registration outcomes. Retain sufficient durable device/public-key and remote-target information until absence or deletion of the grant is confirmed, or compensate and retain pending cleanup when compensation fails. Cover remote-create-then-timeout, malformed success, and post-registration metadata-write failure. Repeated attempts must not accumulate forgotten grants. A transport error is not evidence that the POST had no effect.
