## Blind pass (Why + living spec + blob-store door + host-sidecars, before design.md)

Independent take. Pin / refuse / one tradeoff. Not a competing
product.

1. Pin: Recrypt HTTP in a TAP guest is the only LAN/mesh-visible
   file surface. Blob-door stays `:host_api_ip:7222`
   (`10.200.0.1`). LAN clients never speak to the door.
2. Pin: Identity is `identikey-auth` Challenge/Response with `aud`
   this share. Data grant is `recrypt-storage-auth` `Capability` on
   `SubjectKind::File` (Blake3). Recryption key stays the bearer
   (D-5). Do not collapse the three layers.
3. Pin: Publish is host-side DNAT or reverse-proxy onto
   `192.168.0.18` and `fd01:d28c:7e4a`. Guest stays TAP. This box
   is a mesh *client*; `.mesh` is `meshd publish --ip` on the
   attached OpenWrt router, not `mjolnir-meshd` here, not
   `add-iroh-blobs`.
4. Refuse: directory NAS / `extra_mounts` as namespace; blob-door
   on `0.0.0.0` / `::` / public NIC; password, LAN-trust, Iroh
   ticket; `identikey-core` in the guest; BEAM linking
   `recrypt-storage-auth`; Sites/gateway as the file server;
   L2-bridging the guest onto Ethernet/wifi.
5. Tradeoff: DNAT/proxy vs bridge. Host-publish keeps TAP isolation
   and the door's INPUT-not-FORWARD invariant. Bridging puts a
   process that holds recryption keys on L2 next to every LAN
   device, and the door has no HTTP auth (network isolation only).
   Pick host-publish.
6. TAP is IPv4-only (`network.ex` hash-to-`10.192/10`). Mesh ULA is
   IPv6. Host publish must bind the ULA; the guest does not grow
   v6.
7. `recrypt-server` defaults to `127.0.0.1:7222` (same port as the
   door). Guest namespace vs host door must not collapse. LEARNINGS
   2026-08-24 already names this.
8. Door PUT/GET is unauthenticated. Recrypt guest is the only LAN
   gate. Guest must be a dedicated share appliance.
9. Load-bearing GET is identity fingerprint **and**
   `granted_to` on the File cap. If those are not the same 32
   bytes, the share never serves a file — or it skips a check.
10. Accept hinges on the design pinning that fingerprint join, and
    not licensing a drop-in that already violates the identity and
    cap-gated GET SHALLs.

## Steelman — how the design answers each

Product shape matches the blind take. Keep it.

- **(1) TAP guest + TAP-only door.** Answered.
  `design.md`: "The guest is a Recrypt HTTP process that PUTs/GETs
  the door over TAP INPUT. LAN clients never speak to the door."
  Spec "Blob-door stays TAP-only" copies living `blob-store`
  (`openspec/specs/blob-store/spec.md:260-275`): bind
  `10.200.0.1:7222`, fail closed if missing, reject `0.0.0.0`.
  Verified in `native/mjolnir_blob_door/src/main.rs:17-22` and
  `docs/guide/host-sidecars.md` (`dummy-mjolnir`, not loopback).
- **(2) Three layers.** Answered as a table. Agency stays
  `update-identikey-capability`. `identikey-core` is named as the
  hosted OP and excluded. D-5 cited, not amended. Correct.
- **(3) Host publish + meshd on the router.** Answered.
  `design.md`: "Publish is DNAT or a host proxy onto `192.168.0.18`
  … and … `fd01:d28c:7e4a`." Mesh: client, not `mjolnir-meshd`;
  citation `lightning-mesh` `docs/deploy/mesh-app-publishing.md`
  exists and is the right doc (`--ip` is the stationary-device
  lane). Radio stays plumbing. `add-iroh-blobs` stays ADR 0003
  remaining.
- **(4) Refusals.** Answered in "Contrast rejected" and in spec
  rejection scenarios (directory NAS, hosted OP, iroh-blobs as the
  share, public door bind).
- **(5) DNAT vs proxy vs bridge.** Partial. Design picks host
  publish (good) and leaves DNAT vs proxy open. Both satisfy the
  living spec. Not a product fork. Leave it to `mjolnir-h2fp.3`.
- **(6) v4 TAP / v6 ULA.** Implicit in "host proxy onto … ULA".
  Enough at this density.
- **(7)(8)** Door isolation is pinned. Port-collision and
  unauthenticated door are not named. Implementer notes unless they
  license the wrong binary — they do. See Major 1.
- **(9)(10) Fingerprint join.** Not answered. Spec scenario "Cap
  permits read" uses one `f` for identity and `granted_to`.
  `identikey-auth-challenge-v1.md:146-149` says those namespaces
  are distinct **by construction**. This is the send-back.

Steer closed the product forks (Recrypt share, identikey-auth,
storage-auth File caps, guest HTTP, TAP-only door, those two
binds, meshd on the router). It did not close the identity→cap
join, and the design reopened a binary choice ("Guest may run
`recrypt-server`") that as shipped fails two SHALLs.

## Critical Findings (blocks accept)

1. **Identity fingerprint and `Capability.granted_to` are different
   namespaces. The spec equates them.**

   Evidence:
   - Living delta `specs/lan-files/spec.md` scenario "Claimant holds
     the key": `"the fingerprint is the classical public key
     fingerprint"` after `verify_response` — that is identikey-auth
     §5: `Blake3(dcbor(PublicKey))`.
   - Same spec, requirement "Data access is recrypt-storage-auth":
     `"granted_to` is the claimant's fingerprint"`.
   - Scenario "Cap permits read": `"GIVEN a Capability for hash h
     granted to fingerprint f … AND a verified identity whose
     fingerprint is f … THEN the bytes are returned"`.
   - `identikey-auth-challenge-v1.md:146-149`: for Ed25519, §5
     hashes the self-describing `{"alg":"ed25519","key":…}` map,
     **"not the bare 32 bytes — so IdentiKey-auth fingerprints are
     a distinct namespace from recrypt's raw-Ed25519 fingerprints
     by construction. (If raw-Ed25519 interop is ever needed, it is
     added explicitly, not by accident.)"**
   - `recrypt-storage-auth` `Capability.granted_to` is
     `PublicKeyFingerprint` from `Blake3` of raw key bytes
     (`crates/recrypt-storage-auth/src/fingerprint.rs:21-25`,
     `capability.rs:105-110`).

   - Confidence: HIGH
   - Why this matters: GET of an authorized hash is the product.
     Compare §5 fp to `granted_to` and every legitimate GET 403s.
     Skip the compare to "make it work" and the cap gate is gone.
     Proposal says Recrypt D-5 and identikey-capability-v1 are
     `"cited, not amended"` — so this change does not get to
     pretend the namespaces already match. identikey-capability-v1
     already spent a send-back on holder fingerprint encoding.
     Same class of hole, load-bearing seam of *this* capability.
   - Fix: Pin the join in `design.md` and rewrite the spec
     scenario. One of: (a) map `Response.pub` → storage-auth fp
     (Blake3 of raw Ed25519) before the cap check, and issue Caps
     in that namespace; (b) issue Caps with §5 fps and change
     Recrypt (that *is* amending storage-auth — name it, do not
     sneak it); (c) dual-write during a stated interop window.
     "Explicit, not by accident."

## Major Findings (causes significant rework)

1. **`"Guest may run recrypt-server"` licenses a binary that does
   not satisfy this share.**

   Evidence:
   - `design.md` Licence: `"Guest may run recrypt-server (AGPL
     binary)."`
   - `recrypt-server/src/routes/mod.rs:122` and
     `routes/files.rs:93-121`: `GET /files/{hash}` is public. No
     identikey-auth. No `Capability` check. Hash is the capability
     (CAS layer, Recrypt architecture table).
   - Protected routes use `GET /nonce` (UUID string, no `aud`) plus
     `X-Public-Key` + dual-sig over `"UPLOAD:{fp}:{hash}:{nonce}"`
     (`files.rs:47-51`). That is not identikey-auth
     Challenge/Response.
   - `AppState.from_config` storage is `"local"` or in-memory
     (`recrypt-server/src/state.rs:59-69`). No blob-door HTTP
     backend. Default persistence is memory
     (`recrypt-server.toml`). Caps/accounts die on guest reboot.
   - Default bind is `127.0.0.1:7222` (`config.rs:155-160`). DNAT
     to TAP never hits guest loopback. Host proxy on `0.0.0.0:7222`
     steals the door (LEARNINGS 2026-08-24).

   - Confidence: HIGH
   - Why this matters: `mjolnir-h2fp.3` is "Recrypt guest + LAN
     proxy". An executor who reads "may run recrypt-server" and
     DNATs it ships a LAN file server with unauthenticated GET,
     no identikey-auth, bytes not on the door, grants not durable.
     Spec already forbids that. Design must not license it.
     `"may"` is not a pin; it is a trap.
   - Fix: One sentence in `design.md`: unmodified recrypt-server
     does not satisfy identity, cap-gated GET, door storage, or
     durable grants. `h2fp.3` is a Recrypt HTTP that does those
     four (patch recrypt-server, or a guest that links
     `identikey-auth` + `recrypt-storage-auth` and speaks
     `blob_door_url`). List the four deltas. Do not AGPL-link the
     crates into the BEAM (already pinned — keep it).

## Minor Findings

1. `meshd publish --ip <host>` is the wrong CLI shape. The cited
   doc is `meshd publish <name> --ip <addr> [--port] [--mac]`, and
   `--ip` publishes `name.<node>.mesh`, not a bare name
   (`mesh-app-publishing.md:68-74`). Mesh clients need the ULA,
   not `192.168.0.18` (RFC1918 Ethernet is not the OpenWrt
   `10.42/24` in that doc). Belongs in `mjolnir-h2fp.4`.
2. DNAT vs host proxy left open. Fine at this density. `h2fp.3`
   picks. If DNAT: Forge `ufw_nat` (PREROUTING), not a raw
   `iptables -t nat` that `ufw reload` wipes
   (`lib/mjolnir/forge/resource/ufw_nat.ex:9-11`). Existing MJOLNIR
   NAT is POSTROUTING masquerade only
   (`scripts/bootstrap-host-ubuntu.sh:1084-1087`).
3. Spec scenarios hardcode this laptop (`192.168.0.18`,
   `fd01:d28c:7e4a`). Requirement text is generic ("this box").
   When folding, keep the addresses as examples, not universal
   SHALLs.
4. Door PUT cap is 64 MiB (`DEFAULT_MAX_BYTES`). Not this node's
   job to raise. `h2fp.3` should not advertise an unlimited NAS.

## What's Missing

- Explicit fingerprint mapping (Critical 1). Highest-priority
  unstated assumption: "the claimant's fingerprint" is one value.
- Recrypt HTTP contract vs recrypt-server-as-shipped (Major 1).
- Guest lifecycle: `restart_policy :always` (default) + StateStore
  so Elixir restart (`just deploy`) does not lose the share VM.
  Not owed here if `h2fp.3` spawns via the API.
- Capability durability (sqlite on guest rootfs vs memory). Cluster
  with Major 1.
- LAN port. Recrypt-server default 7222 is a door landmine if the
  host proxy binds `0.0.0.0`. Pin "bind the two named addresses,
  never `0.0.0.0`, never `:host_api_ip`" on the publish path.
  Implementer note unless it stays 7222.

## Ambiguity Risks

- `"Guest may run recrypt-server"` → A: drop-in the AGPL binary and
  DNAT it / B: licence allows AGPL in-guest, the HTTP still has to
  meet the SHALLs. Wrong pick ships public GET on the LAN.
- `"granted_to` is the claimant's fingerprint"` → A: identikey-auth
  §5 / B: recrypt raw Ed25519 Blake3. They never match.
- `"meshd publish --ip <host>"` → A: `--ip` takes the name / B:
  `--ip` takes this box's address. Cited doc is B plus a positional
  name. `h2fp.4`.
- `"DNAT or a host proxy"` → A: L4 DNAT, guest sees client IP / B:
  L7 proxy, Challenge/Response and `Host`/`aud` must survive.
  Both valid; `h2fp.3` owns it.

## Verdict Justification

Send-back. Review ran THOROUGH, then ADVERSARIAL after Critical 1.

Keep: Recrypt objects not NAS; identikey-auth not
identikey-core/password; storage-auth File caps; recryption key
bearer; TAP-only door on `10.200.0.1:7222`; guest is what LAN/mesh
see; host publish onto Ethernet v4 + mesh ULA; meshd on the
attached router; no BEAM link; no `add-iroh-blobs`; no Sites
file server. Those pins are right and verified.

Do not accept: the identity→data join is wrong as written, and
the licence line licenses a binary that fails the share SHALLs.
This is architecture, not `act`. The cost of accepting now is
`h2fp.3` guessing both. Historical analog: identikey-capability
holder fingerprint encoding (send-back 2026-08-26).

Upgrade to accept: close the two owed boxes on `tasks.md`. Do not
need DNAT-vs-proxy, meshd CLI, or 64 MiB for this node.

Realist check: Critical 1 kept CRITICAL — not a style nit; the
protocol already documented the split and this spec ignored it.
Major 1 kept MAJOR — `"may"` is refutable as "optional", but
leaving it unpinned is how public GET ships; mitigated by the
spec's refusal scenarios only if the executor reads them instead
of `design.md`. Detection of the fp mismatch is immediate (first
GET). Detection of public GET is silent until someone curls a
hash. Silent wins the severity.

Pre-commitment vs found: predicted bind mismatch, auth vs
subjects, POSIX vs hashes, mesh publish, guest/host split.
Found: bind/NAS/mesh/split are actually pinned. The miss was the
fingerprint namespace (predicted as "auth vs recrypt subjects",
found one layer down: two Blake3 fingerprints of the same key).
Also found recrypt-server-as-shipped is not the share.
