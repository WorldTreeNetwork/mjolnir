## Independent pass and steelman

I wrote [the ten-line independent take](2026-11-05-independent-take-3.md) before opening design.md, tasks.md, prior reviews, steer.md, or the spikes. Inputs were proposal Why/What, the proposed capability spec (there is no living proxy-guest-net spec), and the cited code anchors.

The strongest answer to that take is the existing division of responsibility. The base image selects the network recipe; explicit false disables Iroh without reclassifying ordinary guests; the api-proxy service cgroup supplies the process egress boundary. The design names the repair script and the spec makes forbidden route/resolver drift non-ok, addressing the actual skip-on-ok branch in Health.do_heal. There is no need for a new holder or persistence mechanism. build_running_record/1 and resume_opts/1 already carry base_image and false, and the supported lifecycle is now explicitly VM.reboot/1, excluding snapshot and dormant restore.

The implementation tests promised by the acceptance requirement still matter: the live release uses the ordinary GuestNetwork probe, so the spike establishes script-based repair after route removal, not the future class-aware probe. That separation is honest and sufficient at this architecture stage. I accept the bounded IPv6 claim on the stated kernel and do not require a kernel rebuild. The paired root/unit connects with a default route are the appropriate evidence for the service boundary.

## What the amendment resolves

- **R4:** The checker now matches the host route's first field exactly, requires precisely the loopback resolver list, checks whole-word unit status, and rejects failed or missing inspection. The pre-heal route removal is asserted, and state inspection binds UUID, image, false flag, and ownership to the spawned guest. I ran the checker through its CLI against valid and broken JSON observations: the three previously accepted bad states now fail, as do failed/missing inspection and a still-present host route before heal. An empty successful route listing correctly passes the wiped-route precondition. The API omits exit_code on successful exec (router.ex:931–936), so accepting its absence alongside a valid output is appropriate.
- **R5, substantially:** accept.sh now calls the supported reboot endpoint, rechecks routes/resolver/unit status, rereads this guest's state, and repeats the paired confinement experiment. The supplied log reports completion. This is materially more than the earlier persistence-only check. The remaining Iroh observation gap is R7 below.
- **R6:** delete_vm now gates both API deletion and direct rootfs/state cleanup on the invocation's accept_run metadata. The before/after list difference alone no longer authorizes guest deletion. Offline CLI checks reject a foreign marker and accept the matching marker.

## Owed before acceptance

**R7 — Observe the resumed guest's relay state on a surface that actually returns it.** At accept.sh:249–257, the reboot response is checked and discarded, followed by pin and StateStore checks. assert_reboot at accept_check.py:141–145 checks ticket and iroh_addr with dict.get. But VM.reboot/1 returns rebooted and guest_healthy (vm.ex:775–787), and the router adds ok and id (router.ex:837–857). Neither returns ticket or iroh_addr. Those two checks therefore always see missing fields, regardless of the resumed guest's endpoint state. No subsequent request in the acceptance script observes those fields. Stored enable_iroh=false is useful evidence of preserved intent; it is not a measurement of the promised no-relay outcome after reboot.

The code and successful reboot evidence make a resumed relay unlikely; I am not claiming one was observed. Nevertheless, the previous review explicitly required the combined boundary, including false Iroh/no relay, to be reasserted on resume. Checking an unrelated response shape cannot satisfy that requirement. GET /api/vms/:id already returns the live detail view with id, state, enable_iroh, ticket, and iroh_addr (router.ex:720–726; views.ex:11–25), so no new product endpoint is needed.

After successful reboot, inspect the owned guest's live detail response, require its expected identity/running state and false flag, require the endpoint fields to be present and empty, and fail if inspection is absent or a relay appears. Keep the existing stored-image and unit/pin checks. Make the reboot acknowledgement itself require ok, rebooted, and guest_healthy to be true: the current checker also accepts both `{"ok": true}` and `{"ok": true, "rebooted": false, "guest_healthy": false}` in offline tests. Those are validator counterexamples, not responses claimed to come from today's router. Add negative fixtures for missing resumed detail and a resumed relay, then capture corrected local evidence under the existing throwaway-only/no-restart bounds. This closes the same lifecycle gate; it does not expand supported lifecycle paths.
