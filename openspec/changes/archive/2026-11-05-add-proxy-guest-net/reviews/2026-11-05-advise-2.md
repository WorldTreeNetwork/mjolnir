## Independent pass and steelman

I wrote [the ten-line independent take](2026-11-05-independent-take-2.md) before opening design.md, tasks.md, steer.md, or the spikes. Its inputs were proposal Why/What, the proposed capability spec, and the packet's code anchors. There is no living proxy-guest-net spec.

The strongest answer to my concerns is the existing division of responsibility: the image supplies the setup script, ConfigureNetwork executes that script, and the service cgroup supplies the process boundary. The revised spec explicitly separates base_image from enable_iroh, preserves ordinary guests with Iroh disabled, and makes forbidden route/resolver drift non-ok. That last change addresses the actual Health.do_heal skip branch rather than merely suppressing the no-default-route warning. Existing build_running_record/1 and resume_opts/1 already carry both fields without turning false into true. No new holder or persistence subsystem is justified.

The new log also answers the previous weak confinement proof: with a default route present, root opens both 1.1.1.1 and 9.9.9.9 while the service cgroup refuses both, and both contexts reach loopback and the host API. The IPv6 result is explicitly limited by the guest kernel; I do not require a new IPv6-enabled kernel for this node. The contract correctly separates the live legacy-health experiment from future class-aware probe tests. I do not require product implementation before architecture acceptance.

Those answers satisfy the substance of the class-selection and health-direction concerns. A concrete image selector must still be implemented consistently at spawn and health evaluation, but selecting its name is not itself another architecture gate. The remaining problems concern what the evidence actually establishes.

## Owed before acceptance

**R4 — Make the acceptance predicates reject broken state.** The post-heal validator at `docs/spikes/proxy-guest-class/accept.sh:245` accepts all three of these independently:

| Injected observation | Why it passes | Offline result |
| --- | --- | --- |
| Only `10.200.0.10 dev eth0`, with no host-API /32 | The route assertion searches for substring `10.200.0.1` | exit 0 |
| Loopback nameserver followed by public nameserver `9.9.9.9` | Only presence of the loopback line is checked | exit 0 |
| Unit output `inactive`, with guest `exit_code: 3` | `active` is a substring of `inactive`; guest exit status is ignored | exit 0 |

I reproduced these by extracting the exact Python validator from accept.sh and invoking it with synthetic exec JSON, without touching a guest. The first case directly violates the spec's scenario that a missing host /32 makes acceptance fail. The boot validator has similar substring checks. The pre-heal mutation at line 234 discards its response, so it does not prove that the host /32 was actually removed before the repair. The persistence check at lines 255–273 searches for any record with this base image rather than the spawned UUID.

Use exact parsed route/address and resolver assertions, exact unit status, and successful inspection status. Assert the missing-route precondition before heal and bind persistence checks to the owned guest. Add negative fixtures for these predicates and rerun the corrected local command with evidence. Retain the useful paired root/unit confinement checks. This repairs the promised fail-closed gate; it does not change the network design.

**R5 — Close the gap between stored configuration and supported resume.** Spec lines 37–43 promise a resumed proxy with the same identity and false flag. R3 in tasks.md says supported resume is covered, but accept.sh only reads a JSON record, and accept-evidence.log contains no resume. Existing code is good evidence that false is preserved; it is not evidence that the combined class remains intact after a supported lifecycle transition, especially once class validation is added.

Name the supported StateStore resume path and either exercise it locally, without restarting mjolnir, then reassert identity, false Iroh/no relay, routes, resolver, and unit confinement; or explicitly require that verification as a landing gate, clearly labeling the current spike as persistence-only. State whether snapshot/dormant restore is supported by this node or outside its scope rather than leaving R1's restore claim implicit. A narrowly scoped landing gate is sufficient; no expanded lifecycle framework is requested.

**R6 — Limit acceptance cleanup to guests owned by this invocation.** On a failed spawn, accept.sh lines 126–144 compares the global before/after VM lists and calls delete_vm on every new ID. A concurrently created unrelated guest can therefore be stopped and have its rootfs and StateStore record deleted; the single protected ID does not establish ownership. Give the fixture an invocation-specific ownership marker or preallocated IDs and verify ownership before cleanup. A failed spawn must not authorize deletion based only on appearing in a list difference. This is necessary to make rerunning the local evidence command consistent with its throwaway-only scope.
