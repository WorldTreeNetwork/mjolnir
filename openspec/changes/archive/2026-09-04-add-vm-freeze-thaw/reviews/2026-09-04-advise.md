## Blind pass (Why + spec + cited code only, before opening tasks/proposal)

1. Shape is sound: distinct verbs (`freeze`/`thaw` vs `snapshot create`),
   refuse-don't-silently-mutate, `kind` by artifact-existence not metadata
   claim, reseed-before-reachable, same-id-only restore.
2. **Pin** — `kind` decided by `state.json` presence under `@snapshots/<name>.mem`,
   not a metadata claim; resists a lying / half-written sidecar. Keep it.
3. **Pin** — same-id-only park (409 on a live id) structurally forbids two live
   copies of one RAM image, sidestepping the duplicate-RNG / VMGENID hazard by
   construction. This is the load-bearing safety choice.
4. **Pin/concern** — freeze is *terminal*: `StateStore.delete` then
   `{:stop,:normal}`, VMM + virtiofsd torn down. Is the artifact verified
   restorable *before* the source dies? Terminal + unverified = silent loss.
5. **Pin** — reseed sits on the with-chain; a reseed failure must abort the thaw
   (fail-closed), not publish an un-reseeded guest.
6. **Concern** — captured guest RAM rests on `@snapshots/<name>.mem` and holds
   secrets; how is that handled at capture time?
7. **Concern** — freeze's `StateStore.delete` → teardown window vs Reconcile
   cold-booting the live subvolume. Ordering must be delete-before-teardown.
8. **Refuse** — nothing structural warrants a design refusal from the blind read.
9. **Tradeoff** — no-fork (out of scope, mjolnir-8m3) is traded away to preserve
   the safety-by-construction. Correct for this scope.
10. Accept hinges on tasks/code covering: freeze-before-teardown handling,
    at-rest-secrets, reseed-fails-closed, list/show `kind`, spawn-refusal.

## Steelman — how the author answered each concern

Every item above is answered in the shipped code. Treated as concerns the
author must have addressed, not a competing design:

- **kind by artifact (2)** — `MemorySnapshot.kind/1` + `annotate/1`
  (`memory_snapshot.ex:112-139`) read `state.json` on disk and *overwrite* any
  `kind` in the sidecar, so a half-written freeze cannot advertise restorable
  RAM. `GET /api/snapshots` and `/:name` both route through `annotate/1`
  (`router.ex:1310,1335`). Spec "catalog distinguishes kinds" satisfied.
- **same-id 409 (3)** — `VM.thaw` → `ensure_id_free/1` (registry lookup) and
  the router maps `{:vm_running, …}` → 409 (`router.ex:1378`). `do_thaw` calls
  `MemorySnapshot.thaw(name, state.id)` with no remap — the same id, as spec'd.
- **terminal freeze (4)** — the residual (no test-restore before killing the
  source) is an *inherent* CH constraint: `vm.snapshot` is terminal for any
  vhost-user VM, and you cannot test-thaw without spinning a fresh VMM, which
  doubles cost. It is mitigated correctly rather than ignored: `capture/4`
  `rm_rf`s the mem dir on any failure (`memory_snapshot.ex:311`); FS snapshot
  is taken read-only inside the pause window; and thaw re-verifies via
  `BTRFS.verify_pin` + drift/generation check (`prepare_thaw/2`,
  `memory_snapshot.ex:334-348`), refusing a drifted or generation-unknown pin.
  This is the right tradeoff for the hardware constraint, and the moduledoc
  argues it explicitly.
- **reseed fails-closed (5)** — `attach_thawed/3` gates on
  `:ok <- Entropy.reseed(vsock_conn)` inside a `with`; the `else` runs
  `abandon_thaw` (`vm.ex:2280-2282`). The generic vsock reply
  (`connection.ex:658-667`) is what lets reseed land; without it reseed *times
  out* → thaw aborts, i.e. fails closed, never publishes an un-reseeded guest.
  Reachability (PTY/ticket/gateway) is only set after reseed. Matches the
  "entropy reseeded before reachable" spec scenario.
- **at-rest secrets (6)** — better handled than I anticipated: for
  `:managed`/`:persistent` VMs `default_quiesce/2` runs `Secrets.Quiesce.suspend`
  (luksSuspend) *before* pause, and freeze *refuses* with
  `{:secrets_quiesce_required, mode}` (→ 409) if the key cannot be wiped
  (`memory_snapshot.ex:207-273`, `router.ex:1279`). A `secrets.json` sidecar
  records the suspended state and thaw reopens it. The DEK is not captured.
- **teardown ordering (7)** — `handle_call({:freeze,…})` deletes StateStore
  intent, publishes `:vm_frozen`, then returns `{:stop,:normal,…}`
  (`vm.ex:1466-1468`), mirroring `handle_done` so Reconcile does not cold-boot
  the live subvolume. Ordering is delete-before-stop.
- **spawn refusal** — `spawn_rejecting_memory_snapshot/1` (`router.ex:1750`)
  returns `{:memory_snapshot_requires_thaw, name}` → 400 with a thaw hint
  (`router.ex:414-418`), by `memory_snapshot?/1` (artifact check). Matches the
  "spawn --snapshot on a freeze artifact" scenario.
- **delete symmetry** — `BTRFS.delete_snapshot/1` removes both `.mem` and
  `.mem.forks` siblings (`btrfs.ex:378-379`), so a deleted FS snapshot cannot
  leave `kind=memory` dangling. (tasks line 9)

## Verdict

**Accept.** The change is scoped exactly to the Why: it wires the pre-existing
`MemorySnapshot.freeze/thaw` behind distinct operator verbs, keeps
`mj snapshot create` filesystem-only, refuses the two silent-footgun paths
(spawn-cold-boots-RAM, snapshot-stops-the-VM) at the point of use, and gates
reachability on entropy reseed. Every blind-pass concern is answered in code
or is an inherent hardware constraint mitigated correctly. No owed boxes added
to `tasks.md`.

## Non-blocking observations (not owed; for the author's awareness)

- The one residual risk — freeze tears down the source without a proof-of-thaw
  round trip — is intrinsic to CH's terminal virtio-fs snapshot and is the
  right call. If a cheap post-freeze integrity check (e.g. `state.json` parse +
  `memory-ranges` size sanity) is ever wanted, it belongs as a follow-up, not a
  blocker here.
- Memory-snapshot artifacts on `@snapshots/*.mem` remain off-box-unprotected
  per the existing backup gap (bead mjolnir-qwp / b2-backup memory). Freeze
  makes RAM-at-rest more common; worth a line in the blob-door/backup runbook
  eventually, out of scope for this change.
- `VM.freeze/3` GenServer timeout is 300s — comfortable for an uncompressed
  full-RAM write; compression/retention is deferred to mjolnir-3y6.9.
