# Browser: send-back

The host-readable notice and independent full-root comparison are correct. The new `jwks` input does not yet supply trusted admission, and the lifecycle has conflicting failure rules. Preserve the accepted path architecture and fix this bounded browser slice.

## Required amendments

**B1 — high: define the authenticated admission producer.** Design D1 takes arbitrary `jwks` alongside invitation inputs, then calls a signature check admission. No route, pin, or trusted origin authenticates that key set. An attacker-supplied key can sign an attacker-supplied matching root; three equal strings do not authenticate the room. `Mint.issue` returns token/expires/root/publish/subscribe/relay_host/kind, no public keys, trust policy or configured TTL ceiling. The filesystem relay key set is not a browser endpoint. Do not expose current.jwk, symmetric secrets, or any signing material.

A minimal implementation is a pre-media HTTPS admission request to a configured trusted gateway origin, using the same Rust assess/profile/grants/open-root/operation checks as the media route. Bind the result to the exact token/request/root and attempt; compare the independently supplied invitation root and mint metadata locally. Only the module's authenticated fetch may produce this result, never arbitrary remote JSON or caller `{ok:true}`. The response is meaningful because it comes from that trusted authority over verified HTTPS, not because its JSON has an `ok` member. Keep it no-store, with no token in URLs/logs/reports. This requires an explicit `.13` endpoint/task amendment. Allow this admission HTTP (and necessary authenticated trust bootstrap) before media; continue forbidding getUserMedia, PC creation and WHIP/WHEP until success. There is no need to create an SDP offer to ask permission to create a PC.

If local verification is retained instead, specify authentic public-JWKS delivery from a trusted configured origin, freshness/cache/rotation/invalid-set rules and trusted max_ttl, plus algorithm/kid/key-operation/key-scope handling, strict claims and types, nbf, required iat/exp, exp >= iat, future-iat allowance, TTL ceiling, canonical root, grant syntax/nonemptiness/validation and requested publish/subscribe path checks. The Rust boundary supports EdDSA and ES256; the browser design mentions only EdDSA. Either declare a deliberate supported mint subset with typed refusal or maintain parity. Pinned moq-auth key.rs:615-702 verifies strict claims and key scope; lib.rs:97-146 adds the relay profile and Grant validation. Signature plus exp/iat/root is insufficient, even with genuine keys. Verification-key import is necessary bootstrap; “no key import before admission” must mean media/content keys, not the public key required to authenticate the token. Never substitute JWT payload decoding for this boundary.

**B2 — high: make join/replacement ownership and failure behavior consistent.** Proposal says any 403/409 tears down; D1 says a WHEP 409 retries without failing join; replacement spec says failure leaves existing PCs, while D1 only protects failures at steps 1–2. New WHIP can succeed before WHEP fails, or a camera promise can resolve after teardown. Define one candidate attempt with its own PCs, tracks, session ids, timers, abort controller and generation. Any candidate failure removes only candidate resources; a still-valid incumbent continues until its own exp. Explicit leave tears down both. Late callbacks cannot install media or delete the successor. Decide when a candidate with `not_started` peers commits (recommend WHIP established plus pending empty peer tiles, with bounded retries), rather than waiting forever for every WHEP to return 201. A 201 SDP response alone does not mean a PC is connected or media flows; define readiness/timeout and test failures after POST success and setRemoteDescription.

Arm expiry/cancellation before awaiting camera permission, ICE or HTTP, and recheck time after each await and before publishing. Re-run credential checks on join/replace/renew. Teardown must DELETE each owned remote session with its admitting token, close PCs, stop owned tracks, clear retries/listeners/timers and reject stale completions. Do not stop a shared camera track still used by the successor; specify reuse/refcount or separate ownership. Old-token timers must never close new-token PCs. Best-effort DELETE is bounded; gateway cleanup and exp are the backstop for a lost response. The current design's teardown only closes local resources and does not promise these remote cleanups.

Long-call behavior also needs an honest boundary: the living room-auth contract reports that existing subscribers do not automatically follow a replacement publisher at the same path. A renewed publisher plus a new 201 does not demonstrate peer continuity. For this slice specify reconnect/retry on ended named-peer playback, or surface that peers must rejoin; test the chosen behavior. Full roster/SSE and conference-wide seamless handover are not prerequisites for this slice. A bearer guest cannot mint a renewal; renew consumes an externally supplied new mint response and must not promise automatic mint authority.

**B3 — medium: pin invitation and HTTP inputs.** D1's input omits self broadcast, peer paths, trusted edge URL and retry settings even though steps 5–6 require them. Define a small validated invitation shape. Check every named path against the admitted operation grant before media permission or any PC/request, reject path traversal/absolute URL tricks, and construct URLs only on the configured gateway origin. Bound retry rate/backoff and peer count; an invitation must not choose a zero-delay retry loop. Preserve per-path 409 not_started as an empty/pending peer; distinguish codec refusal, authentication refusal and transient transport errors. Specify CORS/Location with `.13`. Keep bearer tokens in page memory, scrub fragment inputs, no referrer/third-party leak or arbitrary relay_host destination. The existing spike shell accepts its edge URL from a query parameter and is not a production trust configuration.

**B4 — medium: use the accepted comparison's actual error precedence.** The new old-mint scenario expects `open_refused` when expected root is open and admitted root protected. `RoomJoin.check/4` compares roots first and returns `unexpected_root` in that case; the accepted code review explicitly records both outcomes. Keep that precedence: protected expected root + open ask -> open_refused; open expected root + protected admitted root -> unexpected_root. Both fail closed before media. Also cover open-shaped response with omitted kind -> kind_mismatch. Do not change the accepted helper merely to fit a new test label.
