# Browser: send-back, lifecycle and executable admission

B1's trust choice is resolved: only the module's fetch to a configured trusted HTTPS gateway produces admission; invitations cannot choose the authority and arbitrary JSON is not trusted. No browser JWKS or minting authority is needed. B3's seven-peer limit, relative paths, minimum backoff, per-path retry and configured-origin URL construction are suitable for the authorized slice. Generation-owned resources, bounded DELETE, separate expiry timers and track refcounts substantially address B2. The remaining corrections are concrete.

## B1/B3: admission must cover every media intent and be fresh enough to use (high)

The gateway currently returns before grant matching (companion G1/G3). Fix that endpoint, then require the browser to admit selfPath for publish and every named peer path for subscribe before camera/PC creation, binding each result to immutable token bytes, expected root, operation, canonical path and this attempt. Do not reuse an answer when any of those inputs changes. A trusted origin authenticates a response; it does not make an old response admission for a new credential.

`design.md:43` arms an expiry timer before camera, but does not explicitly check exp *before* the call. A delayed `/admit` 200 can arrive after exp; scheduling a zero-delay timer and immediately calling getUserMedia still prompts the camera. Check finite exp and current time, abort and generation before each media side effect, including the first camera call, and after each await. Test expired-on-arrival admission and expiry during unresolved camera permission; late streams must be stopped. Media POST repeats admission against key state, so a key removed after preflight can still produce a later 403. Do not claim preflight can guarantee that revocation never races a camera prompt or add continuous key polling to solve that impossible promise.

## B2: renewal's commit point precedes readiness (high)

At `design.md:46–49`, new WHIP commits after 201/setRemoteDescription and immediately permits deletion of all old ids. ICE may then fail for ten seconds; the incumbent is already gone. This does not support the broad failed-renewal-keeps-old-call promise. Keep the incumbent until the candidate WHIP reaches bounded ICE readiness (and distinguish transport-ready from demonstrated media). Pending named WHEPs need not block commitment. A failed new publisher must stop candidate-owned tracks and timers as well as that one PC; current timeout text only closes the PC/id and leaves the retryable class undefined.

There is a related pinned API boundary: `server/whip.rs:185–193` announces a new route instance *inside accept*, before HTTP delivery and before the browser's commit. Two tokens publishing selfPath can therefore overlap before commitment. Keeping the old HTTP id is not proof of atomic publication rollback. Test new same-path POST followed by answer failure, setRemoteDescription failure and ICE timeout, with an existing subscriber and a new subscriber. State the bounded promise honestly: old owned PCs/publisher remain until ready, but relay selection/new-subscriber handover is not atomic. If stronger rollback is required, name a feasible gated-publication mechanism first; do not invent a local-playback bypass or require seamless conference handover for this slice.

The named-peer retry on connection end is sensible at this pin: session.rs:218–230 ends egress on catalog failure. Keep the fallback message for failures to restore; the living relay spec says a continuing subscription does not automatically follow a replacement publisher. Record a test for that end/retry, rather than just a fake 409.

A single `generation != current` rule also needs to distinguish current candidate from live incumbent. Beginning generation 2 must invalidate generation 1's *candidate completions*, not drop a committed generation 1 peer retry or expiry ownership while generation 2 is pending/fails. Retain explicit attempt state/ownership; no global timer should tear down the successor. Include failed-renewal with an incumbent callback during the overlap.

## B4: current end-to-end error promises are unreachable (medium)

Gateway `/admit` rejects protected roots with 403 room_not_open before expected-root equality. Browser `design.md:28` collapses every 401/403 to unauthenticated_identity. Consequently neither old-mint unexpected_root nor protected-invitation open_refused in proposal/spec can happen through that gateway. Even an open-root mismatch 403 unexpected_root is erased.

Reconcile the real endpoint and browser error translation, and keep pure RoomJoin comparator tests separately labelled. Options include retaining authenticated typed refusal details with a defined precedence, or explicitly distinguishing gateway refusal from the pure comparison result in the journeys. Never decode an unverified JWT or trust mint metadata to fabricate an admitted protected root. Preserve exact expected-root equality and existing helper precedence; no helper change is required. Tests must exercise real `/admit` refusals, not only mocked 200 protected roots.

## Non-blocking implementation choices and evidence

Use strict finite retryMs validation and a bounded delay; the current minimum plus 30-second cap needs a clear relationship for inputs above the cap. Validate canonical paths before request construction, including percent/dot/backslash forms and limits shared with the gateway; use encoding that cannot introduce a query or fragment. Reject foreign/invalid session Locations before sending a bearer DELETE. These fit the existing input/cleanup tasks, with no roster or new product scope.
