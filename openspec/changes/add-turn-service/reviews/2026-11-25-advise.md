## Verdict

Send back. The shape is right and I would not change it: eturnal as its
own unit and user, off by default, one deploy flag, TURN REST
credentials with the owner taken from the verified `sub`, and two
egress filters. The owner rule does not repeat the first room-token
mistake (spec line 42 and its scenario at 52–55).

It goes back because four sentences of normative security text are
wrong as written (B1, B2, B4, B6), one production route is put at risk
with no stated failure mode (B5), and one open question decides whether
eturnal can stay at all (B3). An accept would let code start against a
kernel rule that was never run and a quota that may not exist.

## Host facts used (`45.76.77.97`, read 2026-11-25)

- Ubuntu 24.04, `iptables v1.8.10 (nf_tables)`, ufw active. `nft` and
  `tc` are installed. Docker is not. fail2ban already keeps its own
  table, `inet f2b-table`.
- `OUTPUT` policy ACCEPT. Its first accepting rules are in
  `ufw-before-output`: `-o lo -j ACCEPT`, then
  `--ctstate RELATED,ESTABLISHED -j ACCEPT`. `ufw-track-output` accepts
  every new TCP and UDP flow. `MANAGE_BUILTINS=no`, so a reload leaves
  an inserted rule above the ufw jumps.
- `INPUT` accepts `-i lo` first. The relay's rule sits above the ufw
  jumps because it was inserted, not appended.
- `rp_filter` 2 (loose). `route_localnet` 0. `accept_local` 0.
- Addresses: `45.76.77.97/23`, `10.200.0.1`, `10.255.255.1` (`hostgw`),
  loopback. No global IPv6, no IPv6 default route. `ip6tables` `OUTPUT`
  policy ACCEPT.
- UDP on `0.0.0.0`: relay 443, one Iroh socket each for the relay and
  the gateway. TCP on `0.0.0.0`: API 4000, `epmd` 4369, controller
  distribution 46261, gateway 80 and 443, sshd.
- nat has no `OUTPUT` rule and no `PREROUTING` DNAT today.
- `nf_conntrack_max` 262144, shared with guest NAT. UDP timeouts 30 s
  and 120 s.
- `net.ipv4.ip_local_port_range` 32768–60999, as the contract says.
- `turn.worldtree.network` resolves to `45.76.77.97`. A random name
  under the zone does not, so it is a record, not a wildcard.

## Findings

### Blocking

**B1. The drop rules are installed after the daemon is up, and nothing
says they come back after a reboot.**
`specs/turn-service/spec.md:25`: "The rules SHALL be added only after
the unit is active and removed when the unit is removed."
`design.md:62` has `deploy.sh --turn` write the rules. This copies the
relay's rule lifecycle (`systemd/mjolnir-relay.service:20-21`,
`docs/plans/webrtc-turn-sfu.md:143`). That lifecycle is right for an
ACCEPT that opens a port and wrong for a DROP that protects the host.
As written, every start has a window with one filter, and a reboot
brings back an enabled unit with no kernel filter at all, because
iptables rules written by a deploy script do not survive a boot. The
relay's rule survives only because its unit adds it.

**B2. The kernel rule is keyed on a number the daemon's own file
controls, was never run, and its position is not pinned.**
`spec.md:25`, `design.md:11`, `design.md:43`, `tasks.md:32`.

- The match is uid and source port 61000–65535. The relay range is set
  in `eturnal.yml`, the same file that holds the first filter. eturnal's
  default range is 49152–65535 (plan line 126). A lost or defaulted
  YAML gives a daemon whose blacklist is `recommended` without the host
  public address and whose relay sockets are mostly outside the kernel
  match. A relayed packet to `45.76.77.97:443` then passes both
  filters. Two filters that fail together on one file are one filter.
- S2 ran a different rule. `spikes/run-s2-followup.sh:135-138` and
  `spikes/evidence/s2-counters.txt` show `owner UID match 948`, all
  protocols, no source port. The specified rule (uid, UDP, source port
  range) has no evidence. `tasks.md:12` is checked against a rule the
  contract then replaces.
- Position. On production an appended `OUTPUT` rule is never reached:
  `ufw-before-output` accepts `-o lo` and established flows, and
  `ufw-track-output` accepts new ones. The spike used `-I OUTPUT 1`
  (`run-s2-followup.sh:134`). The spec does not say so. `INPUT` accepts
  `-i lo`, so `OUTPUT` is the only chain between the daemon and any
  host service.
- The rule is UDP-only by construction. TCP from the uid is unfiltered.
  That is harmless while the daemon is honest and eturnal has no RFC
  6062. It gives nothing if the daemon is compromised, and the
  controller's `epmd` and distribution port are on `0.0.0.0`.
- The reason given for the port match is a lab artefact. The client was
  on `127.0.0.1` (`spikes/verdict.md:52`). On production a real client
  is never in a dropped range unless it is a guest or the host itself.
  Whether those may be clients is a product choice (Duke 2).

**B3. One account can hold every relay port, and the contract does not
know whether any limit exists.**
`design.md:58`: "The spike did not show whether those numbers are per
username or per process. The implementation records which." This is the
question that decides the daemon, and it is deferred to implementation.

- eturnal's changelog for 0.8.0 says `max_allocations` was removed from
  the documentation because the `stun` application ignores it. The
  current source maps the option again. I could not confirm which holds
  for 1.12.3. The spike held two sessions on one username
  (`evidence/s1-sessions.txt`), which shows nothing about a limit of
  ten.
- If a limit exists it is per username. Every mint is a new username
  (new expiry second, any room, any participant label), so it does not
  bound an owner.
- The scope does not bound it either. `lib/mjolnir/api/auth.ex:51` and
  `:250` give every verified user JWT the whole scope set. `tasks.md:18`
  adds `turn:relay` to that list. "Behind scope `turn:relay`" then means
  "every signed-in user", and `c1` reaches every signed-in user through
  the room mint anyway.
- An allocation holds a port for its lifetime without sending a byte.
  The 100 Mbit/s cap does not see it. 4,536 Allocates end the service
  for everyone.
- The plan's own rule (line 71): if eturnal cannot give per-owner
  quota, fall back to Pion. `eturnalctl disconnect <username suffix>`
  exists since 1.8.0, so a small reaper is a third way (Duke 3).

**B4. Rotation overlaps for the allocation lifetime. It has to overlap
for the credential lifetime.**
`spec.md:50`, `design.md:33`: the old secret is dropped after 600 + 60
seconds. A credential minted with the old secret one second before the
rotation is good for up to 3600 seconds, and `strict_expiry`
authenticates every Refresh. Its holder's Refresh fails from second 660,
and the call drops up to 49 minutes early. The relay's rotation waits
`:relay_token_max_ttl` plus 60 (`openspec/specs/relay-room-auth/spec.md:154`).
This one must wait the longest credential life plus 60.

**B5. The room mint is live on production and its behaviour when TURN
is half-configured is not specified.**
`spec.md:44`: `ice_servers` appears "when TURN is configured". Nothing
defines that. `proposal.md:12` says `--turn` does not restart the
controller, so the controller cannot learn it from application config.
The relay mint reads `/etc/mjolnir-relay/relay.env` on every call
(`lib/mjolnir/relay/mint.ex:86-116`) for exactly this reason. Also
unsaid: what the room mint returns when TURN is enabled and the secret
file is missing or has the wrong mode. A 503 there breaks every call on
the host because of an optional feature.

**B6. "IPv6 relay is off" is in the proposal and the design and not in
the spec, and nothing enforces it.**
`proposal.md:50`, `design.md:64`, `docs/decisions/0018-turn-service.md:39`.
The spec never mentions `relay_ipv6_addr`. The ip6tables rules
(`spec.md:25`) drop only listed prefixes. eturnal's documented default
is to detect an IPv6 relay address on a host that has one (from its
documentation as I remember it, not re-read today). Production has
none today, so this is safe by accident of the host. No test asks for an IPv6
allocation. The mapped-address 443 (`evidence/s1b-mapped.txt`) is an
address-family check, as the author says, and proves nothing about the
blacklist.

### Medium

**M1. The expiry limit is stated with the default lifetime, not the
maximum.** `spec.md:48`, `design.md:51`, `design.md:55`,
`spikes/verdict.md:35`. 600 seconds is what the server grants when the
client asks for nothing. A client chooses `LIFETIME`. The server's
ceiling was not measured (the `stun` library's is, from memory, 3600
seconds; unverified). A Refresh one second before expiry that asks for
the ceiling keeps the allocation that long. The honest bound is
credential life plus the server's ceiling. "The implementation SHALL
also send a TURN LIFETIME on the client side" (`spec.md:48`) is not a
control. An attacker writes their own client.

**M2. `STUN_SERVICE=false` is specified and was never set in a run, and
the artefact is not chosen.** `spec.md:10`, `design.md:20`,
`design.md:62`. Neither runner passes that variable
(`run-s1-s2.sh:59-64`, `run-s2-followup.sh:54-57`). The log shows the probe happening
(`evidence/s1-eturnal.log:6`), not it being stopped. The variable
belongs to the container image's wrapper. `design.md:62` says "the
package or the pinned image's extracted binary". Production has no
Docker. Every process fact in the spike (the wrapper, the distribution
listener at `s1-eturnal.log:14`, the cookie) was seen on the container
only. `spec.md:8` pins "1.12.x", which floats.

**M3. The spec has no inbound rules, no failed-enable requirement, and
no requirement that TCP relaying is refused.** The relay's spec names
its one rule and has "A failed enable opens nothing". This delta names
no `INPUT` rule for UDP 3478, TCP 3478 or the relay range.
`proposal.md:36` promises the failed case and the spec has no scenario
for it. `proposal.md:11` rests on RFC 6062 being absent, which is what
keeps the API, `epmd` and Forgejo out of reach, and the spec does not
make "REQUESTED-TRANSPORT TCP is refused" a scenario. An upgrade that
adds it would pass every test.

**M4. "Proven" covers less than the tasks say.**

- `tasks.md:8`: seven IPv4 peers got 403. Not probed: `172.16.0.0/12`,
  `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`, `0.0.0.0/8`, and the
  one entry this contract adds, the host's public address. In the lab
  the host's address was inside `192.168.0.0/16`, so an entry outside
  `recommended` was never shown to refuse.
- `tasks.md:12`: see B2. Also three of the seven rules counted zero
  packets, no TAP was used, and ufw's state on morphie is not recorded.
- A client never reached the server over TCP 3478. Only the relay
  transport was tested. The mint will advertise `transport=tcp`.
- The bead's acceptance is a browser on another network on relay-only
  ICE. No task does that.

**M5. The DNS statement is stale.** `proposal.md:52`, `design.md:13`,
`tasks.md:34`, `docs/decisions/0018-turn-service.md:17`. The name
resolves to `45.76.77.97` today. The production gate is now Duke's word
alone, and the contract should say so.

**M6. The delta holds sentences that are not behaviour.** `spec.md:48`
("the threat text SHALL state…") and `spec.md:50` ("A reload SHALL NOT
be specified as…") are rules about documents. The rate cap
(`spec.md:27`) and the distribution port (`spec.md:10`) have no
scenario. The limits belong in a `## Limits` section, as
`relay-room-auth` has.

**M7. The username carries room and participant labels in clear, and
the `g1` shape disagrees with itself.** `spec.md:42`, `design.md:25`,
`spikes/verdict.md:24`, plan line 84. STUN sends `USERNAME` unencrypted
on 3478, and eturnal logs it. Tenant room names become readable on the
path and in the journal. Nothing in this change reads them back.
Separately, the spec and design give `g1.<owner>`, the spike and the
plan give `g1.<owner>.<label>`, and nothing says who supplies a label.

**M8. The unit's sandbox is one line.** `design.md:62` has
`NoNewPrivileges` and file ownership. The relay unit has
`ProtectSystem=strict`, `PrivateTmp`, `ProtectHome` and a bounding set.
This daemon needs no capability at all (3478 is above 1024). It shares
a host with the controller and every guest and has no memory, task or
CPU limit.

**M9. The secret is under-specified.** `spec.md:42`, `design.md:31`.
Not stated: its length and source of randomness, that the mint checks
the file's owner and mode and refuses to sign on a failed check (the
relay mint does, `mint.ex:149-164`), an emergency replacement with no
overlap, and that the rotation script cannot change anything in the
YAML but the secret list. The script rewrites the file that holds the
blacklist.

**M10. The same-host WebRTC edge is not in "Not covered".**
`design.md:43` declines the exception, which is right. It is not said
that a relay-only browser therefore cannot reach an edge on this host
until a later change opens both filters. It should also say now that
if eturnal's whitelist is per address and not per port, the daemon
filter stops protecting the host's public address the day that
exception lands, and the kernel rule is then the only filter for every
other UDP port on it. That is the case B2 has to be built for.

### Low

**L1. Port 3478 answers anyone, and the numbers are not measured.**
`design.md:53` repeats the plan's unmeasured claim (plan line 111) that
a 401 holds no state. With `rp_filter` 2, a packet with a spoofed guest
source is accepted on the public interface if the upstream network
delivers it, and the answer goes from 3478 to that guest on a port the
sender chose, with twelve bytes the sender chose. A guest can do the
same to another guest. By arithmetic a bare Allocate (20 bytes) draws a
401 of roughly 100 to 130 bytes. Measure both sizes and the memory
under a flood.

**L2. Conntrack.** One allocation may send to any port of a permitted
address. Each tuple is a conntrack entry for 30 seconds, in a table of
262,144 that guest NAT shares. Guests can already do this through NAT.
A packet-rate limit beside the byte cap, or `notrack` for the uid,
closes it.

**L3. Modules and logs.** S1 ran `mod_log_stun`. The contract does not
pin the module list. `mod_stats_prometheus` opens an HTTP listener.
Client addresses go to the journal.

**L4. The published-port overlap is checked at deploy only**
(`spec.md:29`). A later change to `MJOLNIR_PUBLISHED_PORT_RANGE` is not
checked against the relay range.

**L5. Route details are missing for `POST /api/turn/credentials`**:
body, `ttl`, response keys, refusal order, the 503 cases, and that a
`sub` which is not an owner is 403. The room mint spec has each.

## The seven questions

1. **Egress.** The uid-and-port match is not sound as the second
   filter (B2). From 3478 the daemon answers only the source of a
   request; TCP on 3478 needs a handshake, so only UDP sources can be
   forged, and only for guest ranges (L1). IPv6 is assumed (B6). The
   host's public address is in both lists as text; match it by address
   type instead so it cannot go stale. Published guest ports are not
   reachable: a local packet never crosses `PREROUTING`, so it is not
   translated, and the public address is denied anyway. Order against
   ufw is decisive and unpinned (B2). `FORWARD` is not involved: relay
   packets are locally generated.
2. **Admitted gaps.** Mapped and IPv6 peers: honest, no task, needs B6.
   Expiry: honest about the mechanism, wrong about the number (M1); no
   design change if the reaper is taken (Duke 3). Reload: honest, task
   exists (`tasks.md:21`), acceptable either way if the result is
   written as a limit; the overlap length is wrong regardless (B4).
   Rate cap: honest, the task checks presence only; it needs one
   measurement and a named mechanism.
3. **Credentials.** Owner from the verified `sub`: correct. Nothing
   binds a credential to a tenant at the daemon, and the contract says
   so. Lifetime matches the room token. A credential is a bearer token
   and can be shared; the password never crosses the wire, so an
   observer cannot mint from a capture. Weaker than it must be: labels
   in clear (M7), the secret's entropy (M9), and the overlap (B4).
4. **Abuse.** B3. The cap limits bytes, not ports.
5. **Isolation.** M8. Distribution on `127.0.0.1:3470` is shown by
   `s1-eturnal.log:14` for the container. The cookie is not described.
   Both must be seen again on the chosen artefact (M2).
6. **Spec and evidence.** M4, M6. S1 expiry is backed
   (`s1-expiry.txt`, log lines 24–27). S1 blacklist is backed for seven
   addresses. S2 is backed for a rule the contract does not specify.
   The ASK list misses four decisions (below). Task order: see the end.
7. **Edge on the same host.** Left for later, stated in one sentence
   (`design.md:43`). As designed nothing on the host is reachable
   through TURN, the edge included (M10).

## Required changes

1. **Lifecycle (B1).** The unit owns the egress rules. They are
   installed before the process starts, and a failure to install them
   fails the unit. They are removed after the process has exited. They
   are present after a reboot before the daemon runs. Inbound openings
   are added after the unit is active and removed when it stops. Add
   the scenario "the rules cannot be installed: the unit is failed and
   nothing listens on 3478".
2. **Kernel filter (B2).** Rewrite `spec.md:25`:
   - It applies to every packet owned by `mjolnir-turn`, every
     protocol, with no reference to the relay port range.
   - Exceptions, each named: TCP between `127.0.0.1` and
     `127.0.0.1:3470`; and source port 3478 only if Duke 2 is "yes".
   - It drops destinations of type local, broadcast and multicast, and
     the IPv4 ranges written out in the requirement, not "that same
     set". It drops all IPv6 from the uid.
   - Its verdict does not depend on ufw's rules. Either a table of its
     own (`inet`, output hook; a drop there is final whatever ufw
     accepts, and one ruleset covers both families and the rate limit),
     or position one in `OUTPUT` with a check that fails the unit.
   - A repeatable script beside `scripts/test-relay-stop.sh` proves it
     on a host with ufw active, with the daemon blacklist emptied and
     the relay range left at eturnal's default. Targets: loopback, the
     host's own public address, `10.200.0.1`, `10.255.255.1`, a live
     guest on a TAP, `224.0.0.251`, `169.254.169.254`. Every capture is
     empty and a public peer still receives.
3. **Per-owner bound (B3).** Before any code: observe on 1.12.3 whether
   an eleventh Allocate on one username is refused, and what
   `LIFETIME` the server grants when asked for the maximum. Then write
   the bound an owner cannot exceed and the mechanism (Duke 3). Say in
   the threat table that `turn:relay` is held by every signed-in user
   unless Duke 1 changes that.
4. **Overlap (B4).** The old secret stays for the longest credential
   life plus 60 seconds. Add an emergency replacement: new secret only,
   unit restarted, every allocation dropped, stated as host-wide.
5. **Room mint (B5).** Define "configured" as a file read on every
   mint, like the relay's. State that any TURN fault (file absent,
   disabled, secret missing, wrong mode) omits `ice_servers` and
   changes nothing else in the response or its status. Add that
   scenario.
6. **IPv6 (B6).** In the spec: no IPv6 relay address, the daemon
   listens on IPv4 only, an Allocate that requests an IPv6 relay
   address is refused (scenario), the unit cannot open an IPv6 socket
   if the daemon starts that way (`RestrictAddressFamilies`), and the
   uid's IPv6 output is dropped whole.
7. **Expiry (M1).** Replace 600 with the measured ceiling everywhere.
   Remove the client-side `LIFETIME` sentence.
8. **Artefact (M2).** Name one artefact, its exact version and its
   SHA-256, verified by the deploy. Replace "SHALL set
   `STUN_SERVICE=false`" with behaviour: at start the daemon sends no
   packet to any address but its clients, shown by a capture. Observe
   the distribution listener and the cookie file (owner, mode, how it
   is generated) on that artefact.
9. **Spec completeness (M3, M6, L5).** Name each inbound rule. Add
   "a failed enable opens nothing". Add the scenario that an Allocate
   with REQUESTED-TRANSPORT TCP is refused. Add scenarios for the rate
   cap (measured egress stays under it) and the distribution port.
   Move document rules out of the requirements and add `## Limits`.
   Write the credential route's body, response, order of refusals and
   503 cases.
10. **Evidence (M4).** Uncheck `tasks.md:12` or reword it to what was
    run. Add probes for the unprobed ranges and for a blacklist entry
    outside `recommended`. Add a client over TCP 3478. Add the bead's
    journey: a browser on another network, relay-only, through the
    laptop's install.
11. **Facts (M5, M7).** Correct the DNS statements. Make the `g1`
    shape one thing in the spec, design, verdict and tests.
12. **Unit and secret (M8, M9).** Put the sandbox in the spec: empty
    capability set, `ProtectSystem=strict`, `PrivateTmp`,
    `ProtectHome`, `PrivateDevices`, memory, task and CPU limits. The
    secret is at least 32 bytes from the kernel generator. The mint
    checks owner and mode and returns no credential on a failed check.
    The rotation script changes the secret list only and proves the
    rest of the YAML is byte-identical. A malformed YAML fails the unit
    at start and is refused at reload with the old settings kept
    (observe both).
13. **Not covered (M10).** Add the same-host edge and the consequence
    for the two-filter claim.

## Decisions for Duke, in answer order

Each has the recommended option first and the cost of every option.

**1. Who gets a TURN credential before metering exists?**
This is new. The ASK list does not have it, because the scope looked
like the gate.
- **Recommended: an operator list of owner ids.** The room mint adds
  `ice_servers` and `POST /api/turn/credentials` answers only for
  owners on the list, until `mjolnir-rurh.4` lands. Cost: a tenant has
  to ask to be added, and a few lines of code and one file.
- Every signed-in user, as written. Cost: any free account can hold
  ports and spend the host's rate cap, and the only response is to
  switch TURN off for everyone.
- Calls only, no general route. Cost: none in abuse terms, because
  `c1` has the same reach as `g1` on this daemon; it only removes the
  route.

**2. May a guest, or the host itself, be a TURN client?**
This decides the kernel filter's one debatable exception.
- **Recommended: no.** Open 3478 on the public interface only and
  filter the whole uid with no exception for port 3478. Cost: an
  application inside a guest cannot use this server for a relay
  candidate, and a health probe has to come from outside the host.
- Yes. Cost: the filter must let source port 3478 through, which keeps
  a reflection path from 3478 to guest addresses and, if the daemon's
  filter ever fails, a one-way path from one guest to another.

**3. How is an owner bounded, and how long may an expired credential
keep relaying?** Answer after the first owed spike.
- **Recommended: keep eturnal and add a reaper.** A root timer, about
  once a minute, reads `eturnalctl sessions` and disconnects sessions
  whose username time has passed and owners above a fixed number of
  allocations. Cost: a script that parses eturnal's output and can
  break on upgrade, and limits that take up to a minute to bite.
- Keep eturnal with no reaper. Cost: an expired or stolen credential
  relays for the server's maximum lifetime after expiry, and an owner's
  bound is whatever eturnal turns out to enforce, possibly nothing.
- Switch to the Pion daemon. Cost: about 500 lines of Go that we own
  and review, and S1 and S2 are run again. Gain: exact quota by owner,
  a hard lifetime, and `c1` confined per packet.

**4. What does the username carry?**
- **Recommended: expiry, class and owner only.** The mint log keeps
  room and participant. Cost: a TURN session line cannot be tied to a
  room without the mint log.
- Room and participant too, as written. Cost: tenant room names and
  participant labels are readable on the network path and in the
  daemon's journal.

**5. The host-wide cap.**
- **Recommended: 25 Mbit/s until metering lands.** Cost: about five
  relayed video calls at once on the host. Worst case about 270 GB a
  day.
- 100 Mbit/s, as written. Cost: worst case about 1.08 TB a day of
  outbound transfer on the host's plan, beside the relay and the sites.
  Check the plan's allowance before choosing this.

**6. The seven ASKs already in `tasks.md`.** Recommended: confirm the
server (subject to decision 3), the unit, the ports and the REST
credentials. The filter ASK (`tasks.md:32`) is replaced by decision 2.
