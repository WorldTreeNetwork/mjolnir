## Blind pass (Why + living spec + ADR 0008 + `put_opaque/4`, before design.md)

Written independently, then compared. These are the concerns I expected the
author to have answered — not a competing design.

1. Real Blake3 is the critical-path blocker: commitment *and* holder
   fingerprint both sit on `Sites.Crypto.blake3_hash/1`, still SHA-256.
2. Nonce must be server-issued, bound to token identity, single-use, TTL ≤ exp;
   signature over nonce ∧ token-id or a harvested sig replays across tokens.
3. Deposit is owner-only; "guest cannot write `_opaque/secrets/`" is enforced by
   the *absence* of a guest-reachable deposit path, not by FS perms.
4. Commitment binds token→secret-version against a substituting host; recipient
   MUST check `Blake3(domain||salt||V)==C`. Hiding assumes high-entropy secrets.
5. Refuse: unsalted `Blake3(secret)` anywhere; SHA-256 stub as Blake3; redeem in
   `@skip_auth_paths`; a new overlay port + `tokenator_url`.
6. Tradeoff: v1 copy-out to a fat holder is a deliberate confidentiality
   reduction — post-redeem the secret is in guest RAM/tmpfs and the host loses
   control; no-write-to-rootfs is a consumer discipline the host cannot enforce.

## Steelman — how the design answers each

- **(1)** Decision 1 pins real Blake3 and routes NIF wiring to
  `add-biscuit-runtime` (`mjolnir-axsb.1.3`); the spec's *SHA-256-stub-as-Blake3*
  rejection scenario is the review gate that keeps 1.4/1.5 from landing on the
  stub. Answered by a SHALL + a gate, not just prose.
- **(2)** Decision 3 is stronger than my take: server-issued `{nonce, aud, exp}`,
  single-use via the auth-challenge v1 nonce store, reuse fails closed, and the
  holder signs canonical `{biscuit_hash, nonce, aud}` — covering token identity
  **and** audience (cross-service replay too). Fully answered.
- **(3)** Owner deposits through the authenticated host API; the fourth `call/2`
  Auth branch confers *only* redeem+challenge, which is the mechanism that keeps
  a redeem Biscuit off the deposit path. Scenario "Guest cannot deposit" locks it.
- **(4)** Recipient-checks-commitment is explicit ("a value that does not match
  is not this token's secret"); salt defeats the precomputed table. Answered for
  the stated scope (high-entropy foreign secrets).
- **(5)** All four refusals exist as spec rejection scenarios + design "Rejected"
  lists. Affirmed as standing gates for the implementing nodes.
- **(6)** Decision 4 names copy-out as the deliberate v1 superset and the thin
  proxy as the more-secure pattern (handoff: "GitHub proxy that never copies the
  PAT"). The design is honest that no-write-to-rootfs is consumer discipline
  (spec: "unless Z wrote them there in violation").

My blind take converged on the six concerns the author had already closed, and
every send-back from the prior (Fable) round is checked `[x]` with the human
amends folded. That convergence is the accept signal.

## Non-blocking notes (for the implementing nodes, not owed here)

- **N1 — DAG edge, not just numbering.** The Blake3 dependency is currently
  enforced only by the rejection scenario at advise time. When `add-tokenator-
  redeem` / `add-capability-mint` open, state the hard edge explicitly: they MUST
  NOT land before `add-biscuit-runtime` wires real Blake3. Belongs in those nodes.
- **N2 — commitment hiding is scope-bound.** Salt defeats precomputation, but with
  salt+commitment on the wire a *low-entropy* secret is brute-forceable; the
  hiding property holds only because the payload is high-entropy foreign secrets
  (PAT/API key). Fine for v1 scope — worth one line in the mint node's doc so no
  one later deposits a short shared secret and assumes the commitment hides it.
- **N3 — challenge-branch auth.** Decision 3 says the challenge "serves" redeem
  but does not spell out what the challenge branch requires to hand out a nonce.
  Issuing a nonce to a bearer is harmless (a nonce alone grants nothing), so this
  is an `add-tokenator-redeem` implementation detail, not an architecture gap —
  flagging so it is decided there rather than assumed.
- **N4 — terminology.** Decision 3 step 4 calls it "Identikey fingerprint" while
  Decision 1 explicitly says it is NOT `IdentiKey.fingerprint/1`. Same preimage
  (auth-challenge §5 `Blake3(dcbor)`) both places, so no correctness issue —
  readability only.

None of N1–N4 changes the architecture or the delta. They are node-local and
carry forward with the handoffs already listed in `tasks.md`.
