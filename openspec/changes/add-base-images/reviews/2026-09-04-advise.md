## Blind pass (written from Why + living spec + cited code only, before
opening design.md / tasks.md)

What I would pin the author to having answered:

1. **The default flip is not vaporware.** Flipping `mj deploy` off
   `deploy-node-bun` (`orchestrator.ex:50,113`) only converges with
   `mj spawn`'s `ubuntu-24.04` (`config.exs:21`) if `ubuntu-24.04`
   can actually build a Node app. Does `mise install` already exist as
   a keyed deploy layer, or does the flip ship a broken deploy?
2. **Weakening `inject_guest_agent` to a refresh cannot brick spawns.**
   If inject becomes a no-op, every declared image must already bake the
   agent — so the recipe post-condition and the live rebuild must land
   *before* the inject contract is relied on, not after.
3. **In-place alias rebuild + name-keyed deploy cache is a correctness
   hazard.** If `base_layer_id` is the alias *string*, a rebuild leaves
   two different filesystems sharing a cache key and a redeploy clones a
   silently-changed root. Is the cache parent a content pin or a name?

What I would refuse: shipping the D6 pin/alias SHALLs into *living*
specs while the resolver is unimplemented — that repeats the 2026-08-16
"don't import unimplemented behavior" learning.

One tradeoff: four independent debootstraps sharing three helpers buys
freedom from a FROM-ubuntu DSL at the cost of copy-paste drift across
recipes — the exact mechanism that made `ci-ubuntu-24.04` unreproducible
before.

## Carried nits (notes, not blockers — none is send-back grade)

These are owed at the *later* nodes, not at this architecture write.
They do not gate `accept` because none is a defect in the ADR/deltas
themselves; all are for act.

- **N1 (for `mjolnir-b0gb.2`).** Deleting `@base/deploy-node-bun`
  breaks L5 nuke/respawn for any long-lived VM whose StateStore
  spawn_config still records that `base_image`. The retire node should
  sweep StateStore and migrate those records to `ubuntu-24.04` (or
  document a loud nuke failure) before deleting the subvolume. (Fable
  finding 1; concurred.)
- **N2 (for `mjolnir-b0gb.6`, tightening D2×D6).** The pin/unmanaged
  taxonomy is the one genuine spec-internal tension. Living spec:
  "not declared ⇒ unmanaged, never auto-deleted"; D6: pins live under
  `@base/`. A pin (`ubuntu-24.04-20260827`) is not a catalog-v1 table
  name, so by the letter of D2 it reads as unmanaged — which then
  collides with future pin GC ("GC of unreferenced pins is later").
  Resolve before the b0gb.6 delta or the `mj bases` JSON shape freezes
  it: a pin produced by a declared alias's recipe is *declared-archived*,
  not unmanaged. `tasks.md:48-51` already reserves `kind`/`resolves_to`,
  which is the right hook. (Fable finding 3; concurred.)
- **N3 (fold discipline).** The D6 pin SHALLs are present in the change
  delta but are *not yet true of the system*. `tasks.md:25-29` already
  carves the fold correctly ("do not import unimplemented HTTP into
  living specs"); the same guard must apply to the pin/alias
  requirement — fold only the architecture SHALLs already true of the
  design, defer the pin SHALLs to when b0gb.6 lands.
- **N4 (v0 operability, for the D5 runbook).** In-place rebuild deletes
  then recreates the live `@base/` name, so there is a spawn-outage
  window for the duration of a debootstrap. Cheap v0 mitigation:
  build into `@base/<name>.next` and swap, or note "rebuild in a quiet
  window" in the runbook. Structurally fixed by D6. Low urgency —
  tonight's rebuilds are done; this bites the next v0 rebuild.
