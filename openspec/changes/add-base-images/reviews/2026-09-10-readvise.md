## Blind take (Why + living spec + cited code only; written first)

1. **Pin.** `@base/` is declared OS roots; declared = recipe in repo AND on
   the v1 list; a pin from a declared recipe is declared-archived; unmanaged =
   no recipe (`spec.md:3-13`, ADR `0009:17-22`). Closed list, amended via ADR.
2. **Pin.** `ubuntu-24.04` is the default for spawn and deploy. Today
   `config/config.exs:21` already says ubuntu; `orchestrator.ex:50` still says
   `deploy-node-bun` and the anchor says it stays until `remove-deploy-node-bun`.
   Consistent with the spec's "Deploy default" scenario being later-act.
3. **Pin.** Declared recipes fail closed on the agent through one helper. Arch now
   does: `build-rootfs-arch.sh:19` sources it, `:165` calls
   `install_guest_agent`, which exits 1 without a binary (`guest-agent.sh:60-72`)
   and re-verifies binary + unit + wants symlink (`guest-agent.sh:139-153`).
   Replacing `arch-chroot … systemctl enable` with the helper's plain symlink is
   equivalent for `basic.target.wants`.
4. **Refuse.** D5 cache-drop as worded: "delete `@snapshots/deploy-*` layers
   whose cache parent is that alias string" (`spec.md:121-124`, ADR `0009:31-33`).
   (a) Not enumerable: layer metadata records no parent (`btrfs.ex:137-149`); the
   name is `deploy-<sha256(parent‖cmd‖input)>` (`builder.ex:36`,
   `cache_key.ex:74-80`), a one-way hash. (b) Not sufficient, and actively
   harmful: layer N's key is a function of layer N-1's *name*, not its bytes
   (`plan.ex:95-98`), so after an in-place rebuild layers 2..N keep their names.
   Delete only layer 1 → planner marks 1..N miss (`plan.ex:101-102`) → builder
   re-snapshots step 2 to a name that still exists → `{:snapshot_exists, name}`
   (`btrfs.ex:116-117`) → `{:step_failed, …}` (`builder.ex:172-186`). Followed
   literally, the clause wedges every multi-step redeploy after a rebuild. The v0
   clause that is true today: drop the whole `deploy-*` cache (transitive
   ancestry is the same set, since nothing records ancestry).
5. **Refuse (wording).** "SHALL be built by separate **debootstrap** recipes" now
   lists `arch` (`spec.md:195-197`), which is pacstrap
   (`build-rootfs-arch.sh:77`, `:112`). Say "bootstrap recipes".
6. **Concern.** "A pin produced by a declared alias's recipe is declared" needs
   a provenance rule the lister can apply. `@snapshots/` has `.json` sidecars
   (`btrfs.ex:106-150`); `@base/` has none. Name pattern `<alias>-YYYYMMDD` is a
   heuristic: a hand-rolled `ubuntu-24.04-20260901` would report declared. Owed
   by `add-base-image-pins`, but the scenario (`spec.md:51-58`) reads as if
   provenance exists today.
7. **Concern (fold).** `scripts/build-deploy-base.sh:4,32` still produces
   `deploy-node-bun`, so "Recipes SHALL NOT produce it" (`spec.md:70-71`) is
   false on the tree at fold time. `docs/LEARNINGS.md:10`: fold must not import
   unimplemented SHALLs. Needs a fold split that holds that line for
   `remove-deploy-node-bun`, or reframes it as the review rule the next
   paragraph already states.
8. **Tradeoff.** v0 in-place alias rebuild buys single-tenant simplicity at the
   cost of every deploy cache and the reproducibility of prior releases. That is
   fine if the drop is honest (full cache) and D6 lands before a second tenant.
   The "Cache parent is not the alias" scenario is the real fix, correctly
   deferred.
9. **Minor.** Arch keeps its own relative-path `AGENT_BIN` search
   (`build-rootfs-arch.sh:28-40`) that the helper's resolver duplicates with a
   different order (`guest-agent.sh:31-52`). Two resolvers is the shape
   `mjolnir-0e8` removed. Harmless today.
10. **Verdict shape.** If design.md/tasks.md already scope the D5 drop as full
    cache with the collision reasoning, this is a spec-wording fix, not a design
    change. If they repeat the alias-parent wording, it is a send-back on one
    clause.

## Findings (send-back grade)

1. **D5 cache-drop clause is not executable and, approximated, breaks
   redeploy.** `spec.md:121-124` + scenario `:138-139`; ADR `0009:31-33`;
   design.md `:193-200`. Mechanism, all in shipped code:
   - Layer names are `"deploy-" <> CacheKey.compute(parent, cmd, input)`
     (`builder.ex:36`, `cache_key.ex:74-80`). Snapshot metadata written per
     layer is `name / source_vm_id / owner_id / created_at / size_bytes /
     generation / gen_at_creation / readonly` (`btrfs.ex:137-149`). No
     parent, no base. "Whose cache parent is that alias" cannot be listed.
   - `Plan.compute` folds the previous layer's *key* into the next
     (`plan.ex:95-98`). Rebuilding the alias in place changes no name in
     the chain. After deleting any proper subset, the first miss makes the
     rest misses (`plan.ex:101-102`), `run_steps` re-snapshots to the
     surviving names, and `create_snapshot` returns
     `{:error, {:snapshot_exists, name}}` (`btrfs.ex:116-117`), which
     `run_steps` halts on (`builder.ex:174-186`).
   - Deleting *nothing* is the silent-hit case the prior review named;
     deleting a *subset* is a hard fail; only deleting the *whole*
     `deploy-*` cache is correct under v0, and that is what the clause
     must say. Exact v0 wording: *After an in-place alias rebuild the
     operator SHALL delete every `@snapshots/deploy-*` layer, via
     `mj snapshot rm` / `DELETE /api/snapshots/:name` (which also removes
     the `.json` sidecar the planner lists from, `btrfs.ex:306-331`,
     `:365-374`), not raw `btrfs subvolume delete`. Nothing records a
     layer's parent, so the chain under the rebuilt alias is not
     separable from the rest; D6 (`add-base-image-pins`) makes the parent
     a pin and removes this step.* Running service VMs keep their
     `@vms/<uuid>` clones (same BTRFS property the requirement already
     states for base rebuilds). The `.json` point matters: an operator who
     follows the current text with `btrfs subvolume delete` leaves the
     sidecar, the planner reports a hit, and the builder boots from a
     snapshot that no longer exists.
   Apply the same sentence to ADR line 5, design.md step 5, and the
   "Stale ubuntu is rebuilt" scenario (`spec.md:138-139`: "AND every
   `@snapshots/deploy-*` layer is deleted").

2. **Fold table folds one code-state SHALL that is false at fold time.**
   tasks.md `:36`: "Toolchains are not OS roots (review reject) →
   fold-now". The requirement's second paragraph (`spec.md:70-71`,
   "Recipes SHALL NOT produce it") is a claim about the tree, and
   `scripts/build-deploy-base.sh:4,32` produces `@base/deploy-node-bun`
   until `remove-deploy-node-bun` deletes it (tasks.md `:63-64`). Split
   the row: the review-reject paragraph fold-now; "Recipes SHALL NOT
   produce it" PENDING on `remove-deploy-node-bun`. This is exactly the
   `docs/LEARNINGS.md:10` shape the table was added to prevent.
