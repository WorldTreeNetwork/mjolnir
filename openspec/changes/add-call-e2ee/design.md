## Decisions

### D1. Separate admission and content; put the label in the context

Room tokens authorize relay sessions and publish labels under `relay-room-auth`; their issuance, delivery and expiry are not encryption requirements. The mint, token claims and deployed relay remain unchanged. Content uses client-generated `{profile, kid, secret}`, with 32 random secret bytes; every holder derives a separate `Credential` for each publisher label using context **`mjolnir-call/v1/<owner>/<room>/<label>`**. It shares the room secret and kid, not a room-wide context. Opaque is **`credential.path("call")`**. A subscriber constructs the credential from the announced label, never the sender-supplied context.

The relay and host processes never receive usable key material; derived opaque paths, physical names and ciphertext necessarily reach them. The origin serving browser code is trusted for this iteration (Duke accepted 2026-11-23). Deriving the secret from a room token or server secret would give the operator content access and is rejected.

B1 is a correction, not an alternative still offered: the old room-context/path(label) layout does not bind payload keys to the label. Claim 5a demonstrates the attack; claim 5b rejects it with label context (`spikes/complete/logs/b1-relabel.log`). A holder cannot publish under another label if relay grants are enforced; a relay without the secret cannot move ciphertext across label contexts. A relay colluding with a credential holder can impersonate; holders are not cryptographically authenticated against one another.

### D2. Profile-specific path and reader instance rule

For **`moq-e2ee-01-wip` only**, the full path is `t/<owner>/<room>/<label>/<opaque>/<epoch>`, WebTransport relative spelling `<label>/<opaque>/<epoch>`, Iroh absolute spelling. Opaque is 22 base64url characters from D1's label credential and path("call"); epoch is canonical UUIDv7 from `credential.produce()`, never caller-selected for encryption. The owner chooses a random participant label when minting a guest token; the browser client should also choose a random room id. Display names stay encrypted.

The subscriber validates segments/opaque and consumes with that label's credential. **The first authentic bridge.tracks frame accepts the instance**; applying its snapshot still requires manifest schema validation. For one content credential/kid and label, try canonical candidate epochs greatest first, but advance the high-water mark only to the greatest authenticated epoch, never from an announcement. Start the **1500 ms** deadline when subscribing to bridge.tracks. Authentication failure bars that candidate for the rolling 60-second window. A timeout alone does not bar it: fall through, then retry after backoff starting at **3 seconds, doubling** on successive timeouts and **capped at 60 seconds**, so no backoff outlasts the interference by more than the rolling window. A manifest subscription the transport ends before an authentic frame counts as a timeout. Keep any accepted stream playing while probing candidates at/above the mark. Limit **all probes including retries** to **12 per label per rolling 60 seconds**, one at a time; expose `unavailable_retryable` when the budget is spent. Do not let candidate failure or budget exhaustion clear the accepted stream/mark. These bounds limit work, not an active relay's power to deny service.


**Track failure after acceptance is separate:** one authentication failure at the pin terminates that track's subscription, not acceptance of its instance. Resubscribe the track on the same consuming generation, retaining the group-start/last-authenticated-frame mark and its local mirror, at most **6 resubscriptions per track per rolling 60 seconds**. Do not rebind the generation to reset the key budget. On exhaustion expose track-scoped `unavailable_retryable`; retry when the rolling budget permits. A failure here never bars the accepted epoch as a failed candidate. C1 must exercise terminal subscription failure and recovery explicitly.

The mark lives **only in page memory**, scoped to credential/kid/label for the page lifetime; no localStorage, sessionStorage or IndexedDB. Below-mark instances may authenticate diagnostically but are not selected for rendering. If only those remain, expose `older_stream_only`; never silently downgrade. Reload discards the mark and is a fresh reader, potentially vulnerable to same-instance replay again; D3 also requires re-entering the invite after reload.

A publisher watches its own label through the same authentication rule. When another greater instance authenticates, stop this page's old publication and expose `superseded_by_another_instance`. A user action to resume on this device mints a new generation; an announcement alone never stops the publisher. On sane clocks this repairs switching to a second device and back. A fast-clock accepted publisher can still hold the label ahead of a corrected clock; UUIDv7 ordering is not a clock-validity check. Expose `older_stream_only`; manual stream-switch UX belongs to `mjolnir-rurh.5`, not an automatic reset of the mark.


**Replayed fast-clock limit:** a relay with a recording of an authentic instance whose epoch is greater can replay it to any reader, including a fresh page. It accepts, moves the mark, and can make the publisher stop again after each explicit resume while new correct-clock epochs remain lower, until real time passes that epoch's stamp. No new secret is needed for this replay. Candidate for the successor profile, not a WIP rule here: reject epochs over a stated reader-clock margin (proposed **5 minutes**, to validate at that profile change). Reader clock validity and a suitable margin need testing; this does not silently change current epoch parsing.

**Unrun policy:** the browser harness never ran any instance rule: `spikes/complete/page.ts:71,86–88` takes the first matching/active candidate; per-run secrets avoided collisions. The Rust probe sorts but has no mark; `spikes/rust/tests/b1_relabel.rs:297` already asserts the forged re-mount is announced and greatest. The previous announcement-driven mark would have pinned the reader away from the real stream. Complete finding F2 reports the stale first-match incident; the retained `spikes/complete/logs/b-rekey.log` records the later manifest diagnosis, not that incident. C1 must test authenticated advancement, fall-through, rate bounds, second device and reload. A relay can still withhold a newer real stream or replay to a fresh reader; this is not proof of newest content.

This ordering/layout is WIP-specific. A future candidate is an authenticated start stamp/counter in the manifest, but none is added now. D7/ADR carry reconsideration at a successor-profile bump; it is not a behaviour requirement in the spec.

The default wire loses the upstream route Instance (`spikes/e2ee-path.out`); iroh-live cannot supply it at its pin. Epoch-in-path now has native media evidence too (`spikes/complete/logs/b-native.log`), rather than the old inference from a WebTransport test. Alternative A requires every peer and relay to opt into lite-07 plus an iroh-live instance hook; alternative C needs an authenticated application channel absent for guests. Recommend the path fallback at this pin; Duke's existing epoch-layout ASK remains open. The layout belongs to the profile named in the invite. Upstream's successor deletes UUIDv7 epoch ordering: at a `moq-e2ee-01` bump this rule and path must be decided again, not silently carried forward.

### D3. Link delivery and the accepted browser boundary

Content invite fields are `#v=1&p=moq-e2ee-01-wip&kid=<u53>&k=<43 base64url characters>`. The optional initial/cumulative removal field is `removedLabels=<unpadded base64url of UTF-8 JSON array of canonical labels>`, limited to **4096 encoded ASCII characters and 32 unique entries**. Initial omission means empty; replacements must include it, covering **every label removed since CreateCredential**, not just this cycle. Reject invalid encoding, duplicates/noncanonical labels or overflow, never truncate. This is application invite metadata, not a new crypto profile field. Context is derived as D1, not delivered by the link. The call page may also receive an independently issued room token; if a token is delivered in a link it goes only to relay admission, never other page requests, logs or reports. Encryption does not require co-delivery or prescribe its format.

The page reads the fragment, checks the 32-byte length, imports the secret to a non-extractable HKDF CryptoKey, passes only the handle to the library, and replaces the current URL using `history.replaceState`. This removes the fragment from the address bar and **current session-history entry only**. Do not retain raw bytes in application storage or error reporting; parser strings cannot be reliably wiped. Guest handles and parsed invite material live only in page memory. The owner keeps the current raw secret or invite text in a private page-memory closure to issue later invites; no application persistent storage or IndexedDB key caching is allowed. Discard references on leave, call-end or credential replacement (best-effort overwrite byte buffers; strings cannot be wiped), except consuming handles retained under D5. Reload loses both owner copy and guest handle: expose `invite_needed`, join/publish nothing, and require the invite again; an owner without it starts a new call credential rather than recovering from storage. Serve no third-party scripts, Referrer-Policy no-referrer and a CSP limiting scripts and connection origins. The content key must never reach mint requests; token admission and opaque protocol data are explicit network exceptions, not exceptions for the secret.

**Navigated-link limit:** Chromium and Firefox write the full initial invite URL, key and token to persistent history before page script runs; Chromium also retains them in session files and `segmentation_platform/ukm_db`. History sync and URL-keyed metrics sending fragments off-device are **unverified**, not excluded by the network-log test. replaceState cannot prevent or erase this (`spikes/complete/logs/b3c-history-{chromium,firefox}.log`). No claim is made about unscanned compressed Firefox session storage. Duke must accept this limit with a page security note, or choose secret delivery other than a navigated URL. Author recommendation remains paste into an open page after I1 validation. The second reader recommends a disclosed navigated link with one secret per call for the first release, plus paste as a second entry; both recommendations remain in the open ASK. Same-document hash navigation is untested and must not be described as avoiding persistence.

Duke already accepted that the page origin is trusted (2026-11-23). Non-extractable keys are a partial mitigation: both browsers reject export but a script holding the HKDF handle derives raw media keys and decrypts (`spikes/complete/logs/crypto-browsers.log`). They stop export, not use or access to plaintext, and cannot defend against replaced origin code.


**Secret lifetime / Duke decision (97d8a14): one secret per call, no standing room link.** create a fresh 32-byte secret on the owner's explicit CreateCredential/start-new-protected-call action, use it for that active call's invitations until rekey or call-end, and never automatically reuse a cached secret for a new call. Leave/reload deletes application-held state, not browser history or externally saved invitations. An external invite may rejoin that same call, not become a standing link for later calls. A later call creates a fresh secret; page-memory storage and reload-needs-invite rules remain. A retained secret still decrypts recorded ciphertext for that generation; call-end is not cryptographic erasure. This implements the recorded per-call decision; persistence of old invites remains a stated limit.

Admission limits owned by `mjolnir-rurh.5` and existing `relay-room-auth`, not this encryption capability:

1. A link's token expires at its fixed exp, normally at most 3600 s after mint, not after opening (ceiling is operator-configurable).
2. A link guest cannot renew: only the owner can mint this room's tokens. Calls end at exp; owner refresh/reconnect or future delegated invites are separate work, with no delegated-invite change currently named here.
3. One link carries one publish label. Forwarding it shares that label; the reader instance rule selects one stream, not two people. The owner must issue per-guest links.

### D4. Both bridges use one protected manifest surface

Choose the **manifest model demonstrated by the complete spike**, rather than the review's preferred catalog-only model. Both browser and native bridges carry every local semantic track, catalog representations included, plus protected **`bridge.tracks`**, all under D2's broadcast. Each manifest group has one JSON frame:

`{"<semantic>": {"timescale": <units/s or null>, "maxAgeMs": <number or null>, "priority": <i8>}}`

It is a complete current track snapshot, encrypted like any track. Publish an updated snapshot when the track set changes and refresh every second while live, so late readers and rekey do not depend on a single cached snapshot. Readers obtain semantic names from this manifest and derive physical names with their consuming generation; they do not hardcode browser or native track names. The following reader policy replaces the harness native reader's use of relay TRACK_INFO; it has not run. Skip duplicate listed names within a generation instead of creating the same protected track twice. Keep track handles across camera toggles, or mint a new generation when a fresh producer is required.


**Manifest v1 reader policy (unrun):** the JSON map above is selected by invite `v=1` and context `mjolnir-call/v1/...`; a different schema requires a new invite/context version and unsupported versions are refused. No envelope is inserted into the tested v1 map. Cap each decrypted manifest frame at **16 KiB** and **32 entries**, counting UTF-8 bytes; reject the whole snapshot before track allocations/subscriptions if it exceeds either bound. Refuse duplicate JSON keys, empty/non-string names, names over 15 UTF-8 bytes, non-object entries, extra metadata fields or invalid values: timescale is null or a positive safe integer, maxAgeMs null or a finite nonnegative safe integer, priority an integer in [-128,127]. No malformed snapshot partly updates state.

Use **authenticated manifest metadata** to build local tracks, never relay-supplied TRACK_INFO as an authority. A TRACK_INFO difference is reported through `metadata_difference`, never grounds on its own to reject that track or substitute relay values. Lite-05/06 encodes a scale-less track as timescale 1000, so manifest timescale null versus relay 1000 is legitimate; C2 must run this case on moq-lite-06. Apply a complete snapshot only after authentication, schema validation and a group start strictly greater than the last applied manifest group for this kid/label/epoch. Reject duplicate/older groups and ignore any late frame from an older manifest group; accept only one frame per manifest group. This is D6's zero-reorder policy. It cannot establish freshness for a newly loaded page. The existing cross-direction logs establish the shape/interoperability, not these new bounds, precedence or ordering checks.
Evidence: the first bridge died on JS `Failure: reuse` after re-listing; an early manifest missed audio. Duplicate suppression and periodic refresh fixed the harness (`spikes/complete/logs/b-rekey.log`, finding F3). Both directions work with the shared JSON shape (`spikes/complete/logs/b5-cross-{chromium,firefox}.log`); that does not separately establish every native periodic-refresh edge case, which remains a bridge conformance test. The catalog-only/no-extra-track model is **unrun**; adopting it now would discard the tested discovery mechanism. This manifest is an application wire commitment for this profile, to revisit when upstream trait wrappers remove the bridges.

Native Node::publish_with wraps LocalBroadcast's local, never network-connected plaintext origin. Decryption mirrors into another local origin for RemoteBroadcast/Watch. Groups, timestamps and payloads pass through the bridge; names and catalogs reach the relay encrypted. No fork is needed at these pins (`spikes/complete/logs/b-native.log`). **Mixed-room limit, not a codec SHALL:** no signal tells a publisher a native reader is present. Native H.264-only support is a source-derived constraint, not established by the cross-direction log; that log shows Chromium→native decode and WebCodecs H.264 support but does not print the emitted codec. An explicit owner-selected mixed-room codec setting or always-H.264 policy needs I2 before C2 fixes a codec rule. Firefox H.264 publication to native remains unrun. Browser reading native H.264 succeeds in both logs. Disable plaintext stats/echo and never attach a plaintext origin to a session.

### D5. Removal, distribution and immediate retirement

The owner generates a greater kid and fresh secret, and distributes it only to remaining members. This change guarantees same-session switching only for clients **already supplied** the replacement credential through an in-app API. For link guests the baseline is a new per-guest replacement invite and rejoin; delivery into an open page is not demonstrated. Recommend an explicit paste-replacement-invite action in `mjolnir-rurh.5` so a guest can adopt it on the same session, as Duke chose, pending the I1 network/history proof. The rekey harness injects the credential directly, not by paste or hashchange.

The replacement credential handoff also carries an owner-issued **removedLabels** list of canonical participant labels, covering every label removed since CreateCredential, including cycles a reader missed; its invite encoding/bounds are D3. It is application delivery metadata alongside the credential, not a relay announcement or an addition to the frame profile. A receiving page immediately stops rendering and unsubscribes those labels, including buffered old media, even while their tokens/broadcasts remain live. For every other label, old-key reading is permitted only until that label's first accepted/authenticated instance under the new kid **or 10 minutes from adoption**, whichever occurs first; then stop its old subscriptions and discard that label's old consuming handles. Discard the old credential handle when no retained labels need it, or on leave/reload; never use it for producing. Use elapsed page time for the 10-minute bound and never extend retention for the same old credential on a later replacement. When it expires without new-key media, expose `waiting_for_new_key`. **During retention the removed member, helped by the relay, can forge old-key media for any retained label**: the timeout bounds this exposure, not the forgery itself. Ten minutes allows hand delivery taking minutes without unbounded old-key access. The roster/removed-label handoff is unrun and I1/C4 must cover it; it is not inferred from announcements.

On adopting the replacement, a publisher announces its new producing generation and **immediately stops all old-generation seal calls, finishes tracks and closes the old broadcast**, without waiting for readers. Assert no seal under the retired generation **at the publisher**, not from a subscriber's tail or an empty announcement set. Remaining readers still waiting for the new credential lose each publisher that has retired, for the entire hand-out delay; with hand-delivered links this can be minutes. Read-only retention is not permission to keep old-key publishing for continuity.

**Completion at the owner's client** means every canonical label to which that owner issued a replacement credential for this cycle has an accepted/authenticated instance under the new kid; the owner keeps that expected-label set locally and reports missing labels as pending. A non-publishing recipient has no accepted instance to observe and stays `removal_pending` with reason `nonpublishing_unobservable`, not a publication failure. Removed labels are excluded and stopped locally. Reload loses this cycle's local recipient set; report completion unknown until the owner re-establishes it, never rebuild it from announcements. A relay can delay this observation but cannot invent an authenticated instance without a credential holder. This is a local observed-completion definition, not proof that every other tab retired: new instances do not attest old-process termination, and the host/holder-collusion limit remains.

A replacement invite and rejoin can leave the old tab publishing under the old secret. `mjolnir-rurh.5` must instruct guests to close the old tab before rejoining (or implement/test a same-origin stop signal); no new-page action here is claimed to stop another page. Keep this old-tab limit visible even if owner-side completion is observed.

Unloaded Chromium runs 1/2 completed both scenario checks and reported ~190 ms recovery with credentials already injected. They exit code 2 at the watchdog after scenario checks. I6 demonstrates that close returns but the original watchdog was never cleared; exit 2 did not establish a stuck close. This is separate from observed retirement/backfill churn (`spikes/complete/logs/b-rekey-run1.log`, `b-rekey-run2.log`). Leaving old publication up fed removed readers 34–46 more frames; buffered tails of 14–21 frames over 513–722 ms after retirement were measured at the reader, not a test of sealing. Only a 1.5-second immediate-retirement window was observed. Loaded run 3 had a 5 s tail and failed its switch timeout; I6 must explain load and teardown, I3 must cover Firefox, and C4 must cover two publishers receiving credentials at different times and read-only retention. None of those is claimed by runs 1/2.

A removed member retains old recordings and credentials, announcements and metadata access until token exp. A token-only client sees label/opaque/epoch and can fetch ciphertext if given physical names (the relay learns them from subscriptions); failing semantic-name requests is not denial of physical access (`spikes/complete/logs/capture-tokenonly.log`). It cannot decrypt new content. Token expiry ends the session: WebTransport publisher and reader media stop, bare Iroh enters Reconnecting; fresh owner tokens can resume with the same live generation/counters (`spikes/complete/logs/b-expiry.log`). Reconnect is not rekey; never reset counters under an existing generation. Iroh publisher mid-media expiry is still unrun; link guests cannot renew themselves.

### D6. Confidentiality and active-relay capabilities

Semantic track names at most 15 UTF-8 bytes share a padded physical-name length class (59 base64url characters). Catalogs, manifest and display names are protected tracks. Labels/room/owner, opaque/epoch, physical names, track counts/kinds, group/frame structure, public timestamps, sizes and timing remain visible; there is no traffic-analysis protection. Frame timestamps are **not authenticated**: 124→999 ms still decrypts (`spikes/complete/logs/b-interop.log`).

| Active relay capability | Limit / basis |
|---|---|
| Drop, delay, reorder; truncate a group after any frame | No completeness/liveness guarantee; pinned draft §Security Considerations, lines 329, 372–373 |
| Re-serve earlier groups in the same instance to a reader already in the call, as well as a new/late reader | The pinned profile has no grouped replay window (draft lines 326–329); D6 bridge ordering below is additional, unrun protection |
| Shift timestamps | Public metadata not AEAD-bound; `spikes/complete/logs/b-interop.log` |
| Replay a recorded greater/fast-clock instance, including to fresh readers | It authenticates and can repeatedly supersede the publisher after resume until real time passes its stamp; D2 clock limit |
| Hide a newer instance/credential or replay stale announcements | D2 cannot force disclosure; draft line 148, spike F2 |
| Spend a consuming key's budget through failed opens | WIP limits include failed attempts; upstream `quest/m3/e2ee-format.md:64-70` |
| Fetch/serve physical ciphertext to a token-only client | `spikes/complete/logs/capture-tokenonly.log` |
| Re-label to another context without a holder's secret | Rejected with Authentication after D1 fix; `spikes/complete/logs/b1-relabel.log` |
| Read/forge payload or splice across context/kid/epoch/semantic track/group/frame identity | Derivation/nonce boundary. `spikes/complete/logs/b-interop.log` tests payload, group, semantic name, wrong key and other label only; frame-index/kid/epoch rely on source/upstream vectors and need explicit C5 cases. No protection against a colluding holder |

**Group/frame policy (C1 pure rules tested; I8 media choice measured; bridge integration unrun):** per protected track/kid/label/epoch, keep a page-memory pair **(group start, last authenticated frame index)**, advancing only on authentication (and validation before manifest snapshot application). Re-offering the equal group resumes **strictly above** the saved frame index; already authenticated indices never reopen. The local track mirror lives as long as its mark. Resubscription on the same consuming generation resets neither, including a long-lived catalog group or mid-video-group continuation.

Keep zero reorder for **manifest and catalog**, so earlier groups cannot roll mirrored state back. **Media window is 120 ms**, selected by I8: `spikes/complete/logs/i8-shaper.log` delivered9000/refused0 at120ms, versus delivered7194/refused1806 at zero, under the documented userspace delivery model. This is not physical-network/playback proof; C2 still validates integration. At the pin audio is one 20 ms frame per group, so zero allowance discards every audio frame delayed past a later group and prevents the jitter buffer from recovering it; concealment is a real audio cost. Video groups are about 2 seconds, so refusing an equal group on resubscription could also stall video/catalog; the authenticated frame-index continuation addresses that gap. The old loopback bridge's arrival-based drop rule played real media but did not test authenticated marking under loss. C1's transport-free rule table and I8 must test mark/mirror survival and recovery; C2/C5 use the measured media choice. Replay to a fresh page, never-seen delayed content and relay retiming remain limits. No media zero-allowance default is implied; manifest/catalog alone remain zero.

**Adapter states and suggested page copy:** the adapter exposes states, not sentences. `mjolnir-rurh.5` surfaces them; suggested copy is `superseded_by_another_instance` → “you joined somewhere else”, `older_stream_only` → “newer stream expected, older one present”, `unavailable_retryable` → “stream unavailable, retry”, `metadata_difference` → “track metadata differs”, `invite_needed` → “invite needed”, `close_old_tab` → “close the old tab before rejoining”, and `waiting_for_new_key` → “waiting for the new key”. The owner also receives `removal_pending` (including non-publishing/unobservable recipients) and `removal_completion_unknown`. Suggested wording is not an adapter assertion. Tests inspect state and affected scope.


Permanent product consequence: the platform cannot record, transcode, transcribe, compose or preview protected calls while it lacks the credential. Only a credential-holding endpoint can perform those operations; putting one in a Mjolnir guest places its credential inside the host trust boundary. Content encryption permits future untrusted fan-out, but this change delivers no peer bandwidth savings: the relay still serves central egress.

Not chosen: SFrame with MLS would provide forward secrecy, post-compromise recovery and membership removal, but requires member identity keys and a delivery service with no implementation at this pin. A future MLS exporter could supply `{kid, secret}` per MLS epoch through the credential seam; this revision does not implement or claim those group-security properties.

### D7. Upstream is not ready yet; keep the adapter thin

### D8. Per-process-instance uniqueness

Every new publisher process instance calls produce() to mint its generation. Live reconnects may retain that generation only while all original nonce/claim state remains intact; do not serialize/recreate a producing generation. This change ships browser/native process clients, not guest snapshot support. Future guest constraints, including VMGENID/legacy-capture conditions, are in ADR 0017 rather than an unimplemented requirement here.
