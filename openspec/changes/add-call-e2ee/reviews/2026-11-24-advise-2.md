## Verdict in one screen

The architecture is accepted and should not be reopened: two separate credentials, a content secret Mjolnir never holds, the label in the credential context, no relay change, a harness-only capture. B1, B2, B3a, B3b, B3c, B5, B6 and all four evidence labels are resolved. The spike's logs support the claims I spot-checked.

It goes back because three of the seven requirements would be built wrong, or cannot be built, as written. All three are in text this revision added, and none of it has run in any harness.

1. **The reader's instance rule (N1).** The high-water mark is set from an announcement, which the relay writes. One fake announcement with no key pins a reader for good. The same rule locks out an honest person who opens their link on a second device and then goes back to the first. The browser harness never ran this rule: it takes the first matching announcement (`spikes/complete/page.ts:71`, `:86-88`).
2. **Removal (N2).** A remaining reader may keep the old credential "until old broadcasts end". The removed member controls when their own old broadcast ends, so remaining members keep seeing and hearing the removed member until that member's token expires. "Complete" also has no observer and no definition a test can check.
3. **One requirement cannot be built (N4).** "A browser publisher SHALL use H.264 when a native reader is present." A reader publishes nothing, so nothing tells a publisher that one is present.

The rest of the required changes are smaller: one relay power is stated too narrowly (N3), four sentences in the spec are process or pending decisions and not behaviour (N4), and the life of a secret and what a page reload does are not pinned (N5).

The third read can be a check of the edits listed under "Required changes" and nothing else. None of this blocks Duke's decisions, and none of it blocks the cheap owed runs (I7, I2, I6).

## New findings, most severe first

### N1. The reader's instance rule is set from data the relay writes, and it locks out honest people

`spec.md:20`: the receiver SHALL "select the greatest canonical epoch among active matching announcements. It SHALL retain the greatest observed epoch per credential/label and SHALL NOT automatically downgrade when that instance disappears".

"Matching" means the opaque matches. The opaque is public as soon as the label publishes once. "Observed" means announced. So:

- **A relay with no key can pin a reader.** It announces `bob/<bob's opaque>/<any greater canonical UUIDv7>`. `epoch.rs:52-63` accepts any timestamp. The reader selects it, every frame fails to open, and the rule forbids going back to bob's real instance. The spec says what to do when the selected instance disappears. It says nothing for one that stays and never opens. The change's own regression shows the selection: `b1_relabel.rs:297` asserts "the re-mount is still announced and still the greatest". A relay can already deny service by dropping, so this adds no confidentiality loss. It turns one forged line into a state that outlasts the forgery.
- **A second device locks out the first.** The epoch is the publisher's wall clock. A guest opens the link on a laptop (E1), then on a phone (E2, greater), then closes the phone. The laptop is still live and still publishing. Every reader that saw E2 now refuses E1. The laptop's user sees nothing wrong. A forwarded link does the same to the first holder.
- **A fast clock holds the label.** A publisher whose clock is ahead mints a high epoch. After a reload on a corrected clock, or a move to a device with a correct clock, its new honest epoch is lower and is refused until real time passes the old value.
- **Where the mark lives is not said.** In page memory it resets on reload, which the design half says ("replay to a fresh reader"). In storage, every case above becomes permanent for that credential.

No harness ran the rule. The browser reader takes the first match and breaks (`page.ts:71`); the rekey reader takes "the first one that is actually active within 1.5 s" (`page.ts:86-88`); per-run secrets were used so the question did not arise (finding D5). The Rust probe sorts and takes the greatest, with no mark. The design is honest that the behaviour "is not claimed as measured" (`design.md:42`). F2, the observation the rule is built on, has no retained log either, which `design.md:44` also says.

Keeping ordering and refusing rollback is a sound choice for this profile: without it a relay can end the live instance and leave an old real one playing as if live. The rule needs four pins to be buildable:

1. An instance is *accepted* only when a frame from it authenticates. The mark is the greatest accepted epoch for one kid and label. An announcement alone never moves it.
2. Candidates are tried from the greatest down. One that fails to authenticate, or gives no authentic frame within a stated time, is skipped and does not block a lower candidate that is at or above the mark. Bound the number tried per label per minute.
3. The mark lives in page memory for the life of the page. Say so, and say that a reload is a fresh reader.
4. A publisher watches its own label. When another instance under its label authenticates, it tells its user ("you joined somewhere else") and stops or, on the user's action, mints a new generation. This repairs the second-device case on sane clocks. State the clock case as a limit, with what the reader shows ("newer stream expected, older one present") and leave the manual switch to `mjolnir-rurh.5`.

On the question of what happens when upstream removes ordering: D2 and D7 say the rule is decided again at the bump, which is the right scope. A candidate worth recording now, since the manifest already exists: an authenticated start stamp or counter inside `bridge.tracks` gives ordering that the relay cannot write and that does not depend on the Instance type. It would also give a bounded freshness check for a fresh reader. This is a note, not a required change.

### N2. Removal: retention has no end, and "complete" has no observer

`spec.md:48`: "A remaining reader MAY retain its old credential read-only until old broadcasts end." … "Room-wide removal SHALL NOT be reported complete while any remaining publisher still publishes under the old credential."

- **The removed member stays in the call.** Carol's own broadcast is an old broadcast. She holds a valid token until `exp` (no kick, `relay-room-auth` Limits). A reader that kept the old credential keeps decoding carol for up to the token ceiling, 3600 seconds by default. She cannot hear the others. They can still see and hear her. A reader has no way to tell carol from bob-who-has-not-rekeyed-yet: both are old-kid only.
- **"Complete" is not defined for a test.** There is no roster. If completion is read from announcements, a relay can show the owner an empty old set while still serving old broadcasts to carol.
- **The scenario cannot be checked where it is written.** "carol receives no newly encrypted old-key frames after alice's retirement" (`spec.md:54`) is a property of alice's encoder. On carol's side the logs show 14 to 21 more decoded frames over 513 to 722 ms after retirement. That fits a drained buffer and cannot be told apart from new frames at the reader.
- **A rejoin leaves the old page running.** The baseline for a link guest is a new link and a rejoin. The old tab keeps publishing under the old key until someone closes it.

Immediate retirement itself is the right call. The alternative fed the removed member 34 to 46 more frames in about one second of overlap (`logs/b-rekey-run1.log`, `run2`). Its cost should be written once: a remaining reader that has not yet received the new credential loses each publisher that has, for as long as the hand-out takes. With hand-delivered links that is minutes.

Required:

1. Say when read-only retention ends and how a reader avoids rendering the removed member. Recommended: the replacement credential carries the removed labels, and a reader stops rendering those labels at once; for every other label, retention ends when that label has an accepted instance under the new kid. A fixed time limit is the simpler alternative and costs the slow hand-out case.
2. Define completion at the owner's client: every label that was issued a replacement has an accepted instance under the new kid. A relay can delay that. It cannot fake it.
3. Assert "no old-key frame after retirement" on the publisher (no seal under the old generation after the retire call), and keep the reader's tail as an observation.
4. State the old-tab limit and hand the fix (a same-origin signal to the old page, or an instruction to close it) to `mjolnir-rurh.5`.

### N3. Replay inside a live instance is stated too narrowly

`design.md:93` lists "Replay earlier ciphertext of the same producing instance to a new/late reader", citing draft line 329. The draft is wider. "Grouped frames need no duplicate window: a transport delivers each frame of a group once, in order, at its index" and "a relay may still delay, reorder, suppress, or replay ciphertext outside a receiver's window" (pinned `drafts/draft-lcurley-moq-e2ee.md:326-329`). For grouped tracks there is no window, so the profile does not refuse an earlier group re-served to a reader who is already in the call. With timestamps unauthenticated, the relay can also give it a current presentation time.

In a call that is replaying something a person said ten minutes ago. Whether the pinned Hang player drops a group whose sequence is behind the newest was not tested.

Required: correct the row in D6 and the ADR. Then either add a reader rule in the bridge (per protected track, drop a group whose sequence is at or below the newest opened, with a small reorder allowance) and a test in C1 or C5, or list it as an accepted relay power. The same rule protects the manifest from an old snapshot that makes tracks appear to end.

### N5. The life of a secret and a page reload are not pinned

- **When is a secret made, and for how long is it used?** `spec.md:4` says 32 random bytes, client-generated. It does not say per call. A standing room link leaves a working key in every guest's history for the life of the room. With one secret per call, a history entry is worth something only to someone who also holds that call's ciphertext, which means the relay host.
- **A reload drops the participant.** The fragment is removed, raw bytes may not be stored, and the handle lives in page memory. After a reload the URL has no key. Either say that a reload needs the invite again, or allow the non-extractable handle to be kept in IndexedDB for the life of the call and deleted on leave. Both are inside the accepted origin boundary. The contract must pick one, because C3 will build one.
- **The owner's copy.** "An owner making later links must retain secret/link material" (`design.md:52`). Say where: page memory, or storage, and what a reload does to it.

### N6. The manifest needs reader-side rules

Keeping the manifest is defensible. It is the mechanism that ran in both directions, it is encrypted and bound to label, kid, epoch and track like any track, and it leaks only a small steady group whose size tracks the number of names, which the count of physical tracks already shows. Its cost is an application wire format that upstream will not share, and a second list beside the catalog.

Missing on the reader side:

- **Bounds.** A member writes its own manifest. A removed member's manifest is still read by anyone who kept the old credential. Cap the frame size and the number of entries, and refuse names over 15 bytes on read, not only on write.
- **Which metadata wins.** "metadata SHALL agree with TRACK_INFO" (`spec.md:39`) has no consequence, and the native reader "ignores the values and uses the TRACK_INFO of each physical track" (finding §8). TRACK_INFO comes from the relay. Say that the manifest's values are the ones used, or say that timescale is relay-controlled along with timestamps.
- **Order.** Newest group wins, never an older one (N3).
- **Version.** Tie the JSON shape to the `v=1` of the invite and context, so a change to it has a number.

## The new decisions, on their merits

**Label-in-context layout.** Correct and sufficient against a relay without the secret. Owner, room and label are in the context; kid and epoch are in the key info; track is in the key info; group and frame are in the nonce; the profile is the HKDF salt. The reader builds the context from the announced label and the room it already knows, after validating segments, so the string is unambiguous. Still unbound, all stated: timestamps, where a group ends, and TRACK_INFO (N6). Replay across reconnects and across rekeys is covered by the epoch and the kid. Replay within a live instance is N3. A member plus the relay can impersonate, which D1 says.

**Reader instance rule.** N1. Implementable in a browser once the four pins are written: the epoch parser and its ordering vectors exist in both languages.

**Manifest in place of the catalog model.** Accept, with N6.

**Removal as replacement invite and rejoin, with immediate retirement.** Accept the direction, with N2. One mechanism would serve three open questions: pasting a replacement invite into the open page carries a new content credential (removal), a new room token (a call longer than one token), and is the delivery that keeps the secret out of history. That makes I1 the most valuable unrun item.

**Statement of limits.** Accurate on the four named: history, timestamps, token-only visibility, calls ending at `exp`. Missing: the removed member remaining visible (N2), in-instance replay (N3), reload (N5), and off-device copies of history (N7).

## Decisions that are Duke's

1. **Which profile ships on by default.**
   - *Build on `01-wip` now and decide at browser-client readiness* (recommended). If `-01` has landed and passes the vectors by then, cut over before launch. If not, ship `01-wip` on by default with its limits printed. Cost: the adapter, the bridges, the manifest and the reader rule are written once and replaced once. For browsers a cutover is a deploy, because the origin serves the code and nothing is stored. The native helper needs a release.
   - *Hold default-on for finished `-01`.* Cost: `mjolnir-rurh.5` waits on an upstream date nobody can see, or ships without encryption, which Duke ruled out by making the client depend on this node.
   - *Ship `01-wip` and stay.* Cost: Mjolnir maintains a format its maintainer has already replaced.
2. **How the invite secret is delivered, given persistent history.**
   - *Navigated link, disclosed, with one secret per call* (recommended for the first release). Cost: key and token sit in history, in Chromium's session files, and possibly in a synced copy. The key is useful only with that call's ciphertext, which the relay host holds. The origin is already trusted for this iteration, and that is the larger exposure.
   - *Paste into an open page.* Cost: joining stops being one click, and the flow is unrun (I1). Build it anyway as a second entry, because decisions 3 and 4 need the same mechanism. This differs from the author's recommendation, which makes paste the answer.
   - *A link that carries only a bootstrap secret, with the call key wrapped to the joiner inside the call.* Cost: a new protocol, a member must be present to admit, and it needs its own review. It is the one option where a history entry is worthless afterwards. Put it with the Coopbase and FOKS work.
3. **Guest invite lifetime beyond one token.**
   - *Calls end at `exp`, with a visible countdown* (recommended for the first release, as the author recommends). Cost: one hour.
   - *Raise the ceiling.* Cost: it is one line for the whole host, and it lengthens by the same amount the time a removed member keeps metadata access and, until N2 is fixed, stays visible.
   - *Owner sends a fresh link, pasted into the open page.* Cost: I1, and the owner must act for each guest every hour.
   - *Delegated invites.* Cost: a new change in room auth. No bead exists for it.
4. **How remaining link guests get a replacement credential.**
