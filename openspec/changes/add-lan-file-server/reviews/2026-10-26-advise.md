## Independent take (blind pass)

Written before opening design.md or tasks.md, from the packet Why, living lan-files contract, and cited code only.

1. Pin a small guest-owned service linking identikey-auth and recrypt-storage-auth; refuse stock recrypt-server or either crate inside the BEAM.
2. Pin one stable service audience across LAN and mesh, with fresh, bounded, single-use challenge verification before accepting a claimant.
3. Pin the explicit mapping from verified classical Ed25519 key bytes to Blake3(raw key); refuse substituting the identikey-auth §5 fingerprint.
4. Pin complete capability validation for the exact File hash, holder, read permission, and authenticated root issuer equal to durable ownership(h).
5. Pin atomic first-put ownership under concurrent requests and crash/retry recovery; refuse ownership replacement or minting a later putter an owner's authority.
6. Pin canonical bytes on the injected TAP-only blob-door and state on the guest subvolume; refuse direct B2 credentials, directory subjects, and DELETE assumptions.
7. Pin successful PUT acknowledgement to both durable bytes and durable ownership/cap state, with explicit failure behavior for the non-transactional door/index boundary.
8. Pin IPv4 DNAT to the named Ethernet ingress and its actual LAN destination address, with idempotent setup/removal and failure closed on address loss.
9. Pin evidence from a separate LAN client plus negative identity/cap tests; track the mesh ULA proxy and meshd landing explicitly without claiming LAN alone completes the living contract.
10. Tradeoff: a separate guest service and local metadata add deployment/recovery work, but preserve the existing door and authorization boundaries; require a reproducible restart and verification path.

## Comparison

The vehicle is sound, but three integration decisions remain too open for architecture acceptance. This is a pre-implementation review of the ACTIVE BUILD proposal, design, and tasks against `openspec/specs/lan-files/spec.md`; these are omissions in the implementation contract, not claims of bugs in an implementation. The author family is Grok; this independent reader is `astra-arch-review`.

### What the author answered, and the strongest case for accepting

`design.md:10-16` correctly separates guest authorization from the BEAM and the door, explicitly joins the fingerprint namespaces, anchors GET to ownership, and places metadata on the guest subvolume. `design.md:20-24` selects DNAT and fails closed when Ethernet has no address. `proposal.md` and `design.md:26-29` explicitly assign mesh ULA and discovery to `mjolnir-h2fp.4`. That is a legitimate staged landing, not a missing mesh implementation in this node.

The strongest case for acceptance is that the living contract and folded architecture already settle the security model, leaving ordinary implementation choices. The folded design's fingerprint section additionally specifies authenticated PUT, `OwnershipStore::register`, and issuer keys learned from `Verified`. The local crates provide useful mechanics: `identikey-auth/src/verify.rs:33-77` verifies audience, time, signatures, and consumes a nonce; `recrypt-storage-auth/src/sqlite/ownership.rs:48-78` provides first-owner registration and idempotent same-owner registration. I therefore do not ask for new cryptography, a new metadata service, another ADR, or a replacement network architecture.

Those primitives do not settle the following cross-boundary choices. A short addition to the design and explicit acceptance checks is sufficient; implementation is not required to answer this review.

### R1 — Pin the authenticated HTTP and capability issuance/verification flow (high)

Location: `design.md:10-16`, `tasks.md:7-9`.

The design says the guest issues challenges and checks caps, but does not say how the Response authorizes a PUT/GET, how a client obtains a usable signed cap, or how issuer verification keys remain available after restart. This matters because `Verified` contains public keys, not the owner's signing key (`identikey-auth/src/verify.rs:19-24`). A guest cannot simply mint a root cap signed as the putter from that authentication result. The folded design's statement that the share issues caps needs a concrete signing/import or delegation flow compatible with root issuer = owner.

Likewise, the current GET checkbox names the holder fingerprint, read permission, and root ownership, but not the exact File subject or cryptographic verification. `Capability::verify_full` verifies the supplied signature, expiry, and permission; it does not itself compare the requested hash, subject kind, holder, or supplied verifying key's fingerprint with the claimed issuer (`recrypt-storage-auth/src/capability.rs:210-246,282-297`). `verify_chain` also delegates root authority to its caller (`capability_chain.rs:11-29`). Linking the crate alone does not establish those joins.

Owed: identify the minimal request/response flow, proof/session lifetime and nonce consumption, cap signing/import path, and authenticated issuer-key lookup/recovery. State whether parent-bearing caps are supported and fully checked or explicitly refused. Pin signature policy and the complete GET predicate: valid signatures/expiry, File kind, exact hash, mapped holder, read permission, verified root issuer bound to its key and `ownership(h)`. Keep recryption keys with the client. Include wrong-audience/replayed proof, forged issuer, wrong hash/kind/holder, expired/missing cap, and non-owner-root refusal checks, plus an authorized read after guest restart without requiring the original owner to reconnect first.

### R2 — Define first successful PUT across the door and metadata store (high)

Location: `design.md:14-16`, `tasks.md:9-10`.

Persisting the index is necessary but does not order its commit against canonical-byte acceptance. Registering an owner before validating/storing the body can reserve someone else's hash with a failed PUT; writing bytes first and then crashing before registration leaves bytes with no recorded owner. Concurrent different putters and same-owner retries also need deterministic outcomes. `OwnershipStore::register` handles a local ownership record, not a transaction with the HTTP door. The door's existing PUT path checks the hash (`native/mjolnir_blob_door/src/http.rs:98-117`); a door success must not be replaced by a presence-only ownership claim. The packet correctly rules out DELETE rollback.

Owed: specify the ordering and success boundary for body/hash verification, door acceptance, ownership registration, and any acknowledged cap/key metadata. State recovery behavior after each partial failure, including a lost door response, guest crash, and metadata write failure. An orphan blob may be an acceptable consequence; inventing an owner from its mere presence is not. No distributed transaction is demanded. Demonstrate that concurrent different-owner PUTs cannot replace ownership, malformed/failed PUTs cannot establish successful ownership, and acknowledged objects remain readable by the authorized holder after restart.

### R3 — Make interface-scoped DNAT and its lifecycle verifiable (medium)

Location: `design.md:20-24`, `tasks.md:11-12`.

The chosen DNAT approach satisfies the intended architecture, but “does not bind 0.0.0.0” is not an adequate assertion for a NAT rule: DNAT has no listening socket. A rule scoped only by incoming interface can still rewrite traffic for unintended destination addresses. The design also leaves unstated who owns/removes the rule and what happens after address loss/change or guest replacement. The existing TAP code only establishes guest routing (`lib/mjolnir/network.ex:50-73`); it does not supply this publish lifecycle.

Owed: pin the rule's named ingress interface, currently assigned LAN destination address, publish port, and specific guest destination; identify the component responsible for idempotent installation and reconciliation/removal. Cover the FORWARD and return path without broadening unrelated access. Record the behavior on absent/changed LAN address, guest stop/replacement, and repeated setup. Add rule inspection and negative connectivity checks for a wrong interface/destination and absent address alongside the existing separate-LAN-client success check. Continue to leave the door unchanged and the mesh leg in `mjolnir-h2fp.4`.
