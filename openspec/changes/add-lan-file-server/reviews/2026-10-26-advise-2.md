## Blind independent take

Recorded before opening design.md, tasks.md, or the earlier review; inputs were the packet Why, living lan-files contract, cited code, and cited learnings.

1. Pin the guest as the identity and capability enforcement boundary; refuse stock recrypt-server, directory-path authorization, and BEAM crate linkage.
2. Pin one service audience across addresses, and require a fresh, replay-resistant challenge proof before deriving any authenticated request authority.
3. Derive the storage claimant from the verified raw Ed25519 key; never compare a capability holder with the identikey-auth section 5 fingerprint.
4. Require a valid File capability for the requested hash and claimant, including read permission and a verified root issuer equal to durable ownership(h).
5. Pin how first successful PUT claims ownership under concurrent puts, failures, retries, and crashes; refuse ownership replacement by later putters.
6. Pin who signs owner-rooted capabilities and how the client obtains and presents them without giving the guest the owner's private key or plaintext data key.
7. Keep canonical bytes on the injected TAP-only blob-door and persist caps and ownership on the guest subvolume; do not assume a door DELETE exists.
8. Specify durable metadata recovery and failure ordering so an acknowledged put cannot lose its authorization root after guest restart.
9. Scope DNAT to both the named Ethernet interface and its actual IPv4 address, with safe removal/reconciliation on address loss and no wildcard or public-address fallback.
10. Accept the small-guest and IPv4-only landing tradeoff if verification covers authorization negatives, restart durability, and real LAN access while mesh ULA and discovery remain explicitly owed by mjolnir-h2fp.4.

### R1 — Authentication and owner-rooted capabilities answered

`design.md:33` chooses a fresh Response on each PUT/GET, fixed audience verification, nonce consumption, and no session. `design.md:38` explicitly makes the client the root-cap signer and refuses parent-bearing chains. `design.md:43` persists the authenticated owner's public key with ownership so a holder can read after restart without the owner reconnecting. `design.md:48` supplies the application checks beyond `Capability::verify_full`: exact File subject/hash, mapped holder, read, expiry, and the issuer key bound to the recorded owner. Negative cases are listed at `design.md:55`.

The local API supports this separation. `identikey-auth/src/verify.rs:33` checks audience, time window, signatures, and nonce consumption, returning public keys rather than signing authority. `recrypt-storage-auth/src/capability.rs:282` verifies signature, expiry, and permission; the application still has to perform the subject, holder, and owner joins now explicitly required by the design. Client-signed root caps satisfy the living namespace and owner-root requirements without giving the guest the owner's private key. Rejecting delegated chains is a reasonable bounded first landing; the living scenarios do not require delegation support.

### R2 — PUT commit and recovery boundary answered

`design.md:63` orders authenticated body/hash validation, successful door PUT, first-owner registration, and durable metadata before acknowledgment. `design.md:74` explicitly accepts an orphan blob when the guest crashes between door acceptance and registration. A subsequent putter must supply the bytes through its own successful PUT; blob presence is not authority. Different-owner retries cannot replace ownership, and a lost door response is not sufficient to register an owner.

Together with the owner-key record at `design.md:43`, this is a sufficient architectural commit boundary. `recrypt-storage-auth/src/sqlite/ownership.rs:48` provides first-owner registration and same-owner idempotence, but stores only the owner fingerprint: implementation must preserve the design's additional durable issuer-key record as part of that boundary. The existing R2 task already requires failure/race/restart checks; these remain execution obligations, not evidence that tests have run. In particular, successful acknowledgment must imply both ownership and key recoverability. A lost client acknowledgment after a durable commit is retried against the recorded owner, not grounds to replace it.

### R3 — DNAT match and lifecycle answered

`design.md:85` now specifies Ethernet ingress, the currently assigned destination IPv4 address, publish port, and the particular guest TAP target. `design.md:91` assigns lifecycle ownership to the Mjolnir host process, including idempotent setup and removal/reconciliation for guest stop/replacement and LAN address loss/change. FORWARD and conntrack return handling are restricted to this flow. `design.md:98` explicitly requires rule inspection, a real LAN success, and wrong-interface/destination/absent-address failures. This answers the earlier concern that a socket-bind claim alone says nothing about DNAT exposure.

## Steelman against the blind take

My independent take could be overread as requiring a session service, server-side capability minting, a transaction spanning the door and metadata, or the mesh leg in this change. None is necessary. A fresh proof per operation removes session lifetime/recovery from the design; owner-signed single-block caps avoid invented signing authority; orphan bytes are an acceptable consequence of ordering two stores without DELETE; and the proposal explicitly assigns mesh ULA and discovery to `mjolnir-h2fp.4`. These choices answer the concerns with a smaller implementation while retaining the living authorization and publish boundaries.

Concrete wire encoding, bounded challenge settings, crate verification-policy arguments, metadata transaction mechanics, and rule-reconciliation implementation still need to be selected and tested during implementation. The revised decisions and the existing R1–R3 acceptance obligations constrain those choices sufficiently; they do not require another architecture send-back. No replacement design is requested.
