## Blind take

Written before opening design.md, tasks.md, the delta, or prior reviews; based on Why, the living site-certs spec, and cited code.

1. Pin an independently operated UDP relay whose deployment cannot restart the controller or disturb existing gateway connections.
2. Pin a browser-trusted certificate for an explicit relay hostname; the HTTP-01 path cannot supply a wildcard.
3. Pin the distinction between certificate provisioning and routing so enabling a relay cannot capture another service's hostname.
4. Pin private-key custody from initial issuance through renewal, including temporary files and both service identities.
5. Refuse a privileged certificate-copy operation whose inputs, destination, or path ancestry the relay can redirect.
6. Pin certificate/key consistency during replacement and preserve the last working generation on validation failure.
7. Pin authentication before public listening, including concrete relay audience binding and bounded tenant path authority.
8. Refuse to infer that a valid signature alone authorizes a different relay, tenant, or operation.
9. Pin first enable, missing prerequisites, renewal, and restart outcomes without adding a dependency on guest port publication.
10. Accept a relay-only restart on certificate renewal as a simplicity tradeoff if its connection interruption is explicit and bounded.

## Comparison and steelman

The contract answers the blind take with a separate service and deploy owner, a certificate-only subject, mandatory scoped credentials on both transports, private certificate staging, validated generation activation, and explicit first-enable and failure outcomes. D7 continues to prohibit client-directed ticket pulls. The existing R2 and R4 closures remain valid: the amendment does not weaken verification-key activation or bounded shutdown.

The strongest objection to key-based audience binding is that two operators could install the same public key at different relays. The amended contract now expressly prohibits that configuration and defines the audience as `:relay_host`. That is a sufficient trust-provisioning invariant for this node; requiring a global key registry or a new JWT claim would add architecture that the stated boundary does not need. Operator-issued fixtures can exercise the positive and negative cases before the room mint exists.

The strongest objection to the certificate handoff is that the issuer necessarily retains the source key. D4 now acknowledges that access instead of implying that destination permissions erase it. A dedicated private source directory and restrictive creation modes address the actual confidentiality gap while preserving the existing issuer identity. Root-only destination ancestry addresses replacement by the relay user. This permits the chosen root-copy design without broadening the relay's access to other gateway keys.

### R1 — audience binding is explicit and testable

The new requirement closes the precise residual from the second review: relay-purpose-only keys no longer permit silent reuse across independent relay audiences. The A/Ka versus B/Kb scenario holds root, grant, and expiry valid, so it isolates audience trust rather than merely testing malformed credentials. It runs on WebTransport and Iroh, with a positive control. The existing algorithm restrictions, tenant-root validation, segment-aware rights, discovery filtering, and session expiry remain in force. R1 is checked.

### R3 — custody covers the source and the destination

The existing `acme.rs:105` helper creates temporary files with ambient permissions, and `acme.rs:403` tightens the final key mode only after writing. The amendment no longer relies on that sequence to establish confidentiality: the relay subject must have its own issuer-owned private directory, and every file, including temporary files, must be private from creation. Failure to establish custody precedes key writes. The staging scenario denies both `nobody` and the relay user access to the source; D4 preserves legitimate issuer/root access.

The new ancestry requirement covers every directory from `/` through the destination `tls` directory, requires root ownership and exclusive write authority, rejects symlinks or foreign ownership, and places relay-writable state elsewhere. The replaced-parent scenario directly tests the previously missing attack. The intentional `current` pointer is selected inside that protected tree; the root-only ancestry rule does not require making the relay's runtime state read-only.

Private destination staging and the new partial-copy scenario complement the existing pair-match, hostname, validity, expiry, and renewal requirements. The last good generation remains selected on failure. The certificate-only/no-route/no-public-API rule remains intact. These close R3 as a contract obligation; implementation still has to demonstrate the permission and failure cases.

### R5 — first enable no longer has contradictory outcomes

The never-installed disabled case now requires an unset enable flag. Successful first enable requires enabled=true, a hostname, and usable prerequisites. Those cases cannot simultaneously require both an absent and an active unit. Failed enable, repeated disable, unrelated deploys after clearing the flag, and guest firewall-rule preservation remain specified. R5 is checked.
