## Independent take — written before opening design.md or tasks.md

1. Pin the relay as a separately owned host service; preserve the gateway's TCP listeners and guest UDP publication semantics.
2. Pin one exact public hostname and a browser-trusted certificate; refuse wildcard HTTP-01 and self-signed fallback.
3. Require an explicit issuance, file-permission, atomic-install, and renewal handoff between the issuer and the relay user.
4. Require equal admission and operation authorization on WebTransport and Iroh; transport connectivity alone grants no media access.
5. Refuse unspecified token dialects: pin signature trust, mandatory claims, expiry behavior, and publish/subscribe scope semantics.
6. Preserve canonical base58 owner identity at future tenant boundaries without inventing the deferred room-token API here.
7. Require malformed, absent, expired, foreign-key, and out-of-scope credentials to fail closed without token disclosure in logs.
8. Refuse caller-directed ticket pulls and define bounds on unauthenticated connections and stalled verification.
9. Pin repeatable enable, disable, renewal, and relay-only deploy behavior that leaves controller and gateway PIDs intact.
10. Accept a separate process and key handoff as operational cost for a smaller failure domain; demand observable negative-path acceptance.

## Comparison and steelman

The amendment answers much of the blind take. D5 and the delta now distinguish publish from subscribe, require temporal claims, filter announcements, close sessions at expiry, reject foreign credential profiles, and prohibit identity-only admission on either transport. D5a chooses availability loss over silently retaining a revoked trust set and supplies a measurable activation acknowledgment. D4's generation swap is a sound way to reject a mismatched source pair without replacing the installed pair. D8 gives deployment reconciliation one owner and bounds both-transport draining.

Against my initial preference for explicit credential binding, a dedicated verification key can bind purpose and audience without changing moq's wire format. There is no need to invent an `aud` field that the supplied upstream contract rejects. However, the amendment currently isolates keys by **purpose only**, leaving the audience part of R1 unresolved. Likewise, private destination staging is valuable, but it cannot retroactively protect a private key written insecurely at its source. These are remaining obligations from the first review, not demands for another architecture.

Unauthenticated resource bounds and log hygiene from the blind take remain implementation considerations, not additional blockers here. The deferred room mint, tenant accounting, capacity measurement, and E2EE remain outside this verdict.

### R1 residual — purpose isolation does not identify the relay audience

**Evidence:** delta lines 105–132; design D5. The only restriction on a trusted signing key is that its private half signs relay tokens and nothing else. That forbids sharing a login signing key, but permits the same key in independently authorized relay A and relay B. A token intended for A with an otherwise valid tenant root and grant would then satisfy every stated admission condition at B. The prior review explicitly required binding to this relay/audience and a wrong-audience refusal test; neither is supplied by the new login-credential scenario.

**Required:** identify the intended relay trust domain and bind the verifier configuration to it. Per-relay exclusive keys are sufficient; no wire-format change is required. If several endpoints intentionally form one audience, name that scope explicitly instead of silently letting key reuse define it. Add operator-fixture acceptance on both transports showing that a credential for a different trust domain is refused while one for this relay succeeds. This does not require building a second region or the room mint.

The new operation, tenant, expiry, and discovery requirements satisfy those parts of R1. Keep the original R1 box open only for the remaining binding and its negative coverage.

### R2 closed — a reload now has a measurable completion boundary

**Evidence:** delta lines 177–195 and D5a. Within five seconds of replacement the new set must govern new sessions with its exact file hash acknowledged, or all new sessions must be refused with `invalid`. The removed-key scenario expressly prohibits a process restart. Empty/missing/malformed startup data and private/symmetric keys cannot enable service. Existing sessions retaining admission until expiry is now an explicit, bounded policy, not an accidental revocation gap. R2 is checked as a contract obligation; the later loader spike must prove the implementation can honor it.

### R3 residual — custody begins before the root copy

**Evidence:** delta lines 78–95 and D4; `lib/mjolnir/api/certs.ex:326`; `native/mjolnir_gateway/src/acme.rs:104` and `:396`. The issuer writes the source key as `mjolnir`; the existing helper creates a temporary file with ambient permissions, renames it, and only later attempts a final `0600` chmod while ignoring failure. D4 acknowledges this behavior but the new SHALLs protect only the destination generation. There is no source-directory, temporary-file, or issuer-umask requirement that makes the source private from its first byte. Denying `nobody` access to the destination does not test its ability to read the source temporary key.

The destination also requires `/var/lib/mjolnir-relay/tls/` itself to be root-owned, but says nothing about its parent `/var/lib/mjolnir-relay`. A relay-writable parent permits renaming/replacing the `tls` directory even when `tls` is not writable. The original R3 specifically required a destination that the relay cannot redirect through writable parents or symlinks; that obligation remains open.

**Required:** specify private source staging from creation, authorized source readers, and checked failure behavior for custody setup. A private issuer output directory and restrictive creation policy can solve this without changing all gateway issuance. Require a root-controlled destination ancestry and safe handling of symlink/parent substitution; the relay may read the selected pair but may not redirect the root installer. Preserve the legitimate issuer's access to its own source key; do not imply that a destination ACL erases that access.

**Acceptance:** inspect source and destination permissions while a key is being staged; deny an unrelated user access to both; inject failed permission setup, a replaced destination parent, and copy/load failure. None may expose key bytes or activate a bad generation. The existing matching-pair, successful-renewal, running-expiry, and no-route/no-public-API requirements close the corresponding portions of R3. Hot reload versus draining restart remains the excluded spike's decision.

## Newly owed R5 — first enable contradicts the new disabled-host scenario

**Evidence:** delta lines 4–10. The requirement mandates installing and starting the unit when `--relay` runs with enabled=true and a hostname. The following scenario requires no unit and no tagged rule after **any deploy** on a host that has never previously run `--relay` enabled. A fresh host's first intentional enable satisfies both sets of premises and receives opposite expected outcomes.

**Required:** qualify the disabled-host scenario by the current disabled/unset configuration or by an unrelated deploy, and add a separate first-successful-enable scenario. Assert an active relay, the relay-owned rule, and unchanged gateway/controller processes. Keep the existing failed-enable and repeated-disable cases. This is a new acceptance-contract inconsistency, not a request to change the chosen lifecycle design.
