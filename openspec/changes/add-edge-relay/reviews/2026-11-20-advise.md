## Blind take

1. Pin a disabled-by-default service whose enable, failure, disable, and redeploy paths have observable listener and firewall outcomes.
2. Pin one authentication gate for WebTransport and Iroh; refuse missing, malformed, expired, wrong-key, and wrong-audience credentials before media or discovery access.
3. Pin publish/read authority and canonical owner-prefix isolation now; refuse any interim open mode while room-token minting is deferred.
4. Pin credential purpose and trust roots explicitly against edge-auth; refuse implicit conversion of login credentials or Iroh peer identity into relay authority.
5. Pin exact upstream revisions and the supported wire contract; refuse dependency defaults that silently add public access, discovery, or ticket-driven outbound dialing.
6. Pin a certificate for the configured hostname, matching private key, validity checks, and renewal behavior; refuse self-signed fallback or serving after expiry.
7. Pin HTTP-01 issuance without new routing apexes, preserving site-certs lookup/list/renewal semantics and keeping PEMs on the host.
8. Pin gateway-to-relay key transfer with least privilege, private staging, coherent certificate/key replacement, and failure retention; refuse exposing other gateway or identity keys.
9. Pin independent unit/deploy ownership, bounded process resources, and negative tests on both transports; refuse controller restarts or changes to guest UDP publishing as collateral effects.
10. Tradeoff: host termination enables practical browser fan-out but exposes media to the host; state that trust boundary plainly and do not imply end-to-end encryption.

## What the design gets right

D1–D3 isolate an evolving protocol parser and its dependency stack from the gateway. Composing a custom admission loop instead of using the claimed anonymous-read default is the right response to the spike evidence. D7 removes client-directed ticket pulls, and D8 preserves the deployment boundary already present in `scripts/deploy.sh:42`. Neither requires changing guest UDP publishing. Pin changes requiring their own acceptance run are appropriate.

D5 and the delta at lines 25–42 genuinely state deny-by-default: absent, unverifiable, expired, and out-of-path tokens are refused on both transports. The browser scenario expressly denies announcements and catalogs. This is stronger than merely requiring a token-shaped input. The gaps below concern the meaning and lifetime of a verified grant, not an absence of security intent.

The host-media disclosure is direct and honest in both proposal and design. E2EE can remain out of scope; it is not an acceptance blocker for this service. Per-tenant accounting, capacity measurement, browser UI, and a room mint likewise need not move into this node.

## Owed before acceptance

### R1 — Define the minimum relay credential and authorization contract here

**Evidence:** design D5–D6; delta lines 25–59. “JWT,” “valid token,” and “grant” do not identify a verifiable token profile. The delta never explicitly denies publishing with a subscribe-only token. Its publish requirement requires a matching tenant prefix, which by itself does not distinguish operations. It also does not bind a credential to this relay/audience or distinguish relay bearer credentials from the existing login profile.

**Required amendment:** specify the accepted algorithms, required claims and expiry semantics, trusted key source, relay audience/purpose binding, publish versus subscribe rights, and segment-aware path matching. Define how discovery and later operations on an admitted session remain within those rights, including the chosen policy when the token expires. Explicitly reject missing/malformed grants, wrong-purpose credentials, and any default grant inferred from Iroh identity or an empty verifier. An immutable reference to an exact token profile is sufficient; a new token format is not required.

`edge-auth`'s holder-bound login defaults (living spec lines 253–288) do not forbid a separate relay bearer profile. They do forbid silently treating a login capability as bearer. State the separation and avoid giving the relay login signing secrets. The owner parser in `lib/mjolnir/deploy/owner.ex:25` supplies the canonical 32-byte base58 boundary, but not operation authorization.

**Acceptance evidence:** a publish/subscribe refusal matrix on both transports, including subscribe-only attempting publish, wrong audience, missing expiry/grant, malformed owner, and sibling-prefix/normalization escapes; valid narrow grants still work. These tests must run before `add-relay-room-auth` exists, using operator-issued fixtures. Deferring suffix layout and minting is safe once this verifier contract is complete; it must not defer enforcement or allow a temporary public mode.

### R2 — Give key reload a deterministic failure and completion contract

**Evidence:** delta lines 44–51 requires removal to affect new sessions “when” the file changes, without defining when activation completes or what missing, empty, malformed, unreadable, or conflicting key sets do. A watcher event alone cannot be a test oracle for successful revocation.

**Required amendment:** define validated atomic replacement, startup failure behavior, and reload failure behavior. Choose explicitly whether a failed reload denies new admissions or retains a validated prior set; if retaining it, make unsuccessful revocation observable. Define a bounded convergence interval or an observable activation acknowledgment after which new sessions must reject removed keys. Specify trusted ownership/write permissions for the verifier file.

**Acceptance evidence:** successful removal followed by a new-session denial after activation; missing/corrupt startup never authenticates; malformed reload and atomic file replacement produce the chosen result without broadening authority. The current requirement deliberately targets new sessions, so retaining existing sessions after key removal is not itself a defect.

### R3 — Make certificate custody and renewal normative, not just a root-copy task

**Evidence:** design D4 and the certificate task describe a root-owned copy, while the delta at lines 12–23 only specifies serving and startup. The existing issuer does run as `mjolnir` (`lib/mjolnir/api/certs.ex:326`). In `native/mjolnir_gateway/src/acme.rs:104`, temporary writes use ambient creation permissions; lines 396–403 replace chain and key separately and chmod the final key afterward, ignoring chmod failure. Those helpers do not by themselves establish private staging or coherent pair activation.

**Required amendment:** specify ownership and modes for source/staging/destination directories and keys, confidentiality from creation, and separation from unrelated gateway certificates, ACME account credentials, and edge signing keys. Define a root-controlled destination that the relay cannot redirect through writable parents or symlinks. Validate a matching pair for the configured name before activating it as one generation; specify copy/load failure retention and diagnostics. State what happens when the last usable certificate expires while the process remains running. Hot reload versus a draining restart may still be decided by the planned spike.

The root-copy architecture is compatible with `site-certs`; the living spec does not require all host keys to have one reader. Preserve its actual invariants: no new routing apex at renewal, no change to site routing, no PEM exposure through APIs, and no broadening of public issuance/list authorization for an operator-only subject. Whether the issuer integration needs a MODIFIED delta remains the explicitly deferred cert-subject spike, not a reason for this send-back.

**Acceptance evidence:** permission checks including staging, denied access as unrelated service users, mismatched/partial pair and copy-failure injection, successful renewal serving the new pair, and expiry refusal after failed renewal. These are testable with the planned local test CA; public issuance remains the separate human-gated journey.

### R4 — Reconcile disable transitions with independent deployment ownership

**Evidence:** delta lines 3–10 says an unset flag plus *any* deploy leaves no unit or UDP listener; lines 70–71 say gateway/controller deploys leave relay sessions open. D8 says no other flag touches the relay. After an enabled host clears its flag, those statements prescribe incompatible outcomes for a gateway deploy. The current scenario only covers a fresh disabled host. Firewall removal and the native Iroh endpoint's shutdown are unspecified.

**Required amendment:** identify the operation that reconciles enable/disable and hostname removal on an existing installation. Qualify unrelated deploy invariants accordingly. Specify relay-owned firewall rule installation/removal and failed-start outcomes without changing guest publish rules. Define draining observably: stop admitting new sessions, allow a stated grace period, then close remaining sessions and exit within the unit's stop timeout. Disable must stop both relay transports, not merely UDP 443.

**Acceptance evidence:** fresh disabled host, enable, failed enable, enabled-to-disabled transition, repeated disable, and unrelated deploy with an already-running relay. Assert listener/unit/rule state and session continuity or bounded shutdown as appropriate. “Nothing is bound to UDP 443” should be scoped to a host without another legitimate owner; this service must not remove unrelated listeners to satisfy the scenario.

## Testability and scope of the verdict

The current tokenless, cross-tenant, valid-subscribe, missing-certificate, and ticket-refusal examples have observable outcomes. The unresolved definitions above prevent reproducible security and lifecycle acceptance: “valid token” lacks a profile, key change lacks a completion boundary, and “drain” lacks a termination condition. None requires production mutation to resolve. Resource caps remain a useful systemd hardening detail, not a demand to implement the deferred per-tenant limits node.

Four corresponding unchecked items were appended to tasks.md. No design, spec, disposition banner, product code, or deployment was changed. This verdict is `task-red`, not an infrastructure failure.
