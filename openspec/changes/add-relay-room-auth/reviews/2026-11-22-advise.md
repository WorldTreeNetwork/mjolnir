## What I would pin

1. The owner in the token root comes from an authenticated fact about the caller, never from a value the caller types.
2. A user can mint only under their own tenant. The operator is the one principal that may name an owner.
3. Who chooses the participant segment, and who is allowed to be that participant.
4. The exact pattern strings, per transport, from the pinned matcher, not "covers".
5. Expiry closes a session on both transports, proven on both.
6. Rotation never has a moment where the mint signs with a key the relay does not hold.
7. What "revocation" does and does not do, in one honest sentence.
8. A failing-first refusal test per transport for cross-tenant mint, cross-participant publish and cross-room read.
9. How a person with a link and no Mjolnir login gets a token.
10. Tradeoff accepted: no room registry and no kick in this node, if said plainly.

## Verdict

Send back. Four findings block. The first is a cross-tenant mint.

## Must fix

### M1. The owner is caller-supplied, so any signed-in user can mint for any tenant

D3 and the spec take the owner from `x-owner-id` and say "This matches spawn". It does not.

- `Mjolnir.Deploy.Owner.resolve/2` (`lib/mjolnir/deploy/owner.ex:49-61`) honours the header only when the principal is `"localhost"`, the operator. For every other caller it returns `{:ok, user_id}` and ignores the header.
- The router says so in its moduledoc (`lib/mjolnir/api/router.ex:9-16`): "A signed-in caller is stamped as their `sub`. The header cannot impersonate."
- The contract gives `relay:join` only to user JWTs, the one principal for which the header is unauthenticated, and then trusts the header.

Attack: Mallory logs in with her own IdentiKey account, sends `POST /api/relay/rooms/standup/participants/alice/token` with `x-owner-id: <Bob's owner id>`. Owner ids are public (they are the OIDC `sub`). She receives a token rooted at `t/<Bob>/standup` with subscribe `**` and publish under `alice`. She hears the room and publishes as Alice. D6's sentence "Callers of a different owner cannot, because the root would not verify against their header" is false: the header is whatever they send.

D3's reason for rejecting `sub` is also weaker than stated. `owner.ex:8-10` says the canonical base58 XID "is the public OIDC `sub`". Legacy 64-hex subs are the same 32 bytes and the module already decodes them.

Smallest fix: resolve the owner exactly as spawn does. For a user JWT the owner is the caller's verified `sub`, required to pass `Owner.parse/1` (re-encode a legacy hex `sub` to base58, refuse anything else with 403 before signing). `x-owner-id` is ignored for a user, as it is on spawn. If the operator is to mint at all, the header applies to it alone. Add the scenario: a user who sends another owner's id in the header receives a token rooted at their own id, or a refusal, never the other tenant's root.

### M2. Iroh sessions never expire in the relay as built

The design opens with "The relay already ... closes a session when the token's `exp` passes", D8 says "which the relay already enforces", and the spec requires the close "on the transport it used". On Iroh this is false.

- `TokenPolicy::decide` returns `Ok(ext_grant(&grant).into())` (`native/mjolnir_relay/src/lib.rs:284`).
- `impl From<Grant> for Authorization` in `moq-ext-access/src/policy.rs:144-151` fills `expires` with `None`.
- `expiry()` in `iroh_sessions.rs:184-194` then awaits `std::future::pending()`.

The acceptance note's ten-second-token proof (`add-edge-relay/notes/acceptance.md:113`, "lease ended ... why=expired") is the WebTransport lease. No Iroh expiry was ever run.

Consequence: an Iroh participant admitted once keeps reading and publishing until the relay restarts. Every bound this contract states ("up to an hour", "until `exp`", the rotation overlap) is unbounded on Iroh.

Smallest fix: the proposal stops saying the relay is unchanged. Add one task: the Iroh policy carries the token's `exp` into `Authorization.expires`, with a failing-first test that an Iroh session admitted on a ten-second token is closed by fifteen seconds. This may land as a direct fix against `add-edge-relay` instead, but this change cannot be accepted while its expiry requirement rests on it unproven.

### M3. The rotation procedure breaks the mint, and the first overlap refuses every token

Three defects in D9, all in the same steps.

a. Order. Step 1 replaces `current.jwk` before step 2 publishes the new public key. The mint "signs with `current.jwk` only", so from step 1 until step 2 lands and the relay's one-second poll picks it up, every minted token is signed by a key the relay does not know. If the script dies between the steps, that lasts until a human notices. Step 3 ("From that rename, new mints sign with the new key only") contradicts step 1.

b. `kid`. At the pinned revision a token with no `kid` verifies "only when the set holds exactly one key and that key has no `kid`" (`moq-auth/src/set.rs:129`), and a set with a duplicate `kid` does not parse (`set.rs:46-51`). The only key generator in the repo makes keys with no `kid` (`examples/dev-key.rs`, `Key::generate(Algorithm::EdDSA, None)`). The contract never mentions `kid`. So the first time the overlap set holds two keys, every token, old and new, fails as "missing kid". A duplicate `kid` makes the file unusable, and the relay then refuses all new sessions on the host (`keys_ok` false). Nothing has tested a two-key set.

c. No acknowledgement. `add-edge-relay` D5a made `/run/mjolnir-relay/keys.active` so "whoever rotated a key can see that it took". D9 never reads it and never validates the candidate file before the rename. A malformed set fails closed for every tenant.

Smallest fix, as contract text:

1. Every mint key has a unique `kid`. Every minted token carries it in its header.
2. Generate the new key beside the current one (`next.jwk`). Validate the candidate public set with the relay's own loader before the rename.
3. Rename the public set {current, next} into place. Wait until `keys.active` equals that file's SHA-256. If it reads `invalid` or does not change in ten seconds, restore the previous set and exit non-zero.
4. Only then rename `next.jwk` to `current.jwk`.
5. After max TTL plus skew, rename a set of the new key only, and confirm `keys.active` again.

Drop `previous.jwk`. The mint never signs with it, so keeping the old private half for an hour is exposure with no use. Only its public half needs to stay in the set.

Add tests: a two-key set admits a token from each key; a token with no `kid` against a two-key set is refused; the mint is never observed signing with a key absent from the active set during a scripted rotation.

### M4. "Revocation is key rotation" revokes nothing, and the contract does not say so

D9's overlap is one maximum token life. Every token signed by the old key expires on its own inside that window. So routine rotation, as specified, shortens no token and removes no participant. It is key hygiene. The requirement title "Rotation revokes a signing key after one token life" is accurate about the key and misleading about access.

What is true and must be written down in the proposal and D9:

- A participant removed from a call keeps a working token until its `exp`, up to 3600 seconds. They stay connected for that time and may reconnect any number of times inside it. On Iroh, until M2 is fixed, they stay connected indefinitely.
- There is no per-participant, per-room or per-tenant revocation in this node.
- The only early cut is an emergency procedure the contract does not define: replace the public set with a new key at once, with no overlap, and restart the relay to end live sessions. That drops every call of every tenant on the host. A compromised mint key needs exactly this procedure, and D9's overlap would instead keep the stolen key trusted for another hour.

Smallest fix: split D9 into "routine rotation (overlap, revokes nothing early)" and "emergency revoke (no overlap, relay restart, host-wide)". State the three bullets above in the proposal. Specify the TTL the mint actually issues: the contract only says "at most" the maximum, and with no kick the default lifetime is the real revocation bound. A shorter default with a caller-chosen `ttl` up to the maximum is the cheap lever.

## Should fix

### S1. H1 is settled: patterns are exact, the subtree form is `/**`

From `moq-pattern/src/lib.rs:24` and `moq-auth/src/claims.rs` (the `Claims` doc): "`foo` matches only `foo`, `foo/**` matches its subtree including `foo`, `**` matches every path". H1's hypothesis, that a bare segment is a prefix, is wrong. A publish pattern of only `<participant>` grants one broadcast named exactly that and refuses `<participant>/track`.

Correct strings, relative to the root, as the token carries them:

- `root`: `t/<owner id>/<room>`
- `publish`: `["<participant>/**"]`
- `subscribe`: `["**"]`

`**` matches zero or more segments, so the participant may also publish a broadcast at exactly `<participant>`. On Iroh the relay prefixes the root itself (`ext_grant`, `lib.rs:312-347`), giving `t/<owner>/<room>/<participant>/**` and `t/<owner>/<room>/**` against `origin.scope("", …)`. `moq-ext-access` uses the same `moq_net::Pattern` at the same moq revision, so both transports match alike. The relay sets `grant.root`, and moq-relay scopes a session to the grant's root rather than the dialed path (`moq-relay/src/auth.rs:299`), so dialing a deeper path does not shift the patterns.

Replace H1 with these strings in D7 and the spec. Keep the fixture test.

### S2. Say how names are spelled on each transport

A WebTransport session is rooted at the token root, so its client publishes `P/track`. An Iroh client uses the absolute `t/<owner>/R/P/track` (`acceptance.md:120,187-188`). The spec's "Own track" scenario has the WebTransport client publish the absolute path. Taken literally that is `t/<owner>/R/t/<owner>/R/P/track`, which the pattern refuses. State both spellings.

### S3. In-band credentials exist at the pinned revision; D8 says they do not

D8: "There is no mid-session replace-the-token message." At `4a6f522`, `moq-net/src/auth.rs:1-10` documents in-band AUTH: a client "presents another [token] without reconnecting" and the session's grant is the union. `moq-relay` hands those to the embedded decider as an `Admission` whose `attached()` is true (`moq-relay/src/auth.rs:1035-1039`). Mjolnir's `spawn_decider` does not look at `attached()` and runs the same `assess` on them.

So the relay as built probably already accepts a second token on a live WebTransport session, untested, while the spec says "This capability SHALL NOT replace the token on an open session". Pick one:

- refuse `attached()` admissions in the decider, with a test, or
- adopt it as the WebTransport refresh path and spike it: the session survives the first token's `exp` when a second was added, a token for another room added in band is refused, and the pinned JS client can present one.

I did not verify the lifetime semantics or the JS client, so this is a hypothesis for the spike list, not a demand. It is not available on Iroh, where Mjolnir's own handler admits once. Without it, the cheap mitigation for D8's gap is make-before-break: the client mints and opens the new session before `exp`, then drops the old. Whether two sessions may hold the same broadcast path for that moment also needs a spike.

For calls, a forced media gap once an hour is tolerable for a first version if the client reconnects before expiry rather than after. Say that in D8.

### S4. Participant identity and guests are undefined

The participant segment is a URL parameter the caller picks. With M1 fixed, the only possible minter for a tenant is the account that owns it. Then:

- The owner picks every participant name and can mint a second token for a name already in use. Nothing stops two live sessions publishing as `alice`. That is acceptable only if the contract says the minter is trusted for every identity in its rooms and that participant names are labels, not authenticated identities.
- `mjolnir-rurh.5` is "a person opens a link ... and is in a multi-party call". That person has no Mjolnir JWT and cannot call this mint. The contract must say how they get a token. The honest v0 answer is that the room's owner mints one per invitee and hands it over as a bearer, good for its full life with no kick. A delegated invite (the codebase already has Biscuit capabilities checked as `right(resource, operation)`) is a later change, but the gap has to be named here because the journey depends on it.
- A second Mjolnir user cannot join another user's room by their own login. State it.

### S5. The operator claim is false, and the scope mechanism as described cannot work

D2: "The operator socket stays scope-empty and cannot mint." The operator principal is assigned `@all_scopes` (`lib/mjolnir/api/auth.ex:69-73`), the same attribute the user path uses (`auth.ex:250`). Appending `relay:join` to it gives the operator the scope. To meet the spec's 403 for the operator, the route must also require `principal_kind == :user`, or the scope must be added on the user path only. Capability and ceremony principals are the scope-empty ones. Say which mechanism.

### S6. Co-location, first install, and the disabled state

- The rotation script renames into `/etc/mjolnir-relay/` on the controller. That only works when controller and relay are one host. Say that this node requires it, and that a remote relay needs its own root-run copy step with the `keys.active` check.
- The proposal says the token is "signed with a key whose public half is already in `relay-keys.json`". Today that file holds an operator fixture key whose private half sits in someone's home directory (`docs/runbooks/edge-relay.md:19`). First install must make the set exactly the mint key and remove any earlier key. State it and test it.
- The proposal's "Empty" case (mint fails when its key is not in the relay file) appears in no requirement. The "Off" case returns a token when the relay is disabled, and `relay_host` may be `nil`. Specify: no `current.jwk`, relay disabled, or host unset is a 503 with no signature.
- Say that the mint reads `current.jwk` at each mint (or reloads on change), and refuses to sign if the file or its directory is not root-owned with no group or other access. A key cached at boot keeps signing with the retired key after a rotation.

### S7. Token shape the Elixir mint must match

moq-auth refuses any unknown claim (`wire.rs:46-52`): only `root`, `publish`, `subscribe`, `exp`, `iat`, `nbf`, `jti`, `iss`, `sub`. A default `aud` from a JWT library fails verification. Add a hypothesis and a cross-language fixture: a token signed by the Elixir mint verifies under `KeySet::verify` at the pinned revision, with `kid`, EdDSA, integer `exp` and `iat`. Recommend a `jti` per token and a mint log line of caller `sub`, owner, room, participant, `jti` and `exp`, never the token. With no kick, that log is the only record of who can be in a room.

### S8. Tests (question 7)

The tasks do not require failing-first, and three refusals are missing or test the wrong thing.

- Cross-tenant mint (M1): absent.
- Cross-room read: the "Another room" scenario presents a room-R token to a session dialed at S. That tests the dial check, which is not the boundary, since a client simply dials its own root. Required: a session admitted for R, on each transport, asks for a broadcast under S by every spelling available to it and is refused, and its announcements list nothing from S.
- Cross-participant publish is present on both transports. Keep it and add the exact-name case: `Q` alone, and `P` alone (admitted).
- Iroh expiry (M2), two-key set and `kid` (M3): absent.
- Segment rule: name the cases. Empty, 65 characters, `.`, `..`, `%2F`, `%5C`, `*`, `%0A` and a trailing newline. The rule must be a whole-string match (`\A…\z`); an Elixir `^…$` accepts `"room\n"`.
- Every refusal test is written first and seen to fail for the stated reason before the code that makes it pass.

## Notes

- Root and traversal (question 3). The relay needs no change for the room root: `root_allowed` accepts `t/<owner>` "or a path below it", and it refuses empty, `.` and `..` segments in the root and the dialed path. The segment alphabet `[A-Za-z0-9_-]` excludes `/`, `\`, `*`, `.` and `%`, so a minted root cannot traverse, escape a separator, or form a wildcard. The `.` and `..` exclusions in D7 are redundant with the alphabet but harmless. `mjolnir-nopublish` is a top-level segment outside `t/`, so a room named that would not collide; the exclusion is harmless too. moq paths are literal, so `P/../Q/x` is a broadcast under `P` and no relay-side escape. A client that normalises paths before attributing a track to a participant could be fooled, which is `call-client`'s to handle: attribute by the first segment as received.
- Participant names are case-sensitive and may look alike (`alice`, `Alice`, `a1ice`). A client concern, worth one line.
- Fail-closed loading still holds mid-rotation: the rename is atomic and a bad file refuses new sessions. The watcher compares only mtime and reads the file three times (trust check, load, hash), so two renames within a moment could record a hash of a different file than the one loaded. The rotation's steps are an hour apart, so this is not reachable in practice.
- The mint's `:relay_token_max_ttl` and the relay's `MJOLNIR_RELAY_TOKEN_MAX_TTL` are two settings. If the mint's is larger, every token is refused.
- A user JWT is also accepted from `?token=` and the `mj_term` cookie on every route. The mint changes no state and the response is not readable cross-origin, so I see no CSRF harm. The WebTransport token rides in the URL query (`?jwt=`); keep it out of logs.
- D4's custody choice is sound: root-only directory outside `/etc/mjolnir`, not a deploy secret, public half only in the relay file. D10 (no API route for keys) and D11 (one key, one relay) are consistent with `add-edge-relay` D5.
- No mint rate limit. Left to `add-relay-limits-metering`, which is fine if that node knows it.
