## Conditions (should fix, carried into `act`)

### C1. Emergency revoke must never put the old key back

D10 says "Confirm `keys.active`". D9 defines confirmation as: on `invalid` or ten seconds unchanged, "rename the previous set back". An implementer who reuses that function in the emergency path restores a set that holds the stolen key, at exactly the moment the relay is slow or down. Bind it: the emergency path never restores. On a failed confirmation it leaves the new set in place, still restarts the relay, and exits non-zero.

Also state:

- The bound. A restart sends SIGTERM, and the relay drains for `MJOLNIR_RELAY_DRAIN_SECONDS` (30 by default) before it stops (`main.rs:192-201`). A live session on a stolen-key token survives that long. New sessions are cut within the one-second key poll.
- `next.jwk` is deleted if a routine rotation was in flight.
- The mint key is host-wide. Whoever holds it can sign a root under any tenant, not only the rooms it was used for.

The scenario `Stolen mint key` exists, but no task box requires its test. Add one.

### C2. "Enabled", host and ceiling live in a file the mint does not read

The relay's settings are in `/etc/mjolnir-relay/relay.env`. `scripts/relay-deploy-remote.sh:8-12` says it "Does not read /etc/mjolnir/env". The controller reads `MJOLNIR_RELAY_ENABLED` and `MJOLNIR_RELAY_HOST` from its own environment (`config/runtime.exs:40-46`), and `:relay_token_max_ttl` is a constant in `config/config.exs:258` with no env override.

Consequences:

- On a host installed by the runbook, the mint returns 503 forever until someone also sets both variables in `/etc/mjolnir/env`. No task or runbook line says so.
- The reverse also holds: the controller can say enabled while the relay is off, so "The route does not return a token for a relay that is not configured" is not guaranteed.
- D12's "The mint reads the relay's ceiling and will not issue above it" is not what any existing code does. If an operator lowers `MJOLNIR_RELAY_TOKEN_MAX_TTL` in `relay.env`, the mint keeps issuing up to 3600 and those tokens are refused.

Pick one and write it: the mint reads `relay.env` (the BEAM is root and the file is `0640 root`), or the installer writes the three values to both files and the contract says they are two settings.

### C3. The rotation script: what is stated but not enforced

- **No lock.** Two root invocations share `next.jwk`. Run A times out and restores the old set while run B renames its `next.jwk` onto `current.jwk`. The signer is then absent from the set. One `flock` for routine, emergency and first install.
- **Step 5 has no owner.** It runs an hour later. Say whether the script sleeps, schedules a timer, or is run again, and where the pending state is recorded. A reboot must not lose it. A second rotation started inside the overlap must either refuse or keep the oldest public key.
- **First install has no order.** Publish and confirm the public set before `current.jwk` exists, the same rule as step 4. Say what happens when the relay is not running, since `keys.active` then never changes.
- **"The relay's own loader" has no entry point.** No binary exposes `load_verify_keys`. `dev-key` is "Not installed". The task list says not to reopen the relay. Name the validator (a `mjolnir-relay --check-keys <path>` mode is the smallest) or drop step 2's claim and rely on step 3.
- **The loader does not check what D9 says it checks.** Its algorithm loop iterates an empty list (`lib.rs:81-97`, `public_keys` returns `Vec::new()`), so "EdDSA or ES256" is not enforced at load. It also accepts a key with no `kid`. The script must check both itself. Token-time checks still hold (`token_alg_disallowed`), so this is not an admission hole.
- **`kid` spelling.** moq-auth accepts only `[A-Za-z0-9_-]`, 1 to 128 characters (`key_id.rs`). A timestamp with `:` makes the set unparseable. State the alphabet and the source (random 128 bits, or the RFC 7638 thumbprint).

### C4. Pin the owner rule to the byte

The mapping is sound. 32 bytes are at most 44 base58 characters, so a 64-character hex string can never also parse as an owner id, and the two spellings of one id are the same identity by design (`owner.ex:12-14`). Two things would make it many-to-one, and the contract leaves both open:

- `Owner.parse/1` trims whitespace (`owner.ex:32`). `"X"` and `"X\n"` would mint the same root.
- "64-hex" does not say lowercase. `owner.ex:20` uses `~r/^[0-9a-f]{64}$/`, the same `^…$` form D7 warns about.

Bind: no trim, the `sub` must equal its canonical re-encode, and hex is `\A[0-9a-f]{64}\z`. There is no existing function that turns hex into base58. `claim/2` only compares, and `decode_legacy_hex` is private, so a new public function is needed and the task should say so. Tests: a hex `sub` and the base58 of the same bytes give the same root; uppercase hex, hex plus newline, padded base58, a 31-byte id, and a non-canonical base58 spelling are each 403.

### C5. Request and response shape

- Where `ttl` rides (body or query), that it is a JSON integer, and that `0`, a negative, `3601`, a string, and a float are 400 before a signature.
- The JSON key names of the response.
- `Cache-Control: no-store` on the response.
- Test the sites, capability and ceremony principals, not only the operator.

### C6. The contract leans on a handoff nobody has shown

D12: "300 seconds is a mint interval, not a media gap." Three things stand between that sentence and the truth:

- The spec's "A client that still wants the room SHALL open a new session ... before the current token expires" binds `call-client`, which does not exist. Nothing here can test it. Move it to that node as an obligation, or mark it as one.
- "Two sessions MAY hold the same path" is asserted, not verified. In moq-net a second publisher at a path is another instance, and subscribers get `Restart`: "drop it and request afresh to follow the new one" (`moq-net/src/model/origin.rs:2165-2170`). So each handoff is visible to every other participant. Add it as a second unverified hypothesis with a relay test on both transports: a subscriber keeps receiving across a publisher's make-before-break.
- A guest cannot mint. For a guest, 300 seconds is the length of the call unless the owner asked for a longer `ttl`, and 3600 is the hard end. Say that in the journey.

### C7. Test the decider that ships

`spawn_decider` is in `main.rs`, which tests cannot reach. `tests/webtransport.rs:81-100` carries its own copy, and that copy calls `assess`, not `web_grant`. Every WebTransport refusal in S8 would be proven against a hand-written decider. Move the decider into the library and run the suite on it. Add the integration case for the in-band refusal, asserting the session stays up with its grant unchanged.

### C8. Test boxes the tasks do not have

The scenarios exist; the boxes do not. Add: emergency revoke, confirmation failure, first install (a fixture-signed token is then refused), each 503 cause including a bad file mode, and the `ttl` bounds.

Say where they run. The relay refuses a key file not owned by uid 0, so the rotation tests need root on Linux: the Framework laptop under `sudo`, as `scripts/test-relay-stop.sh` already does. The mint's own mode check needs an injectable uid or path for `mix test`.

Add one end-to-end acceptance on a single host with no browser: mint through the API, then drive `examples/wt-session`, `iroh-publish` and `iroh-subscribe` with that token. Finish by searching the relay journal for the token string. I found no line in moq-relay that logs the query, but "not written to a log by this work" is a promise worth one grep.

Build order: the H-mint fixture first, since its kill condition stops the mint.

### C9. The mint rate limit has no owner yet

The proposal says `add-relay-limits-metering` "owns a mint rate limit". The bead `mjolnir-rurh.4` lists session, pull and bandwidth limits and does not mention the mint. Record it there. The exposure meanwhile is small: only a signed-in user can call, only for their own tenant, and each call is one file read and one signature.
