Then compared those documents and the three named sibling deltas. No product implementation, activation, or fold was performed.

The proposal answers the central concurrency concern well: private CoW work trees, immutable published generations, owner/app scope, and publication only after successful work are an appropriate foundation. Last successful **publication** winning is reasonable for disposable tool state; there is no need for a transaction spanning every cache. Non-byte-identical release equivalence is also reasonable. The blockers below concern promises the current mechanisms do not yet support, not a request for a competing architecture.

## R1 — Preserve outputs and prerequisites across layer hits (blocking)

[Design lines 71–73](../design.md#presets-detector-driven) move both Cargo outputs and mise installs outside layers. The existing [manifest example](../../../../lib/mjolnir/deploy/manifest.ex) builds with `cargo build --release` and starts `./target/release/myapp`. Automatically setting `CARGO_TARGET_DIR=/cache/cargo-target` changes where that binary is produced, but this change provides no materialization into the release. The artifacts sibling supplies that operation and depends on this change; it cannot make this node independently safe to enable.

The problem also affects partial hits: if a mise-install layer hits after its mutable cache is evicted, the planner skips the install while the next step needs its toolchain. A Node service may need that runtime after build teardown too. Cache absence must not invalidate a supposedly sufficient layer.

**Owed:** specify which outputs/prerequisites remain in layers, which are recreated despite a layer hit, and how existing start commands remain valid. Either provide the minimum materialization here, gate the affected presets until the sibling lands, or reconcile the dependency order. Define how cache configuration changes affect step keys without hashing mutable contents. Add Rust and mise/Node scenarios for empty-cache partial resume and service boot with all cache mounts absent.

## R2 — The proposed publication is not atomic (blocking)

[Design lines 46–50](../design.md#layout-and-lifecycle) move `current` to `prev` and then move `current.new` to `current`. Between those operations there is no `current`; a host crash leaves that state indefinitely. A lock serializing commits neither removes the crash window nor protects checkout/eviction unless they participate. A leftover fixed `current.new` also needs reconciliation before the next commit. Updating the same `hint-<sha>` is unspecified.

**Owed:** name an implementable atomic publication point and its durability/recovery ordering, including first creation, repeated hints, `prev`, metadata, and abandoned candidates. Define reader/GC locking or generation pinning. State whether winner order means completed steps or completed publication, and what a cache-commit failure does to an already valid release. Test process interruption and host-restart states at each transition, plus checkout/remove/commit races on real btrfs. Independent per-cache publication is sufficient.

## R3 — Teardown and orphan ownership are underspecified (blocking)

The promise to reap orphaned `work-*` at boot/sweep does not define an orphan. [Builder.run_build](../../../../lib/mjolnir/deploy/builder.ex) protects only the post-spawn path with `after`; a future pre-boot checkout can leak on spawn failure. Process death bypasses cleanup, and failed stop is only logged. [VM.do_snapshot](../../../../lib/mjolnir/vm.ex) resumes the guest after each layer snapshot, so successful final snapshot does not itself prove that cache writers are stopped. CILease explicitly documents durable reconciliation reviving job VMs after their controller dies.

**Owed:** record build-to-work-tree/VM ownership durably; define flush/quiesce, publication, unmount/stop, and discard order. Coordinate reaping with reconciliation and positively establish that no guest/export still writes a work tree. Unknown liveness must preserve it pending recovery. Cover pre-spawn failure, caller kill, stop failure, restart during execution/publication, and idempotent cleanup of work and unpublished generations.

## R4 — CI policy needs enforceable provenance and confidentiality (blocking)

Owner-derived paths answer cross-owner naming, but “owner's own deploy” does not identify a trusted server-side signal that separates a human deploy from CI using owner credentials. [CILease](../../../../lib/mjolnir/ci_lease.ex) is a lifecycle mechanism based on purpose metadata, not a cache-write authorization mechanism. Also, “read-only checkout” conflicts with the writable clone in the delta: Cargo must write intermediate files even when publication is forbidden.

Read-only access is still data access. Whole `CARGO_HOME` can include `credentials.toml`, configuration, and private dependency sources. The official [Cargo home documentation](https://doc.rust-lang.org/cargo/guide/cargo-home.html) enumerates these files. Refusing mounts over `/run/mjolnir` does not stop a tool from writing credentials into its own home or a PR from reading a previously committed secret.

**Owed:** define trusted ingress/provenance and deny publication when it is absent or ambiguous; bind checkout/commit/list/remove to authorized owner/app identity, including internal callers. Define CI as a private writable disposable clone if that is the intent, and specify which cache contents PRs may read. Narrow credential-bearing presets and define treatment of private sources/custom caches; no generic claim that arbitrary tool output is secret-free. Specify safe name encoding, guest-path normalization/symlink handling, protected-path overlap, duplicate mounts, and env-name validation. Test forged trust, cross-owner administration, PR writes without publication, and a credential sentinel inaccessible to an untrusted build.

## R5 — Base compatibility cannot be only a restore hint (blocking)

[Design lines 90–93](../design.md#base-image-rebuilds) assume Cargo/bun invalidate everything affected by a base rebuild. The living [base-images requirement](../../../specs/base-images/spec.md#requirement-declared-live-images-match-current-recipes) permits replacement under the same alias; native libraries or a system compiler can change without changing source, Cargo.lock, or the Rust version. Cargo's [build-script change detection](https://doc.rust-lang.org/cargo/reference/build-scripts.html#change-detection) tracks declared paths/environment and package changes, not an arbitrary OS-image replacement. A native build script that does not declare a system-header dependency supplies a concrete counterexample. A new hint still falls back to incompatible `current` in this design.

**Owed:** distinguish mandatory compatibility from optional affinity hints. Pin a base-generation/ABI/toolchain boundary for compiled caches, or specify an explicit safe invalidation mechanism on alias rebuild, including old builds finishing after that boundary moves. Download-only caches may survive independently. Test changed system headers/libraries with unchanged source/lockfile/toolchain and rejected incompatible fallback. Custom caches need a bounded correctness contract rather than assuming every tool detects every stale input.

## R6 — Quota/eviction needs an admission and active-build contract (blocking)

[Design lines 97–100](../design.md#quota-and-eviction) name qgroups and LRU but not a limit, accounting definition, or active-generation behavior. Filesystem path nesting does not establish the proposed owner qgroup: btrfs requires quota enablement and explicit group relationships; inconsistent accounting can disable limit enforcement. See the [btrfs qgroup documentation](https://btrfs.readthedocs.io/en/latest/btrfs-qgroup.html).

**Owed:** specify configurable defaults, accounting of shared extents and all work/current/prev/hint generations, qgroup setup and unavailable/inconsistent states, hint bounds, and concurrent admission/growth. Coordinate eviction and `mj cache rm` with live clones and pending commits; define whether an in-flight build may repopulate a removed cache. Handle EDQUOT/ENOSPC without publishing partial state or exhausting unrelated tenant storage. Test quota pressure during two builds, removal during checkout/commit, 30-day expiry, and no reclaimable generations. “Eviction never breaks a build” needs a mechanism or a narrower promise.

## R7 — Correctness scenarios can currently pass without exercising caches (blocking)

The delta's cold/warm and forced-cold scenarios redeploy identical source after deleting only mutable caches. [Builder.build/3](../../../../lib/mjolnir/deploy/builder.ex) lines 106–116 return the existing release without booting a VM on a full layer hit. Both tests can therefore pass while checkout, compilation, and materialization are broken. The forced-cold expectation also contradicts the sibling's full-hit-no-VM contract.

**Owed:** explicitly force the relevant layer misses in cold/warm comparisons and assert that compiler steps actually execute. Separately test full hits with zero cache work and partial hits after eviction. Check runnable outputs and source-sensitive behavior, including a source edit that must change the response, rather than only filenames plus a generic liveness probe. Add failure/recovery and trust scenarios from R1–R6 as normative acceptance criteria, not solely implementation task labels.

## R8 — Make the performance gate reproducible (required before rollout)

Deferring a disk backend until measurement is sensible. However, “warm rebuild,” “local disk,” and “~25%” in [design lines 79–86](../design.md#performance-gate-virtiofs-or-a-reflinked-disk) do not define an executable gate. An unchanged-source deploy can measure a layer hit; repeated VM stalls cannot establish either backend's performance.

**Owed:** require resolution of `mjolnir-mne7` before measurement and preserve that as an open gate. Define the same source edit, seeded cache contents, pinned tools, VM resources, compiler work, guest-local disk baseline, repetitions/statistic, and exact threshold. Include checkout/commit overhead or report it separately. If the image backend is selected, revisit flush/unmount, crash recovery, sizing, and quota behavior before declaring its lifecycle unchanged. This review does not require the benchmark to run while the design is PENDING.
