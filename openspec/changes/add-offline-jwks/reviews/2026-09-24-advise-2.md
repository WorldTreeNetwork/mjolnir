## Blind independent take

Written before opening design.md, tasks.md, or the proposed edge-auth delta; inputs were the packet's Why, the living web-pty-edge spec, and the four cited source files.

1. Pin successful application boot without issuer reachability, including when no usable disk cache exists; hosted verification then fails closed.
2. Pin cache identity to the configured issuer and JWKS source so reconfiguration cannot silently import another authority's keys.
3. Pin authenticated HTTPS retrieval and validation of public signing keys before either memory or disk publication.
4. Refuse weakening signature, issuer, expiration, audience-at-the-existing-layer, or authorization checks merely because verification is offline.
5. Refuse unknown-kid fallback, token-directed key sources, and ambiguous reuse of one kid for different key material.
6. Pin finite rotation retention with a stated clock and token-lifetime policy; a JWK's presence alone does not define its expiry.
7. Pin atomic, restrictive cache writes under /var/lib/mjolnir/auth outside btrfs_root, with failed updates preserving the last usable state.
8. Pin deterministic treatment of corrupt, missing, incompatible, and unwritable caches without making network recovery a supervisor dependency.
9. Pin bounded asynchronous refresh and bootstrap seeding, with tests covering cold restart, overlap, retirement, and malformed refreshes.
10. Accept an explicit tradeoff between offline availability and delayed revocation, provided the retention bound and operator recovery are concrete.

## Comparison and steelman

Decisions 1, 3, and 4 substantially answer the boot, provenance, and persistence concerns: creation-time permissions, path-alias rejection, issuer/source binding, rejection of unusable refreshes, atomic writes, and explicit degraded durability. Decision 5 identifies a viable owned signer-table seam; the installed `JokenJwks.SignerMatchStrategy` callback is `match_signer_for_kid/2`, which the existing hook invokes. Decision 6 and the delta now include bootstrap, and the delta preserves negative signature, issuer, and expiry checks. These are meaningful amendments, not reasons to repeat the original five findings wholesale.

The strongest case against my blind take is issuer-managed overlap: trust the most recent validated issuer set, let the issuer publish both keys during rotation, and retain that snapshot indefinitely while offline. This is executable without a numeric TTL or knowledge of outstanding tokens. I withdraw a finite retention bound as a prerequisite because the steer skipped a numeric window. This policy explicitly trades immediate revocation for outage availability. It can be accepted once the remaining contract agrees with it; the review does not require a competing retention algorithm.

Likewise, serving a validated new set from memory when disk persistence fails is a defensible availability choice. Restart can then restore older trust, including a key retired in memory. The design acknowledges the older snapshot; the normative verification rules and operator recovery must acknowledge the same consequence.

## Required amendments

### R6 — P1: Reconcile issuer-set replacement with additive retention

**Evidence:** `design.md:24–27` versus `design.md:55–57`; `specs/edge-auth/spec.md:31–37`; `proposal.md:23–24`; `steer.md:10–13`.

Decision 2 and the retirement scenario require `{A,B}` → `{B}` and rejection of A even for an otherwise-valid unexpired token. Decision 5 still requires additive merging “per Decision 2,” while the proposal and recorded steer retain previously fetched unexpired keys. An additive union preserves A; exact replacement removes it. These are observably different authentication policies, not interchangeable descriptions of an atomic publication.

**Owed:** reconcile the proposal, design, delta, and recorded steer interpretation around one transition rule. If issuer-set retirement is the intended amendment, say explicitly that overlap is supplied by the issuer publishing `{A,B}`, omitted A is retired upon successful publication, and the prior retention wording is superseded. Keep atomic publication so there is no transient empty table. Add one sequence proving `{A}` → `{A,B}` → `{B}` both in the running verifier and after restart, with successful persistence distinguished from R8's failure case. The reader does not select a new policy on the author's behalf.

### R7 — P1: Make operator trust withdrawal apply to the serving state

**Evidence:** `design.md:28–32,55–60`; `specs/edge-auth/spec.md:39–45`.

The claimed compromise-recovery action is deleting the cache, but verification reads an in-memory signer table. Removing the file alone does not specify any invalidation of that table. The scenario does not require stopping/restarting the process, and no reload or invalidation mechanism is contracted. A completed in-flight fetch can also repopulate disk or memory unless the procedure accounts for it. This matters especially offline: removing a compromised issuer key remotely cannot inform the disconnected edge, so the local withdrawal procedure is the remaining recovery path.

**Owed:** specify a complete operator sequence with a definite point after which the key cannot verify. A documented stop → delete → start procedure while the issuer is unavailable is sufficient for the existing offline scenario; live invalidation is not required if it is not promised. If deletion during operation is promised, define memory invalidation and how stale in-flight work is prevented from restoring trust. State that an empty JWKS is rejected under Decision 4, so issuer-side removal of the final key alone does not clear this cache. Test the chosen procedure against an already-loaded key and subsequent restart. Clarify similarly whether an operator seed after empty boot requires restart/reload; Decision 5 currently promises recovery from that seed without naming the trigger.

### R8 — P1: Align verification with the declared memory/disk divergence

**Evidence:** `design.md:44–51`; `specs/edge-auth/spec.md:10–14,25–37,63–70`.

Decision 4 permits serving a valid fetched set from memory when persistence fails. The delta instead requires rejection whenever the kid is absent from the persisted set. With disk `{A}`, a valid fetch `{A,B}`, and a failed write, the design accepts B while the delta rejects B. With disk `{A,B}`, fetch `{B}`, and a failed write, the design restores A after restart while the retirement scenario unconditionally requires rejection. The implementation cannot satisfy both contracts.

**Owed:** distinguish the active validated signer set from the durable boot snapshot in the normative rules. Define unknown-kid rejection against the active set, qualify durable retirement on successful persistence, and carry the already-chosen degraded-durability behavior into acceptance. Add failed-persist scenarios for both adding B and removing A, checking behavior before and after restart and the durability diagnostic. Explicitly document that an unpersisted retirement can be undone by restart and how the operator recovery procedure handles that case. Alternatively amend the design's publication policy, but do not leave this choice to the implementer.

## Non-blocking implementation and scope notes

- Preserve the agreed background-fetch isolation with finite network deadlines and retry/concurrency bounds. The blocked-refresh scenario should exercise signer lookup while network work is stuck; also test empty offline boot followed by issuer recovery.
