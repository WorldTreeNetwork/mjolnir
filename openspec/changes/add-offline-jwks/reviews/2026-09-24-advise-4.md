## Blind take

Written before opening design.md, tasks.md, or the edge-auth delta, using only the proposal Why, living web-pty-edge spec, and cited code.

1. Pin application startup to local state; unavailable issuer networking must not prevent the API supervisor from starting.
2. Pin cached keys to the configured issuer and key source so reconfiguration cannot silently reuse another authority's trust.
3. Pin signature and existing claim enforcement on both online and offline paths; cached verification must not grant new scopes or identities.
4. Refuse unknown key IDs, invalid signatures, and invalid claims even when fetching or loading the cache fails.
5. Refuse malformed or unusable JWKS updates before they can destroy the last usable trust set.
6. Pin each accepted JWKS as a complete replacement, with overlap supplied by the issuer rather than indefinite local key accumulation.
7. Pin explicit behavior for failed persistence: distinguish the active process's trust set from what an offline restart can recover.
8. Pin atomic protected cache writes outside btrfs_root, with a trustworthy directory and no partially written boot document.
9. Pin cold-start and recovery behavior when no usable cache exists, keeping hosted authentication closed until trusted keys arrive.
10. Accept stale-key availability as a tradeoff only with an explicit retirement boundary and tests spanning refresh, write failure, and restart.

## Comparison and steelman

Decisions 1, 3, and 4 address boot independence, issuer/source binding, protected placement, validation before publication, and preservation of good state on rejected refreshes. Decision 5 identifies the integration seam: the installed `JokenJwks.before_verify/2` calls `strategy.match_signer_for_kid/2` (`deps/joken_jwks/lib/joken_jwks.ex:51`). A Mjolnir-owned table can therefore serve the existing Token hook without tying known-key lookup to background network work. Decision 6 applies the same trust and persistence rules to bootstrap. The delta preserves signature, algorithm, issuer, and expiry enforcement and refuses empty-cache or issuer-disabled authentication.

Decisions 2, 5, and 7 choose complete replacement by a validated issuer document. Overlap comes from `{A,B}` at the issuer, and `{B}` retires A in the running process. Decision 7 expressly qualifies the earlier summary language about restart and operator deletion: durable retirement requires persistence, and local withdrawal is stop → delete → start offline. Empty issuer JWKS does not withdraw the final key. Operator seeding becomes active at the next start. These are concrete answers to the blind take, not unresolved implementation choices.

The strongest argument against demanding stricter persistence or a key TTL is that a validated refresh provides current issuer intent immediately, even during a disk fault. Gating publication on disk success would retain a withdrawn key in the running process. The selected policy applies the retirement now, reports degraded durability, and accepts restoration of older trust after restart when persistence failed. That is a consequential but explicit availability tradeoff, with a defined operator recovery procedure. I do not require a revocation ledger, numeric TTL, or live invalidation to accept this bounded change.
