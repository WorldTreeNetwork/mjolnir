## Owed before acceptance

1. **Captured-kernel eligibility and legacy images.** The unconditional requirement that a thaw has `CONFIG_VMGENID` (`specs/vm-freeze/spec.md:37`) has no old-image behavior. Restore resumes saved RAM and device state; the local backend sequence starts an unbooted VMM and restores it (`lib/mjolnir/memory_snapshot.ex:953`). Replacing the host kernel file therefore cannot retrofit the kernel captured in an existing image. Specify capture eligibility, detection of missing/unknown support, and the operator-visible refusal or explicitly bounded compatibility policy. The disposable proof must cold-boot the candidate kernel before capture. Include an old-kernel image case and retain the original image on refusal. This follows the [v54 restore model](https://raw.githubusercontent.com/cloud-hypervisor/cloud-hypervisor/v54.0/docs/snapshot_restore.md), which restores saved RAM and component state.

2. **A causal proof and an honest guarantee boundary.** Tasks currently require changed IDs and different streams, but samples taken after independent `Entropy.reseed` calls can pass without VMGENID working (`tasks.md:6`; `lib/mjolnir/entropy.ex:115`). Specify evidence of the guest's VMGENID-triggered kernel reseed, separately from the mandatory host reseed, and state when stream divergence is promised. Driver-event evidence or an isolated unpublished experiment can establish causality; production gating stays intact. Reconcile the residual race with the unqualified SHALL and the pre-userspace assertion in `lib/mjolnir/entropy.ex:34`. Also correct `proposal.md:15`: kernel reseeding alone does not reset arbitrary copied userspace PRNGs. The [Linux driver](https://raw.githubusercontent.com/torvalds/linux/v6.12/drivers/virt/vmgenid.c) calls `add_vmfork_randomness` from its notification handler; [CH's documentation](https://raw.githubusercontent.com/cloud-hypervisor/cloud-hypervisor/v54.0/docs/snapshot_restore.md) explicitly requires userspace generators to obtain fresh randomness themselves. No generic application-reset mechanism is demanded here; accurately state the limit.

3. **Public fork reachability versus the existing remap boundary.** The helper explicitly leaves guest IP, MAC, and Iroh identity unchanged and says the entropy probe works without a full fork (`lib/mjolnir/memory_snapshot.ex:715`). The new API contract promises a second running guest and retains the normal reachability gate. Distinct VM ids/CIDs/filesystem sockets alone do not establish correct ticket or gateway routing; `Publish` accepts any ready, nonempty Iroh node id (`lib/mjolnir/thaw/publish.ex:72`). Explain how simultaneous guests remain independently addressable, or explicitly bound unsupported configurations with a refusal. Require a two-guest proof that each published ticket/route reaches its intended guest and that failed fork cleanup leaves the first guest usable. This applies the existing reachability requirement to the newly allowed fork; it does not reopen clock, storage, or Iroh's folded health semantics.
